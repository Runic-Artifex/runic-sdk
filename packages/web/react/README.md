# `@runic-artifex/react`

React hooks and outlet for clients generated by Runic Views. The generated
modules import `@runic-artifex/views`, which this package also builds on, so
install both:

```sh
npm install @runic-artifex/react@preview @runic-artifex/views@preview
pnpm add @runic-artifex/react@preview @runic-artifex/views@preview
bun add @runic-artifex/react@preview @runic-artifex/views@preview
```

Previews are published under the `preview` dist-tag. Install the versions that
match your Runic SDK packages. React 18.3 and 19 are supported.

```tsx
import { useCommand, useView, ViewOutlet, type ViewRegistry } from "@runic-artifex/react";
import { connectWorkspace, type WorkspaceState } from "./generated/workspace.js";
import type { CounterPageReference } from "./generated/counter.js";

const workspace = { connect: connectWorkspace };
const pages = { counter: CounterPage } satisfies ViewRegistry<WorkspaceState["main"]>;

export function App() {
  const { state, client, error } = useView(workspace);
  const showCounter = useCommand(() => client?.showCounter());
  if (error) return <p role="alert">{String(error)}</p>;
  return <>
    <button disabled={!client} onClick={() => void showCounter.run()}>Counter</button>
    <ViewOutlet content={state?.main} registry={pages} fallback={<p>Connecting…</p>} />
  </>;
}

export function CounterPage({ page }: { page: CounterPageReference }) {
  const { state, client } = useView(page);
  const increment = useCommand(() => client?.increment());
  return <>
    <button disabled={!state?.canIncrement || increment.pending} onClick={() => void increment.run()}>{state?.count ?? "…"}</button>
    {increment.error !== undefined && <p role="alert">{String(increment.error)}</p>}
  </>;
}
```

## `useView(source, options?)`

Returns `{ state, client, error, pending, retry }`. `options.release(client)`
replaces `client.dispose()` for a client the hook connected, for example to keep
a client alive in a cache:

- A generated page reference, or `{ connect: connect<Name> }` for a root
  ViewModel, is connected while the component is mounted. A reference is
  identified by its `connect` function, so an inline
  `{ connect: connectWorkspace }` does not reconnect.
- When the component unmounts or the reference changes, the client stays
  connected for `options.keepAlive` milliseconds (2000 by default), and the
  next `useView` of the same reference takes it over with its state. StrictMode's
  second mount, Fast Refresh, `<Activity>` and A→B→A navigation therefore
  neither flash "Connecting…" nor remount a `ViewOutlet` subtree nor open the
  route again; a component that mounts while its reference's client is kept
  renders the state in its first render. `keepAlive: 0` disposes at once.
  Kept clients are handed over, not shared: two mounted components of the same
  reference have a client each.
- An already connected client is observed and left to its owner.
- `client` stays the same object for the connection, so
  `useEffect(…, [view.client])` does not run again when the View's state
  changes.
- `state` renders through `useSyncExternalStore`, so concurrent rendering sees
  one consistent snapshot.
- `pending` is true while a reference connects. `error` holds a failed
  connection; `retry()` connects again. While the same reference connects again
  (after `retry()`, or after a hidden `<Activity>` outlived the grace period),
  `state` stays the last state.

A `connect` function created during render, such as
`useView({ connect: () => connectWorkspace() })`, is a new reference on every
render, so each render reconnects. In development `useView` logs a warning when
this repeats. Pass the generated function itself, a generated page reference,
or memoize the source with `useMemo`.

### Selecting state: `useViewState(view, selector, isEqual?)`

`useView` renders its component on every change of the View. A component that
shows one member can select it and re-render only when it changes, like
`useSyncExternalStoreWithSelector`. Pass the connected client, which keeps its
identity, to a memoized child:

```tsx
const Title = memo(function Title({ editor }: { editor: EditorClient | undefined }) {
  const title = useViewState(editor, state => state.title);
  return <h1>{title ?? "…"}</h1>;
});

function EditorPage({ page }: { page: EditorPageReference }) {
  const editor = useView(page);
  return <><Title editor={editor.client} /><Body editor={editor.client} /></>;
}
```

`view` is a client or a `useView` handle (`undefined` while nothing is
connected returns `undefined`). The selector may be an inline function.
Members the View did not change keep their identity, so selecting a member,
also an object or a list, needs no `isEqual`; pass one for a derived value, such
as `state => state.items.filter(item => item.done)` with a shallow comparison.

### Large lists and concurrent rendering

The client applies each frame when it arrives and notifies once per animation
frame (0.14), so a burst of .NET changes renders once per frame, not once per
frame received. `useSyncExternalStore` renders those updates synchronously,
though, so a component that renders thousands of rows blocks typing for the
length of that render. Let React render the list in a background pass with
`useDeferredValue`, and keep the input outside the deferred part:

```tsx
const { state } = useView(page);
const rows = useDeferredValue(state?.rows);
const stale = rows !== state?.rows;
<input {...filter.inputProps} />
<List rows={rows ?? []} style={{ opacity: stale ? 0.6 : 1 }} />  {/* List is memo() */}
```

`useTransition` is not needed for commands: their calls are asynchronous and
the state they produce arrives as a View change. For a scrolling window over a
large .NET collection, request only the visible rows with
[`useCollectionViewport`](#usecollectionviewportoptions).

### Read-only state and two-way binding

As in any MVVM View, the ViewModel's C# setters decide what the page may set.
Read state one way from `state`. A property with a public C# setter also gets a
`set<Property>` client method, so a control can bind it two way; status with a
`private set`, such as `IsDirty` or `Error`, has no setter and is only rendered:

```tsx
// C#: public partial int Count { get; private set; }  public partial int Step { get; set; }
export function CounterPage({ page }: { page: CounterPageReference }) {
  const { state, client } = useView(page);
  const setStep = useCommand((step: number) => client?.setStep(step));
  return <>
    <p>{state?.count ?? "…"}</p>
    <select value={state?.step ?? 1} onChange={event => void setStep.run(Number(event.currentTarget.value))}>
      <option value={1}>1</option>
      <option value={5}>5</option>
    </select>
  </>;
}
```

The control shows the ViewModel's value, so it reverts when the setter throws
or keeps a different value.

### Fields: `useField(view, field, options?)`

Binds an `<input>`, `<textarea>` or `<select>` to a member while the component is mounted. Pass the generated
`{View}Fields` descriptor; it knows the member's kind, setter, checked write and validation:

```tsx
import { EditorFields, type EditorPageReference } from "./generated/editor.js";

export function EditorPage({ page }: { page: EditorPageReference }) {
  const editor = useView(page);
  const title = useField(editor, EditorFields.title, { commit: "pause", checked: true });
  const step = useField(editor, EditorFields.step);
  const done = useField(editor, EditorFields.done);
  return <>
    <input {...title.inputProps} />
    {title.errors.map(message => <p key={message} role="alert">{message}</p>)}
    {title.conflict && <p role="alert">
      Changed elsewhere to “{title.conflict.value}”.
      <button onClick={title.retry}>Keep mine</button> <button onClick={title.reset}>Take theirs</button>
    </p>}
    <input inputMode="decimal" {...step.inputProps} />
    <input type="checkbox" {...done.inputProps} />
  </>;
}
```

It returns the field's state (`value`, `text`, `editing`, `error`, `errors`, `conflict`), `input(value)`,
`commit()`, `retry()`, `reset()` and `inputProps`. For a boolean field `inputProps` is `checked`, `onChange`,
`onBlur` and `aria-invalid` for a checkbox; otherwise it is the field's `text` as `value`, `onChange`, the
composition handlers, `onBlur` and `aria-invalid`. Text inputs of numbers keep `-` and `1.` while the user types: a
text that does not parse stays the draft with an `invalid-text` error and nothing is written. The handlers are the
same on every render. `aria-invalid` is true while the field has `errors` or an `error`.

`options` are read once, when the field is created:

- `commit: "pause"` writes the draft after `delay` milliseconds without input (700 by default) and at once on
  `commit()`, which blur calls; use it where each write is an undo step or starts work in .NET. The default,
  `commit: "input"`, writes each input. `commit()` resolves with the field's state once its writes settled, so a
  command that depends on the field can follow them and skip a failed write:
  `if ((await title.commit()).error === undefined) await editor.save()`. Read the error from the resolved state: the
  handle is the state of the render that created it.
- `checked: true` writes with the member's checked write, so a change by another writer while the user edits is a
  conflict instead of being overwritten. A `rejected` receipt keeps the draft and sets `error` to a `FieldError` with
  the setter's message; a `conflict` keeps the draft, sets `conflict` to the producer's `{ value, version }` and
  writes nothing until `retry()` writes the draft over it or `reset()` takes it.
- `coalesce` and `keepDraftOnError` as for text inputs below.

`errors` holds the member's validation messages from the descriptor (`[]` when valid), `error` why the latest write
or text failed (a `BridgeError` or a `FieldError`, whose `kind` is `rejected`, `conflict`, `committed-with-error` or
`invalid-text`). `FieldError`, `FieldOptions`, `FieldState` and `BridgeField` are exported from this package. See the
[field controller](https://github.com/Runic-Artifex/runic-sdk/tree/main/packages/web/views#fields) for the receipts
and text forms. An `invalid-text` error has a `reason` and `arguments`: render `useText(name.error)` after
`configureFieldErrorText` to show your own text for it in the window's language
([Translating field errors](https://github.com/Runic-Artifex/runic-sdk/tree/main/packages/web/views#translating-field-errors)).

#### Row cells and nested members

Since 0.16, `InvoiceFields.address.street` and `InvoiceFields.lines.at(line.id).quantity` are fields too
(`field-paths/1`): a member of an object member, and a cell of a row that .NET edits with `[RunicRowEditor]`. Bind
each cell in the row's component; `at(key)` returns the same descriptor for the same key, so the field survives
re-renders and moves:

```tsx
function LineRow({ invoice, line }: { invoice: InvoiceView; line: InvoiceLine }) {
  const quantity = useField(invoice, InvoiceFields.lines.at(line.id).quantity, { commit: "pause" });
  return <td><input {...quantity.inputProps} />{quantity.conflict && <button onClick={quantity.retry}>Keep mine</button>}</td>;
}
```

Such a field always writes checked, conflicts only when another writer changed the same cell, and shows the messages
.NET reports at the cell's validation path. See [Fields below a member and row cells](../views/README.md#fields-below-a-member-and-row-cells).

### Forms: `useForm(fields, options?)`

One state over a component's field handles, and a `submit` that writes every field before its command
(`createFormController` in `@runic-artifex/views`). `dirty` counts drafts not written yet and the `dirty` option, such
as the View's `isDirty`; `pending` is true while a draft, a check (`validating`) or a submit runs.

```tsx
const form = useForm({ title, step }, { dirty: editor.state?.isDirty });
<button disabled={!form.valid || form.submitting} onClick={() => form.submit(() => editor.client!.save())}>Save</button>
```

### Text inputs: `useTextField(view, read, write, options?)`

Binds a controlled text input to a member through the framework-neutral
[text field controller](https://github.com/Runic-Artifex/runic-sdk/tree/main/packages/web/views#text-inputs)
while the component is mounted. `read` and `write` may close over render values:

```tsx
export function PersonPage({ page }: { page: PersonPageReference }) {
  const person = useView(page);
  const name = useTextField(person, state => state.name, (client, value) => client.setName(value));
  return <>
    <input value={name.value} onChange={name.onChange}
      onCompositionStart={name.onCompositionStart} onCompositionEnd={name.onCompositionEnd} />
    {name.error !== undefined && <p role="alert">{String(name.error)}</p>}
  </>;
}
```

It returns `value`, `editing` and `error` with the `onChange`, `onCompositionStart`
and `onCompositionEnd` handlers and `reset()`. `view` is a `useView` handle or any
`{ state, client }`. The options `coalesce` and `keepDraftOnError` are read when the
component mounts.
The field shows what the user typed while its writes are in flight, so a reply or
frame that answers an older keystroke never replaces newer text. At most one write is
in flight; text typed meanwhile is written next as one value (`coalesce: false` writes
every change). Nothing is written during IME composition. Once the last write settled,
the field shows the View's value again, including any normalization the ViewModel
applied (trimmed, upper-cased). `write` may also be a command or a checked write,
whose receipt the field reads: `rejected` and `conflict` keep the draft and set `error`
to a `FieldError` of that kind, `committed-with-error` drops the draft and sets it too,
and `applied.validation` is `errors`. A failed write keeps the draft and sets `error`
(`keepDraftOnError: false` shows the View's value instead); `reset()` drops the draft. `editing` is true while a draft
exists. Don't disable the input on the View's busy state (`isSaving`, `can…`) while
the user types: the field's own write causes it, and keys typed meanwhile would be
lost. Test such fields by typing key by key (Playwright `pressSequentially`, Testing
Library `user.type`) against the mock with `latency: "slow"`; `fill()` sets the whole
text at once and hides the race.

## `useSuspenseView(source, options?)`

Suspends the component until a reference connects, then returns
`{ state, client }` without `undefined`. A failed connection is thrown to the
nearest error boundary. Call `retrySuspenseView(reference)` when the boundary
resets, so the next render connects again; an unretried failure is forgotten
after `releaseTimeout`:

```tsx
<ErrorBoundary fallback={<p role="alert">Offline</p>} onReset={() => retrySuspenseView(page)}>
  <Suspense fallback={<p>Connecting…</p>}><Counter page={page} /></Suspense>
</ErrorBoundary>

function Counter({ page }: { page: CounterPageReference }) {
  const { state, client } = useSuspenseView(page);
  return <button onClick={() => void client.increment()}>{state.count}</button>;
}
```

Components that pass a reference with the same `connect` function share one
client, which is disposed `options.keepAlive` milliseconds (2000 by default,
`0` at once) after the last of them unmounts, so a component that mounts again
meanwhile renders without suspending. The reference must be stable: a `connect`
function created during render never resolves.

The connections live in a module-wide cache until a component claims them,
because Suspense discards the state of a component that never mounted.
`options.releaseTimeout` is how many milliseconds a connection that no mounted
component has claimed, or a failure that no `retrySuspenseView` has cleared,
stays cached. It defaults to 10000 (ten seconds); `Infinity` keeps the entry
until it is claimed or retried. Other values must be whole numbers from 1 to
2147483647, or the hook throws a `RangeError`. It is not a connection timeout.
Components that share a `connect` function share one entry, which keeps the
largest `releaseTimeout` any of them passed:

```tsx
const { state } = useSuspenseView(page, { releaseTimeout: 30_000 });
```

## `ViewOutlet`

`<ViewOutlet content={reference} registry={pages} fallback={…} />` renders the
component registered for `reference.kind` with the reference as its `page`
prop. Declare the registry with `satisfies ViewRegistry<State["main"]>` so each
kind has a component whose `page` prop matches. A component whose `page` is a
shared page reference, such as `ResultPagePageReference` of a .NET
[`[RunicSharedClient]`](../../dotnet/Runic.Application.Views/README.md#shared-clients)
interface, registers for each of its kinds:
`{ ...registryEntries(resultPageKinds, ResultPage), settings: Settings }`. A different reference
remounts the component, and `fallback` renders while `content` is empty. A kind
without a component renders an English `<p role="alert">` in a development build
(`process.env.NODE_ENV` is not `production`); a production build renders nothing
and reports the kind once through the page's error reporting
(`installErrorReporting`, `onBridgeDiagnostic`).

`missing` replaces that alert, for example with localized text. It receives the
reference whose kind has no component, and its markup (including any `role`) is yours:

```tsx
<ViewOutlet content={state?.main} registry={pages}
  missing={page => <p role="alert">{t("missingView", { kind: page.kind })}</p>} />
```

### Region collections

A .NET `[RunicRegionCollection]` member, such as `state.documents`, lists
regions that each keep their own back stack. `<RegionOutlets>` renders a
`ViewOutlet` for each region, keyed by the region's key, inside a
`<div data-region-key>`. The default `mode="keep-mounted"` keeps every region mounted
and sets `hidden` and an inline `display: none` on all but the selected one, so
a tab keeps its component, scroll position and unsent input. Author CSS cannot
show a hidden panel without `!important`. `mode="selected"` renders only the
selected region. `fallback` renders while there is no region, and `missing` is
passed to each outlet. A region with `content: null` renders nothing.

The package has no tab bar. Build one with `regionEntries` and the generated
`selectDocuments(key)` and `closeDocuments(key)`. `panelProps(entry)` returns attributes for each region's wrapper, such as `id`,
`role="tabpanel"` and `aria-labelledby`, so each tab can name its panel in
`aria-controls`. `hidden` and `data-region-key` stay controlled by the outlet,
and a returned `style` is merged with its `display: none`.

```tsx
const tabId = (key: string) => `document-tab-${key}`;
const panelId = (key: string) => `document-panel-${key}`;
const [refocus, setRefocus] = useState(false);
useEffect(() => {
  if (!refocus) return;
  const key = selectedRegion(state?.documents)?.key;
  if (key) document.getElementById(tabId(key))?.focus();
  setRefocus(false);
}, [refocus, state?.documents]);
async function close(key: string) {
  if ((await client?.closeDocuments(key))?.kind === "Committed") setRefocus(true);
}

<div role="tablist">
  {regionEntries(state?.documents).map(tab => (
    <span key={tab.key}>
      <button id={tabId(tab.key)} role="tab" aria-selected={tab.selected} aria-controls={panelId(tab.key)}
        onClick={() => void client?.selectDocuments(tab.key)}>
        {tab.content?.kind ?? "Empty"}
      </button>
      <button aria-label="Close" onClick={() => void close(tab.key)}>×</button>
    </span>
  ))}
</div>
<RegionOutlets collection={state?.documents} registry={documentPages} fallback={<p>No open documents</p>}
  panelProps={tab => ({ id: panelId(tab.key), role: "tabpanel", "aria-labelledby": tabId(tab.key) })} />
```

`selected` changes only when a switch or close commits. A departure guard can
keep the current tab, so highlight `selected` and do not move the highlight
before the request settles. `select…` and `close…` resolve to the .NET
`NavigationOutcome`, such as `{ kind: "Rejected", rejection: "Guard" }`.

Closing the selected tab removes its button, and the next tab becomes selected
when the close commits. After `closeDocuments` resolves with `kind: "Committed"`,
move focus to the button of the new selected tab, as `close` above does.

In both modes the region collection keeps presenting every region's content,
so the pages of hidden tabs stay live and still receive state. `"selected"`
mode only unmounts the components of the regions that are not selected.

`regionEntries`, `selectedRegion` and the region types are re-exported from
`@runic-artifex/views`.

## `useCommand(command)`

Returns `{ run, pending, error, failure, reset }`. `run(...args)` calls the latest
`command`, so it may close over the current client, and resolves to its result
or to `undefined` after a failure, which `error` then holds until the next run.
It never rejects, so handlers need no `try`/`catch`. Unmounting disposes the
command's controller, so `pending`, `error` and `failure` stop updating; a run in
flight still resolves. One command can serve several buttons:

```tsx
const navigate = useCommand((name: "showWelcome" | "showCounter") => client?.[name]());
<button onClick={() => void navigate.run("showWelcome")}>Welcome</button>
```

`pending` covers only this component's run. Whether .NET can run the command is
the View's state: a command without an argument publishes `can<Name>`, so a
button combines both, as in `disabled={!state?.canSave || save.pending}`, and is
disabled before the client connects. A command with an argument has the
`can<Name>(input)` query on the client instead.

For a command that declares a failure (`[RunicFailure]` in .NET), `run` resolves the
`BridgeOutcome`, and `failure` holds the declared failure of the latest run, typed
from the outcome, while `error` keeps unexpected failures. Starting a run and
`reset()` clear both, and a run superseded by a later run or by `reset()` sets
neither.

## `useOperation(start, options?)`

Observes a generated `start<Command>()` operation through the framework-neutral
[operation controller](https://github.com/Runic-Artifex/runic-sdk/tree/main/packages/web/views#operation-feedback-and-latest-selection).
`run(...args)` calls the latest `start`, so it may close over the current client:

```tsx
const push = useOperation((remote: string) => client?.startPush(remote));
<button disabled={!client || push.pending} onClick={() => void push.run("origin")}>Push</button>
{push.pending && <button disabled={push.cancellationRequested} onClick={() => void push.cancel()}>Cancel</button>}
{push.cancelled && <p role="status">Push cancelled.</p>}
{push.error !== undefined && <p role="alert">{String(push.error)}</p>}
```

The result has `pending`, `admitting`, `operation`, `status`, `progress`, `outcome`, `failure`,
`error`, `cancelled`, `cancellationRequested`, `cancelling`, `cancellation` and
`cancelError`, with `run(...args)`, `cancel()` and `reset()`, which never reject. A
run that ends with a `cancelled` status sets `cancelled` and resolves to `undefined`
without an `error`; `failed` and `timed-out` statuses are still `error`. `pending`
stays true after a Cancel response until the operation reaches its terminal status.
`progress` is how far the running operation got, from 0 to 1, when its command
reports progress (`RunicOperationProgress.Report` in .NET), for example
`<progress value={push.progress} />`; it is `undefined` while unknown and after the run.
Unmounting disposes the controller, as `useCommand` does: a run still in flight
resolves to `undefined`, `waitForCompletion` is not called after it, and accepted
work is never cancelled. StrictMode's simulated unmount, and a component that
React shows again, start with a fresh controller, so feedback of a run started
before the unmount ends there. The optional
`cancel(operation)` and `waitForCompletion(operation, status)` callbacks are the
controller's options.

## `useLatestOperation()`

Admits only the newest of several reads, for example loading the item the user
selected last, through the framework-neutral
[latest-operation controller](https://github.com/Runic-Artifex/runic-sdk/tree/main/packages/web/views#operation-feedback-and-latest-selection).
Each `run(intent)` replaces the queued intent and cancels the active read; the next
read starts only after the previous one reaches its terminal status and the intent's
optional `waitForCompletion` barrier:

```tsx
const load = useLatestOperation<Item>();
// `client` comes from useView; the intent captures the one it starts on.
const select = (id: string) => { if (client) void load.run({ start: () => client.startLoad(id) }); };
{load.outcome?.ok && <ItemView item={load.outcome.value} />}
{load.blocked && <p role="alert">Reconnect before selecting again.</p>}
```

The result has the `useOperation` fields plus `blocked`, with `run(intent)` and
`clear(mode?)`, which never reject. The intent carries `start` and the optional
`cancel`, `waitForCompletion` and `isCurrent` callbacks, so it captures the client or
session it belongs to. `blocked` means admission is uncertain, for example after a
lost Start reply; only `clear("replace")`, called after the application has
established a fresh session, clears it. `clear()` drops the queued intent and cancels
the active read. Unmounting disposes the controller like `useOperation`: pending runs
resolve to `undefined` and accepted work is never cancelled. StrictMode's simulated
unmount starts a fresh controller.

## `useBridgeConnection(options?)`

Renders the page's connection to its .NET host while the component is mounted.
It wraps `onBridgeConnection` from `@runic-artifex/views` (re-exported here since 0.11, with the
`BridgeConnectionState` and `BridgeConnectionOptions` types) and returns
`{ state }`, where `state` is a `BridgeConnectionState`: `connecting`,
`connected`, `reconnecting`, `lost` or `closed` (the application closed the
window, since 0.15; a closed set, see
[Connection state](https://github.com/Runic-Artifex/runic-sdk/tree/main/packages/web/views#connection-state)):

```tsx
import { useBridgeConnection } from "@runic-artifex/react";

function ConnectionBanner() {
  const connection = useBridgeConnection({ lostAfter: 5_000 });
  return connection.state === "lost" ? <p role="alert">The application stopped responding.</p> : null;
}
```

The first render already has the current state. Unmounting unsubscribes, and
StrictMode's simulated unmount keeps one subscription. A changed `lostAfter`
subscribes again; an invalid one throws a `RangeError`. A server render reads
`connecting` and does not observe.

## `useMenuBar(options?)`

Follows the declared menu bar of a Runic Desktop window that leaves it to the
page (`DesktopMenuBarPresentation.Page`) while the component is mounted. It
wraps `createMenuBarController` from `@runic-artifex/views` (see
[In-page menu bar](https://github.com/Runic-Artifex/runic-sdk/tree/main/packages/web/views#in-page-menu-bar)) and returns `{ state, invoke, handleKeyDown }`: `state` is a
`MenuBarState`, and the bar is rendered by the menubar component of the
application's own UI library. Runic ships no menubar component.

```tsx
import { useMenuBar } from "@runic-artifex/react";

function AppMenuBar() {
  const [open, setOpen] = useState("");
  const menuBar = useMenuBar({
    onRequest: request => request.kind === "open" ? setOpen(request.menu.key) : focusFirstTrigger(),
  });
  // On macOS the application menu bar keeps the menus ("global"): render nothing.
  if (menuBar.state.placement !== "page") return null;
  // Map menuBar.state.menus to the component; an item's select handler calls menuBar.invoke(item).
}
```

Options are those of `createMenuBarController` (`shortcuts`, `keyboard`)
without `signal`, plus `onRequest`, which receives the `focus` and `open`
requests; the latest function is called. A changed `shortcuts` or `keyboard`
creates a new controller, and unmounting disposes it, which also returns the
`shortcuts: "app"` lease. StrictMode's simulated unmount keeps one controller.
The controller starts in an effect, so a server render reads `connecting`, and
`invoke` rejects with a `BridgeError` (`disconnected`) until then.

### With Base UI or Radix

Base UI's `Menubar` (`@base-ui/react`, the base of shadcn/ui's Base UI
Menubar) with a controlled open menu; the
[Notes example](https://github.com/Runic-Artifex/runic-sdk/tree/main/examples/notes-view-first#in-page-menu-bar) adds submenus, check and radio
items and is tested with real keys:

```tsx
import { Menu } from "@base-ui/react/menu";
import { Menubar } from "@base-ui/react/menubar";
import { splitAccessKey, type MenuBarItem, type MenuBarMenu } from "@runic-artifex/views";
import { useMenuBar } from "@runic-artifex/react";

function AppMenuBar() {
  const bar = useRef<HTMLDivElement>(null);
  const [open, setOpen] = useState<string | null>(null);
  const menuBar = useMenuBar({
    onRequest: request => request.kind === "open"
      ? setOpen(request.menu.key)
      : bar.current?.querySelector<HTMLElement>("[role=menuitem]")?.focus(),
  });
  const { placement, menus, accessKeyHints } = menuBar.state;
  if (placement !== "page") return null;
  const label = (entry: MenuBarMenu | MenuBarItem) => {
    const [before, key, after] = splitAccessKey(entry);
    return <>{before}{accessKeyHints ? <u>{key}</u> : key}{after}</>;
  };
  return (
    <Menubar ref={bar} aria-label="Application">
      {menus.map(menu => (
        <Menu.Root key={menu.key} disabled={!menu.enabled} open={open === menu.key}
          onOpenChange={next => setOpen(current => next ? menu.key : current === menu.key ? null : current)}>
          <Menu.Trigger>{label(menu)}</Menu.Trigger>
          <Menu.Portal><Menu.Positioner align="start"><Menu.Popup>
            {menu.entries.map(entry => entry.kind === "separator" ? <Menu.Separator key={entry.key} />
              : entry.kind === "item" ? (
                <Menu.Item key={entry.key} disabled={!entry.enabled} aria-keyshortcuts={entry.ariaKeyShortcuts}
                  onClick={() => void menuBar.invoke(entry)}>
                  {label(entry)} <kbd aria-hidden>{entry.shortcutText}</kbd>
                </Menu.Item>)
              : null /* a submenu: Menu.SubmenuRoot */)}
          </Menu.Popup></Menu.Positioner></Menu.Portal>
        </Menu.Root>
      ))}
    </Menubar>
  );
}
```

With Radix (`@radix-ui/react-menubar`) the open menu is the root's controlled
`value`: `<Menubar.Root value={open} onValueChange={setOpen}>`, each
`<Menubar.Menu value={menu.key}>`, and `<Menubar.Item onSelect={() => menuBar.invoke(item)}>`.
Check items are `Menubar.CheckboxItem checked`, radio groups
`Menubar.RadioGroup value` with `Menubar.RadioItem`.

## `useText(value, fallback?)`

Shows a text reference that a ViewModel produced, such as a status line or a
validation error's `text`, in the window's language, and renders again when the
language changes. A string shows as it is; `null` and `undefined` show
`fallback`. Connect the page's Translations runtime once with
`configureTranslatedText` ([Translated text](https://github.com/Runic-Artifex/runic-sdk/blob/main/packages/dotnet/Runic.Application.Views/README.md#translated-text)).
`useWindowLocale()` reads the window's locale.

`useTextLocale()` renders the locale that text is shown in, and renders again
when it changes. Call it in a component that renders the page's own messages,
so `m.*()` runs again after a language switch; the component's children render
with it, except memoized ones. `syncDocumentLocale()`, once in `main.tsx`, keeps
`<html lang dir>` on that locale.

```tsx
function Toolbar() {
  useTextLocale();
  return <button>{m.save()}</button>;
}
```

```tsx
const status = useText(view.state?.status);
<p>{status}</p>
function ErrorLine({ error }: { error: BridgeValidationMessage }) {
  return <li>{useText(error.text, error.message)}</li>;
}
```

## `useAppearance()`

Renders the page's appearance and renders again when it changes: the colour
scheme, contrast and reduced motion of the page's engine, combined with the
desktop's text scale, accent colour, forced-colours palette, contrast and motion
that a Runic host pushes ([Appearance](https://github.com/Runic-Artifex/runic-sdk/blob/main/packages/web/views/README.md#appearance)). The server snapshot
has every member `null`.

```tsx
function Shell({ children }: { readonly children: ReactNode }) {
  const { textScale, reducedMotion } = useAppearance();
  return <main style={{ fontSize: `${textScale ?? 1}rem` }} data-motion={reducedMotion ? "reduce" : "full"}>{children}</main>;
}
```

## Errors

The `error` of `useView` and of a command or operation handle is typed
`unknown`: it holds whatever the connection or the call rejected with. Show it
with `describeBridgeError(error)`, one sentence (in the window's language with `configureRunicViewsText()`), instead of
`String(error)`. A Bridge failure is a `BridgeError` from
`@runic-artifex/views`; narrow it with `isBridgeError` (or `instanceof`) before
reading `kind`, `route` or `detail`:

```tsx
import { describeBridgeError, isBridgeError } from "@runic-artifex/views";

const offline = isBridgeError(error, "disconnected");
{error !== undefined && <p role="alert">{describeBridgeError(error)}</p>}
```

`instanceof` holds for errors from every copy of the package on the page.
[Errors and diagnostics](https://github.com/Runic-Artifex/runic-sdk/tree/main/packages/web/views#errors-and-diagnostics)
lists the kinds. Any other value, such as an exception that your own connect
function or command callback throws, arrives unchanged.

The hooks run in the browser or webview that a Runic host serves. `useView`
connects in an effect, but `useSuspenseView` connects during render, so a server
render would try to connect: render the components that use them on the client
only.

## Interactions

A ReactiveUI `Interaction<TInput, TOutput>` on the ViewModel, such as the
question of a `ReactiveLeaveConfirmation.WithInteraction` leave guard, is
`client.interactions.<name>` on the generated client. Register the page's
answer in an effect: `handle((prompt, { signal }) => …)` returns the function
that removes it, so React removes the handler when the page unmounts or its
client changes:

```tsx
export function EditPage({ page }: { page: EditPageReference }) {
  const { state, client } = useView(page);
  useEffect(() => client?.interactions.confirmDiscard.handle(
    async (prompt, { signal }) => confirmDialog(`Discard the changes to ${prompt.itemName}?`, signal),
  ), [client]);
  const close = useCommand(() => client?.close());
  return <button disabled={!client || close.pending} onClick={() => void close.run()}>Close {state?.name}</button>;
}
```

`prompt` and the answer are typed from the ViewModel's interaction. The
handler may return the answer or a promise of it; `confirmDialog` stands for
the application's own dialog.

- The page is asked for a departure that its own window starts: its Close, the
  shell's Back in the same window, or a guarded window close.
- `signal` aborts when .NET no longer needs the answer, for example when the
  departure is superseded or the window closes. Close the dialog then; a late
  answer is ignored.
- The handler exists only after the effect has run. A departure before that,
  such as a close during the page's first render, is answered by the
  ViewModel's .NET fallback handler, or fails closed without one.

The [ReactiveUI leave confirmation](https://github.com/Runic-Artifex/runic-sdk/blob/main/packages/dotnet/Runic.Application.Views.ReactiveUI/README.md#leave-confirmation-in-a-web-view)
has the .NET side and which View answers which departure. In a frontend test,
the generated mock's `interactions.<name>.request(input)` resolves with the
registered handler's answer; see the
[Testing guide](https://github.com/Runic-Artifex/runic-sdk/tree/main/packages/web/views#testing).

## View requests

A `ViewRequest<T>` property of the ViewModel asks the View for a one-way
presentation action, such as focusing a field or showing a toast, and is
`client.requests.<name>` on the generated client. Register the page's
handler in an effect: `handle((input, { signal }) => …)` returns the function
that removes it, so React removes the handler when the page unmounts or its
client changes:

```tsx
export function EditPage({ page }: { page: EditPageReference }) {
  const { client } = useView(page);
  const name = useRef<HTMLInputElement>(null);
  useEffect(() => client?.requests.focus.handle(({ member }) => {
    if (member === "name") name.current?.focus();
  }), [client]);
  return <input ref={name} />;
}
```

`input` is typed from the request's `ViewRequest<T>`. The handler runs once
the page painted the state the request was raised with, so the field of that
state is rendered; `signal` aborts when the handler is replaced or removed, the
client is disposed or the connection is lost. A request is never replayed: one
raised before the effect ran, or while the page is disconnected, is not
delivered later. See [View requests](https://github.com/Runic-Artifex/runic-sdk/tree/main/packages/web/views#view-requests) for the rules, and in a frontend
test raise one with the generated mock's `requests.<name>.raise(input)` (the
[Testing guide](https://github.com/Runic-Artifex/runic-sdk/tree/main/packages/web/views#testing)).

## `useCollectionViewport(options)`

Follows a fixed-row-height scroll container and returns `{ viewport, ref }`.
`viewport` is the [`collectionViewport`](https://github.com/Runic-Artifex/runic-sdk/tree/main/packages/web/views#collectionviewportoptions)
range for the container; it changes only when the range or sizes change. Send
the range to the ViewModel from an effect:

```tsx
const { state, client } = useView(rows);
const { viewport, ref } = useCollectionViewport({ totalCount: state?.totalCount ?? 0, rowHeight: 32 });
useEffect(() => {
  if (viewport.size !== 0) void client?.setViewport({ start: viewport.start, size: viewport.size });
}, [client, viewport.start, viewport.size]);
return <div ref={ref} style={{ height: 480, overflow: "auto" }}>
  <div style={{ height: viewport.totalSize }}>
    <div style={{ transform: `translateY(${viewport.offset}px)` }}>{/* state.rows */}</div>
  </div>
</div>;
```

## `useQueryCollection(collection, options)`

Follows a scroll container for a [query collection](https://github.com/Runic-Artifex/runic-sdk/tree/main/packages/web/views#query-collections) (`client.queries.{name}`), whose rows stay in .NET: it
loads the rows the container shows, with placeholders until they arrive, and lays them out with variable heights
(`estimateSize` for rows not measured yet). It returns the `QueryViewport` (`items` with `top` and `size`, `totalSize`,
`total`, `query`, `loading`, `error`), `ref` for the container, `measure(index)` for each row, and `scrollToKey`,
`scrollToIndex`, `setQuery` and `retry`:

```tsx
const list = useQueryCollection(client.queries.rows, { estimateSize: 32 });
return <div ref={list.ref} style={{ height: 480, overflow: "auto" }}>
  <div style={{ height: list.totalSize, position: "relative" }}>
    {list.items.map(item => <div key={item.key ?? `p${item.index}`} ref={list.measure(item.index)} style={{ position: "absolute", top: item.top, width: "100%" }}>
      {item.row?.label ?? "…"}
    </div>)}
  </div>
</div>;
```

## Hosted regions (experimental)

`RunicHostedRegion` from `@runic-artifex/react/experimental` renders

import { RunicHostedRegion } from "@runic-artifex/react/experimental";

<RunicHostedRegion name="check" style={{ height: 420 }}
