# `@runic-artifex/react`

React hooks and outlet for clients generated by Runic Views. The generated
modules import `@runic-artifex/views`, which this package also builds on, so
install both:

```sh
npm install @runic-artifex/react@preview @runic-artifex/views@preview
pnpm add @runic-artifex/react@preview @runic-artifex/views@preview
bun add @runic-artifex/react@preview @runic-artifex/views@preview
```

Previews are published under the `preview` dist-tag. Install the versions that
match your Runic SDK packages. React 18.3 and 19 are supported.

```tsx
import { useCommand, useView, ViewOutlet, type ViewRegistry } from "@runic-artifex/react";
import { connectWorkspace, type WorkspaceState } from "./generated/workspace.js";
import type { CounterPageReference } from "./generated/counter.js";

const workspace = { connect: connectWorkspace };
const pages = { counter: CounterPage } satisfies ViewRegistry<WorkspaceState["main"]>;

export function App() {
  const { state, client, error } = useView(workspace);
  const showCounter = useCommand(() => client?.showCounter());
  if (error) return <p role="alert">{String(error)}</p>;
  return <>
    <button disabled={!client} onClick={() => void showCounter.run()}>Counter</button>
    <ViewOutlet content={state?.main} registry={pages} fallback={<p>Connecting…</p>} />
  </>;
}

export function CounterPage({ page }: { page: CounterPageReference }) {
  const { state, client } = useView(page);
  const increment = useCommand(() => client?.increment());
  return <>
    <button disabled={!client || increment.pending} onClick={() => void increment.run()}>{state?.count ?? "…"}</button>
    {increment.error !== undefined && <p role="alert">{String(increment.error)}</p>}
  </>;
}
```

## `useView(source, options?)`

Returns `{ state, client, error, pending, retry }`. `options.release(client)`
replaces `client.dispose()` for a client the hook connected, for example to keep
a client alive in a cache:

- A generated page reference, or `{ connect: connect<Name> }` for a root
  ViewModel, is connected while the component is mounted and disposed when it
  unmounts or the reference changes. A reference is identified by its `connect`
  function, so an inline `{ connect: connectWorkspace }` does not reconnect.
- An already connected client is observed and left to its owner.
- `state` renders through `useSyncExternalStore`, so concurrent rendering sees
  one consistent snapshot. StrictMode's extra mount disposes its connection.
- `pending` is true while a reference connects. `error` holds a failed
  connection; `retry()` connects again.

A `connect` function created during render, such as
`useView({ connect: () => connectWorkspace() })`, is a new reference on every
render, so each render reconnects. In development `useView` logs a warning when
this repeats. Pass the generated function itself, a generated page reference,
or memoize the source with `useMemo`.

### Read-only state and two-way binding

As in any MVVM View, the ViewModel's C# setters decide what the page may set.
Read state one way from `state`. A property with a public C# setter also gets a
`set<Property>` client method, so a control can bind it two way; status with a
`private set`, such as `IsDirty` or `Error`, has no setter and is only rendered:

```tsx
// C#: public partial int Count { get; private set; }  public partial int Step { get; set; }
export function CounterPage({ page }: { page: CounterPageReference }) {
  const { state, client } = useView(page);
  const setStep = useCommand((step: number) => client?.setStep(step));
  return <>
    <p>{state?.count ?? "…"}</p>
    <select value={state?.step ?? 1} onChange={event => void setStep.run(Number(event.currentTarget.value))}>
      <option value={1}>1</option>
      <option value={5}>5</option>
    </select>
  </>;
}
```

The control shows the ViewModel's value, so it reverts when the setter throws
or keeps a different value.

## `useSuspenseView(source, options?)`

Suspends the component until a reference connects, then returns
`{ state, client }` without `undefined`. A failed connection is thrown to the
nearest error boundary. Call `retrySuspenseView(reference)` when the boundary
resets, so the next render connects again; an unretried failure is forgotten
after `releaseTimeout`:

```tsx
<ErrorBoundary fallback={<p role="alert">Offline</p>} onReset={() => retrySuspenseView(page)}>
  <Suspense fallback={<p>Connecting…</p>}><Counter page={page} /></Suspense>
</ErrorBoundary>

function Counter({ page }: { page: CounterPageReference }) {
  const { state, client } = useSuspenseView(page);
  return <button onClick={() => void client.increment()}>{state.count}</button>;
}
```

Components that pass a reference with the same `connect` function share one
client, which is disposed after the last of them unmounts. The reference must
be stable: a `connect` function created during render never resolves.

The connections live in a module-wide cache until a component claims them,
because Suspense discards the state of a component that never mounted.
`options.releaseTimeout` is how many milliseconds a connection that no mounted
component has claimed, or a failure that no `retrySuspenseView` has cleared,
stays cached. It defaults to 10000 (ten seconds); `Infinity` keeps the entry
until it is claimed or retried. Other values must be whole numbers from 1 to
2147483647, or the hook throws a `RangeError`. It is not a connection timeout.
Components that share a `connect` function share one entry, which keeps the
largest `releaseTimeout` any of them passed:

```tsx
const { state } = useSuspenseView(page, { releaseTimeout: 30_000 });
```

## `ViewOutlet`

`<ViewOutlet content={reference} registry={pages} fallback={…} />` renders the
component registered for `reference.kind` with the reference as its `page`
prop. Declare the registry with `satisfies ViewRegistry<State["main"]>` so each
kind has a component whose `page` prop matches. A different reference
remounts the component; a kind without a component renders an English
`<p role="alert">`, and `fallback` renders while `content` is empty.

`missing` replaces that alert, for example with localized text. It receives the
reference whose kind has no component, and its markup (including any `role`) is yours:

```tsx
<ViewOutlet content={state?.main} registry={pages}
  missing={page => <p role="alert">{t("missingView", { kind: page.kind })}</p>} />
```

## `useCommand(command)`

Returns `{ run, pending, error, failure, reset }`. `run(...args)` calls the latest
`command`, so it may close over the current client, and resolves to its result
or to `undefined` after a failure, which `error` then holds until the next run.
It never rejects, so handlers need no `try`/`catch`. Unmounting disposes the
command's controller, so `pending`, `error` and `failure` stop updating; a run in
flight still resolves. One command can serve several buttons:

```tsx
const navigate = useCommand((name: "showWelcome" | "showCounter") => client?.[name]());
<button onClick={() => void navigate.run("showWelcome")}>Welcome</button>
```

For a command that declares a failure (`[RunicFailure]` in .NET), `run` resolves the
`BridgeOutcome`, and `failure` holds the declared failure of the latest run, typed
from the outcome, while `error` keeps unexpected failures. Starting a run and
`reset()` clear both, and a run superseded by a later run or by `reset()` sets
neither.

## `useOperation(start, options?)`

Observes a generated `start<Command>()` operation through the framework-neutral
[operation controller](https://github.com/Runic-Artifex/runic-sdk/tree/main/packages/web/views#operation-feedback-and-latest-selection).
`run(...args)` calls the latest `start`, so it may close over the current client:

```tsx
const push = useOperation((remote: string) => client?.startPush(remote));
<button disabled={!client || push.pending} onClick={() => void push.run("origin")}>Push</button>
{push.pending && <button disabled={push.cancellationRequested} onClick={() => void push.cancel()}>Cancel</button>}
{push.cancelled && <p role="status">Push cancelled.</p>}
{push.error !== undefined && <p role="alert">{String(push.error)}</p>}
```

The result has `pending`, `admitting`, `operation`, `status`, `outcome`, `failure`,
`error`, `cancelled`, `cancellationRequested`, `cancelling`, `cancellation` and
`cancelError`, with `run(...args)`, `cancel()` and `reset()`, which never reject. A
run that ends with a `cancelled` status sets `cancelled` and resolves to `undefined`
without an `error`; `failed` and `timed-out` statuses are still `error`. `pending`
stays true after a Cancel response until the operation reaches its terminal status.
Unmounting disposes the controller, as `useCommand` does: a run still in flight
resolves to `undefined`, `waitForCompletion` is not called after it, and accepted
work is never cancelled. StrictMode's simulated unmount, and a component that
React shows again, start with a fresh controller, so feedback of a run started
before the unmount ends there. The optional
`cancel(operation)` and `waitForCompletion(operation, status)` callbacks are the
controller's options.

## `useLatestOperation()`

Admits only the newest of several reads, for example loading the item the user
selected last, through the framework-neutral
[latest-operation controller](https://github.com/Runic-Artifex/runic-sdk/tree/main/packages/web/views#operation-feedback-and-latest-selection).
Each `run(intent)` replaces the queued intent and cancels the active read; the next
read starts only after the previous one reaches its terminal status and the intent's
optional `waitForCompletion` barrier:

```tsx
const load = useLatestOperation<Item>();
// `client` comes from useView; the intent captures the one it starts on.
const select = (id: string) => { if (client) void load.run({ start: () => client.startLoad(id) }); };
{load.outcome?.ok && <ItemView item={load.outcome.value} />}
{load.blocked && <p role="alert">Reconnect before selecting again.</p>}
```

The result has the `useOperation` fields plus `blocked`, with `run(intent)` and
`clear(mode?)`, which never reject. The intent carries `start` and the optional
`cancel`, `waitForCompletion` and `isCurrent` callbacks, so it captures the client or
session it belongs to. `blocked` means admission is uncertain, for example after a
lost Start reply; only `clear("replace")`, called after the application has
established a fresh session, clears it. `clear()` drops the queued intent and cancels
the active read. Unmounting disposes the controller like `useOperation`: pending runs
resolve to `undefined` and accepted work is never cancelled. StrictMode's simulated
unmount starts a fresh controller.

## `useBridgeConnection(options?)`

Renders the page's connection to its .NET host while the component is mounted.
It wraps `onBridgeConnection` from `@runic-artifex/views` and returns
`{ state }`, where `state` is a `BridgeConnectionState`: `connecting`,
`connected`, `reconnecting` or `lost` (a closed set, see
[Connection state](https://github.com/Runic-Artifex/runic-sdk/tree/main/packages/web/views#connection-state)):

```tsx
import { useBridgeConnection } from "@runic-artifex/react";

function ConnectionBanner() {
  const connection = useBridgeConnection({ lostAfter: 5_000 });
  return connection.state === "lost" ? <p role="alert">The application stopped responding.</p> : null;
}
```

The first render already has the current state. Unmounting unsubscribes, and
StrictMode's simulated unmount keeps one subscription. A changed `lostAfter`
subscribes again; an invalid one throws a `RangeError`. A server render reads
`connecting` and does not observe.

## `useMenuBar(options?)`

Follows the declared menu bar of a Runic Desktop window that leaves it to the
page (`DesktopMenuBarPresentation.Page`) while the component is mounted. It
wraps `createMenuBarController` from `@runic-artifex/views` (see
[In-page menu bar](https://github.com/Runic-Artifex/runic-sdk/tree/main/packages/web/views#in-page-menu-bar)) and returns `{ state, invoke, handleKeyDown }`: `state` is a
`MenuBarState`, and the bar is rendered by the menubar component of the
application's own UI library. Runic ships no menubar component.

```tsx
import { useMenuBar } from "@runic-artifex/react";

function AppMenuBar() {
  const [open, setOpen] = useState("");
  const menuBar = useMenuBar({
    onRequest: request => request.kind === "open" ? setOpen(request.menu.key) : focusFirstTrigger(),
  });
  // On macOS the application menu bar keeps the menus ("global"): render nothing.
  if (menuBar.state.placement !== "page") return null;
  // Map menuBar.state.menus to the component; an item's select handler calls menuBar.invoke(item).
}
```

Options are those of `createMenuBarController` (`shortcuts`, `keyboard`)
without `signal`, plus `onRequest`, which receives the `focus` and `open`
requests; the latest function is called. A changed `shortcuts` or `keyboard`
creates a new controller, and unmounting disposes it, which also returns the
`shortcuts: "app"` lease. StrictMode's simulated unmount keeps one controller.
The controller starts in an effect, so a server render reads `connecting`, and
`invoke` rejects with a `BridgeError` (`disconnected`) until then.

### With Base UI or Radix

Base UI's `Menubar` (`@base-ui/react`, the base of shadcn/ui's Base UI
Menubar) with a controlled open menu; the
[Notes example](https://github.com/Runic-Artifex/runic-sdk/tree/main/examples/notes-view-first#in-page-menu-bar) adds submenus, check and radio
items and is tested with real keys:

```tsx
import { Menu } from "@base-ui/react/menu";
import { Menubar } from "@base-ui/react/menubar";
import { splitAccessKey, type MenuBarItem, type MenuBarMenu } from "@runic-artifex/views";
import { useMenuBar } from "@runic-artifex/react";

function AppMenuBar() {
  const bar = useRef<HTMLDivElement>(null);
  const [open, setOpen] = useState<string | null>(null);
  const menuBar = useMenuBar({
    onRequest: request => request.kind === "open"
      ? setOpen(request.menu.key)
      : bar.current?.querySelector<HTMLElement>("[role=menuitem]")?.focus(),
  });
  const { placement, menus, accessKeyHints } = menuBar.state;
  if (placement !== "page") return null;
  const label = (entry: MenuBarMenu | MenuBarItem) => {
    const [before, key, after] = splitAccessKey(entry);
    return <>{before}{accessKeyHints ? <u>{key}</u> : key}{after}</>;
  };
  return (
    <Menubar ref={bar} aria-label="Application">
      {menus.map(menu => (
        <Menu.Root key={menu.key} disabled={!menu.enabled} open={open === menu.key}
          onOpenChange={next => setOpen(current => next ? menu.key : current === menu.key ? null : current)}>
          <Menu.Trigger>{label(menu)}</Menu.Trigger>
          <Menu.Portal><Menu.Positioner align="start"><Menu.Popup>
            {menu.entries.map(entry => entry.kind === "separator" ? <Menu.Separator key={entry.key} />
              : entry.kind === "item" ? (
                <Menu.Item key={entry.key} disabled={!entry.enabled} aria-keyshortcuts={entry.ariaKeyShortcuts}
                  onClick={() => void menuBar.invoke(entry)}>
                  {label(entry)} <kbd aria-hidden>{entry.shortcutText}</kbd>
                </Menu.Item>)
              : null /* a submenu: Menu.SubmenuRoot */)}
          </Menu.Popup></Menu.Positioner></Menu.Portal>
        </Menu.Root>
      ))}
    </Menubar>
  );
}
```

With Radix (`@radix-ui/react-menubar`) the open menu is the root's controlled
`value`: `<Menubar.Root value={open} onValueChange={setOpen}>`, each
`<Menubar.Menu value={menu.key}>`, and `<Menubar.Item onSelect={() => menuBar.invoke(item)}>`.
Check items are `Menubar.CheckboxItem checked`, radio groups
`Menubar.RadioGroup value` with `Menubar.RadioItem`.

## Errors

The `error` of `useView` and of a command or operation handle is typed
`unknown`: it holds whatever the connection or the call rejected with. A Bridge
failure is a `BridgeError` from `@runic-artifex/views`; narrow it with
`instanceof` before reading `kind`, `route` or `detail`:

```ts
import { BridgeError } from "@runic-artifex/views";

const offline = error instanceof BridgeError && error.kind === "disconnected";
```

`instanceof` holds for errors from every copy of the package on the page.
[Errors and diagnostics](https://github.com/Runic-Artifex/runic-sdk/tree/main/packages/web/views#errors-and-diagnostics)
lists the kinds. Any other value, such as an exception that your own connect
function or command callback throws, arrives unchanged.

The hooks run in the browser or webview that a Runic host serves. `useView`
connects in an effect, but `useSuspenseView` connects during render, so a server
render would try to connect: render the components that use them on the client
only.

## Interactions

A ReactiveUI `Interaction<TInput, TOutput>` on the ViewModel, such as the
question of a `ReactiveLeaveConfirmation.WithInteraction` leave guard, is
`client.interactions.<name>` on the generated client. Register the page's
answer in an effect: `handle((prompt, { signal }) => …)` returns the function
that removes it, so React removes the handler when the page unmounts or its
client changes:

```tsx
export function EditPage({ page }: { page: EditPageReference }) {
  const { state, client } = useView(page);
  useEffect(() => client?.interactions.confirmDiscard.handle(
    async (prompt, { signal }) => confirmDialog(`Discard the changes to ${prompt.itemName}?`, signal),
  ), [client]);
  const close = useCommand(() => client?.close());
  return <button disabled={!client || close.pending} onClick={() => void close.run()}>Close {state?.name}</button>;
}
```

`prompt` and the answer are typed from the ViewModel's interaction. The
handler may return the answer or a promise of it; `confirmDialog` stands for
the application's own dialog.

- The page is asked for a departure that its own window starts: its Close, the
  shell's Back in the same window, or a guarded window close.
- `signal` aborts when .NET no longer needs the answer, for example when the
  departure is superseded or the window closes. Close the dialog then; a late
  answer is ignored.
- The handler exists only after the effect has run. A departure before that,
  such as a close during the page's first render, is answered by the
  ViewModel's .NET fallback handler, or fails closed without one.

The [ReactiveUI leave confirmation](https://github.com/Runic-Artifex/runic-sdk/blob/main/packages/dotnet/Runic.Application.Views.ReactiveUI/README.md#leave-confirmation-in-a-web-view)
has the .NET side and which View answers which departure. In a frontend test,
the generated mock's `interactions.<name>.request(input)` resolves with the
registered handler's answer; see the
[Testing guide](https://github.com/Runic-Artifex/runic-sdk/tree/main/packages/web/views#testing).

## `useCollectionViewport(options)`

Follows a fixed-row-height scroll container and returns `{ viewport, ref }`.
`viewport` is the [`collectionViewport`](https://github.com/Runic-Artifex/runic-sdk/tree/main/packages/web/views#collectionviewportoptions)
range for the container; it changes only when the range or sizes change. Send
the range to the ViewModel from an effect:

```tsx
const { state, client } = useView(rows);
const { viewport, ref } = useCollectionViewport({ totalCount: state?.totalCount ?? 0, rowHeight: 32 });
useEffect(() => {
  if (viewport.size !== 0) void client?.setViewport({ start: viewport.start, size: viewport.size });
}, [client, viewport.start, viewport.size]);
return <div ref={ref} style={{ height: 480, overflow: "auto" }}>
  <div style={{ height: viewport.totalSize }}>
    <div style={{ transform: `translateY(${viewport.offset}px)` }}>{/* state.rows */}</div>
  </div>
</div>;
```
