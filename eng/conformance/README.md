# Conformance driver

One driver runs a conformance corpus against any implementation of it, through a small adapter process written in the
implementation's language ([PROTOCOL.md](PROTOCOL.md), `rax.conformance-adapter/1`). The driver owns everything the
corpus defines, so every implementation is checked by the same reading of the spec (D075.13; R7 G8, from the R6
spike).

| Corpus | Directory | Implementations |
| --- | --- | --- |
| Views protocol 4 (`views/4`) | [`specs/application/conformance`](../../specs/application/conformance/README.md) | `dotnet-views` (the .NET producer), `ts-client` (the TypeScript client) |
| Assets archives (`assets/2`) | [`specs/assets/vectors`](../../specs/assets/vectors/README.md) | `dotnet-assets` (the .NET reader) |
| Desktop server (`desktop-server/1`) | [`specs/desktop/server`](../../specs/desktop/server/README.md) | `rax-server` (runic-server) |

## Run it

From the repository root:

```sh
bun run conformance list                                   # the implementations
bun run conformance dotnet-views                           # every case, compared with its status file
bun run conformance dotnet-views --only operations.cancel  # cases whose id contains the text
bun run conformance dotnet-views --set handshake --verbose # one set, every outcome
bun run conformance cases [--write]                        # check, or write, each corpus's cases.json
bun run conformance lint                                   # the status files, without running anything
bun eng/conformance/demo-gate.ts                           # the status rules on an edited copy of the corpus
```

A run builds the adapter (`--no-build` skips it), runs the cases, and prints each failure with its step, the expected
and actual message, the case's file and its rerun flag. It writes a receipt (`rax.conformance-receipt/1`) and the
adapter's log to `artifacts/conformance/`. Then it compares the outcomes with the implementation's status file. It exits
1 on a blocking finding. The whole Views corpus takes about 2 seconds for .NET.

Other options:

- `--jobs <n>` runs cases on n adapter processes;
- `--corpus <dir>` runs a copy of the corpus, with its own status files;
- `--receipt <file>` writes the receipt elsewhere;
- `RAX_TEST_TIMEOUT_SCALE` or `--timeout-scale <x>` scales the 5-second receive timeout;
- `CONFIGURATION` selects the .NET build configuration (`Debug` by default);
- `RAX_CONFORMANCE_PREFIX=runic` writes the format names before the rename (D079.27). Both spellings are read.

The driver has unit tests in [`eng/conformance.test.mjs`](../conformance.test.mjs), which the engineering job runs. CI
does not run a corpus through the driver yet: that gate is a later slice (D075.16; R6 section 4).

## Status files

Each corpus directory holds:

- `cases.json`: the corpus's case list, generated by `bun run conformance cases --write`. Each case has its id, set,
  file, roles, requirements and the `sha256` of its content, so a semantic edit to a case shows in review.
- `status/<implementation>.json` (`rax.conformance-status/1`): the expected outcome of every case for one
  implementation, with the implementation's roles and `maturity` (`development`, `preview` or `stable`). There is one
  case per line.

| Status | Meaning | Requires | Allowed for |
| --- | --- | --- | --- |
| `pass` | runs and passes | — | all |
| `unsupported` | a feature or seam that the implementation does not list, or a gap tracked by an issue | `requires` or `issue` | all |
| `excluded` | a role or profile the implementation does not have | `reason` (`role:…`, `profile:…`) | all |
| `known-failure` | it should pass, and does not | `issue` | `development`, `preview` |
| `deviation` | an intentional difference (D011) | `deviation`: `<file>#<anchor>` of a row of the area's difference table, such as [`specs/application/language-mappings.md#date-time-offset`](../../specs/application/language-mappings.md#intentional-differences) | all |

An issue is `#<n>`, `<owner>/<repo>#<n>` or an issue URL. A stable implementation has no `known-failure` (R7 T1-13).

**Comparison.** A run reports these findings:

| Finding | Rule | Blocks |
| --- | --- | --- |
| `REGRESSION` | the status is `pass`, and the run observed anything else | yes |
| `NEW-CASE` | a case of the corpus has no status | yes |
| `STALE-STATUS` | a status names a case that the corpus does not have | yes |
| `MISMATCH` | the run observed another outcome than an `unsupported`, `excluded` or `known-failure` status allows, or a `deviation` that neither passes nor fails | yes |
| `FIXED` | a `known-failure` or `unsupported` case now passes: update its status | only when `CI` is set |
| status-file problems | a rule of the table above is broken | for `preview` and `stable` implementations |
| `cases.json` out of date | the committed case list differs from the corpus | yes |

A `deviation` may also pass: a difference can depend on the machine, as .NET's local offset does on a machine at UTC.
A filtered run (`--only`, `--set`) checks only the cases it ran.

**A new implementation** starts its status file with `--write-status`, which records the run as it is. Failures
become `known-failure` with the issue `TODO`, which only a `development` implementation may keep. Rerunning it keeps
the `deviation` and `known-failure` entries that still fail.

**A corpus change** regenerates `cases.json`. It adds a status for every implementation that has a status file: for
example `known-failure` with the issue of the follow-up pull request, or `unsupported` with the new feature in
`requires` (R6 section 5).

## Layout

| Path | Content |
| --- | --- |
| [`cli.ts`](cli.ts) | the command's entry point, which registers runic-sdk's corpus modules |
| [`core/`](core/README.md) | the parts every corpus and repository shares: the command (runs, receipts, the status check, `cases`, `lint`), the adapter process client, cases, outcomes, status files and their comparison, the format names. runic-cli-sdk and runic-translations-sdk vendor it unchanged |
| [`views/`](views) | the Views protocol 4 module: corpus loading, message writing and matching, producer steps, vectors |
| [`assets/`](assets) | the Assets archive module: corpus loading and the `assets.read` comparison |
| [`server/`](server) | the Desktop server module: corpus loading, and the client that runs a case's steps over sockets and checks the server's responses and frames |
| [`implementations.json`](implementations.json) | each implementation: corpus, roles, adapter build and command, status file |
| [`adapters/ts-client.ts`](adapters/ts-client.ts) | the TypeScript client's adapter (message vectors; client scenarios are #1350) |
| [`tests/dotnet/Runic.Application.Views.Conformance`](../../tests/dotnet/Runic.Application.Views.Conformance) | the .NET producer's adapter, which compiles the in-repository test Views and scenario transport |
| [`tests/dotnet/Runic.Assets.Conformance`](../../tests/dotnet/Runic.Assets.Conformance) | the .NET Assets reader's adapter, on `Runic.Assets`' public API |
| [`native/crates/server-conformance`](../../native/crates/server-conformance) | runic-server's adapter, on its Rust API, with the corpus's test application |
| [`demo-gate.ts`](demo-gate.ts) | the status rules on a temporary copy of the corpus with three edits |

**Adding an implementation:**

1. Write its adapter in the implementation's test tree, never shipped (R7 T1-17).
2. Add its entry to `implementations.json`.
3. Run `bun run conformance <id> --write-status`.
4. Set its `maturity`, and give each remaining failure an issue, or a `deviation` row in the area's difference table.
