Implementation plan · draft 4

MVVM for a web UI—without giving up Native AOT.

Build a reusable, framework-conscious bridge on top of cs-webui that gives HTML and web frameworks the same role XAML and code-behind have in desktop MVVM: the browser renders the View, C# supplies the ViewModel/DataContext, and a generated binding layer connects them. Angular, React, Vue, Svelte, and HTMX are first-class View targets, all safe for trimming and Native AOT.

01 · Outcome

What this repository should become

A small infrastructure product, not a second application framework. It supplies the repeatable bridge between .NET MVVM state and several web View technologies while letting each consumer own its presentation, domain services, and visual system.

01

Reusable runtime

Lifecycle, request dispatch, state snapshots and patches, notifications, cancellation, reconnect, and structured errors.

02

Generated binding layer

Closed, statically reachable getters, setters, commands, subscriptions, serializer metadata, and typed web clients generated from mapped ViewModels.

03

Frontend integrations

Native reactive primitives and lifecycle adapters for Angular, React, Vue, and Svelte, plus server-driven HTMX Views—without prescribing a design system.

04

Reference implementation

A non-proprietary sample proves navigation, editing, validation, progress, cancellation, dialogs, reconnect, disposal, and a published Native AOT executable.

05

Adoption seam

A consumer UI library maps existing ViewModels to any supported web View. Standard bindings require no handwritten transport DTOs, controllers, or adapter classes.

Self-contained implementation contract: this document, the linked template-engine plan, and the companion candidate plans are the complete public planning inputs. Implementers must not require private source trees, unpublished APIs, historical desktop implementations, or conversation context. When a detail is intentionally undecided, an ADR and its acceptance test are a deliverable of the phase that owns the decision.

Hard exclusion: Microsoft.Web.WebView2 is not a dependency. Window creation, embedded browser ownership, server startup, and native webview transport remain responsibilities of cs-webui.
Companion library portfolio: reusable application hosting, navigation/dialog/workflow/operation mechanics, generated text resources, and command-line hosting are specified in the candidate plans. Normative language

Must and must not are release requirements. Should records the preferred design and requires an ADR to deviate. May is optional. “Core” means the CsWebUi.MVVM .NET package plus the framework-neutral cs-webui-mvvm TypeScript package; it never means a consumer application.

Explicit non-goals for 1.0

No remote-browser hosting, authentication framework, general RPC, arbitrary object graph synchronization, runtime View discovery, visual component kit, router, dialog policy, persistence, offline mutation queue, SSR for the JavaScript adapters, mobile embedding, or compatibility layer for desktop UI frameworks. Accessibility helpers may be supplied, but accessibility remains a View responsibility.

03 · View layer

The WPF authoring model, translated to the web

Application developers should experience this as a View technology—not as an RPC system. They author a C# ViewModel, a web View, and optional web code-behind. CsWebUi.MVVM supplies the equivalent of DataContext, the binding engine, view discovery/mapping, dispatcher crossing, and lifetime cleanup.

What a consumer writes

  • An ordinary C# ViewModel using BCL MVVM contracts, CommunityToolkit.MVVM, or ReactiveUI.
  • An Angular, React, Vue, or Svelte View with optional TypeScript code-behind—or a typed .cwhtml View with optional C# code-behind.
  • One explicit mapping between the logical ViewModel contract and the web View.
  • Attributes only for opt-out, naming, advanced serialization, or intentionally exposed nonstandard behavior.

What the framework writes

  • Typed getter/setter delegates, command executors, change subscriptions, and validation adapters.
  • AOT-safe JSON metadata, TypeScript types, property handles, command handles, and binding manifests.
  • Angular signals/directives, React hooks, Vue composables, Svelte runes/stores, or generated HTMX endpoints and fragments.
  • Session creation, DataContext replacement, dispatch, reconnect, and teardown mechanics.

Authoring rule: view policy stays in C# ViewModels; DOM state, focus, measurement, animation, and browser-specific behavior stay in TypeScript code-behind. The framework connects them but does not collapse the separation.
HTML-framework boundary: no frontend framework is a Core dependency. Angular, React, Vue, and Svelte adapt the same generated property/command handles; HTMX consumes the same ViewModel contract through compiled HTML fragments and generated endpoints. Plain HTML/TypeScript and future adapters remain possible without changing .NET bindings or the transport protocol.
04 · Architecture

A generated binding engine over a narrow protocol

The .NET side keeps ordinary ViewModels. Mapping a ViewModel opts its supported public binding surface into a local View contract. The binding compiler generates direct access and subscriptions; the TypeScript client presents that surface as typed properties, collections, validation, and commands.

State flows .NET → web. Intent flows web → .NET. A monotonic revision reconciles reconnects and rejects stale writes.

Runtime packages

  • CsWebUi.MVVM — public .NET abstractions and mapping attributes, runtime, registration API, serializer context hooks.
  • CsWebUi.MVVM.Build — binding compiler, MSBuild integration, analyzers, and generated C#/TypeScript; distributed as transitive build assets, never loaded at runtime.
  • CsWebUi.MVVM.CommunityToolkit — first-party CommunityToolkit.MVVM conventions and richer command/validation support.
  • CsWebUi.MVVM.ReactiveUI — first-party ReactiveUI properties, observables, commands, activation, and disposal.
  • cs-webui-mvvm — framework-neutral TypeScript protocol client.
  • cs-webui-mvvm-angular — Angular providers, signals, lifecycle, and component registry.
  • cs-webui-mvvm-react — React context, hooks, external-store subscriptions, and lifecycle.
  • cs-webui-mvvm-vue — Vue plugin, refs, composables, directives, and lifecycle.
  • cs-webui-mvvm-svelte — Svelte runes/store bridge, context, actions, and teardown.
  • CsWebUi.MVVM.Html / .Htmx — typed template runtime/compiler assets and HTMX request/fragment integration.

Key runtime abstractions

  • IWebUiBindingAdapter is the low-level extension point used by generated and framework-specific bindings.
  • IWebUiSession owns scope, view model, subscriptions, revision, and disposal.
  • IWebUiClient pushes snapshots, patches, events, errors, and command availability.
  • WebUiContract is a stable string-backed logical view identity.
  • IWebUiSessionFactory opens an explicitly registered contract in a new DI scope and is the only runtime entry point that resolves a ViewModel.
  • IWebUiDispatcher serializes mutations per session and never executes consumer code on the transport callback.

Registration semantics: contracts are ordinal, case-sensitive, non-empty UTF-8 identifiers limited to 128 bytes. Duplicate contracts fail during registration. Missing contracts, duplicate generated member IDs, incompatible serializers, and selecting more than one binding adapter for a ViewModel fail host validation before the webview opens. A session creates one child DI scope, resolves one ViewModel and one generated adapter from that scope, and disposes subscriptions, ViewModel, then scope in reverse creation order. Async disposal is awaited; repeated close is idempotent.
Dependency direction: CsWebUi.MVVM.Build consumes project metadata and emits Core adapters but is never a runtime dependency; CommunityToolkit/ReactiveUI → CsWebUi.MVVM; CsWebUi.MVVM.Htmx → CsWebUi.MVVM.Html + CsWebUi.MVVM; every JavaScript framework adapter → cs-webui-mvvm. Core must not reference an MVVM integration, template compiler, frontend framework, or companion application library. Frontend adapters must not reference one another.
Binding boundary: explicitly mapping a ViewModel opts in its supported public bindable surface—not arbitrary methods, injected services, or an unbounded object graph. Properties and recognized commands bind by convention; [WebUiIgnore] opts out, while complex/nonstandard types require an explicit web contract or custom adapter.
05 · Protocol

Small enough to reason about

Start with a single protocol version and one request entry point. Separate message kinds are represented by typed envelopes rather than accumulating ad-hoc cs-webui bindings.

Identity

Protocol version, contract ID, session ID, request ID, view instance ID, and monotonic state revision.

Client → host

Handshake, open, close, execute command, set property, cancel request, acknowledge revision, and request snapshot.

Host → client

Handshake result, snapshot, property patch, collection change, command state, validation, domain-neutral event, result, and fault.

Correctness rules

  • Messages for an individual session are serialized; unrelated sessions may run concurrently.
  • Every mutation carries the revision it was based on. Stale writes fail predictably or request a fresh snapshot.
  • Reconnect starts with a full snapshot. Patches are an optimization, never the only source of truth.
  • Cancellation and timeout are first-class results. Exceptions are sanitized before crossing the boundary.

Security and limits

  • Local-only server by default; public binding requires an explicit opt-in outside this library.
  • Per-session random capability token attached during bootstrap and checked for every invocation.
  • Configurable maximum payload, collection patch, command duration, pending request count, and sessions.
  • No remote type names, arbitrary method names, filesystem paths, or stack traces in protocol messages.
{
  "v": 1,
  "kind": "setProperty",
  "contract": "settings",
  "session": "8b5cb7e9-8084-4fb9-b9ba-8bb47602ee82",
  "view": "root",
  "request": "bd86214e-f76c-4035-b1df-f4c7d329d5f3",
  "baseRevision": 12,
  "payload": { "member": 1, "value": "example" }
}
Schema ownership: canonical JSON Schemas live under protocol/schema/v1/; valid and invalid examples live under protocol/corpus/v1/. Schemas and the accompanying protocol specification are the hand-reviewed source of truth. C# and TypeScript wire models, discriminators, serializer contexts, and corpus tests are generated from them and must never be edited independently. The wire references stable numeric member IDs; generated APIs expose their logical names from the binding manifest. CLR or TypeScript type names never appear on the wire. Session and request IDs use lowercase hyphenated UUIDs, revisions are non-negative signed 64-bit integers, and all comparisons and encodings are culture-invariant.
Version and failure rules: the handshake negotiates one protocol major and advertised optional capabilities. Unknown message kinds, unknown members, invalid payloads, stale revisions, limits, cancellations, timeouts, and disposed sessions return stable machine codes (protocol.unsupported, request.invalid, member.unknown, revision.stale, limit.exceeded, request.cancelled, request.timeout, session.closed) plus a sanitized message. Minor additions are capability-gated; a breaking wire change requires a new schema directory and protocol major. A successful mutation increments the session revision exactly once; rejected mutations do not increment it.
06 · Binding compilation

Compile bindings the way XAML compiles bindings

Binding compilation helps precisely where AOT, independent MVVM generators, and a cross-language View boundary meet. The build inspects the final ViewModel shape, validates the mapped binding surface, and emits all C#, serializer, manifest, TypeScript, and template artifacts before the application and selected View build consume them.

IDE analyzer

  • Validates view mappings and attributes immediately.
  • Reports unsupported types and ambiguous binding names.
  • Offers framework-aware diagnostics and code fixes.
  • Does not depend on another generator's output.

Binding compiler

  • Runs as an MSBuild-integrated design-time compiler before final C# and web builds.
  • Uses Roslyn symbols and framework plugins; it never loads or executes the consumer assembly.
  • Generates direct getters, setters, command calls, subscriptions, registries, and serializer contexts.
  • Writes only to intermediate output; tracked source is never rewritten by a normal build.

Web contract output

  • Generates DTOs, property/command handles, validation maps, and logical view identifiers.
  • Generates framework-neutral TypeScript plus typed helpers for Angular, React, Vue, and Svelte; HTMX uses generated C# routes and fragment descriptors.
  • Uses deterministic ordering, invariant formatting, and protocol/compiler version headers.
  • Supports materialized snapshots for API review and a verify CI mode.
Why a binding compiler instead of only a Roslyn Source Generator: generators have no defined execution order and see the same initial compilation, so one generator cannot reliably consume properties emitted by CommunityToolkit.MVVM or ReactiveUI.SourceGenerators. The binding compiler performs a separate design-time compilation, observes the complete generated ViewModel surface, and then emits inputs that the final C# and View builds compile normally. See the ReactiveUI.SourceGenerators interoperability note.

MSBuild contract: CsWebUiGenerateBindings runs before CoreCompile and before the selected web build, declares complete Inputs/Outputs, and writes only under IntermediateOutputPath. Its discovery compilation excludes CsWebUi-generated files to prevent recursion. Design-time builds may emit diagnostics and contracts but must not run npm, launch a browser, or modify tracked files. Identical semantic inputs must produce byte-identical UTF-8/LF output across machines; absolute paths and timestamps are forbidden.

07 · MVVM frameworks

First-party adapters, not consumer boilerplate

The core binding model starts with the portable contracts familiar from desktop MVVM. Separate packages add compile-time recognition and richer runtime semantics for popular frameworks without forcing those dependencies on every consumer.

IntegrationRecognized surfaceGenerated behaviorPackage
BCL / POCO baseline INotifyPropertyChanged, INotifyCollectionChanged, INotifyDataErrorInfo, ICommand One-/two-way properties, collection deltas, errors, CanExecute, execution, and cleanup CsWebUi.MVVM
CommunityToolkit.MVVM ObservableObject, ObservableValidator, [ObservableProperty], [RelayCommand], relay command interfaces Generated property names, validation, dependent command state, async execution, running/cancel state, and typed parameters CsWebUi.MVVM.CommunityToolkit
ReactiveUI ReactiveObject, IReactiveObject, [Reactive], [ObservableAsProperty], ReactiveCommand<,>, activation Observable values, output properties, typed command input/output, CanExecute, IsExecuting, command faults, activation, and disposable subscriptions CsWebUi.MVVM.ReactiveUI

Convention with a safe boundary

  • A ViewModel is invisible until explicitly mapped or marked with [WebUiViewModel].
  • Once mapped, supported public observable properties and recognized commands bind by convention—matching DataContext expectations.
  • Ordinary public methods, injected services, delegates, streams, and unknown object graphs are never exposed automatically.
  • [WebUiIgnore] removes a member; [WebUiName] stabilizes its web name; [WebUiData] explicitly admits a complex DTO graph.

Compatibility policy

  • Each framework integration is a separate NuGet package with no reference from Core back to the framework.
  • Support one current major and one previous major where their public contracts permit it; publish the tested version matrix.
  • Compile compatibility tests against real framework packages and their source generators—not hand-written fakes.
  • A framework convention change must produce a clear build diagnostic and manual-adapter fallback, never silent missing bindings.

CommunityToolkit.MVVM mapping

The integration understands toolkit source attributes in original source and verifies their generated public members in the design-time compilation. IAsyncRelayCommand contributes execution, cancellation, and running state; ObservableValidator contributes validation without a consumer adapter.

Official MVVM Toolkit documentation

ReactiveUI mapping

The integration subscribes to reactive properties and command observables using generated closed delegates. Command results and faults cross as typed results/faults, while activation and every Rx subscription are tied to the web View session's disposal.

Official ReactiveUI command documentation

Extensibility: publish a documented binding-compiler plugin API so future integrations—such as Prism, Caliburn.Micro, or custom in-house MVVM bases—can describe observable properties, commands, validation, activation, and disposal without changing the transport protocol or frontend packages.

Cross-framework semantic contract

The public API may look native in each framework, but behavior is identical: initial snapshot, ordered updates, two-way property writes, collection changes, command parameters/results, CanExecute, running/cancel state, validation, nested Views, reconnect, DataContext replacement, and deterministic teardown.

Support and release policy

Each adapter is independently packaged but released in lock-step with Core. Support one current framework major at a time, add the previous major only where maintenance cost remains bounded, and publish an exact compatibility matrix. A shared conformance kit prevents an adapter from becoming a second-class target.

Adapter conformance API: every JavaScript adapter must implement the framework-neutral test driver operations mount(contract, host), replaceContext(session), read(member), write(member, value), execute(command, parameter), cancel(request), disconnect(), reconnect(), and unmount(). The shared kit owns fixtures and expected event traces; adapters own only framework mounting and observation. Required fixture IDs are properties, collections, commands, validation, nested-view, replacement, reconnect, stale-write, cancellation, fault, and teardown. No adapter may waive a fixture for a stable release.
09 · Typed HTML + HTMX

Server-driven Views deserve a real compiler

HTMX follows a different model from the TypeScript frameworks: C# owns most state and interaction, while the browser swaps compiled HTML fragments. A Maud-inspired template language provides concise markup, C# expressions and control flow, automatic escaping, composition, strong diagnostics, and a tiny AOT-safe runtime.

01

.cwhtml templates

HTML-shaped, brace-based syntax with typed C# splices, @if, @foreach, @switch, attributes, partials, components, layouts, and fragments.

02

Generated renderer

Templates compile into direct HtmlWriter calls and typed render methods. No runtime parsing, expression compilation, reflection, or MVC/Razor dependency.

03

HTMX bridge

Generated command/form endpoints render named fragments, validation, out-of-band updates, response triggers, focus hints, and revision metadata.

@view SettingsView(SettingsViewModel model)

main #settings .settings-page {
    h1 { (model.Title) }

    form hx-post=(Htmx.Command(model.SaveCommand))
         hx-target="#settings" hx-swap="outerHTML" {
        label for="serverName" { "Server name" }
        input #serverName name=(Bind.Name(model.ServerName))
               value=(model.ServerName);
        @validation(model.ServerName)
        button type="submit" disabled[=!model.SaveCommand.CanExecute(null)] {
            "Save"
        }
    }
}
Separate design: the template language, compiler pipeline, safety model, editor experience, HTMX request model, test matrix, and its own 16–24 engineer-week estimate are specified in the dedicated template-engine plan.
AOT rationale: ASP.NET Core's current Native AOT matrix supports Minimal APIs but not MVC. The template engine therefore compiles directly to a small renderer and generated endpoints instead of depending on MVC or runtime Razor compilation. Official Native AOT compatibility guidance.
10 · Native AOT

A release gate, not a later optimization

Every architecture decision is tested against a published Native AOT executable from the first implementation slice. “Works when trimmed” is insufficient; the automated test must start the host and execute a complete browser-to-view-model round trip.

Required properties

  • IsAotCompatible=true
  • IsTrimmable=true
  • Trim and AOT analyzers enabled
  • Warnings treated as errors

Forbidden runtime patterns

  • Assembly or member scanning
  • Type.GetType dispatch
  • Activator.CreateInstance
  • Expression compilation / emit

Serializer rules

  • Only JsonTypeInfo<T>
  • No polymorphic object
  • Closed message union
  • Build error for unknown shapes

AOT acceptance smoke test

On Windows x64: restore from packed artifacts, publish with PublishAot=true, launch the executable, load each View target scheduled for the current wave through cs-webui, open a sample View, change a bound value, execute an async command, observe state and availability or the returned fragment, close the window, and verify deterministic disposal with exit code 0. Wave D exercises the framework-neutral SDK and HTMX; Wave E adds React/Vue/Svelte; Wave F adds Angular and ReactiveUI-backed Views.

Gate mechanics: CI publishes a fresh package-consumer project with PublishAot=true, PublishTrimmed=true, TrimMode=full, EnableTrimAnalyzer=true, EnableAotAnalyzer=true, and all trim/AOT warnings treated as errors. The test runs the published binary—not dotnet run—and exercises the protocol corpus plus every adapter fixture owned by the current wave. Suppressions, DynamicDependency, reflection roots, and serializer fallbacks require a public ADR naming the exact member and proving why generation cannot replace it; no blanket warning suppression is accepted.

15 · Adoption

How a UI library consumes it

Adoption happens through a thin View package and a product-owned web workspace or compiled template project. Existing renderer-neutral ViewModels are mapped directly; the selected View adapter handles standard binding mechanics while consumer code owns the actual HTML View.

A

Reference

Product.UI.Web references CsWebUi.MVVM, its chosen .NET MVVM integration, and exactly one View adapter; the build compiler emits the required C# and web contracts.

B

Map

The consumer maps each ViewModel contract to a framework component or compiled HTML View. Standard properties, collections, validation, and commands need no adapter code; only exceptional object graphs use explicit adapters.

C

Render

The consumer's View package owns theming, components/partials, shell, navigation, dialogs, icons, branding, and accessibility regardless of the selected target.

D

Integrate consumers vertically

Port one complete flow first—startup, shell, navigation, form, validation, operation, and dialog—then repeat in a second independent consumer. Avoid building the entire component catalog before a real application validates the seam.

E

Keep platform capabilities outside

File picking, process execution, shutdown, native dialogs, and installation services remain application capabilities invoked by view models. The generic bridge only transports their typed inputs, progress, results, and faults.
