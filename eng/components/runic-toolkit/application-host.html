Standalone implementation specification · draft 2

One deterministic host for services, commands, MVVM, and the web window.

Build a public application framework on Microsoft.Extensions.Hosting that composes configuration, logging, dependency injection, application lifetime, cs-webui, generated MVVM bindings, frontend assets, and optional command-line execution. This document is the complete implementation brief: no private repository, existing application, or prior discussion is required.

01 · Product boundary

A host framework, not a service locator

The framework owns process-wide ordering, launch selection, lifetime, validation, errors, exit codes, threading seams, and asset/native-runtime readiness. Applications own business policy and opt into integrations explicitly.

01

Generic Host composition

Expose normal HostApplicationBuilder, configuration, logging, options, dependency injection, IHostApplicationLifetime, and hosted-service conventions.

02

Launch intent

Classify arguments into UI, command, help/version, or invalid input before any native window work. The classifier is replaceable and side-effect free.

03

UI lifetime

Initialize cs-webui through an adapter, create a window, open a root MVVM session, await closure asynchronously, and translate native close into host shutdown.

04

Validation

Validate the root View, generated manifests, frontend entry point, command collisions, required options, native runtime, and exactly one runtime adapter.

05

Failure policy

Classify expected configuration, asset, startup, command, UI, cancellation, and teardown failures; log once and return a stable exit code.

06

Deterministic teardown

Stop accepting work, cancel the active mode, close sessions and windows, stop participants in reverse order, stop the Generic Host, and dispose once.

Non-goals for version 1: no branding or component library; no updater, elevation, single-instance, crash reporting, file picker, telemetry, or logging provider; no proprietary command parser; no remote web hosting; no attempt to replace Microsoft.Extensions.Hosting. Each may be an application service or a later optional adapter.

Dependency rule: Abstractions ← Hosting ← WebUi/CommandLine. Generators may reference Abstractions for symbol names but no runtime project references Generators or Build. Lower-level MVVM, CLI, and cs-webui libraries must never reference Hosting.

Target and language

Version 1 targets net10.0, enables nullable references, implicit usings, deterministic builds, package validation, analyzers, and warnings-as-errors for repository code. OS-specific code belongs only in the WebUi adapter and uses runtime checks.

Version policy

Pin exact build versions centrally in Directory.Packages.props and commit a restore lock file. Use the Microsoft.Extensions major matching the target framework. Pin the tested cs-webui version exactly inside the repository because native binaries and managed bindings must match. Public NuGet dependencies declare the lowest tested compatible version; major upgrades require a compatibility review. All first-party packages use SemVer and ship in one release train until 1.0.

Do not copy version numbers into source files or MSBuild targets. Automated dependency updates must run unit, package, Native-AOT publish, and launch smoke tests before merge. Preview dependencies are allowed only in preview releases and must be visible in release notes.

03 · Lifecycle state machine

Every launch follows one legal path

A built application is single-use. It contains no mutable global state, supports multiple independently built hosts in one test process, and serializes all state transitions.

1 · Created

Build

Compose services and immutable descriptors; resolve launch intent without native side effects.

2 · Validating

Fail early

Run common validation, then validation for the selected mode.

3 · Starting

Start once

Start Generic Host and ordered participants under a startup timeout.

4 · Running

CLI or UI

Exactly one mode runner owns the active operation and result.

5 · Stopping

Drain

Cancel, close, reverse-stop, dispose; transition to Stopped or Faulted.

StepRequired orderFailure behavior
BuildDefaults → user host configuration → service registrations → generated registrations → immutable descriptor snapshotThrow from Build() only for programmer errors such as duplicate singleton configuration
ClassifyParse raw arguments without resolving application services; return one LaunchDecisionInvalid input produces Usage failure and never starts the host
ValidateCommon validators in registration order → selected-mode validators in registration orderAggregate all deterministic validation errors; do not initialize native UI
StartIHost.StartAsync → startup participants by phase and registration orderStop only participants that completed, in reverse completion order
ExecuteCLI runner or UI runner, never both; capture one primary result/failureFirst terminal result wins; later failures are logged as secondary
StopSignal stop → cancel active mode → close root session → close window/runtime → reverse-stop participants → IHost.StopAsync → disposeTeardown never replaces an earlier non-success exit code
Created → Validating → Starting → RunningUi ─┐
                         └→ RunningCommand ─┼→ Stopping → Stopped → Disposed
Any non-disposed state ─────────────────────┘             └→ Faulted → Disposed
Idempotency: concurrent window-close, Ctrl+C, StopApplication(), and fatal-failure signals race through one atomic stop request. Only the winner initiates shutdown; all callers await the same completion task. RunAsync may be invoked once and DisposeAsync may be invoked repeatedly.
04 · Public API

Familiar hosting with typed integration points

The application retains normal access to configuration, logging, options, and services. Hosting adds only launch, UI, command, validation, and lifetime concepts.

internal static class Program
{
    public static Task<int> Main(string[] args)
    {
        var builder = CsWebUiApplication.CreateBuilder(args);
        builder.Services.AddApplicationServices();

        builder.AddWebUi(ui =>
        {
            ui.UseRootView<MainViewModel>();
            ui.UseGeneratedBindings();
            ui.UseFrontendAssets<GeneratedFrontendAssets>();
        });

        builder.AddCommandLine(cli =>
        {
            cli.UseAdapter<GeneratedCommandLineAdapter>();
            cli.UseUiWhenNoCommandMatches();
        });

        return builder.Build().RunAsync();
    }
}

CsWebUiApplicationBuilder

Exposes HostApplicationBuilder Host, plus convenience properties for Services, Configuration, Logging, and Environment. AddWebUi and AddCommandLine may each be called once; duplicates throw with registration-source information. Build() freezes configuration and returns CsWebUiApplication.

CsWebUiApplication

Implements IAsyncDisposable. Task<int> RunAsync(CancellationToken) performs the state machine. Exposes read-only State and Completion for diagnostics, but not the root service provider.

Participants with the same phase start in DI registration order and stop in reverse completion order. They must be idempotent on StopAsync. The framework registers keyed mode runners and rejects zero or multiple runners for the selected launch kind.

public interface IApplicationValidator
{

        ApplicationValidationContext context,

{

}
API constraints: no IServiceProvider property as a locator; no static current application; no public native window type; no stringly typed state; no user callbacks that are silently fire-and-forget. Adapter factories may receive a scoped service provider only at the moment they create a scoped object.
05 · Integration seams

Web UI, CLI, and assets meet at contracts

The host depends on abstractions instead of a particular command parser or JavaScript framework. Adapters translate their native lifecycle into the common state machine.

Web runtime and window

    event EventHandler? CloseRequested;

    ValueTask ShowAsync(CancellationToken token);
    Task WaitForCloseAsync(CancellationToken token);
    ValueTask CloseAsync(CancellationToken token);
}

Root MVVM session

public interface IRootViewSessionFactory
{
    ValueTask<IRootViewSession> OpenAsync(
        IWebUiWindow window, CancellationToken token);
}

public interface IRootViewSession : IAsyncDisposable
{
    ValueTask ActivateAsync(CancellationToken token);
    ValueTask DeactivateAsync(CancellationToken token);
}

The WebUi adapter creates one DI scope for the root session. ViewModel, binding bridge, navigation/dialog flow, and view session resolve from that scope. Disposal closes the scope after deactivation.

Command-line adapter

public interface IHostedCommandLineAdapter
{
    LaunchDecision Classify(IReadOnlyList<string> arguments);
    ValueTask<CommandExecutionResult> ExecuteAsync(
        IReadOnlyList<string> arguments,
        IServiceProvider scopedServices,
        CancellationToken cancellationToken);
}

public sealed record CommandExecutionResult(int ExitCode, string? Summary = null);
  • Classify is pure, fast, and safe before IHost.StartAsync. It must not construct command handlers.
  • The mode runner creates one async DI scope per command and passes only that scoped provider to the adapter.
  • Help/version may be rendered without starting hosted services when the adapter declares RequiresHost = false; otherwise the normal start/stop path is used.
  • Unknown arguments fail with Usage by default. Falling back to UI must be an explicit option, never a heuristic.
  • Command completion requests stop. Its exit code is preserved even if graceful teardown reports secondary errors.
  • CLI mode must not resolve IWebUiRuntime, verify UI assets, create an MVVM session, or load native webui binaries.

The build task sorts paths ordinally, rejects traversal, duplicate case-insensitive paths, symlinks escaping the output root, absolute URLs as entry points, unsupported manifest versions, and inconsistent hashes. Normal dotnet build does not perform a package-manager restore. CI runs the frontend build explicitly, then manifest generation and verification. 06 · Errors, exit codes, threading

Predictable under races and failure

Expected failures are data; programming errors remain exceptions. The first terminal failure is primary, cleanup continues, and secondary failures are attached to logs and diagnostics.

Exit codeNameUse
0SuccessNormal UI close, successful help/version, successful command
1UnhandledFailureUnexpected exception not mapped by a registered policy
2UsageInvalid command, unknown option, or ambiguous launch intent
10ConfigurationInvalid options, duplicate registrations, missing root View
11HostStartupGeneric Host or startup participant failed/timed out
12FrontendAssetsMissing entry point, hash mismatch, invalid asset manifest
13NativeRuntimecs-webui native binary or runtime initialization failed
20CommandFailedCommand adapter failed without its own non-zero code
30UserInterfaceWindow, transport, binding bootstrap, or root session failed
40ShutdownTeardown failed when no earlier failure existed
130CancelledExternal cancellation or Ctrl+C before normal completion

Application commands may return any value from 0–125. Framework-reserved values above are used only when the command did not return a result. IExitCodePolicy maps ApplicationFailure to a code and may be replaced. If a command returns non-zero and shutdown also fails, retain the command code.

public enum ApplicationFailureCategory
{
    Usage, Configuration, HostStartup, FrontendAssets,
    NativeRuntime, Command, UserInterface, Shutdown, Cancelled, Unhandled
}

public sealed record ApplicationFailure(
    ApplicationFailureCategory Category,
    string Code,                 // stable machine-readable identifier, e.g. CWH-ASSET-001
    string SafeMessage,          // contains no secrets or raw frontend content
    Exception? Exception = null,
    bool IsExpected = true);

public interface IExitCodePolicy
{
    int GetExitCode(ApplicationFailure failure);
}

Thread ownership

The entry thread builds and runs the host. The WebUi adapter documents and enforces whether native initialization/window calls require that thread. All later UI access goes through IUiDispatcher; adapter callbacks immediately capture data and post typed work rather than executing application code on native callback threads.

Async discipline

No sync-over-async, blocking waits, or unobserved tasks. Event-to-task bridges use TaskCompletionSource with RunContinuationsAsynchronously. Cancellation registration and event subscriptions are disposed. User callbacks are awaited and exceptions enter the failure policy.

Timeouts

Options define startup, session-close, window-close, host-stop, and total-shutdown timeouts. Use TimeProvider for tests. Timeout expiry records a failure and advances cleanup; it never blocks disposal indefinitely.

Logging and security

Use structured event IDs and log launch kind, phase, durations, safe identifiers, and primary/secondary status. Never log argument values marked secret, asset content, bridge payloads, or authorization tokens. Bind the embedded server to loopback only and validate origin/session tokens.

07 · Native AOT and generation

Publish-and-run is the compatibility test

The host is where DI activation, JSON, native assets, generated bindings, and shutdown paths meet. Every supported extension point must be statically knowable or explicitly annotated.

No runtime discovery

Never enumerate assemblies for Views, commands, participants, serializers, or adapters. Registrations are explicit or emitted by an incremental generator.

Closed factories

Generate strongly typed factories for root ViewModels, sessions, adapters, and commands. If ActivatorUtilities is exposed as an escape hatch, annotate its requirements and cover it with trim tests.

JSON metadata

All host-owned JSON uses generated JsonSerializerContext. Adapter payload serialization is owned by the MVVM protocol package and registered through typed metadata.

Native manifest

Verify runtime identifiers, native library names, hashes, single-file extraction requirements, and managed/native version compatibility before window creation.

Analyzer package

Ship generator binaries under analyzers/dotnet/cs, mark them PrivateAssets=all, and ensure generator output is deterministic across paths and machines.

Real consumer gate

Pack locally, restore into a clean sample with no project references, publish Native AOT, run CLI and UI smoke flows, close cleanly, and permit no IL2026/IL3050 warnings.

09 · Delivery plan

Six gated milestones

Do not begin optional convenience APIs until the lifecycle and Native-AOT path are proven. Each phase ends in shippable documentation and tests.

H0 · Contract

Freeze vocabulary and dependency direction

Create projects, architecture tests, contracts, failure/exit model, launch kinds, state transition table, options, and fakes. Write an ADR for mode selection and shutdown ordering.

Acceptance: abstractions build with no cs-webui, MVVM implementation, CLI parser, or native dependency.
3–5 daysPublic foundation
H1 · Kernel

Implement runner and failure-safe lifecycle

Builder, immutable descriptor, validation pipeline, state machine, participants, stop controller, timeouts, structured logging, exit policy, and complete fake-based race tests.

Acceptance: every transition/failure point has deterministic order, exit code, and disposal assertions.
1–2 weeksHost kernel
H2 · WebUi

Integrate cs-webui and root MVVM session

Native/runtime validation, window adapter, dispatcher, root scope/session, asset provider, close bridge, and one minimal HTML frontend.

Acceptance: packaged Windows x64 Native-AOT sample opens, binds one property/command, and closes with code 0 and no AOT warnings.
1–2 weeksRetire native risk
H3 · CLI

Add optional hosted command mode

Pure classification, command scope, cancellation, exit preservation, help/version path, explicit UI fallback, and proof that CLI mode never initializes UI.

Acceptance: UI and CLI share registered services but have isolated runtime side effects.

Version 1 acceptance checklist

  • All published APIs have XML documentation and API-approval files.
  • Dependency direction is enforced by project and architecture tests.
  • UI, CLI, help/version, invalid input, and cancellation produce documented results.
  • Every partially started resource stops in reverse completion order.
  • CLI-only execution loads no window, assets, MVVM session, or native UI binary.
  • Root View/session registration is typed and validated before native initialization.
  • Frontend and native manifests are deterministic, hashed, and verified.
  • No supported path uses assembly scanning, runtime code generation, or untyped JSON.
  • Windows x64 Native-AOT package consumer publishes with zero trim/AOT warnings.
  • Window-close, Ctrl+C, fatal error, and host-stop races are stress tested.
  • Expected failures are sanitized, structured, logged once, and mapped to stable exit codes.
  • Samples document minimal UI, combined UI/CLI, and custom adapter composition.
  • Package READMEs document compatibility, threading, assets, security, and disposal.
  • Two independent consumers run without private hooks or copied host code.

Deferred beyond 1.0: multi-window orchestration, background/tray lifetime, single-instance activation, automatic updater/elevation, additional operating-system acceptance matrices, remote content, and plugin discovery. Each requires a separate proposal because it changes lifetime or security assumptions.
