Standalone implementation specification · draft 2

Typed HTML from C#. No runtime magic.

Design a Maud-inspired template language for .NET: concise HTML-shaped .cwhtml files, real C# expressions and control flow, automatic contextual escaping, composable render functions, specialized generated code, and a deliberately tiny Native-AOT-safe runtime. HTMX becomes its first complete View integration.

Working package CsWebUi.MVVM.Html Templates .cwhtml + .cwhtml.cs Primary target HTMX Runtime Native AOT Status implementation-ready specification
CompilationMarkup becomes direct C# render code

No runtime parser, expression evaluator, reflection, MVC, or dynamic compilation.

LanguageC# remains the expression language

The template grammar owns HTML structure; values, conditions, loops, and helpers stay typed C#.

SafetyEscaped and validated by default

Raw markup is a capability type. Dynamic script/style content is outside the normal language.

CompositionFunctions, components, layouts, fragments

One rendering model serves full pages, reusable pieces, and precise HTMX swaps.

01 · Outcome

A compiler product, not a string helper

A good template engine must make common HTML concise while catching structural, type, binding, and security mistakes before the application starts. Its generated renderer must be fast enough for frequent HTMX fragments and predictable enough for Native AOT.

01

Strongly typed

Every splice, condition, loop, component argument, ViewModel property, route, command, and form field is checked against the consumer compilation.

02

HTML-aware

The compiler understands elements, void tags, boolean and URL attributes, nesting, IDs, ARIA names, custom elements, fragments, and escaping contexts.

03

Composable

Normal C# methods return renderable fragments; layouts and typed slots add higher-level structure without a second component runtime.

04

HTMX-native

Generated endpoints and helpers connect commands, form fields, validation, named fragments, out-of-band swaps, triggers, revisions, and focus restoration to the same ViewModel session.

05

AOT-native

The release binary contains direct renderer code and static route tables. The runtime is limited to encoded writing, fragments, render context, pooling, and small HTMX response primitives.

02 · Inspiration

Borrow Maud's principles, not Rust's macro system

Maud compiles HTML macros to specialized Rust code, uses host-language values and control flow, escapes interpolated text by default, composes through renderable functions, and retains a small runtime. Those are the architectural qualities to reproduce in a .NET-native form.

Maud principle.NET interpretationDeliberate difference
Compile-time macro.cwhtml binding compiler emits specialized C# renderer methodsC# has no Rust-style procedural expression macro; an MSBuild/Roslyn compiler owns the extra language
Host-language expressionsSplices and control flow contain type-checked C# expressionsExpressions are embedded in a template file and mapped back with source diagnostics
Escaping by defaultText, attributes, URLs, and trusted markup have distinct generated writer pathsContextual policies are stricter than a single generic escape function
Functions as partialsC# methods/components return HtmlFragment or implement IHtmlRenderableTyped layouts and slots are added because application Views need standardized composition
Minimal runtimeGenerated direct writer calls over IBufferWriter<byte>HTMX helpers add local request/fragment metadata, but no MVC View engine
Independent implementation: use Maud as design research, not as source to translate. Record a license/provenance review, define an original grammar for C#/.NET, and keep syntax choices driven by Roslyn tooling, HTML correctness, and HTMX needs.
03 · Authoring model

Template file plus optional C# code-behind

The file stem pairs markup with a generated partial View class. Simple Views need only .cwhtml. Complex Views add .cwhtml.cs for preparation, event coordination, helper fragments, and View-only behavior while domain policy stays in the ViewModel.

@using SampleApp.Presentation
@view SettingsView(SettingsViewModel model)

@fragment pageHeader(string title) {
    header .page-header { h1 { (title) } }
}

main #settings .settings-page {
    @render(pageHeader(model.Title));

    form hx-post=(Htmx.Command(model.SaveCommand))
         hx-target="#settings"
         hx-swap="outerHTML" {

        label for="serverName" { "Server name" }
        input #serverName
              name=(Bind.Name(model.ServerName))
              value=(model.ServerName)
              aria-invalid=(model.HasErrors ? "true" : "false");

        @render(Validation.For(model.ServerName));

        button type="submit"
               disabled[=!model.SaveCommand.CanExecute(null)] {
            @if (model.SaveCommand.IsRunning) {
                "Saving…"
            } @else {
                "Save"
            }
        }
    }
}
public sealed partial class SettingsView
{
    protected override ValueTask OnOpenedAsync(CancellationToken cancellationToken) =>
        ViewModel.LoadAsync(cancellationToken);

}

Template owns

  • HTML structure, classes, attributes, ARIA relationships, and HTMX declarative behavior.
  • Presentation conditionals and loops over already prepared ViewModel state.
  • Choice of full View, named fragment, partial, layout, and focus/scroll hints.

Code-behind owns

  • View activation, DOM/HTMX coordination, helper fragments, formatting, and presentation-only state.
  • Never business policy that belongs in the ViewModel.
  • No direct arbitrary HTTP controller surface; events bind through generated handles.
04 · Language

Small grammar, full C# values

The template grammar should remain intentionally smaller than Razor. It describes HTML and composition; it delegates computation to C#. Every new syntax feature carries parser, formatter, editor, diagnostics, security, and compatibility cost.

Version 1 includes

HTML5 elements/custom elements, text and attribute splices, C# conditionals/loops/switch/locals, render functions, typed components and layouts through fragment arguments, named fragments, forms/validation, localization helpers, HTMX attributes, source diagnostics, formatter, and deterministic code generation.

Version 1 excludes

Runtime template loading, arbitrary scripting, dynamic member lookup, expression strings, MVC/Razor compatibility, implicit service location, database/I/O calls during rendering, CSS/JavaScript templating, full browser DOM diffing, and user-authored compiler plugins.

05 · File model and grammar

A complete input contract

An implementation must not infer syntax from the examples. Version 1 uses the lexical and grammar rules below. Any later syntax is a language-version change, enabled explicitly with <CwhtmlLanguageVersion>; silently reinterpreting an existing valid file is forbidden.

Files and identity

  • Views/Settings.cwhtml is an MSBuild AdditionalFiles item with logical path preserved; UTF-8 is required and a BOM is accepted.
  • The header must contain exactly one @view ViewType(ModelType model) after optional namespace, using and injection directives. The generated class is partial; the model parameter and injected names are in scope for every expression.
  • An optional same-stem Settings.cwhtml.cs is an ordinary C# compile item declaring that same partial class. It may provide helpers and lifecycle overrides. It is not required.
  • @namespace, repeatable @using, then repeatable @inject ServiceType name directives precede @view; no header directive is legal afterward. Injection generates constructor parameters and readonly properties—never runtime service lookup.
  • If namespace is omitted, MSBuild RootNamespace plus the logical folder path is used. Two templates may not produce the same fully qualified View type. Template identity is the normalized project-relative path with / separators, compared ordinal and case-sensitive on every OS.

Whitespace and lexical rules

  • Whitespace separates tokens but emits no output. Visible text is an ordinary, verbatim, or raw C# string literal node; its decoded value is HTML-encoded on write. Authors therefore control significant spaces explicitly.
  • @* ... *@ is a nestable template comment and emits nothing. @htmlcomment("text") emits an encoded HTML comment and rejects -- or a trailing -.
  • Declaration identifiers follow C# rules. Tag/attribute names use ASCII HTML/custom-element names. Shorthand CSS names use [A-Za-z_][A-Za-z0-9_-]*, allowing .page-header; other static ID/class values use quoted attributes. Custom elements must contain -.
  • Static names are normalized to lowercase only for validation, never rewritten in diagnostics. Parenthesized C# is scanned with Roslyn tokenization, including nesting, comments, generic types, interpolated/raw strings and collection expressions.
  • Line endings normalize to LF for hashing and generated output. Source spans retain original line/column positions. Tabs advance according to the configured formatter width, default four.

06 · Compiler

A reproducible two-pass build

A normal source generator cannot reliably inspect members emitted by another generator in the same compiler pass. The build therefore runs a self-contained template compiler before CoreCompile. It creates a Roslyn probe compilation, runs the consumer's configured generators, binds templates against that updated compilation, writes deterministic .g.cs files under obj/, and lets the normal compiler build the application.

.cwhtmlsource + spans
→
ParserHTML/template AST
→
Probe compilationconsumer sources + generator output
→
Generated C#renderer + descriptors

MSBuild contract

  • The NuGet build package adds CompileCwhtml after ResolveReferences and before CoreCompile; generated files enter Compile and FileWrites.
  • Inputs are Compile, AdditionalFiles, resolved metadata references, analyzer/generator references, analyzer config options, parse/nullable/language settings, root namespace, target framework, template options, and compiler version.
  • The probe excludes prior CwhtmlGenerated files, adds declaration stubs for templates without code-behind, then runs the same generator assemblies and options as the real compilation exactly once.
  • On design-time builds, generation is cancellable and may use the last successful cache. Command-line/CI builds never accept stale output.
  • The task is out-of-process by default to avoid locking compiler assemblies. It writes atomically and deletes orphaned generated files through a manifest.

Determinism and cache

  • Cache keys use SHA-256 of normalized template/source content, metadata/analyzer file content, options, compiler/runtime versions, and referenced public symbol fingerprints. Absolute paths and timestamps never affect generated bytes.
  • Files are processed by normalized logical path; symbols, attributes, and generated tables use ordinal stable ordering. Generated files use LF, UTF-8 without BOM, invariant culture, and no current date or machine path.
  • A no-op incremental build reads the manifest and emits no file writes. Changing one template rebuilds it plus templates that reference its component/fragment signatures.
  • dotnet cwhtml verify performs a clean temporary generation and byte-compares the manifest and outputs; CI runs it after the normal build.
  • Compiler and runtime major/minor versions must match. A generated CwhtmlCompilerStamp causes a clear build error on incompatible packages.

Repeat the generated-member and lifecycle proof for ReactiveUI at the Wave F entry gate; ReactiveUI does not block grammar expansion or the Wave D core release candidate.
07 · Runtime and composition

Small primitives, ordinary C# composition

The runtime should be boring. It owns encoded output and a few capability types; generated code owns structure. Reusable markup remains normal typed C# so partials can be tested without booting a browser or server.

Utf8HtmlWriter

A stack-friendly writer over IBufferWriter<byte> with pooled buffers, explicit element/attribute/text methods, invariant scalar formatting, and async flush only at response boundaries.

HtmlFragment

An immutable render capability, not a string. It can compose without escaping its own markup while all values written into it remain encoded.

IHtmlRenderable

The Maud-like extension seam for typed application components. Implementations render to the provided writer and context without allocating intermediate HTML strings.

TemplateContext

Explicit culture, localization, URL policy, session/revision, cancellation, assets, and request metadata. Dependencies are constructor-injected into the View; there is no ambient or contextual service locator.

TrustedHtml

An intentionally hard-to-create capability accepted only from audited framework helpers or an explicit sanitizer. It never converts implicitly from string.

HtmlUrl

A validated relative/local URL value. Dynamic URL attributes require it or a generated route; unsafe schemes fail before writing output.

Generated class contract

  • The generated partial class derives from TemplateView<TModel>, has one public constructor accepting the model plus declared injected services, and overrides synchronous Render/TryRenderFragment.
  • Rendering itself is synchronous because a by-reference stack writer must not cross an await. Endpoint code renders into a pooled buffer and asynchronously writes that completed buffer to the transport.
  • Each View emits an internal static descriptor and a module-initializer-free registration method. The application generator creates one closed, sorted descriptor table and DI factory table.
  • Fragment IDs are deterministic 32-bit hashes of template ID plus fragment name; collision detection is a compile error. Public/log messages use names, transport paths use opaque endpoint handles.

Lifetime and ownership

  • The DI scope owns the ViewModel, View, injected services and session. The host calls public OpenAsync/CloseAsync; the base guarantees each protected lifecycle hook runs at most once.
  • DisposeAsync closes an open View and is idempotent. If close/open fails, scope disposal still runs. Objects implementing both disposal interfaces are disposed asynchronously only.
  • TemplateContext is per render and never cached by a View or fragment. A View instance is not rendered concurrently; different View sessions may render concurrently.
  • Generated renderer code has no asynchronous path, I/O, locks, static mutable state or service lookup except an explicit component/localizer access emitted from declared dependencies.
Rendering rule: templates are pure with respect to I/O. Load or mutate state before rendering through ViewModel commands/code-behind. A render may format and compose current state, but it may not query a database, call a remote service, or block.
08 · Safety

Context is part of the type system

“HTML escape the string” is not a complete security model. The compiler knows whether a value is text, an attribute, a boolean attribute, a URL, trusted markup, or a forbidden dynamic script/style context and selects or rejects the operation accordingly.

ContextDefault behaviorEscape hatch
Element textEncode & < > " ' correctly as UTF-8 HTML textTrustedHtml only
Quoted attributeAttribute encoding and invalid control-character rejectionNone; trusted markup cannot break an attribute
Boolean attributeEmit attribute name only when the typed condition is trueNone
URL attributeRequire generated route, relative URL, or validated HtmlUrl; reject unsafe schemesExplicit policy service with tests
style / event handlerDynamic interpolation forbidden in v1Use classes/data attributes and static assets
scriptDynamic interpolation forbidden; CSP-compatible static script reference onlyTyped JSON data block may be designed separately
HTMX route/valuesGenerated opaque local route and encoded form values with session capabilityNo arbitrary method or URL strings

Compile-time checks

Unknown/duplicate attributes, invalid void content, duplicate static IDs, wrong ARIA references where statically knowable, missing fragment targets, unsafe URL/script/style interpolation, invalid component arguments, unsupported render types, and unbound HTMX commands.

Runtime checks

Capability token, session and revision, maximum form/body/fragment sizes, request timeout/cancellation, culture-invariant protocol parsing, allowlisted upload types if ever supported, and sanitized errors with no stack trace in HTML.

Normative encoding

  • Text encodes &, <, >, double quote and apostrophe. Attributes additionally reject U+0000 and unpaired surrogates; other disallowed C0 controls are rejected rather than silently removed.
  • Static literals are sent through the same encoders at compile time. Generated constants may contain pre-encoded UTF-8 only when the compiler proves their context.
  • Numbers use invariant culture. Dates, times and application objects have no implicit renderer; authors must format them explicitly. Enum values do not become attribute names automatically.
  • Attribute and tag names are always compiler-known UTF-8 constants. There is no runtime API for a dynamic name in 1.0.

Capabilities and policy

  • TrustedHtml has no public constructor. Only generated static markup and an explicitly registered IHtmlSanitizer can create it; the sanitizer implementation/version is recorded in diagnostics.
  • The default URL policy allows same-origin absolute paths, relative paths without a scheme, fragments, and generated routes. It rejects protocol-relative URLs, credentials, control characters, backslash confusion, data:, javascript:, vbscript: and unknown schemes.
  • Applications may add https, mailto or other schemes through an immutable allowlist. URL validation occurs before percent encoding and again after canonicalization.
  • The host ships a restrictive CSP baseline: no inline script, no inline style, object-src 'none', base-uri 'none', and frame restrictions appropriate to the embedding host. Nonces/hashes are host policy, never template strings.
Threat model: assume every ViewModel string, localization value, form value, route parameter and persisted record is attacker-controlled; assume another local process can reach the loopback listener; and assume a malicious web page can attempt cross-origin requests. Protect transport/session endpoints even in a desktop-only deployment. Security tests must run against generated release code, not only writer primitives.
09 · HTMX integration

C# state in, HTML fragment out

HTMX requests should execute through the same ViewModel session and command contracts as the TypeScript adapters. The difference is representation: the response is an encoded fragment plus declarative swap metadata rather than a JSON state patch.

01

Trigger

A generated hx-post/hx-get route carries the view instance, command/property handle, current revision, and session capability without exposing a .NET method name.

02

Bind and execute

Generated converters bind allowlisted fields, set properties through typed delegates, run validation, check CanExecute, execute with cancellation, and update the authoritative revision.

03

Render and swap

The endpoint renders the declared target fragment and optional out-of-band fragments, then returns HX headers/triggers and focus/scroll hints.

Session lifetimeOpening a View creates a DI scope and random 128-bit handle. Close, navigation removal, idle expiry or host shutdown runs close lifecycle and async disposal exactly once. Default idle expiry is 30 minutes and refreshes only after authenticated activity.

Generated action descriptor

For every bound action, generate closed delegates for field conversion/setters, validation, CanExecute, synchronous or asynchronous execution, result mapping and render-plan selection. The descriptor records allowed fields, size overrides, mutation/read-only classification and target fragments. There is no reflection fallback.

Companion script boundary

One versioned, CSP-compatible ES module may restore focus/scroll, bridge local host push notifications to named DOM events, acknowledge child View removal and handle expired-session refresh. It exposes no arbitrary .NET invocation API, uses no eval, and has browser integration tests. HTMX remains an external pinned dependency with its version and integrity metadata documented.

ReactiveUI · Wave FA deferred official compiler adapter recognizes reactive properties and ReactiveCommand<TInput,TOutput>, converts the generated input value, awaits one execution result and disposes the subscription. Validation support is an explicit adapter capability, not inferred by reflection.
Unknown shapeCompilation fails with a diagnostic describing the required property/command/validation contract. Runtime duck typing, dynamic and silent fallback to a string property name are forbidden.
No application JavaScript target: standard forms, commands, validation, dialogs/overlays, progress, navigation, and fragment refresh should require only templates plus C#. A tiny shipped companion is acceptable for cs-webui push events, focus restoration, and desktop-window integration; consumers do not author it.
Use HTMX's own model: target/swap behavior and out-of-band fragments are first-class concepts, not a simulated client-side state store. See the official HTMX documentation and out-of-band swap contract.
10 · Developer experience

Compiler quality includes tooling

A concise language is not productive if errors point into generated C#. Template paths and source spans are permanent compiler inputs, and editor support follows the same grammar/semantic model as builds.

Diagnostics

Stable diagnostic IDs, exact source spans, clear expected/actual types, related locations, suggested fixes, and no cascade of meaningless parser errors.

Formatting

Deterministic formatter with configurable indentation and line width, preserving intentional text whitespace and producing stable diffs.

Editor

Syntax highlighting, brace/tag matching, completion for HTML/attributes/ViewModel members/components/fragments, hover types, go-to-definition, and rename where reliable.

Watch mode

Incremental recompile and browser refresh in development. Shipped applications contain no compiler and never compile templates at runtime.

Generated source

Opt-in readable renderer output under obj/, source maps, per-template timing, dependency graph, and a command to explain why a template rebuilt.

Testing helpers

Render a full View or named fragment with a test context, parse it as HTML, query semantic nodes, and approve stable normalized snapshots without a live webview.

12 · Diagnostics

Errors belong to the template

Every user-actionable failure has a documented stable ID, severity, primary .cwhtml span, message with actual/expected values, and related C# or template locations. Generated C# diagnostics are translated back through #line and the compiler source map.

RangeCategoryRequired examples
CWH0001–0099Internal/compiler compatibilityUnexpected compiler failure with crash-bundle path; runtime/compiler stamp mismatch
CWH1000–1999Lexing and parsingUnclosed block/string/C# delimiter, unexpected token, invalid recovery boundary
CWH2000–2999File/declarationMissing/duplicate @view, duplicate generated type, invalid namespace or same-stem code-behind

CWH4000–4999HTML/accessibilityVoid content, duplicate attribute/ID, invalid ARIA reference, missing fragment root
CWH5000–5999Escaping and securityDynamic script/style/event, unsafe URL context, raw string-to-markup conversion

CWH7000–7999Build, AOT and configurationStale manifest, nondeterministic output, unsupported target, reflection/dynamic-code dependency

Severity policy

Syntax, type, structural HTML, security, route collision and incompatible-version findings are errors and cannot be downgraded. Accessibility and performance guidance begins as warnings. Standard .editorconfig keys such as dotnet_diagnostic.CWH4102.severity configure eligible diagnostics; suppressions require an inline reason or project-level audit entry.

Recovery and fixes

At most 100 diagnostics per file and 1,000 per build are emitted. Parser recovery suppresses descendants of the same missing token. Code fixes cover only semantics-preserving edits: close delimiter, add void terminator, rename duplicate fragment, convert dynamic boolean attribute, and generate a missing code-behind partial.

Documentation gate: every shipped diagnostic has a documentation page containing cause, bad and corrected examples, default severity, configurability and version introduced. A diagnostic snapshot test fixes its ID, message arguments, severity and exact UTF-16 line/column span.

14 · Verification

Definition of good

Template correctness is broader than snapshot equality. The release suite proves language behavior, generated C#, valid HTML, contextual security, ViewModel semantics, HTMX interaction, editor diagnostics, performance, and the final native executable.

Grammar

Golden ASTs, recovery, Unicode, whitespace, nesting, ambiguous tokens, every control structure, and deterministic formatter round trips.

Semantics

C# types/nullability, generated framework members, component parameters, fragments, route/command/property handles, and diagnostic locations.

HTML

HTML5 parser verification, void/custom elements, boolean attributes, accessibility relationships, stable IDs, full pages, and fragment roots.

Security

OWASP-style XSS payload corpus in every context, URL schemes, trusted markup, form limits, session capabilities, stale revisions, CSP, and error sanitization.

HTMX

Targets/swaps, OOB updates, validation, progress/cancel, triggers, focus/scroll, nested sessions, push refresh, errors, reconnect, and teardown.

AOT/performance

Zero trim/AOT warnings, packaged consumer publish/run, cold start, full/fragment render throughput, allocations, output size, concurrency, and memory ceilings.

AOT rules

  • Release code contains no RequiresUnreferencedCode, RequiresDynamicCode, runtime code generation, assembly scanning, dynamic dependency file or reflection-based serializer path owned by this project.
  • All JSON uses generated JsonSerializerContext; DI registrations and endpoint tables are closed generated calls. Optional integrations that cannot meet this rule live in separately named, non-AOT packages.
  • CI treats IL2026, IL205x, IL206x and IL3050 warnings from owned assemblies as errors. Suppressions require a linked issue, narrow member scope and a publish-and-run regression test.

Performance budgets

  • Against an equivalent hand-written Utf8HtmlWriter renderer on a pinned CI runner, generated full and fragment rendering must reach at least 85% of baseline throughput and no worse than 1.25× baseline p95 latency.
  • After View/context creation and with a preallocated output buffer, static and scalar model renders allocate 0 managed bytes. A component may allocate only when its documented public behavior requires it; allocation snapshots are approved.
  • The 100-template/10,000-node reference project adds at most 3 seconds to a clean build, 250 ms to a no-change build, and 750 ms when one leaf template changes on the pinned runner. CI also fails on a regression over 15% from the checked-in benchmark baseline.
  • HTMX framework overhead, excluding user command time, network and browser swap, stays below 1 ms median per warm local request; limits and concurrency tests show bounded memory with 1,000 live View sessions.
1.0 acceptance: from the published packages and this repository's public documentation alone, a new consumer can create a typed ViewModel and paired .cwhtml/.cwhtml.cs View; obtain exact editor/build diagnostics in the template; render valid contextually escaped HTML; bind culture-aware forms and commands through protected generated HTMX routes; update primary and OOB fragments; survive validation, cancellation, stale revision and session expiry; run without consumer-authored JavaScript; and publish/run the application as Native AOT with zero owned trim/AOT warnings. Clean and incremental build, security, package, browser, deterministic-output and performance gates must all pass.
