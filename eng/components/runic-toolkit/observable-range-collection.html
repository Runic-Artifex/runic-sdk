Dedicated collection utility plan · draft 1

Range mutations with boring, exact semantics.

Build a small, dependency-free observable collection for .NET applications that need efficient range changes and deterministic synchronization with MVVM Views. It extends the standard collection notification model; it does not pretend to be thread-safe, a reactive query engine, or a frontend transport.

PackagingUtilities first

Ship inside a focused collections project; publish a standalone package only after independent adoption proves the extra package is useful.

ContractBCL notifications

ObservableCollection<T>, INotifyCollectionChanged, and INotifyPropertyChanged remain the compatibility surface.

No locks, dispatcher capture, or implicit marshalling. The caller owns thread/dispatcher affinity.

DiffsDeterministic, bounded

01 · Product decision

A utility, not a framework

The implementation is valuable because the BCL collection exposes only single-item mutation helpers. Its public boundary must remain useful to ordinary desktop, web-hosted, console, test, and server code without depending on a specific MVVM framework.

01

Own

Range insertion, removal, replacement and movement; deterministic reconciliation; standard notifications; immutable event payloads; snapshots; reentrancy protection.

02

Do not own

Dispatching, synchronization contexts, serialization, web protocols, selection state, paging, virtualization, reactive queries, persistence, validation or item property tracking.

03

Promotion gate

Begin in CsWebUi.Collections under a utilities project. Promote to a standalone CsWebUi.Collections.Observable package only when at least two unrelated consumers use it without depending on the MVVM runtime.

Stable-name rule: use the independent CsWebUi.Collections namespace from the start. Moving the assembly later then does not force source changes or couple the collection to a particular frontend.
02 · Public API

One sealed type, a few explicit options

The first release deliberately favors index-based operations. Item-based removal is ambiguous in the presence of duplicates and therefore remains outside v1 until a real use case establishes strict matching semantics.

namespace CsWebUi.Collections;

public sealed class ObservableRangeCollection<T> : ObservableCollection<T>
{
    public ObservableRangeCollection();
    public ObservableRangeCollection(IEnumerable<T> items);
    public ObservableRangeCollection(ObservableRangeCollectionOptions options);
    public ObservableRangeCollection(
        IEnumerable<T> items,
        ObservableRangeCollectionOptions options);

    public void AddRange(IEnumerable<T> items);
    public void InsertRange(int index, IEnumerable<T> items);
    public void RemoveRange(int index, int count);
    public void ReplaceRange(int index, int count, IEnumerable<T> replacement);
    public void MoveRange(int oldIndex, int count, int newIndex);

    public CollectionUpdateResult UpdateTo(
        IEnumerable<T> target,
        IEqualityComparer<T>? comparer = null,
        Func<T, T, T>? resolveMatch = null,
        CollectionUpdateOptions? options = null);

    public CollectionUpdateResult UpdateTo<TKey>(
        IEnumerable<T> target,
        Func<T, TKey> keySelector,
        IEqualityComparer<TKey>? keyComparer = null,
        Func<T, T, T>? resolveMatch = null,
        CollectionUpdateOptions? options = null)
        where TKey : notnull;

    public T[] ToSnapshot();
}

public sealed record ObservableRangeCollectionOptions
{
    public RangeNotificationMode RangeNotifications { get; init; }
        = RangeNotificationMode.Range;
}

public enum RangeNotificationMode { Range, Reset }
public enum UpdateNotificationMode { Auto, Granular, Reset }

public sealed record CollectionUpdateOptions
{
    public UpdateNotificationMode Notifications { get; init; }
        = UpdateNotificationMode.Auto;
    public int MaxGranularEvents { get; init; } = 64;
    public int ResetRatioMinimumCount { get; init; } = 64;
    public double ResetChangeRatio { get; init; } = 0.35;
}

public readonly record struct CollectionUpdateResult(
    int Added, int Removed, int Moved, int Replaced,
    int NotificationCount, bool UsedReset)
{
    public bool Changed => Added != 0 || Removed != 0 ||
                           Moved != 0 || Replaced != 0;
}

Argument rules

  • All source sequences are non-null and enumerated exactly once into a private buffer before structural mutation.
  • Enumeration, comparer, key-selector, or match-resolver failure leaves the collection structure unchanged.
  • index is in [0, Count] for insertion; existing ranges require index >= 0, count >= 0, and index + count <= Count without integer overflow.
  • Self-sources such as AddRange(collection) are safe because input is materialized first.
  • Empty ranges and already-satisfied updates are no-ops: no property or collection notifications.

Operation rules

  • AddRange is InsertRange(Count, items).
  • ReplaceRange(index, 0, items) inserts; an empty replacement removes.
  • MoveRange's newIndex is the block's start index in the final collection after removal; it must be in [0, Count - count].
  • A move whose old and final start indices are equal is a no-op.
  • ToSnapshot returns a new shallow T[]; later collection changes cannot alter its membership or order.
API approval gate: before release, compile the declaration above into an approval file. Adding convenience overloads is easy later; removing ambiguous overloads is not.
03 · Notification contract

Observers see the post-mutation collection

Every event follows the BCL's observable collection conventions. Range payloads are private read-only copies, never the caller's mutable list. Handlers may enumerate or snapshot the collection but may not structurally modify it during notification.

MutationPropertyChanged orderCollectionChanged in Range mode
Add / Insert rangeCount, then Item[]One Add, immutable new-items list, insertion index
Remove rangeCount, then Item[]One Remove, immutable old-items list, original start index
Replace, equal countsItem[]One Replace, immutable new/old lists, common index
Replace, unequal countsCount only when changed, then Item[]One Reset; a single standard Replace is not used for unequal cardinality
Move rangeItem[]One Move, immutable moved-items list, final new index and original old index
ClearCount, then Item[], unless already emptyOne Reset
UpdateTo granularNormal property sequence for every coherent stepDeterministic single-item Add, Remove, Move, or Replace events
UpdateTo resetCount only when changed, then Item[]Final content is installed, then one Reset

Reset mode

When collection options select RangeNotificationMode.Reset, every multi-item range operation emits the appropriate property changes followed by one Reset. Existing single-item APIs retain ordinary BCL events.

Event exceptions

Subscriber exceptions propagate. The mutation that preceded the failing event remains applied; there is no rollback. For granular UpdateTo, the collection remains coherent but may be only partially reconciled.

Compatibility tests

Test event action, item identity, copied payload, indices, property ordering, handler-visible collection state, and no-op silence against hand-written expected traces.

Do not fake atomicity: standard observable events are synchronous. Range methods complete one structural mutation before one event. Granular reconciliation intentionally exposes a sequence of valid intermediate states; consumers requiring one refresh must select Reset.
04 · Reconciliation

UpdateTo preserves identity by default

Reconciliation turns the current sequence into a target sequence while retaining matched object instances where possible. This matters for ViewModels with subscriptions, focus, validation state, or expensive initialization.

01

Materialize

Enumerate the target once. Snapshot current entries. Validate options and keyed uniqueness. No structural mutation has happened.

02

Match

The comparer overload pairs each target occurrence with the first unmatched equal current occurrence in original order. This FIFO rule makes duplicates deterministic.

03

Resolve

For each match in target order, call resolveMatch(existing, incoming). The default returns existing. The returned instance becomes the desired item.

04

Plan

Generate a deterministic left-to-right edit script: retain, move an already-matched item forward, insert an unmatched target, replace a matched item resolved to another instance, then remove unmatched tail items.

05

Select notifications

Granular always applies the script. Reset always installs the desired list once. Auto uses the documented event-count and change-ratio thresholds.

06

Apply

Apply the chosen plan under the mutation guard. Return operation and notification counts. A successful result guarantees sequence equality under the chosen match contract.

ConcernRequired decision
Default identityEqualityComparer<T>.Default; equal occurrences match FIFO and retain the existing instance.
Keyed identityKeys must be unique in both current and target snapshots. Null or duplicate keys throw ArgumentException before mutation, with the side and key position identified in the message.
Match resolverCalled exactly once per match before structural mutation. It may return existing, incoming, or another item. It must not structurally mutate this collection; that attempt throws InvalidOperationException.
Auto resetReset when planned event count exceeds MaxGranularEvents, or when the larger sequence has at least ResetRatioMinimumCount items and eventCount / max(oldCount, newCount) exceeds ResetChangeRatio.
ComplexityKeyed matching must be O(n) expected matching plus edit planning no worse than O(n log n). Arbitrary comparer/FIFO duplicate matching may be O(n²); document keyed use for large collections.
MinimalityThe edit script must be deterministic and reasonably compact, not mathematically minimal. Correct identity, order, and bounded notification volume take priority over minimum edit distance.
Resolver example: returning existing preserves a live ViewModel; returning incoming replaces immutable records. A consumer that copies fields into the existing item may do so in the resolver, but those item-level changes are the consumer's responsibility and cannot be rolled back.
05 · Ownership and safety

Single-threaded by contract, guarded against reentrancy

Observable collections are normally bound to one UI or application context. Hiding cross-thread access behind locks would not make synchronous event handlers, item mutation, or UI adapters safe.

Threading policy

  • The type is not thread-safe and captures no SynchronizationContext.
  • All reads, enumeration, mutations, and subscriptions must be coordinated by the owner.
  • Concurrent read/write and write/write access is unsupported even if it appears to work.
  • A frontend or MVVM bridge must marshal inbound work through its own dispatcher before calling collection APIs.
  • No Invoke, Post, async mutation, lock, or dispatcher overload belongs in this package.

Reentrancy policy

  • Seal the type and route inherited InsertItem, RemoveItem, SetItem, MoveItem, and ClearItems through one guard.
  • Reject every structural mutation attempted from PropertyChanged, CollectionChanged, input enumeration, key selection, comparison, or match resolution.
  • Throw InvalidOperationException consistently, independent of subscriber count.
  • Reading, enumerating, snapshotting, and changing properties on contained items remain allowed during notification.

Enumeration

Live enumeration follows normal List<T> fail-fast behavior when structurally modified. It is not a snapshot and provides no concurrent-read guarantee.

Snapshots

ToSnapshot is shallow: collection membership and ordering are copied, contained reference objects are not cloned. It is safe from later structural changes, not from item mutation.

Items

The collection does not subscribe to INotifyPropertyChanged on items. Generated bindings continue to observe item ViewModels through their normal mechanisms.

Exception-safety boundary: argument validation, enumeration, matching, and planning complete before structural mutation. Once synchronous notifications begin, external handler failures cannot be made transactional without changing standard observable semantics.
06 · MVVM bridge

Translate notifications; do not couple the collection

The collection remains transport-neutral. A generated MVVM bridge can recognize standard actions and serialize typed item payloads using its existing generated metadata.

Collection actionBridge behaviorRecovery
Add / Remove / ReplaceSend one typed range patch with index and item payloads; preserve list order and one binding-session revision.If the client rejects the revision, send a full generated snapshot.
MoveSend old index, new final index, and count. The client performs one block move without recreating retained item bindings.Fall back to snapshot when the target adapter cannot represent block move.
ResetRead ToSnapshot after the event and send a replace-all patch. Diff reconstruction from old state is unnecessary.Snapshot is already authoritative.
Granular UpdateToForward ordered events or coalesce them in the bridge's scheduler. Coalescing is a transport policy and must preserve the final revision.On disconnect/reconnect, discard queued deltas and send the current snapshot.

Generated metadata

Source generation supplies item serializers and binding descriptors. The collection performs no reflection, runtime type scanning, or JSON work.

Adapter conformance

Angular, React, Vue, Svelte, and HTMX adapters receive the same action/index/item trace and must converge to the same DOM-visible ordering.

Virtualization

Virtualized Views may interpret changes against their window, but the source collection always describes the complete logical list. Paging is a separate abstraction.

No custom wire event in v1: avoid a second parallel change-event protocol until bridge benchmarks prove standard notifications insufficient. Reset plus snapshot is the universal escape hatch.

08 · Verification

Examples are not enough for sequence algorithms

Combine conventional unit tests with generated operation sequences, model comparison, notification trace validation, package consumption, Native AOT execution, and allocation benchmarks.

Property-test oracle

Use a plain List<T> as the structural oracle and a separate shadow observer that knows only emitted event arguments. After every successful public call, collection, oracle, shadow, and snapshot must contain equivalent sequences.

Benchmark matrix

Measure 10, 100, 1,000, and 10,000 items; append/remove/replace/move; 1%, 10%, and 50% reconciliation churn; keyed and duplicate comparer paths; Range, Granular, and Reset. Record time, allocations, event count, and retained identities.

Performance gate: do not promise a universal speedup over repeated Add. Report the workload and observer cost. The goal is fewer coherent notifications and bounded synchronization work, not a benchmark headline.
09 · Alternatives and non-goals

Keep attractive complexity outside v1

Several adjacent features sound convenient but weaken the collection's contract or belong at another layer.

AlternativeDecisionReason
Repeated ordinary Add/RemoveSupported baseline, not the range implementationCorrect but produces excessive notifications and bridge traffic for bulk changes.
Always ResetAvailable option, not defaultMaximally compatible but loses identity-preserving move/replace information and may recreate frontend state.
Custom change-set-only eventDeferWould reduce BCL interoperability and create a second observer ecosystem before evidence requires it.
Item-based RemoveRangeDeferDuplicate matching, missing-item behavior, comparer selection, and event grouping require a separate explicit contract.
Async/thread-safe collectionRejectLocks cannot safely marshal synchronous UI observers; dispatch belongs to the owning application or frontend adapter.
Automatic item-property forwardingRejectChanges event meaning, adds subscription lifetime, and duplicates MVVM binding behavior.
Minimal edit distanceReject as a requirementCPU and allocation cost can exceed the value; deterministic bounded edits and Reset fallback are sufficient.
Virtualized/paged collectionSeparate libraryLoading, eviction, total count, cancellation, and errors are a different abstraction.

11 · Acceptance

Definition of done

The candidate is complete only when its behavior can be implemented and verified from this public specification without access to another repository, product, or historical implementation.

Semantics

Every method, index, duplicate, no-op, notification, exception, resolver, reset threshold, reentrancy, and threading rule above is implemented and documented.

Correctness

Unit and property suites prove model equality, event replay, identity retention, copied payloads, coherent failure states, and deterministic results.

Compatibility

Ordinary INotifyCollectionChanged observers work without referencing custom events; adapters handle Range and Reset; a migration example starts from ObservableCollection<T>.

AOT

The production assembly contains no reflection discovery, expression compilation, dynamic code, runtime serializer lookup, dispatcher, or frontend dependency and passes packed Native AOT execution.

Performance

Benchmarks publish allocations, event counts, and time across the defined matrix; Auto thresholds are justified by measured bridge behavior and then treated as versioned defaults.

Release

Public API approval, XML docs, notification contract, examples, package metadata, license, changelog, and compatibility policy are present; promotion to a separate package is evidence-based.
