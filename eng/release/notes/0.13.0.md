# Runic SDK 0.13.0

Install matching `0.13.0` packages from NuGet and npm;
`Runic.Application.Views.CsWebUi` is `0.13.0-preview.1`.
Command Line versions remain independent of this SDK.

0.13.0 is the last minor release before the release candidates (D051.1). It
replaces Views protocol 3 with **Views protocol 4**, the protocol that 1.0
keeps: after 0.13.0 the protocol takes only fixes. It also turns on spell
checking in Linux windows with the application's languages on every platform,
and restores GTK 4 window positions on X11. After 0.13.0 come the release
candidates `1.0.0-rc.N`, which take only fixes, stabilization and
documentation, and then 1.0.0.

Highlights:

- **Views protocol 4:** one request endpoint and one push channel per
  connection with a `hello` handshake, frames that carry member changes, replies
  that name a revision instead of repeating the state, numbered edits so that
  typing never loses keys, operation progress, the RFC 8785 canonical form, and a
  language-neutral specification with a conformance corpus. At 10,000 rows a
  setter or command now sends about half a kilobyte instead of two copies of the
  2 MB state.
- **Text inputs:** a pending setter value shows at once; the text field bindings
  `injectTextField` (Angular) and `useTextField` (React, Vue, Svelte) coalesce
  writes and keep the draft after an error; the mock Bridge can be slow and
  reorder requests, and the Vite development client warns about a field that
  loses keys.
- **Runic Desktop:** spell checking on Linux, spelling languages for the
  application, and an off switch per window; GTK 4 windows keep a restored
  position under X11 window managers.

## Upgrading

Update every Runic NuGet and npm package to 0.13.0 together, rebuild so that the
generated clients, bridges and mocks are regenerated, and reload open pages: a
page and a host of different Views protocol versions do not connect. Code that
uses generated clients compiles unchanged. Check these if they apply to you; the
[migration guide](https://github.com/Runic-Artifex/runic-sdk/blob/v0.13.0/docs/migration-1.0.md#from-012-to-013)
has before and after tables:

- `TimeSpan` values travel as ISO 8601 durations (`"PT1H30M"`), not
  `"01:30:00"`; code that parses or stores the text changes
  ([#686](https://github.com/Runic-Artifex/runic-sdk/pull/686)).
- A custom `IBridgeTransport` (custom window host) implements `Serve` and
  `BroadcastAsync` instead of `Bind`, `BindAsync` and `Publish`
  ([#681](https://github.com/Runic-Artifex/runic-sdk/pull/681)).
- A custom `__runicBridge` or test double implements `request`, `onMessage` and
  `onConnectionChange` instead of `call`
  ([#680](https://github.com/Runic-Artifex/runic-sdk/pull/680)).
- Tests that use the untyped mock name members (`commands: { increment }`,
  `set: { name }`) instead of route suffixes (`routes: { Increment }`); tests
  that call `InMemoryBridgeTransport.Call` use the `RunicViewDriver` methods or
  `Request(json)` ([#680](https://github.com/Runic-Artifex/runic-sdk/pull/680),
  [#684](https://github.com/Runic-Artifex/runic-sdk/pull/684)).
- Copies of `runic-desktop-views.js` or `runic-cswebui.js` kept outside the web
  content are replaced by the 0.13 copies
  ([#681](https://github.com/Runic-Artifex/runic-sdk/pull/681)).
- Linux windows check spelling by default; set
  `DesktopWindowOptions.SpellChecking = false` to keep the 0.12 behaviour
  ([#675](https://github.com/Runic-Artifex/runic-sdk/pull/675)).

### Compatibility

- **Views protocol 4** is a strict version, like protocol 3. A cached 0.12 page
  connected to a 0.13 host reports a `protocol` diagnostic and its calls fail; a
  0.13 page connected to a 0.12 host does the same. Every contract fingerprint
  changes (prefix `runic-bridge-contract-v5`), so an operation started under
  0.12 and recovered after the upgrade is `unknown`.
- **Tmds.DBus.Protocol 0.95.2** ([#677](https://github.com/Runic-Artifex/runic-sdk/pull/677);
  see [Fixes](#fixes)). No public API exposes it.

## Breaking changes

0.13.0 breaks where Views protocol 4 needed it (D051.3). Generated code changes
shape and is regenerated by the build; the tables give what hand-written code
changes. Package validation runs against 0.12.1 with the suppressions recorded
in each package's `CompatibilitySuppressions.xml`.

### Views protocol 4

Protocol 4 replaces the route surface of the WebUI era with one message protocol
between a producer (the generated .NET bridges and `WindowContentSession`) and a
client (`@runic-artifex/views` and the generated TypeScript clients)
([#679](https://github.com/Runic-Artifex/runic-sdk/pull/679),
[#681](https://github.com/Runic-Artifex/runic-sdk/pull/681),
[#684](https://github.com/Runic-Artifex/runic-sdk/pull/684),
[#687](https://github.com/Runic-Artifex/runic-sdk/pull/687),
[#686](https://github.com/Runic-Artifex/runic-sdk/pull/686),
[#680](https://github.com/Runic-Artifex/runic-sdk/pull/680),
[#685](https://github.com/Runic-Artifex/runic-sdk/pull/685); issues
[#664](https://github.com/Runic-Artifex/runic-sdk/issues/664),
[#665](https://github.com/Runic-Artifex/runic-sdk/issues/665),
[#666](https://github.com/Runic-Artifex/runic-sdk/issues/666),
[#668](https://github.com/Runic-Artifex/runic-sdk/issues/668),
[#669](https://github.com/Runic-Artifex/runic-sdk/issues/669),
[#670](https://github.com/Runic-Artifex/runic-sdk/issues/670),
[#671](https://github.com/Runic-Artifex/runic-sdk/issues/671),
[#672](https://github.com/Runic-Artifex/runic-sdk/issues/672) and
[#673](https://github.com/Runic-Artifex/runic-sdk/issues/673)):

- **One request endpoint and one push channel per connection.** A request is
  one JSON object `{kind, route, member, …}` and its reply one JSON object.
  Pushes (`state`, `frame`, `failure`, `operation`, `interaction`,
  `interaction-cancelled`, `menu-bar`) reach the one listener the runtime
  registers with `__runicBridge.onMessage`. Host route names, positional and
  type-dependent arguments, JSON inside string arguments, the
  `__{route}Changed` globals and the long-poll routes are gone. Runic Desktop
  carries the protocol on one capability, `__runicViews`, and its raw push;
  CS-WebUI on one binding and `SendRaw`, with a bounded `receive` request for
  pushes to one connection, because WebUI cannot address one client.
- **`hello`** opens each connection with both protocol versions and the
  producer's `implementation {name, version}`. Both sides refuse another
  protocol (`protocol-mismatch`); the `version` diagnostic compares only
  `Runic.Application.Views` with `@runic-artifex/views`
  ([#666](https://github.com/Runic-Artifex/runic-sdk/issues/666)).
- **Frames carry member changes.** The producer compares each member's encoding
  with the one it last published and sends a `set` for each member that
  differs, beside the keyed-collection and text changes, so derived members,
  `can…`, validation and getters that never notify are correct without a full
  state. A full state is sent only in `open` and `snapshot` replies and after an
  overflow ([#670](https://github.com/Runic-Artifex/runic-sdk/issues/670)).
- **Replies name a revision.** A request that changes state replies with the
  `revision` of the first published state that includes its effects, and the
  client resolves the call once its route reached that revision; a change
  without a notification is published as a frame before the reply. After 5 s
  the client reads a snapshot and reports `revision-timeout`
  ([#671](https://github.com/Runic-Artifex/runic-sdk/issues/671)).
- **Edits.** A `set` carries `edit`, numbered per route and member; the producer
  skips an edit older than one it applied and answers `superseded`. Until the
  route reached the reply revision of a member's latest edit, the client shows
  that edit's value (D051.12, [#673](https://github.com/Runic-Artifex/runic-sdk/issues/673)).
- **`open`/`close`** replace `Snapshot` and `Mount`/`Unmount`: one request reads
  the state and registers the presentation and its interaction handlers.
- **Operations** are identified by `(contract, route, operation id)` with
  `contract = {view}:{fingerprint}`; inputs are compared in canonical form;
  `watch` pushes status changes, `progress` and the terminal status with its
  `revision`, and `wait()` is client-only. A start is admitted in order with the
  window's other requests that change state
  ([#672](https://github.com/Runic-Artifex/runic-sdk/issues/672)).
- **Values** are named by what they carry (`uuid`, `local-date`,
  `offset-date-time`, `duration`, …) with one normal form each; integers are
  read by value (`1.0`, `1e2`); `TimeSpan` is an ISO 8601 duration (D051.11);
  enum values keep their C# member names or `[RunicAlias]`, as documented
  (D051.4, [#668](https://github.com/Runic-Artifex/runic-sdk/issues/668)). A
  failure's `detail` is `{type?, message, stack?}`
  ([#669](https://github.com/Runic-Artifex/runic-sdk/issues/669)).
- **Menu bar page protocol 2:** the in-page menu bar uses requests to the
  reserved route `runic.menu-bar` and `menu-bar` pushes instead of the four
  `__runicMenuBar*` routes and `__runicMenuBarWait`.

Protocol 4 sends much less per change. Measured with a notes ViewModel of rows
of about 195 bytes, a filter setter, an `addNote` command and three derived
members (`RunicWindowTestHost`, in-memory transport, Release, .NET 10 on Linux,
median of 20 runs; bytes are what reaches the page)
([#684](https://github.com/Runic-Artifex/runic-sdk/pull/684)):

| At 10,000 rows | Protocol 3: bytes | Protocol 3: producer | Protocol 4: bytes | Protocol 4: producer |
| --- | --- | --- | --- | --- |
| Initial state | 1.97 MB | — | 1.97 MB (`open` reply) | — |
| Add one row and raise three derived members | 4–6 MB | 15.4 ms | 499 B, one frame | 0.82 ms |
| The same inside `BridgeSnapshotBatch` | 1.98 MB | 8.9 ms | 499 B | 0.67 ms |
| Setter `filter` (push and reply) | 1.98 MB + 1.98 MB | 14.2 ms | 138 B + 26 B | 0.53 ms |
| Command `addNote` (push and reply) | 1.99 MB + 1.99 MB | 12.4 ms | 501 B + 26 B | 0.77 ms |

The client parses only those messages and decodes only the changed members, and
rows a frame does not touch keep their identity. Protocol 4 is not cheaper for
the first state, a collection reset (a `set` of the whole field), or large data
outside keyed collections, which is still serialized to compare but sent only
when it differs.

## Added

### Views

- **Operation progress.** `RunicOperationProgress.Report(double fraction)`
  reports the progress of the operation whose flow calls it, clamped to 0 to 1
  (NaN is ignored). Watching clients receive it at most every 100 ms;
  `BridgeOperationStatus` `running` has `progress`, `BridgeOperation` has
  `subscribe(listener)`, `OperationState` and `LatestOperationState` have
  `progress`, and the Angular, React, Vue and Svelte operation handles expose it
  ([#687](https://github.com/Runic-Artifex/runic-sdk/pull/687),
  [#680](https://github.com/Runic-Artifex/runic-sdk/pull/680),
  [#685](https://github.com/Runic-Artifex/runic-sdk/pull/685);
  [#672](https://github.com/Runic-Artifex/runic-sdk/issues/672)).
- **Text field bindings.** `createTextFieldController({ read, write, coalesce?,
  keepDraftOnError? })` in `@runic-artifex/views` holds the user's draft while
  writes are in flight, keeps at most one write in flight, writes nothing during
  IME composition, keeps the draft and sets `error` after a failure, and shows
  the View's normalized value once the last write settled. `injectTextField`
  (`@runic-artifex/angular`) and `useTextField` (`@runic-artifex/react`, `vue`,
  `svelte`) wrap it with the component's lifecycle
  ([#680](https://github.com/Runic-Artifex/runic-sdk/pull/680),
  [#685](https://github.com/Runic-Artifex/runic-sdk/pull/685);
  [#673](https://github.com/Runic-Artifex/runic-sdk/issues/673)). See
  [Text inputs](https://github.com/Runic-Artifex/runic-sdk/blob/v0.13.0/packages/web/views/README.md#text-inputs).
- **A slow mock.** `createMockBridge({ latency, reorderRequests })`: `latency`
  delays every request, reply and push (milliseconds, `{ min, max }` or
  `"slow"`, 30 to 120 ms) while keeping their order, on real timers or the
  mock's virtual clock; `reorderRequests` admits requests out of order, so stale
  edits answer `superseded`. `MockOperation` and `MockTypedOperation` gain
  `progress` and `reportProgress(value)`
  ([#680](https://github.com/Runic-Artifex/runic-sdk/pull/680)).
- **`stale-input` warning.** During `vite dev`, the development client of
  `@runic-artifex/vite-plugin-runic` warns once per field when script sets a
  focused `<input>` or `<textarea>` to a value it had before the user's last
  edit while a Bridge request is in flight, and points to the text field
  bindings. It reports the Views diagnostic `stale-input` and never includes the
  field's value. `runic({ staleInputWarning: false })` turns it off
  ([#673](https://github.com/Runic-Artifex/runic-sdk/issues/673)).
- **Error reasons and diagnostics.** `BridgeErrorReason` adds `capacity`,
  `invalid-request`, `no-hello`, `protocol-mismatch` and `state-withheld` (the
  call ran, but no state with its effects can be published; don't retry it as
  if it had not run). `BridgeDiagnosticCode` adds `revision-timeout` and
  `stale-input`. Both stay open
  ([#680](https://github.com/Runic-Artifex/runic-sdk/pull/680)).
- **Log events** of `Runic.Application.Views`: 1018 `BridgeProtocolMismatch`
  (Warning, once per connection), 1019 `BridgeRequestBeforeHello` (Debug), 1022
  `BridgeRequestFailed` (Error) and 1023 `BridgeMailboxOverflowed` (Warning: a
  connection's pushes waiting for `receive` passed 1,024 messages or 4 MiB, and
  the oldest were dropped)
  ([#681](https://github.com/Runic-Artifex/runic-sdk/pull/681)).

### Runic Desktop windows

- **Spell checking on Linux and a switch on every platform.** The GTK 3 and
  GTK 4 windows now turn on WebKitGTK's spell checker, so `spellcheck` fields
  are checked as with WebView2 and WKWebView.
  `DesktopHostOptions.SpellCheckingLanguages` and
  `DesktopHost.SetSpellCheckingLanguagesAsync` choose the application's spelling
  languages (BCP 47; invalid tags make `StartAsync` throw `ArgumentException`).
  They are one setting for the application, because WebKitGTK and macOS check
  spelling per process and WebView2 cannot set languages (D051.14). They select
  enchant dictionaries on Linux (`de-CH` uses `de_CH` or `de`, never another
  region; without languages the user's `LANGUAGE`, `LC_ALL`, `LC_MESSAGES` and
  `LANG` apply) and `NSSpellChecker`'s language on macOS (one language, or
  automatic identification for several or none). Windows ignores them and
  `Validate` reports `window-option-unsupported`. A language without a
  dictionary is reported once per language set as the window diagnostic
  `spell-checking-dictionary-missing` (Warning, event 3010), and a failure to
  apply them to an open window as `spell-checking-languages-failed`.
  `DesktopWindowOptions.SpellChecking = false` keeps the native checker off in a
  window, for editors that draw their own marks; an element with its own
  `spellcheck="true"` is still checked. Custom window hosts get
  `DesktopWindowHostOptions.SpellChecking`/`SpellCheckingLanguages` and the
  optional `IDesktopSpellCheckingWindowHost`, which the GTK 4 host implements
  ([#675](https://github.com/Runic-Artifex/runic-sdk/pull/675),
  [#688](https://github.com/Runic-Artifex/runic-sdk/pull/688);
  [#662](https://github.com/Runic-Artifex/runic-sdk/issues/662)). See the
  Runic.Desktop README,
  [Spell checking](https://github.com/Runic-Artifex/runic-sdk/blob/v0.13.0/packages/dotnet/Runic.Desktop/README.md#spell-checking),
  which also covers editors such as ProseMirror that rewrite their text.

### Nix

- `buildRunicApplication { spellingDictionaries ? [ ] }` adds hunspell
  dictionaries such as `with pkgs.hunspellDicts; [ de_CH en_US ]` to the
  wrapper's `XDG_DATA_DIRS`. Only the `desktop` and `desktop-gtk4` hosts accept
  it ([#675](https://github.com/Runic-Artifex/runic-sdk/pull/675)).

## Behaviour changes

- **Views: pending setter values show at once.** `snapshot` and `subscribe`
  show a member's latest setter value until the route reached the state that
  includes it, so a field bound with `[value]="state.name" (input)="setName(…)"`
  no longer loses keys when replies arrive late. Code that treats `snapshot` as
  confirmed state, such as a "Saved" indicator, sees the value before .NET
  accepted it; the setter's promise is still the confirmation. A failed setter
  rejects and the member returns to .NET's value (D051.12,
  [#680](https://github.com/Runic-Artifex/runic-sdk/pull/680)).
- **Views: a route publishes nothing before its first state.** Frames need a
  baseline, so a route pushes only after a client read its state with `open` or
  `snapshot`. Content that the parent's state presents is therefore presented
  when a client first reads the parent, not at the parent's first change
  ([#684](https://github.com/Runic-Artifex/runic-sdk/pull/684)).
- **Views: notifications coalesce.** A notification requests a publication unit
  that runs in a later model turn, so a burst of notifications publishes one
  frame; `BridgeSnapshotBatch` publishes at its end
  ([#684](https://github.com/Runic-Artifex/runic-sdk/pull/684)).
- **Views: Runic Desktop admits calls in arrival order.** Each call's admission
  is queued on the WebSocket's receive path instead of racing after
  `Task.Yield`, so a burst of calls runs in the order the page sent them
  ([#681](https://github.com/Runic-Artifex/runic-sdk/pull/681)).
- **Views: operations outlive their route.** `status`, `watch`, `cancel` and
  `stream` of an operation the window still knows are answered after its route
  was released or suspended, so a page that left can still observe it
  ([#687](https://github.com/Runic-Artifex/runic-sdk/pull/687)).
- **Views: the canonical form is RFC 8785 (JCS)**
  ([#678](https://github.com/Runic-Artifex/runic-sdk/pull/678);
  [#664](https://github.com/Runic-Artifex/runic-sdk/issues/664)).
  Checked-field equality, operation duplicate detection, interaction reply
  retries and `BridgeWire.EncodeCanonical`, `Canonicalize` and
  `StructuralEquals` now read JSON numbers as IEEE 754 doubles, as the page
  does, and write them as ECMAScript does. `0.1` and `0.10000000000000000001`
  are one value, and integers above 2^53 in `JsonElement`/`JsonNode` members
  compare as the page compares them. Typed `long` and `decimal` members are
  unaffected because they travel as strings. A number beyond the double range
  (`1e400`) and a string that is not valid Unicode (a lone surrogate, invalid
  UTF-8) are rejected with `FormatException`. Canonical strings escape only
  `"`, `\` and control characters. Nothing persisted changes: the SDK keeps
  every digest in memory.
- **Views: messages escape strings minimally.** The .NET producer no longer
  escapes non-ASCII characters or `<>&'+` in states, replies and pushes, so a
  non-ASCII character takes 2 to 4 bytes instead of 6 or 12. The JSON values
  are unchanged ([#678](https://github.com/Runic-Artifex/runic-sdk/pull/678),
  [#689](https://github.com/Runic-Artifex/runic-sdk/pull/689)).
- **Linux windows check spelling by default.** Fields without
  `spellcheck="false"` get native marks in GTK 3 and GTK 4 windows, as in
  WebView2 and WKWebView; `DesktopWindowOptions.SpellChecking = false` restores
  the previous behaviour ([#675](https://github.com/Runic-Artifex/runic-sdk/pull/675)).
- **GTK 4 window position on X11.** A GTK 4 window that opens at a position,
  such as a restored `DesktopWindowPlacement` (`DesktopWindowOptions.Placement`,
  `RunicDesktopHostOptions.Placement`), carries it in its `WM_NORMAL_HINTS`
  (`USPosition`) when it is first shown, as GTK 3's `gtk_window_move` did, so
  the window manager keeps the position instead of placing the new window
  itself, and a maximized placement restores to its saved position and size.
  Before, the window manager placed the window first and Runic moved it once it
  was shown, and a window opened maximized restored to where the window manager
  had put it ([#676](https://github.com/Runic-Artifex/runic-sdk/pull/676);
  [#663](https://github.com/Runic-Artifex/runic-sdk/issues/663)).
- **GTK 4 reported position on X11.** `DesktopWindowState.X`/`Y` and the
  placement's position are the top-left corner of the window manager's frame as
  its `_NET_FRAME_EXTENTS` give it, also when the window manager does not
  reparent the window into a frame window, as KWin does for X11 windows on
  Wayland. Before, the position there was that of the content below the title
  bar, so each save and restore moved the window down and right by the frame
  ([#676](https://github.com/Runic-Artifex/runic-sdk/pull/676);
  [#663](https://github.com/Runic-Artifex/runic-sdk/issues/663)).
- On Wayland the position of a placement is still ignored: Wayland gives
  windows no global position, so GTK 3 and GTK 4 report `null` and the
  compositor places the window. The `DesktopWindowOptions.Placement`
  documentation now says so instead of stating that GTK 4 ignores the position
  everywhere.

## Specifications

- **Views protocol 4** is specified language-neutrally in
  [specs/application](https://github.com/Runic-Artifex/runic-sdk/tree/v0.13.0/specs/application):
  the protocol (`README.md`), frames and recovery (`state-changes.md`), wire
  value types and the canonical form (`values.md`) and how .NET and TypeScript
  map them (`language-mappings.md`). The
  [conformance corpus](https://github.com/Runic-Artifex/runic-sdk/tree/v0.13.0/specs/application/conformance)
  (`runic.views.vector/1` and `runic.views.scenario/1`) has canonical, value and
  message vectors and producer and client scenarios compared by JSON value, so
  another implementation can check itself; the .NET producer and the TypeScript
  client run every scenario
  ([#679](https://github.com/Runic-Artifex/runic-sdk/pull/679);
  [#665](https://github.com/Runic-Artifex/runic-sdk/issues/665)). Protocol 3's
  specification and the fixtures the corpus replaced are removed;
  `collection-deltas.md` stays while a .NET test still reads its fixtures.
- **Menu bar page protocol 2** in `specs/desktop/menu-bar-page.md`.
- Every Runic Desktop conformance scenario now creates each resource it uses
  and names the surface in every request and session operation, so another
  implementation can run the scenarios without inventing a host, a surface or a
  default surface. `specs/desktop/conformance/operations.json` defines the
  closed operation vocabulary, and `npm run verify:contract` rejects a scenario
  that uses an id its `arrange` block or an earlier step did not create
  ([#674](https://github.com/Runic-Artifex/runic-sdk/pull/674);
  [#667](https://github.com/Runic-Artifex/runic-sdk/issues/667)).

## Known issues

- With more than eight appends of a repeated line in one frame, the text change
  gives up and the frame sets the whole append-only text field, which for a
  long log can be large ([#684](https://github.com/Runic-Artifex/runic-sdk/pull/684)).
- A CS-WebUI window-wide push sent right after a reply can overtake that reply,
  and WebUI does not keep a client's call order; the protocol allows both, and
  edits carry their numbers ([#681](https://github.com/Runic-Artifex/runic-sdk/pull/681)).
- A dispatcher failure (a route handler that throws) answers `failed` without
  `detail` even when failure detail is on
  ([#684](https://github.com/Runic-Artifex/runic-sdk/pull/684)).
- The `stale-input` warning is a heuristic: an autocomplete library that writes
  an earlier value into a focused field can trigger it. It warns once per field
  and can be turned off.
- GTK 4 placement on X11 is tested with Openbox and KWin, not Mutter or xfwm4
  ([#676](https://github.com/Runic-Artifex/runic-sdk/pull/676)).
- WebView2 has no setting for spelling languages
  ([WebView2Feedback#584](https://github.com/MicrosoftEdge/WebView2Feedback/issues/584)).
- Orca does not speak live regions on WebKitGTK
  ([#318](https://github.com/Runic-Artifex/runic-sdk/issues/318)).
