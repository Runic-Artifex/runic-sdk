# Runic SDK 0.17.0

Install matching `0.17.0` packages from NuGet and npm;
`Runic.Application.Views.CsWebUi` is `0.17.0-preview.1`.
Tested with Runic Translations 0.9.1 and Runic Command Line 0.11.0.

0.17.0 makes a Runic application speak its user's language everywhere, not only
on its own pages. One application locale drives every window, the page, the
native menus, dialogs, packages and Runic's own messages, and Runic's own text
is available in English and German as an optional catalog. Runic Translations
0.9.1 plugs in from the template on (`dotnet new runic-app --translations`).
Windows and pages follow the desktop's contrast and forced colours as well as
light and dark. ViewModels that publish the same members share one generated
TypeScript client (#839). An experimental API lets one Runic Desktop
application show another one's windows as its own (hosted application windows,
`RUNICDESK103`). The release also fixes a local-process issue in the CS-WebUI
blob endpoint that 0.16.0 introduced.

Everything is additive: no public API was removed or changed. The new wire
members are Views protocol 4 features negotiated in `hello`
(see [Views protocol 4 features](#views-protocol-4-features)), so a 0.16 page and
a 0.17 host, or the reverse, connect and behave as in 0.16. Some existing
behaviour and output changes; [Upgrading from 0.16](#upgrading-from-016) lists
all of them, and the
[migration guide](https://github.com/Runic-Artifex/runic-sdk/blob/v0.17.0/docs/migration-1.0.md#from-016-to-017)
collects them.

## Upgrading from 0.16

Update every Runic NuGet and npm package to 0.17.0 together and rebuild, so that
the generated clients are regenerated. Applications that use Runic Translations
use 0.9.1 of every Translations package, not 0.9.0. CS-WebUI applications that
use blobs or uploads should update for the [security fix](#security-cs-webui-blob-endpoint).

There are no breaking changes. These are the behaviour and output changes:

**Pages and the Views protocol**

- `ViewOutlet` and `RegionOutlets` show the English "No web component is
  registered for …" alert only in development builds. Production builds render
  nothing and report the kind once through the page's error reporting. Pass
  `missing` to render your own text (#825).
- A window locale that the Translations runtime does not support now falls back
  to its parent (`de-CH` → `de`) before the page reports an error; a parent in
  another script (`zh-Hant-TW` → `zh`) is skipped (#826).
- Pages send the browser's preferred languages in `hello`
  (`client-languages/1`), and `RunicConnection.Languages` lists them. They are
  personal data: use them only to choose a language and don't log them. A page
  opts out with `configureClientLanguages({ send: false })` (#831).
- On Runic Desktop, windows that only this computer can reach receive the
  desktop's appearance (`appearance/1`) after `hello` and on each change (#836).
- Tests that compare the in-memory test transport's messages exactly: its
  `hello` now lists `client-languages/1` with `"languages":[]` and
  `appearance/1`, and the connection receives an `appearance` push (every member
  `null`) after its `hello` (#831, #836).
- Generated output: member metadata now names the property of members that have
  validation attributes (#832), and the page references of ViewModels that
  implement a `[RunicSharedClient]` interface extend the shared one (#844).
  Nothing else in the generated output changes.

**Native windows, menus and dialogs**

- On Windows and Linux, a Runic Views Desktop window opens with the native
  layout direction and web view language of its window locale
  (`IRunicWindowLocale`) and mirrors when the locale changes.
  `DesktopWindowOptions.LayoutDirection` and `Language` in
  `RunicDesktopHostOptions.WindowOptions` still win, and a configured
  `ProfilePath` keeps the platform's language (#827).
- Windows menu shortcut labels use the keyboard layout's modifier names, such as
  `Strg+S` on a German layout (#830).
- The GTK 3 file chooser shows GTK's own, translated button labels (#830).
- Runic Desktop's Resource Not Available and Access Denied pages take their text
  from `DesktopPlatformTexts` (English by default) and, in Runic Views windows,
  `lang` and `dir` from the window locale (#830).
- The Linux spell checker ignores `LANGUAGE` when the messages locale is `C`, as
  gettext does (#826).
- On macOS, `DesktopAppearance.ColorScheme` reports the desktop's scheme also
  while the application sets one for every window (#835).
- `IDesktopSettings.WatchAsync` on Windows and macOS waits for the desktop's
  change notifications instead of reading the settings once a second, and the
  Windows loading surface follows a contrast theme turned on or off while a
  window loads (#835).

**Packaging**

- Linux `.desktop` files no longer XML-escape the application name and
  description in `Name=` and `Comment=` (`Notes &amp; Co` → `Notes & Co`), also
  with a `linux/app.desktop` copied into `packaging/` (#833).
- Once an application sets `RunicApplicationLocales`, `dotnet runic package`
  fails with `RAPPPKG1006` for a manifest copied into `packaging/` before 0.17
  that lacks the new fields; the error names the file, the field to add and
  where. Without the property nothing changes (#833).

**Testing**

- Windows that `RunicWindowTestHost.CreateWindowAsync` opens use the
  application's `RunicValidationOptions` and the Window's `MaximumUploadBytes`,
  as on Runic Desktop and CS-WebUI. Before, they showed untranslated validation
  messages and the default upload limit (#846).

**CS-WebUI**

- The blob endpoint holds both loopback addresses of `localhost` on its port,
  serves loopback clients only, and on Linux and macOS answers only
  `Host: localhost:{port}` (or `127.0.0.1:{port}` when its URLs fall back to
  that address). Endpoint URLs never name another host. A client that reaches
  it over `127.0.0.1` while `localhost` resolves to `::1` first is now served
  instead of answered 404 (#848).
- On Windows the blob endpoint skips ports that an http.sys URL reservation
  names (#851).
- New log events 2103 `CsWebUiBlobEndpointPortsHeld` and 2104
  `CsWebUiBlobEndpointPortsReserved` (Warning) explain a window that starts
  without blobs because every port it tried was held or reserved (#848, #851).

## Security: CS-WebUI blob endpoint

**Fixes a local-process issue in 0.16.0** (#848, #851). It affects only
applications on the CS-WebUI host (`Runic.Application.Views.CsWebUi`
0.16.0-preview.1); Runic Desktop and WPF applications are not affected, and
nothing is reachable from another computer.

0.16.0 gave every CS-WebUI window a loopback endpoint of its own for blobs and
uploads, at a `http://localhost:{port}/` URL. On Linux and macOS it listened on
only one of the two loopback addresses that `localhost` names. Another process
on the same computer could listen on the other address under the same port and
receive blob and upload requests meant for the window.

In 0.17.0 the endpoint holds both loopback addresses on its port. After it
starts it confirms that its own listener answers on each, and it never uses a
port where another process holds or answers either one. It serves loopback
clients only. On Windows, where http.sys already refuses such ports, it now
also skips ports that an http.sys URL reservation names. Applications don't
need to change anything.

The page server that WebUI itself runs for a CS-WebUI window had a related
local-process issue. It is fixed in
[CS-WebUI 2.5.0-beta.4.9](https://github.com/Runic-Artifex/cs-webui/releases/tag/v2.5.0-beta.4.9)
([cs-webui#27](https://github.com/Runic-Artifex/cs-webui/pull/27),
[cs-webui#30](https://github.com/Runic-Artifex/cs-webui/pull/30)), which also
moves to .NET 10.0.14 and WebUI nightly `24c7d196e`.
`Runic.Application.Views.CsWebUi` 0.17.0-preview.1 depends on `CsWebUi` and
`CsWebUi.Native` `[2.5.0-beta.4.9, 3)`, so upgrading Runic brings the fix.
Applications that call `CsWebUi.Native`'s `Show`, `StartServer` or `GetUrl`
themselves stay exposed until WebUI listens on both loopback addresses; see the
`CsWebUi.Native` README.

## The application's language and Runic's own text

### One locale for the application (S1)

- **`IRunicApplicationLocale`** sets one language for every Window. Windows that
  set none follow it, also those opened later. `Follow(translations.SetLocaleAsync)`
  binds a Runic Translations context or manager, and `LocaleChanged` tells menu
  bar, status icon and notification code to rebuild. Without it, nothing changes.
- `IRunicWindowLocale.Locale` returns the application's locale while the Window
  sets none of its own; setting `null` follows the application again.
  `IRunicWindowLocale.OwnLocale` is the Window's own locale, `null` while it
  follows; save that one to restore a Window's language.
  `WindowContentSession.Locale = null` follows the application's locale too.
- Windows follow an application switch in a turn of their model context, and
  each `LocaleChanged` handler runs on the `SynchronizationContext` it
  subscribed on. Overlapping switches raise their events in order. A Window
  whose update fails does not stop the switch: `SetLocaleAsync` throws an
  `AggregateException` afterwards, and calling it again with the same locale
  retries those Windows.
- **`DesktopLanguages.Preferred`** (Runic.Platform) lists the user's preferred
  languages from the operating system.
- **Client languages** (`client-languages/1`): `RunicConnection.Languages` lists
  the preferred languages of the browser that connected, in BCP 47 case, each
  once, so an application can choose a window's language from its first
  connection after negotiating them against its shipped locales. A window keeps
  one language for all of its connections (S7).
- **Culture flow (opt-in).** Set `FlowCultureFromLocale` on `RunicWindowOptions`
  or on the Desktop, CS-WebUI or test host options. A window's commands,
  setters, validation, menu commands and close guard then run with
  `CurrentCulture`/`CurrentUICulture` of its locale, so C# formatting matches the
  page's language. Work started inside such an invocation keeps its culture;
  start long-lived work outside it or under `ExecutionContext.SuppressFlow()`
  (S6).

### The page follows the locale (S2)

- A reactive text locale for templates that call `m.*()`: `useTextLocale()`
  (React, Vue, Svelte), `textLocaleSignal()` (Angular), `textLocales()`
  (views-effect).
- `syncDocumentLocale()` keeps `<html lang dir>` on the window's locale;
  `textDirection()` and `TextTranslations.direction` give the direction. The
  starter templates call `syncDocumentLocale()`.

### Runic's own text (S4, S5, SR)

- **`DesktopPlatformTexts`** (Runic.Platform) holds the text Runic shows where
  the platform has none: Linux dialog titles, the untitled file name, the macOS
  "Choose an application" title, the Secret Service collection label, shortcut
  modifier names, Runic Desktop's error pages and, new, `LoadingTitle`, the
  title and accessible name of a Windows window while WebView2 starts. Set
  `DesktopPlatformTexts.Current` from the application's translations and again
  after a language switch.
- **Field errors apps can translate.** A text that does not parse
  (`invalid-text`) has a `reason`, such as `not-a-number`,
  `too-many-fraction-digits` or `not-a-date`, and `arguments` (`text`, `scale`,
  `choices`, `patterns`, `expected`). Call
  `configureFieldErrorText((error, locale) => …)` once, and `useText(name.error)`,
  `{{ name.error() | runicText }}`, `resolveText(error)` and
  `describeBridgeError` show your text in the window's language. Without the
  hook the English messages stay as they were.
- **Built-in validation messages in the window's language.** Register
  `RunicValidationOptions { TextFor = (attribute, member) => … }` to give
  `[Required]`, `[MaxLength]`, `[Range]` and other `ValidationAttribute`
  messages a Runic Translations text reference. The page shows them in the
  window's language, with the .NET message as fallback. This works for
  CommunityToolkit `ObservableValidator` and hand-written `INotifyDataErrorInfo`
  over `Validator`, on ViewModel, DTO and union-case members, whatever culture
  the message was formatted in.
- **New: `Runic.Application.Views.Translations` (NuGet) and
  `@runic-artifex/views-translations` (npm)**, optional English and German text
  for everything Runic says itself: the built-in validation messages, field
  errors of number, date and time fields, Linux dialog titles, the suggested
  "Untitled" name, shortcut key names, a browser window's error pages, the
  Windows loading title and the standard macOS menus. They are a Runic
  Translations library catalog, `runic-views`, built on Translations 0.9.1.
  - `services.AddRunicViewsTranslations()` adds the catalog to the
    application's Translations context, sets `RunicValidationOptions.TextFor`
    and keeps `DesktopPlatformTexts` in the application's locale, also with a
    scoped Translations context. On the page, `configureRunicViewsText()`
    translates field errors, and `runicViewsCatalog` joins
    `createReferenceResolver`. The standard macOS menus take
    `RunicViewsTranslations.MenuTitles(context)` through
    `DesktopHost.SetStandardMenuTitles`.
  - Change single messages or add a language in your `runic.json`:
    `"overrides": [{ "catalog": "runic-views", "from": ["Runic.Application.Views.Translations", "@runic-artifex/views-translations"] }]`.
    Because the catalog has English and German, `ITranslationContext.SupportedLocales`
    lists only those until the application adds its other languages with one
    override file each; the first window logs the missing ones (event 1261).
  - New log events 1260 `PlatformTextsRejected`, 1261
    `LocalesWithoutRunicViewsText` and 1262 `PlatformTextsContextFailed`.
  - The core packages still don't depend on Runic Translations; without these
    packages Runic's text stays English, as in 0.16.
- CS-WebUI windows still show WebUI's own English "Access Denied" and "Resource
  Not Available" pages; `DesktopPlatformTexts` applies to Runic Desktop browser
  windows only (#847).

### Native surfaces and packages (S3, S8)

- `DesktopWindow.SetLayoutDirectionAsync` and `LayoutDirection`,
  `DesktopWindowCapabilities.LayoutDirection` (WebView2, WebKitGTK 4.1, GTK 4)
  and `IDesktopLayoutDirectionWindowHost` for custom hosts. Runic Views Desktop
  windows use them for their window locale (see [Upgrading](#upgrading-from-016)).
- `DesktopHost.SetStandardMenuTitles` retitles the standard macOS menus after a
  language switch.
- **Packages declare their languages.** Set
  `<RunicApplicationLocales>en;de</RunicApplicationLocales>` (and optionally
  `<RunicApplicationLocale Include="de" Name="…" Description="…" />`).
  `dotnet runic package` then adds `CFBundleLocalizations` and `.lproj` folders
  to the macOS bundle, so AppKit's own text such as the About panel and the open
  and save panels follows the user's language. It adds `<Resource Language>`
  rows to the MSIX and translated `Name[xx]`/`Comment[xx]` and metainfo names to
  the Linux packages. The `dotnet run` development bundle on macOS declares
  them too. Manifests copied into `packaging/` before 0.17 need the new fields
  (`{{Localizations}}`, `{{Resources}}`, `{{LocalizedEntries}}`,
  `{{LocalizedNames}}`, `{{LocalizedSummaries}}`); `RAPPPKG1006` names them.

## Runic Translations 0.9.1 and the translated template (SX)

- runic-sdk's tests, fixtures and documentation use Runic Translations 0.9.1.
  The Views generator keeps calling `TranslationReference.Parse` and
  `TranslationReferenceJsonContext.Default.TranslationReference`, which 0.9.1
  keeps; the core packages don't depend on Runic Translations.
- **`dotnet new runic-app --translations`** (also `Runic.Create --translations`)
  starts a translated application: one catalog in English and German for the
  page and C# with all of the starter's text, ViewModels that produce text
  references, an application-wide language with a language switch, and page
  and .NET tests of the translated text. It works with every frontend and both
  ViewModel libraries.
- **`RUNIC_LOCALE`:** applications created with `--translations`, and the
  multi-window example, start in the catalog's language for the locale this
  environment variable names. For example,
  `RUNIC_APPLICATION_SERVE_ONLY=1 RUNIC_LOCALE=de` runs a browser test in German.
- **Test-host locale.** `RunicWindowTestHostOptions.Locale` starts a test window
  in its own locale; `RunicWindowTestHostOptions.ApplicationLocale` starts the
  application in a locale for the test and sets it back afterwards;
  `RunicWindowTestHost.ApplicationLocale` reads it. The Testing README shows how
  to assert the text a user sees with `TranslationContext.Resolve`.
  `InMemoryBridgeTransport.SetLanguages` sets a test connection's client
  languages.
- **`RunicApplicationFrontendTranslations`** (Runic.Application.Views build,
  opt-in) keeps `Frontend/.runic/translations` equal to the Runic Translations
  ESM that the .NET build writes, for pages that import it without the
  Translations Vite plugin. `RUNICBRIDGE037` (error) reports a missing ESM or a
  directory that holds other files.
- **The multi-window example** is translated into English, German and Arabic
  with one catalog for the page, the ViewModels and the native menu bar. CI runs
  it end to end.
- The "Translated text" section of the `Runic.Application.Views` README covers
  Translations 0.9: generated `References` factories, `TranslationContext` and
  `LocaleNegotiation`, `configureSharedLocaleResolver`, references of several
  catalogs with `createReferenceResolver`, right-to-left placeholder isolation,
  and the new guide "Translate a Runic Views app".

## Appearance beyond light and dark (S10)

- `DesktopAppearance.Contrast` reports the desktop's contrast preference in
  three states (no preference, more contrast, forced colours), and
  `DesktopAppearance.SystemColors` the palette of a Windows contrast theme.
  `HighContrast` is unchanged and derived from `Contrast`; `DesktopColorScheme`
  stays light/dark.
- New Views feature **`appearance/1`**: Runic Desktop pushes the desktop's
  appearance (colour scheme, contrast including forced colours and their
  palette, reduced motion, text scale, accent colour) to each window's pages and
  keeps it current, only to windows that nothing but this computer can reach.
  `WindowContentSession.Appearance` sets it directly.
- `@runic-artifex/views` adds a page appearance store (`appearance`,
  `onAppearance`) that combines the engine's media queries with the host's
  values, the latest change winning. React, Vue and Svelte add `useAppearance`,
  Angular `injectAppearance`, views-effect `appearances()`.
- Testing: the mock bridge adds `setAppearance`; `RunicWindowTestHost.AppearancePushes`
  reads the pushes in .NET tests.
- The Runic.Desktop README documents what `prefers-contrast`, `forced-colors`
  and `prefers-reduced-motion` report in each embedded engine.

## Shared clients for ViewModels with the same members (SC, #839)

- Mark an interface `[RunicSharedClient]`, and the ViewModels that implement it
  share one generated TypeScript client: `{Name}State`, `{Name}Client` and
  `{Name}PageReference`, whose `connect()` returns the shared client, plus
  `{name}Kinds`. One web component then renders all of them.
- The React, Vue, Svelte and Angular `ViewRegistry` types accept that component
  for every kind without a cast; `registryEntries(kinds, component)` from
  `@runic-artifex/views` registers it for all of them.
- New generator error `RUNICBRIDGE036`: a ViewModel does not publish a member
  of a `[RunicSharedClient]` interface alike (for example another
  `[JsonPropertyName]`, nullability or command input), or the interface cannot
  have a shared client.
- `RunicWindowTestHost`'s `View<T>` and `Views<T>` accept an interface or
  abstract class that the presented ViewModel implements, also from another
  library.

## Owner-less file dialogs for CS-WebUI

- `WindowsPlatformProvider.CreateUnownedFileDialogs()` and
  `MacOSPlatformProvider.CreateUnownedFileDialogs()`: the platform's file,
  directory and save dialogs without an owner window, for presentations without
  a native window. On Windows each dialog runs on a thread of its own, so
  dialogs of several windows close independently, and two dialogs shown at
  the same moment are initialized one at a time (#834, #845).
- Runic.Application.Views.CsWebUi: `services.AddRunicPlatformServices(unownedFileDialogs)`
  makes each window's `IFileDialogs` show a provider's unowned dialogs (Windows,
  macOS, or the portal's `CreateUnparentedFileDialogs()`) for
  `OwnerPolicy.PreferOwner`. Only a window that no other computer can reach gets
  them: not serve-only, not shown by `ShowWindow`, and its server on loopback
  only. On macOS, with unowned dialogs registered, `RunicCsWebUiHost.Run` serves
  the main thread's run loop while the application runs.
- macOS: an unowned file panel shown without an AppKit event loop runs
  modally, and cancellation closes it; cancelling an unowned alert ends it too.
  Unowned panels are ordered in front of other applications' windows.

## Hosted application windows (experimental, `RUNICDESK103`)

A Runic Desktop application, the *host*, can show another Runic Desktop
application's Windows, the *guest*'s, in native windows of its own, over the new
Runic host protocol `runic-host/1` (S11). A launcher or suite can show its tools
as part of itself while each tool stays its own application. The API and the
protocol are experimental through 1.0: code that uses them does not compile
until it suppresses `RUNICDESK103`, and they may change in a minor release,
also after 1.0.
Nothing changes for an application that does not opt in.

- **Guest.** A guest opts in on a code path of its own, reached by a parameter
  it defines: `RunicDesktopHost.Run(…, new RunicDesktopHostOptions { Guest = RunicGuestOptions.FromStandardInput() }, …)`.
  In hosted mode it listens on a loopback WebSocket of its own and
  authenticates the host with a key and a nonce exchanged over the process's
  pipes. It refuses to start elevated, with network exposure other than
  loopback, or, on Linux and macOS, when it does not run as its host's user. It
  never shows a window of its own, and it ends normally when the host goes
  away. Recent documents are unavailable; notifications, the status icon,
  global shortcuts, settings and the secret store stay the guest's own (#837,
  #838).
- **Host.** `IRunicHostedApplications` (`RunicDesktopHost.HostedApplications`,
  `AddRunicHostedApplications()`) starts a guest with
  `StartAsync(new RunicGuestStartInfo(path, ["hosted"]))` and shows its
  Windows (#843):
  - The guest's page loads from the guest's loopback origin without the host's
    credentials, in a data store that is not persisted: an InPrivate profile per
    guest session on WebView2, and on WKWebView and WebKitGTK a store that lives
    while one of the session's windows is open. Hosted windows need an embedded
    web view; there is no installed-browser fallback, and a Linux host selects
    `DesktopHostOptions.Linux.EmbeddedBackend`.
  - A guest gets only the permissions the host grants its own windows, unless
    the host's policy grants more. Closes go through the guest, and
    presentation is mirrored.
  - The guest runs in a Job object (Windows), joined before it runs, or in its
    own process group (Linux, macOS). When it exits or crashes, its windows
    close and `Exited` reports its exit code. `WindowOpened` and `WindowClosed`
    report its windows.
  - `IRunicHostedWindowPolicy` decides which windows open, which presentation
    requests apply, and each menu, dialog and service request, within
    `RunicHostedLimits`.
  - Custom window hosts show hosted windows by implementing
    `IDesktopEphemeralDataStoreWindowHost` and honouring
    `DesktopWindowHostOptions.EphemeralDataStore`.
- **Menus and dialogs** (#849, #854). A guest's menu bar shows in the host's
  native window for each of its Windows, with its items' states, shortcuts and
  localized titles; choosing an item runs the guest's command, in order. On
  macOS the guest's menus join the host's application menu bar while its window
  is key. Context menus, file dialogs and message boxes show as the host's
  native dialogs, owned by the guest's window, and the guest receives the same
  results as from its own. By default the host limits menu requests (20 per
  second per window, 80 per guest), rebuilds a native bar at most every 50 ms,
  shows context menus only in the guest's active window and inside it, and
  shows one dialog per guest at a time, at most 10 per ten seconds.
- **Appearance, locale and window services** (#852). A guest follows its host's
  appearance and application locale. With the `window-services/1` feature it
  uses the host's clipboard, monitors and file launcher and receives files
  dropped onto its windows. By default the host reads and writes the clipboard
  and opens files and links only for the window the user works in, not for one
  the guest brought to the front itself, and opens only web and mail links and
  files the user gave the guest through its open dialogs or a drop. **A guest's
  first window therefore starts as the guest's, not the user's**, until the
  user switches to it, uses its native menu bar or drops files onto it; a host
  that started the guest at the user's request can mark it as the user's
  (`RunicGuestStartInfo.UserStarted`). Requests that can activate a window and
  screen-reader announcements are rate-limited. Drags out of a hosted window,
  the taskbar badge and progress, and the clipboard's change watch are not
  available to a guest.
- **Testing.** `RunicTestHost` (Runic.Application.Testing) plays the host: it
  starts a guest, records its menu bar, chooses items, answers its dialogs and
  simulates the window services, so a guest is tested without a host
  application.
- **Docs and example.** "Hosted applications" in the
  `Runic.Application.Views.Desktop` README, the protocol specification
  `specs/desktop/host-protocol.md` with conformance scenarios in
  `specs/desktop/host-conformance`, the security guide's section on hosted
  application windows, and `examples/hosted-windows`, a shell that hosts a
  counter tool (#853).

## Views protocol 4 features

0.17 adds two features to protocol 4, negotiated in `hello` like those of 0.16;
hosts and pages of earlier releases ignore them.

| Feature | What it adds | Section |
| --- | --- | --- |
| `client-languages/1` | The browser's preferred languages in `hello` | [The application's language](#one-locale-for-the-application-s1) |
| `appearance/1` | The window's `appearance` push | [Appearance](#appearance-beyond-light-and-dark-s10) |

The hosted-window protocol `runic-host/1` is separate from the Views protocol;
its `window-services/1` feature is negotiated between host and guest.

## Known issues

- WebKitGTK 6.0 (GTK 4) reads the contrast and reduced-motion settings only when
  the first window opens; the page's appearance store still follows the host's
  live values (`appearance/1`) (#835).
- With `Runic.Application.Views.Translations`, a Window with a locale of its own
  still gets the application's dialog titles and shortcut labels, which are
  process-wide, and Windows and in-page menu bars keep the old key names after
  a language switch until the application sets the menu bar again; rebuild it
  in `LocaleChanged` (#841).
- Hosted windows on GTK 4: choosing an item in the host's native menu bar does
  not yet count as the user working in a window that the guest brought to the
  front, so the guest's clipboard and launcher requests from it are refused
  until the user switches to it (sdk#855).
- Left to manual checks, not CI: AppKit text in packaged macOS bundles,
  Windows shortcut labels on non-English keyboard layouts, appearance pushes
  under real portal, Windows and macOS sessions, choosing in shown unowned
  dialogs and their foreground behaviour, and hosted windows' native menus,
  dialogs and activation on real window managers
  (#830, #833, #834, #836, #849, #852).
