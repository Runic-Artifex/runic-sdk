# Runic SDK 0.7.0-preview.1

This preview contains breaking changes; see [Upgrading](#upgrading).

## Assets

- `AssetManifest.TryGetAsset` returns `false` for an invalid path instead of
  throwing. The new `AssetPath.TryNormalize` validates a path without throwing.
- The Desktop and ASP.NET Core adapters accept `IAssetSnapshotSource`, so a
  source that cannot deliver snapshots is a compile error instead of an
  `ArgumentException` at run time.
- Both adapters resolve request paths with the new
  `AssetManifest.TryResolveRequestPath` and `AssetRoutingOptions`, so one archive
  routes identically on both hosts. By default the root serves the entry point
  and missing paths without a file extension fall back to it.
- The [packer README](https://github.com/Runic-Artifex/runic-sdk/blob/main/tools/Runic.Assets.Packer/README.md)
  documents running the packer directly and `--trusted-generated-output`.
- Fix: with `--output json`, packer failures report their `RAS1001`–`RAS1004`
  code instead of `RCLI5000` ("The command failed unexpectedly."). Fault
  messages no longer contain paths or exception text; the source directory,
  entry point and underlying reason are in `fault.details`. Values that look
  like home, `/tmp` or `/root` paths, drive or UNC paths, or exception text are
  redacted there; other absolute paths, such as macOS `/var/folders/...` or
  `/srv/...`, are shown. Human output and exit codes are unchanged.

## Application hosts

- `Runic.Application.Desktop` and `Runic.Application.CsWebUi` depend on
  `Microsoft.Extensions.DependencyInjection.Abstractions` instead of the
  `Microsoft.Extensions.DependencyInjection` container.
- The CS-WebUI dependency is updated to `2.5.0-beta.4.6`. Large (over ~2 KB)
  Bridge replies no longer intermittently arrive with stray bytes after their
  JSON.
- Fix: concurrent CS-WebUI Bridge calls no longer occasionally lose their reply
  (#53). The page sends each call once .NET has received the previous one, or
  after at most 1.5 s. After a WebSocket reconnect, calls that were in flight
  when the connection dropped no longer delay the calls that follow.
- `Runic.Application.CsWebUi` adds `ValidateWindow<TViewModel>()`, which checks
  at startup that the generated Bridge is registered. `OpenWindow` runs the same
  check before it creates the native window, so a missing `AddRunicViews()`
  throws a `CsWebUiConfigurationException` with `bridge-not-registered`, the
  code Runic Desktop reports, instead of a dependency-injection error. It
  derives from `InvalidOperationException` and is logged as event 1050.

## Views

- A failed Bridge call names its route and keeps its cause: `BridgeError` has
  `route`, `cause` and, in development, `detail` with the .NET exception type,
  message and stack. Production replies keep the bounded message. Development
  means the host environment is `Development` or
  `BridgeDiagnostics.IncludeFailureDetail` is `true`.
- `waitForBridge({ timeout })` reports a missing `window.__runicBridge`, for
  example a frontend opened from a plain Vite server, as `unavailable` with
  remediation, and a Bridge that does not connect as `timeout`.
- `operation.wait({ timeout })` cancels the operation when the timeout passes
  and resolves to a `timedOut` status.
- `onBridgeDiagnostic(listener)` observes runtime failures. While serving,
  `@runic-artifex/vite-plugin-runic` forwards them to its DevTools dock, which
  shows the latest failure with its stack.
- Incremental collections recover more reliably. A failed snapshot read is
  retried up to four reads in total, with each retried failure reported to
  `onBridgeDiagnostic`. Frames that arrive during the read are applied after
  it instead of being dropped. A repeated full state with the same revision and
  content no longer notifies subscribers again.
- A `[RunicCollection]` with a null row or a null, empty or duplicate key,
  including a key changed in place on a row, is no longer published for the
  client to reject. The route withholds its state, logs
  `BridgeCollectionKeysRejected` (event 1012) naming the model, field and key,
  and the client reports a `failed` `BridgeError` for the route through
  `onBridgeDiagnostic` while keeping its last state. The first change after
  the keys are fixed publishes a full state. Collection changes never throw,
  so bindings such as DynamicData `Bind` keep running.
- A command can declare its expected failure with
  `[RunicFailure(typeof(SaveFailure))]` on the command property or on its
  CommunityToolkit `[RelayCommand]` method, and signal it by throwing
  `RunicFailureException(new TitleRequired())`. The Bridge replies
  `domain-failed` with the encoded failure instead of `rejected` or `failed`,
  in every environment and never with `detail`. An operation ends with the
  new `domain-failed` status: a stream keeps the values it published, and the
  failure counts against the window's retention budget like a result. A value
  that is not the declared type, cannot be encoded or is over 4 KiB is still
  reported as `failed`. The contract fingerprint covers declarations, so
  models without one keep their fingerprint.
- In `@runic-artifex/views`, a command that declares a failure resolves a
  `BridgeOutcome`: `{ ok: true, value }`, or `{ ok: false, failure }` for its
  declared failure, while unexpected failures still reject with `BridgeError`.
  Operations add `outcome()`, which waits and resolves the same way, and
  `BridgeOperationStatus<TResult, TFailure>` is a union discriminated by `kind`
  that includes `domain-failed` only for an operation that declares a failure.
  `matchCase(failure, handlers)` handles every case of a `$case` union, and
  `bridgeSuccess`, `bridgeFailure` and `isBridgeOutcome` build and recognize
  outcomes. The generator emits the declared signatures; see
  [Upgrading](#upgrading) for the control-flow change.
- `createCommandController` (behind `useCommand` and `injectCommand`) adds
  `failure` to its state: the declared failure of the latest run, kept apart
  from the unexpected `error`.
- `Runic.Application.ReactiveUI` and its `.Reactive` flavor add
  `ObserveBridgeExceptions` on `IHandleObservableErrors`. A `ReactiveCommand`
  also reports a declared `RunicFailureException` on `ThrownExceptions`, and
  without a subscriber ReactiveUI's default handler breaks into the debugger
  and throws. The helper ignores declared failures and cancellations, which
  the client already received, and passes every other exception to a callback,
  or logs it as `ReactiveCommandFailed` (event 1042) named after the command
  expression, such as `SaveCommand`.
- The Views wire protocol is version 2 (`BridgeProtocol.Version`), which adds
  `domain-failed`. Snapshot replies report `"protocol": 2`; the version stays
  informational. A client reports a host with another version once through
  `onBridgeDiagnostic` (`code: "protocol"`) and treats a reply error kind it
  does not know as `failed`. The
  [protocol specification](https://github.com/Runic-Artifex/runic-sdk/blob/main/specs/application/README.md)
  has portable fixtures for declared failures.
- Bridges are registered only per composition. The process-wide registration
  path is removed: `Bridge.Register`, `Bridge.Attach`,
  `WebUiWindow.AttachBridge`, the generated module initializer that called
  `Bridge.Register`, and the `RunicBridgeRegisterGlobally` MSBuild property.
  A project that references `Runic.Application.Views` without a host adapter
  no longer registers its Bridges globally. Set `RunicBridgeCompositionType`
  to generate a composition and call its `AddRunicBridges()`. A project that
  constructs the generated `<Name>Bridge` directly must exclude that code from
  the bootstrap pass, which compiles before the Bridges exist: set
  `OutputType` to `Library` and `Compile Remove` the file under
  `'$(RunicBridgeBootstrap)' == 'true'`, as
  `tests/fixtures/application/reactiveui-reactive-flavor` does.
  As in host-adapter projects, each settable state property now also gets a
  checked `write<Name>` and `fieldBaseline` in its generated client;
  `set<Name>` is unchanged. Checked writes work only on a Bridge attached
  with a window content session, as host windows and the composition's
  `Func<IBridgeTransport, WindowContentSession, T, IDisposable>` factory do. A
  directly constructed `<Name>Bridge`, or one from the composition's
  transport-only factory, replies `failed` to `write<Name>`. The new `Write<Name>`
  routes can collide with existing names, for example a `WriteNameCommand`
  next to a settable `Name`, which is a `RUNICBRIDGE004` error.
  `RUNICBRIDGE001` no longer reports ViewModel content or interactions
  generated for the global path; it still reports an invalid generator
  invocation or build configuration and internal generator errors.

## Logging and telemetry

- Bridge, View mount and model-context failures are logged with
  `Microsoft.Extensions.Logging` instead of `Trace` and standard error when
  the Window's service scope has an `ILoggerFactory`; `WindowContentSession`
  accepts one as `loggerFactory`, and `RunicModelContext` takes an
  `ILogger<RunicModelContext>`. Without a logger the earlier output remains.
  Entries name the ViewModel, member, route and exception type and always carry
  the exception; `BridgeDiagnostics` still governs only what replies show. `Runic.Application.Desktop`
  logs delivery failures, and `DesktopHostOptions.LoggerFactory` receives
  Runic Desktop close-confirmation failures.
- The `Runic.Application.Views` `ActivitySource` traces commands, setters,
  checked writes and operations, and the `Meter` of the same name measures
  calls, failures, durations, snapshot frames and sizes, delivery latency,
  recovery snapshots and delivery queue depth. `RunicViewsTelemetry` has the
  names. The
  [Views README](https://github.com/Runic-Artifex/runic-sdk/blob/main/packages/dotnet/Runic.Application.Views/README.md#logging-and-telemetry)
  lists the event IDs, spans and instruments.
- `Runic.Application` depends on `Microsoft.Extensions.Logging.Abstractions`.
- A declared failure is an expected outcome: it is logged at Debug with its
  exception as `BridgeCommandDomainFailed` (event 1006) or
  `BridgeOperationDomainFailed` (1007), its span has the outcome
  `domain_failed` with status Unset and no `error.type`, and
  `runic.bridge.failures` does not count it. A `RunicFailureException` that is
  reported as `failed` instead logs `BridgeDomainFailureNotEncoded` (1008) at
  Error.

## Generated TypeScript clients

- Every enum, DTO and union in a Bridge contract is one exported type named
  after its C# type, declared once in a generated `types.ts` and re-exported by
  each module that uses it. Enums are literal unions of their case names, so a
  `switch` over one can be exhaustive.
- `<summary>` comments on ViewModels, state properties, commands, interactions,
  DTOs and enum cases are copied into TSDoc. The bootstrap pass writes the XML
  documentation file for this; set `RunicBridgeDocumentation=false` to skip it.
- Command arguments keep the parameter name of their CommunityToolkit
  `[RelayCommand]` method instead of `argument`.
- Generator errors that were all `RUNICBRIDGE001` have their own IDs,
  `RUNICBRIDGE006` to `RUNICBRIDGE011`, name the member, and point at its
  source line. The
  [Runic.Application README](https://github.com/Runic-Artifex/runic-sdk/blob/main/packages/dotnet/Runic.Application.Views/README.md#generator-diagnostics)
  lists each ID with its fix.
- The generator cache key includes the XML documentation files, so a comment
  edit regenerates the clients.
- The generator reads `[RunicFailure(typeof(X))]` on a command property or its
  `[RelayCommand]` method. The failure type becomes a named type in
  `types.ts`; the command returns `Promise<BridgeOutcome<State, X>>` and its
  operation is `BridgeOperation<Result, X>` (`start{Command}`,
  `start{Command}WithRequestId` and `recover{Command}WithRequestId` keep their
  names and parameters). The generated bridge encodes the declared failure. The
  generated mock encodes it too: `failNext(method, { kind: "domain-failed", failure })`
  and `failWith(failure)` are type-checked against the method's failure type,
  while `throw mockFailure(failure)` in a handler is not tied to it. A misplaced,
  repeated or unsupported declaration is the new `RUNICBRIDGE012`.
- An operation of a command without a result is `BridgeOperation<void>`
  instead of `BridgeOperation<never>`, and its mock operation's `succeed()`
  takes no argument.
- A generic DTO member declared `T` takes its nullability from the type
  argument where the DTO is used: in `Box<string>` it is `string`, in
  `Box<string?>` it is `string | null`. Previously it was always nullable in
  TypeScript, and .NET accepted `null` for it even when the C# type did not.
  When the two uses differ in shape they get separate declarations,
  `BoxOfString` and `BoxOfNullableOfString`. A member declared `T?` stays
  nullable. Members inherited from a generic base class follow the same rule,
  and a type without annotations, such as `[RunicCommandInput(typeof(Box<string>))]`,
  is non-nullable throughout.
- A C# type named like a TypeScript reserved word, such as `delete`, is
  qualified like other colliding names (`Modelsdelete`) instead of producing
  an invalid declaration.
- Fixed: a generated client did not compile when a command argument, setter or
  checked write took a list of DTOs (such as `List<Item>` or
  `IReadOnlyList<Item>`), or when a ReactiveUI interaction returned a DTO (such
  as `Interaction<string, Item>`). 0.6 emitted an object literal as an arrow
  function body, as in `items.map(item => { ["name"]: item["name"] })` and
  `encodeOutput: (value: unknown) => { ["name"]: ... }`, which TypeScript reads
  as a block and rejects; applications with such members failed their frontend
  build.
- Generated modules import their runtime from the new
  `@runic-artifex/views/generated` entry and their wire decoders from
  `@runic-artifex/views/generated/wire`, and pass the interaction, operation
  and keyed collection runtimes to `connectView` only when their ViewModel
  has them. A View without interactions, operations or keyed collections, such
  as the first-window Counter, bundles 16.9 KB minified (5.9 KB gzip) instead
  of 32.3 KB (9.7 KB gzip). The root `@runic-artifex/views` entry exports only
  the API applications use. See [Upgrading](#upgrading). The plain Notes
  client, whose Save declares a failure, is 7.8 KB gzip, down from 9.4 KB
  before the entry split; declared failures account for about 1 KB of it.

## Testing

- The generator writes a `{name}.mock.ts` file next to each client module in
  every application's `RunicBridgeTypescriptDir`, so regenerated frontends gain
  one new file per ViewModel. Applications import it only from tests, so it is
  not bundled; commit it with the other generated files. Its
  `mock{Name}(bridge, { state, setters, commands, operations })` serves the
  client from `@runic-artifex/views/mock` with state, handlers, operations,
  interactions and keyed collections typed from the client, so renaming a
  ViewModel member breaks a frontend test at compile time.
- The mock Bridge has deterministic scheduling (`createMockBridge({ scheduling:
  "manual" })` with `flush()` and `flushUntil()`), a virtual clock (`sleep`,
  `advance`), delta frames (`collection(field)` and `batch`), failure notices
  (`pushFailure`), injected failures (`failNext`), checked writes, recoverable
  operations and interaction requests.
- `Runic.Application.Testing` adds a `RunicWindowTestHost` constructor that
  takes `RunicWindowTestHostOptions`. The window uses a `FakeTimeProvider` (the package now depends on
  `Microsoft.Extensions.TimeProvider.Testing`) and numbers content routes `content1`, `content2`, ...; `host.Root` and
  `View<T>(...)` return a `RunicViewDriver<T>` that calls setters, commands,
  operations and checked writes by ViewModel member instead of route name.
  `Track()` follows a route's frames, applying collection deltas as the client
  does, and `Verify()` checks them against a fresh snapshot.
- `WindowContentSession` accepts `WindowContentSessionOptions`, including a
  `TimeProvider` for interaction deadlines and close timeouts and a `CreateId`
  source for content ids.
- The [CommunityToolkit Notes example](https://github.com/Runic-Artifex/runic-sdk/tree/main/examples/notes-view-first)
  has .NET and frontend unit tests that CI runs.
- Mock handlers throw `mockFailure(failure)` to fail with a declared failure,
  `failNext(method, { kind: "domain-failed", failure })` injects one (typed by the
  method in a generated mock), and a manual operation's `failWith(failure)` ends
  it `domain-failed`. Like .NET, the mock reports `protocol: 2` on snapshot
  replies only.
- `RunicCallReply.Failure` and `RunicOperationStatus.Failure` hold the encoded
  failure of a `domain-failed` reply or operation, such as
  `{"$case":"titleRequired"}`.

## Framework bindings

- React, Vue, Svelte and Angular share one connect, observe and release
  controller from `@runic-artifex/views` (`createViewController`), so the
  four bindings behave the same. Their View handles add `pending`, and a
  changed reference no longer shows the previous client's state until the new
  one is followed.
- React and Vue have a `ViewOutlet` that renders the registered component for a
  generated reference, like the Svelte and Angular outlets. All four registries
  are typed `ViewRegistry<R>` over the reference union, so a missing kind or a
  component with the wrong `page` type is a compile error.
- `useCommand` (React, Vue, Svelte) and `injectCommand` (Angular) run a command
  and expose `pending` and `error`; `run` never rejects. The starters use them
  instead of hand-written `try`/`catch`. For a command that declares a
  failure they also expose `failure`, typed from the command's `BridgeOutcome`:
  a Svelte rune, React state, a Vue reactive property and an Angular signal.
  Latest-run-wins and `reset()` apply to `error` and `failure` together, and
  `reset()` also supersedes a run in flight, so its late result sets neither.
  A command may return one of several commands' promises without being
  `async`, as in `name => name === "save" ? client.save() : client.discard()`:
  the result is their union and `failure` the union of their declared failures.
- `useCollectionViewport` (React, Vue, Svelte) and `injectCollectionViewport`
  (Angular) follow a scroll container and return the
  `collectionViewport` range to request from .NET.
- React adds `useSuspenseView`, which suspends until a reference connects
  (`retrySuspenseView` reconnects after an error boundary reset), and
  in development warns when an inline `connect` function makes `useView`
  reconnect on every render.
- The Angular outlet creates components outside its effect's dependency
  tracking.
- `@runic-artifex/svelte` and `@runic-artifex/sveltekit` declare
  `"sideEffects": false`, so bundlers drop the bindings an application does
  not import.

## Effect adapter

- The new optional `@runic-artifex/views-effect` package wraps any generated
  client for Effect 4 applications (peer `effect` `^4.0.1`): `connect` scopes a
  client to an Effect `Scope`, `states` is a `Stream` of its state, and
  `command` and `operation` fail with tagged errors such as `ViewDisconnected`
  and `ViewCommandFailed`. Interrupting an operation, or its timeout, cancels
  it in .NET, and `retry` is offered only for operations started with an
  explicit request ID. `followViewport` sends viewport ranges and interrupts
  stale requests, and `useEffectAction` from `@runic-artifex/views-effect/react`
  runs a workflow from a component. Code generation, the runtime and the plain
  TypeScript API are unchanged, and no other package depends on it. The
  [package README](https://github.com/Runic-Artifex/runic-sdk/blob/main/packages/web/views-effect/README.md)
  lists the API and its bundle cost. The adapter is supported, not a preview.
- A declared failure (`[RunicFailure]`) arrives in the error channel of
  `command` and `operation` as `ViewDomainFailure<F>`, and the success value is
  the outcome's value; `catchCase(effect, handlers)` handles every `$case` of a
  declared `[RunicUnion]`. Commands without a declaration keep their types. The
  Effect Notes editor handles Save's `SaveFailure` this way. `operation`
  resolves to `void` for a command without a result.

## SvelteKit

- The `@runic-artifex/sveltekit` exports drop the legacy Toolkit name, and the
  adapter no longer writes the unused `runic-toolkit.sveltekit.json` manifest.

## Build

- The MSBuild properties of the Application and Platform projects drop the
  legacy Toolkit name: `RunicApplicationBuildMode`,
  `RunicApplicationShippingProject` and
  `RunicApplicationDefaultTargetFramework`.
- The Application and Platform NuGet packages carry the `application` package
  tag instead of `toolkit`.

## Platform

- The generic `Runic.Platform` result types are renamed so they no longer collide
  with `System.Reactive.Unit` and similar names when both namespaces are imported:
  `PlatformUnit`, `PlatformFailureCode` and `PlatformUnavailableReason`.
- `PlatformResult<T>.Failed` has an optional `Diagnostic`. When a provider observed a
  native error, a `PlatformDiagnostic` reports its domain, its code and, when the
  OS error table describes that code, a message for logs and support. Sources are
  HRESULTs and Win32 errors on Windows; `errno`, `GError` domains, D-Bus error names
  and portal response codes on Linux; and `NSError` domains, `OSStatus` and
  `IOReturn` codes on macOS. Free-form service text (GError and D-Bus
  messages, NSError descriptions) is left out, so diagnostics contain no paths.
  `PlatformDiagnostic.FromHResult`, `FromWin32Error` and `FromErrno` describe a code
  for custom providers.

## Desktop

- `DesktopWindowOptions.Browser` defaults to `BrowserKind.Embedded`: windows
  open in the platform WebView unless an installed browser is selected. See
  [Upgrading](#upgrading).
- `DesktopHost.Validate(windowOptions)` checks a window request before anything
  opens: the presentation and its native prerequisites, every window option the
  selected host rejects or ignores, and how permission grants apply. Each
  `DesktopDiagnostic` has a stable `Code`, the `Option` it concerns, a
  `Remediation`, and a `Severity` (`Error` or `Warning`). `ThrowIfInvalid()`
  throws a `DesktopConfigurationException` listing the errors, and each
  diagnostic is logged through `DesktopHostOptions.LoggerFactory` (events 3002
  and 3003). `GetPresentationPreflight` adds the same option checks as
  `OptionDiagnostics`. The
  [Runic.Desktop README](https://github.com/Runic-Artifex/runic-sdk/blob/main/packages/dotnet/Runic.Desktop/README.md)
  lists the codes.
- `IDesktopWindowHostFactory.ValidateOptions` lets a window host report the
  options it rejects or ignores; the default reports none. The GTK4 provider
  reports global placement, centering, transparency, high contrast, profile
  path, browser arguments and icon files, which it previously rejected only
  when the window opened.
- Preflight reports Safari and Opera, which Runic Desktop cannot launch, as
  `browser-unsupported` instead of `presentation-unavailable`.
- An `EmbeddedThenBrowser` fallback opens without the `MediaCapture` grant,
  because a browser cannot limit it to the presented origin: Chromium's flag
  accepted capture for every origin. The fallback reports
  `permission-grant-withheld` to the diagnostic sink and the logger.
- `Runic.Application.Desktop` adds `ValidateDesktopWindow<TViewModel>`, which
  also checks that the generated Bridge is registered, and warns
  (`viewmodel-not-registered`) when the container does not report the
  ViewModel. `OpenDesktopWindowAsync` runs the Bridge check before it creates a
  surface, so a missing `AddRunicViews()` throws a
  `DesktopConfigurationException` with `bridge-not-registered` instead of a
  dependency-injection error.
- `DesktopSurfaceOptions.Content` is a typed `DesktopContent`: a
  `Directory` with an optional entry file, an `Html` document, an
  `ExternalUrl` or a request `Handler`. Runic Desktop no longer guesses from a
  string whether it is HTML, a path, a folder or a URL, and only directory
  content serves local files. See [Upgrading](#upgrading).

## Window lifetime

- Both Window hosts implement the new `IBridgeWindow` contract from
  `Runic.Application.Views`. `CloseAsync(timeout)` returns one shared
  `BridgeWindowCloseResult` on CS-WebUI and Runic Desktop, and
  `WindowContentSession.BeginCloseAsync` and `RunicWindowTestHost.BeginCloseAsync`
  return the same type. Its `Completion` reports when the remaining operations finish.
- CS-WebUI Windows release asynchronously only, as Desktop Windows do.
  `CsWebUiBridgeWindow<TViewModel>` and `CsWebUiWindow<TViewModel>` no longer
  implement `IDisposable`, whose `Dispose()` returned before anything was released.
- CS-WebUI keeps writing state snapshots and collection delta frames in order to every
  client without the acknowledged delivery Runic Desktop uses, because WebUI's only
  acknowledged script call answers from one client and blocks a native thread. Its
  writes block under WebUI's process-wide send lock until the socket accepts each
  frame, so a slow client applies TCP-level back-pressure. Frames queue in the bridge
  until it falls back to a recovery snapshot, and sends to other CS-WebUI windows wait.
  The `IBridgeTransport` and `IAsyncBridgeTransport` documentation states the contract.

## dotnet-runic

- `dotnet runic doctor --output json` writes a `runic.commandline/1` envelope
  whose `runic.application.tool.doctor/1` payload lists every check with its
  `id`, `status`, `message` and `remediation`, the detected Views `host`, and
  the `target` runtime identifier. Failing and warning checks are repeated as
  `RCLI8101` and `RCLI8102` diagnostics.
- `dotnet runic doctor --fail-on <never|fail|warn>` selects which check status
  fails the command, in human and JSON output.
- `dotnet runic doctor --rid <rid>` checks deployment prerequisites for a
  runtime identifier: whether Runic supports and CI-verifies the RID, whether
  `RuntimeIdentifiers` includes it, whether this machine can compile it with
  Native AOT (Native AOT does not cross operating systems), and the WebView2,
  GTK/WebKitGTK or browser runtime target machines need. It evaluates the project
  as `dotnet publish -r <rid>` does; `--aot` and `--self-contained` add the
  matching publish switches. The
  [dotnet-runic README](https://github.com/Runic-Artifex/runic-sdk/blob/main/tools/dotnet-runic/README.md#deployment-checks-for-a-target)
  lists the checks.
- The `dotnet runic size --verify` help no longer says the check is a published
  file. It is any executable, given as a path or a command on `PATH` such as
  `node`, and receives the `--verify-argument` values, then the publish
  directory and the published application's path.

## Upgrading

- Applications that build a `ServiceCollection` with
  `Runic.Application.Desktop` or `Runic.Application.CsWebUi` add the container
  package themselves:
  `dotnet add package Microsoft.Extensions.DependencyInjection`. Projects
  created from the 0.7 `runic-app` template already reference it.
- `MapRunicAssetSource` and `RunicAssetEndpointExtensions.WriteAssetAsync`
  take `IAssetSnapshotSource`, and `ToDesktopContentHandler` extends
  `IAssetSnapshotSource`. `AssetArchiveSource`, `EmbeddedAssetSource`,
  `DevelopmentDirectoryAssetSource` and `WithDevelopmentDocument` results already
  implement it; a custom `IAssetSource` must implement `OpenSnapshotAsync`.
- `DesktopAssetOptions` is removed. Replace
  `new DesktopAssetOptions { EnableSinglePageApplicationFallback = false }` with
  `new AssetRoutingOptions { EnableSinglePageApplicationFallback = false }`.
- `MapRunicAssetSource` now serves the entry point at the route root and for
  missing extensionless paths, as the Desktop adapter does. An unknown
  extensionless `GET` below the mount, such as `/api/typo`, therefore returns
  the entry point with status `200`. Its endpoint claims only `GET` and `HEAD`
  requests for paths that resolve, and runs after the application's endpoints
  and before `MapFallback`. An application that serves an API from the same
  origin should mount the assets under a prefix or pass
  `routing: new AssetRoutingOptions { ServeEntryPointAtRoot = false, EnableSinglePageApplicationFallback = false }`
  to keep the previous exact-path behavior.
- Code that caught `ArgumentException` from `AssetManifest.TryGetAsset` can drop
  the handler; use `AssetPath.Normalize` where an invalid path must throw.
- The global Bridge registration path is removed; there are no compatibility
  aliases. Register Bridges with the generated composition and attach them
  through a DI scope:

  | 0.6 | 0.7 |
  | --- | --- |
  | `<RunicBridgeRegisterGlobally>…</RunicBridgeRegisterGlobally>` | delete the property; per-composition registration is the only model |
