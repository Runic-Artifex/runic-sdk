## `dotnet runic dev --browser`: a stable address for one browser (#1187)

`--browser`'s `http://127.0.0.1:9224/` is now a proxy to the serve-only Window's pages instead of a redirect to the
Window's own address, so a tab keeps its address when `dotnet watch` restarts the Window. A Runic Desktop page reloads
itself onto the new Window (the stopping Window's close command reaches it as the Bridge's token refusal), and the
JavaScript debugger's breakpoints stop again; reload a CS-WebUI tab.

- **One browser, by a one-time code.** The `[dev] Browser:` lines carry the current code
  (`http://127.0.0.1:9224/?code=…`), and `dev` writes `obj/runic/dev-browser.html`, a page only you can read
  (mode 0600, or an access list of your account alone on Windows), which opens the address with the newest code. The
  session file names it as `browser.codeFile`. The code admits one browser with `dev`'s `HttpOnly`, `SameSite=Strict`
  cookie and is then replaced; a new admission ends the previous browser's, and closes its open connections. Every other
  client gets 403. The cookie is a bearer credential that the browser sends to every `127.0.0.1` port it loads. On a
  machine shared with other users, use `--browser` on Linux only: macOS and Windows cannot tell a loopback connection's
  user.
- **The template's `Window in Chrome`** opens that page (`"file": "${workspaceFolder}/obj/runic/dev-browser.html"`)
  instead of the fixed URL, so it also follows a moved port.
- **The Window's side.** `dev` sets `RUNIC_APPLICATION_SERVE_ORIGIN` for the serve-only Window: Runic Desktop admits
  the address as an origin of its pages and connects their Bridge through it; Runic's CS-WebUI host admits it at its
  upload endpoint.

See [Debug the page in Chrome](https://github.com/Runic-Artifex/runic-sdk/blob/v0.23.0/tools/dotnet-runic/README.md#debug-the-page-in-chrome---browser)
and [Development server security](https://github.com/Runic-Artifex/runic-sdk/blob/v0.23.0/docs/security.md#development-server).
