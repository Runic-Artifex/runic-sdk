# Runic SDK 0.7.0-preview.7

Install matching `0.7.0-preview.7` packages from NuGet and npm. Command Line
versions remain independent of this SDK.

This preview contains breaking changes; see [Upgrading](#upgrading).

## WPF Bridge generation

- Referencing `Runic.Application.Wpf` alone now generates the Bridge,
  `AddRunicViews()` and the TypeScript client. Host adapters set
  `RunicApplicationHostAdapter` in their build props, so generation also turns on
  when an adapter is referenced transitively.
- WPF's temporary `*_wpftmp` markup-compile project no longer runs the generator
  or its bootstrap build, which removes the duplicate-member errors in
  single-project WPF applications with local XAML types. The generator skips
  types that depend on WPF assemblies instead of failing with `RUNICBRIDGE005`.
- `RunicBridgeTypescriptDir` now defaults to `<RunicBridgeFrontendDir>/src/generated`.
  A project that set only `RunicBridgeFrontendDir` previously wrote its client to
  `Frontend/src/generated` under the project folder.
- An application copies the built frontend of a referenced project that declares
  the Views to its own `www/` on build and publish. Custom copy targets, such as
  the ones the hybrid WPF example had, are no longer needed.
- A missing frontend folder or `package.json` is one `RUNICBRIDGE014` error
  instead of a raw `MSB6003`. A project that declares a Window or View while
  generation is off by default gets a `RUNICBRIDGE015` warning.
- WPF projects keep generation optional, so a WPF application whose Views live
  in a model project builds without its own Views.

## WPF navigation and hosting

- `Runic.Application.Wpf` (experimental) adds the `RunicViewHost` control and
  the `RunicViewHostState` enum. Host a generated web View in XAML with
  `Model="{Binding}"`; the control manages open timing, serialized swaps,
  cancellation, disposal order and the native fallback. The README snippet is
  corrected.
- `Runic.Navigation.Wpf` (experimental) adds `NavigationHost.GuardWindowClose`,
  which runs the region's departure guards before its window closes and logs
  event 1088 when a guard fails. `NavigationDialogHost` supports
  `Button.IsDefault` and `Button.IsCancel`.
- `RunicModelContext.Closed` is now marked experimental (`RUNICNAV001`), like
  the `IRunicModelContextLifetime` interface it implements. The member remains
  binary compatible; code that reads it directly must suppress `RUNICNAV001`.
- `WpfBridgeView` publishes its close before releasing the session, so a
  `CloseAsync` or `DisposeAsync` re-entered on the same thread during release
  joins that close instead of releasing the session twice.
- `NavigationSelector` no longer throws `ObjectDisposedException` when a
  selector detaches or selects after a selection ended during dispatcher
  shutdown.
- The hybrid WPF editor example keeps a save that the store completed even when
  Cancel arrives afterward, and no longer reports a cancelled web-editor open
  as a host failure after a fast unload and reload.

## Navigation

- A request in a child region is now always `Rejected(Closed)` when a parent's
  navigation closes that region. Before, it could intermittently end
  `Superseded` if the parent committed just as the child request reached its
  guard or preparing step.
- `NavigationResult<T>.IsCommitted` and `ThrowIfFailed()` are added
  (experimental, `RUNICNAV001`).

## Experimental APIs

- `RUNICNAV001` and `RUNICWPF001` diagnostics link to
  [Experimental APIs](https://github.com/Runic-Artifex/runic-sdk/blob/v0.7.0-preview.7/docs/experimental.md)
  for the release you use. The page lists what each ID covers and how to
  suppress it, project-wide (`<NoWarn>`) or per site
  (`#pragma warning disable`), and the criteria for stabilizing navigation,
  which remains experimental.
- These diagnostics no longer appear in generated code. `Runic.Navigation.Wpf`
  and `Runic.Application.Wpf` suppress their ID in the code that the WPF markup
  compiler generates for a named control such as
  `<rn:NavigationHost x:Name="Host" />`, so a per-file or per-site suppression
  in your own code is enough with `TreatWarningsAsErrors`.
  `Runic.Navigation.Wpf` therefore ships a small `buildTransitive` targets file.

## Model context and async commands

- Async command bodies started by the bridge resume on the window's model
  context after `await`, in both CommunityToolkit.Mvvm and ReactiveUI. Set
  ViewModel properties directly after `await`; `IRunicModelContext.InvokeAsync`
  is only needed for code that left the context (`ConfigureAwait(false)`,
  `Task.Run`, timers). `RunicModelContext` runs each turn under a
  `SynchronizationContext` that queues continuations as turns, in ready order.
  After the context closes, continuations run on the thread pool outside any
  turn. An exception thrown by an `async void` method started in a turn is
  reported through `UnhandledTurnException` instead of crashing the process.
- ViewModels no longer need `RunicModelContextRegistry.Shared.Bind`: the
  window binds its root and every child it presents, including one a ViewModel
  creates later, and a navigator binds the entries it owns. The ReactiveUI
  template and README no longer bind manually. An existing `Bind` to the
  window's context remains valid.
- A Bridge attached directly to a `WindowContentSession`, for example in a
  hand-built session without a root ViewModel, binds its ViewModel to the
  session's model context for the Bridge's lifetime. Previously the ViewModel
  stayed unbound, so its Bridge fell back to a lock that could deadlock with
  the window's model turns
  ([#132](https://github.com/Runic-Artifex/runic-sdk/issues/132)).
- A window root, presented content, directly bridged ViewModel or owned
  navigation entry that is already bound to a different model context fails
  with an `InvalidOperationException` naming the ViewModel type and the fix.

## Bridge generation and generated clients

- A command whose generated client member is reserved in a TypeScript object
  type fails the build with `RUNICBRIDGE004` and a suggested name. `NewCommand`
  generated `new(): Promise<…>`, a construct signature, so the TypeScript did
  not compile; `constructor`, `then`, `__proto__`, `toJSON`, `toString` and
  `valueOf` are rejected as well. State properties with these names are
  unchanged.
- Presenting a ViewModel without a View in a content property, ViewModel
  collection or navigation region throws a `NotSupportedException` that names
  the region or slot and the ViewModel type and shows the View to declare,
  instead of "Main contains an unregistered ViewModel type."
- The new `RUNICBRIDGE013` build warning reports a public, concrete ViewModel
  in the application assembly that such a slot admits but that has no View.
  Broad slot types are skipped to avoid false positives: framework types, an
  application-wide base that the owner or a Window ViewModel shares, and a type
  that more than eight ViewModels without a View could fill. Add the View, or
  suppress the warning with `NoWarn` for a type that is never presented there.
  A build that reuses the cached generation repeats it.
- Read-only ViewModel state follows standard MVVM rules: as in WPF, Avalonia or
  MAUI, the C# setter's accessibility decides what any View, including the web
  frontend, may set. Only properties with a public setter get a generated
  `set<Property>` client member, as before, and that member now documents the
  setter it calls. Give status such as `IsDirty` or `Error` a private setter:
  `[ObservableProperty] public partial T X { get; private set; }` for
  CommunityToolkit.Mvvm, or a private setter (`RaiseAndSetIfChanged` or
  `[Reactive]`) for ReactiveUI. A field-based `[ObservableProperty] private T x;`
  generates a public setter, so the web frontend can set it.
- Generated `connect<Name>()` functions accept `{ timeout }`, in milliseconds
  (default 5000). `@runic-artifex/views` exports `BridgeConnectOptions`.
- `ViewRegistry<State["main"]>` accepts nullable region slots in React, Vue,
  Svelte and Angular.
- `RunicViewState.Read` explains how to read non-scalar properties.
- Generated TypeScript documents `long`, `ulong` and `BigInteger` as `bigint`.
  Summaries on partial `[ObservableProperty]` and `[Reactive]` properties appear
  in the generated client
  ([#169](https://github.com/Runic-Artifex/runic-sdk/issues/169)), and
  CommunityToolkit cancel commands are documented as "Cancels the running `x`
  call." instead of copying the Toolkit generator's C# comment.
- Generated-code plumbing in `Runic.Application` and
  `Runic.Application.ReactiveUI[.Reactive]` (`ViewModelBridge<T>`,
  `PropertyDescriptor<T>`, `CommandDescriptor<T>`, `BridgeJson`, `BridgeWire`,
  `ReactiveCommandExecution` and related descriptors) is hidden from
  IntelliSense with `[EditorBrowsable(Never)]`. The API itself is unchanged.
- `Runic.Application` and its Bridge generator recognize CommunityToolkit.Mvvm
  and ReactiveUI through per-library convention modules; the shared contract
  and generator core work only with `ICommand`, `INotifyPropertyChanged`,
  `INotifyDataErrorInfo` and the Runic attributes. Generated bridges, TypeScript
  clients and contract fingerprints are unchanged. General-purpose packages
  (Views and Navigation cores, Platform, Desktop, Assets and tools) stay free
  of ReactiveUI, System.Reactive and CommunityToolkit.Mvvm dependencies, which
  CI now enforces.

## Cancelled web operations are not errors

- `createOperationController` and `createLatestOperationController` treat a
  `cancelled` terminal status as a normal end. The new `cancelled` state becomes
  true, `run()` resolves to `undefined`, and `error` stays undefined; previously
  pressing Cancel published `BridgeError("cancelled")` as `error`. `failed` and
  `timedOut` statuses are still `error`. Starting a run and `reset()` clear
  `cancelled`. A direct `operation.outcome()` call still rejects with
  `BridgeError("cancelled")`.
- Svelte `useOperation` exposes `cancelled`. `@runic-artifex/react` and
  `@runic-artifex/vue` add `useOperation(start, options?)`, and
  `@runic-artifex/angular` adds `injectOperation(start, options?)`, with the same
  operation state, including `cancelled`, and `run`, `cancel` and `reset`.

## Per-window platform services

- `services.AddRunicPlatformServices()` for Runic.Application.Desktop and
  Runic.Application.CsWebUi registers per-window `IWindowPlatformServices`,
  `IFileDialogs`, `ITextClipboard` and `IDesktopFileLauncher` that a ViewModel
  can take in its constructor. On Desktop they bind when the window opens and
  use the Windows, macOS, GTK 3 or GTK 4 (xdg-desktop-portal) provider for the
  running backend; a GTK 4 process never loads the GTK 3 provider. On CS-WebUI
  they report `OwnerUnavailable`.
- New `PlatformServices.ForWindow(DesktopNativeOwner)`,
  `PlatformServices.CurrentProvider` and
  `WindowPlatformServices.Unavailable(reason)`.
- `PickerResult<T>.Selected` deconstructs:
  `is PickerResult<IReadFileLease>.Selected(var lease)`.
- Runic.Application.Desktop now depends on the Runic.Platform.Windows, MacOS,
  Linux, Linux.Gtk4 and Linux.Portal packages, so the `runic-app` template calls
  `AddRunicPlatformServices()` and no longer references
  `Runic.Platform.Linux.Gtk4` or `Runic.Platform.Linux.Portal` directly.

## Directory access and native choosers

- The GTK3 file and directory chooser completes when its GTK loop stops while
  the chooser is open, so presentation shutdown no longer waits indefinitely.
  If the loop never runs again, the native dialog is left to the stopped loop.
- `PresentationFiles.OpenDirectoryAsync` always calls the backend's
  `OpenDirectoryAsync`. A custom `IPickerBackend` that implements directory
  selection must return `true` from `SupportsDirectorySelection`, which reports
  the `platform.directories.open` capability. An undeclared backend that returns a
  selection now throws `InvalidOperationException` instead of being reported
  unavailable without explanation.
- `IDirectoryLease.DisplayName` names a filesystem root by the root path, such
  as `/` or `C:\`, instead of returning an empty string.
- Presentation close releases directory leases. Preview.6 suggested retaining a
  lease in the presentation scope; when accepted application work, including
  recovery, uses the lease after the window closes, drain that work before
  stopping the `PresentationLifetime`, or dispose the lease at the end of the work.

## Accepted work and callback lifetime

- `AcceptedWorkScope` drain and disposal started from the scope's own accepted
  work, such as "Save and close" disposing its model, wait for all other
  accepted work but no longer for the calling task, which previously hung.
- Faults of accepted tasks are logged once instead of being silently observed:
  event 1013 at Error, or 1014 at Debug for a declared `RunicFailureException`.
  Pass a logger with `new AcceptedWorkScope(logger)`; without one, entries go
  to `Trace`. Drain still completes without throwing.
- The Runic.Desktop README and `RegisterCapability` documentation describe
  callback concurrency: async capability handlers hold a connection's turn only
  until their first incomplete await, can overlap other handlers and connection
  events, and can reply out of order. `Disconnected` follows every accepted
  call. Serialize handlers that need exclusive access, for example with a
  `SemaphoreSlim`.

## Desktop shutdown and windows

- `DesktopEventLoop.Run(options, application)` handles Ctrl+C, SIGTERM and
  SIGHUP (on Windows, closing the console window) like closing the last window
  ([#128](https://github.com/Runic-Artifex/runic-sdk/issues/128)). The first
  signal cancels the new `DesktopHost.ShutdownRequested` token and closes every
  open window without close confirmation; `WaitForClose` returns, the
  application releases its work and returns its exit code, and the host is
  disposed before the GTK, AppKit or plain loop ends. Previously the process
  ended without disposing the host or an installed-browser fallback profile.
- A second Ctrl+C, a second or more after the first signal, ends the process
  at once; copies of the signal forwarded by `dotnet run`, `dotnet watch` or
  `dotnet runic dev` do not.
- Set `DesktopHostOptions.HandleShutdownSignals = false` to keep the default
  signal handling, for example when the application registers its own handlers.
  The generated `Program.cs` is unchanged.
- Runic.Desktop reports `close-confirmation-unavailable`. When
  `ConfirmCloseAsync` is set with an explicit browser, opening fails with a
  `DesktopException` (`CapabilityDenied`) instead of an `ArgumentException`.
  With `EmbeddedThenBrowser`, a browser fallback opens without confirmation and
  reports a Warning.
- A `DesktopContent.Directory` entry is checked before a window waits for it.
  An entry with a `?query` or `#hash` is rejected when constructed with a
  `DesktopConfigurationException` (`content-entry-invalid`), and
  `CreateSurfaceAsync` with an entry that does not exist throws
  `DesktopConfigurationException` (`content-entry-not-found`), naming the entry
  and the known HTML pages. Both previously produced a window that timed out.

## dotnet-runic

- `dotnet runic dev` prepares a development document for every HTML page in
  the Vite build input, not only `index.html`, so a second window with its own
  page loads in `dev` as it does after build and publish. You no longer need
  `RunicApplicationFrontendDevServerDocument` for that; when set, it still
  overrides the list. Angular projects keep `index.html`.
- A window page that is a build input but has no file stops `dev` before the
  build with `RAPPDEV1009: Window entry not found: '<page>'`, instead of a
  window that fails with `presentation-connection-timeout`.
- `dev` now reads the build inputs with Node.js (or Bun for a Bun frontend)
  before the build; a Vite configuration that cannot be resolved for
  `vite build` reports `RAPPDEV1010`.
- `dev` resolves `webui.js` and the host client scripts from the web root in
  nested pages such as `pages/settings.html`.
- `dev` stops the Window gracefully on Ctrl+C or SIGTERM and before a restart:
  the app gets SIGTERM (Ctrl+C on Windows) and up to 5 seconds to close its
  windows and finish its work before it is killed. `dev` sets
  `DOTNET_WATCH_PROCESS_CLEANUP_TIMEOUT_MS=5000` unless you set it, so
  `dotnet watch` gives the same grace when a C# edit restarts the app. `dev` no
  longer reports `Exited with error code 143` when `dotnet watch` restarts the
  application or `dev` stops it.
- `dev --no-restore` no longer requires `node_modules` for a frontend without
  dependencies.
- `doctor` and `size` both accept `--rid`, `--runtime` and `-r`, and both accept
  `--aot` and `--no-aot`. `doctor --rid <rid> --no-aot` checks a publish with
  `PublishAot=false`.
- `doctor --output json` exits 1 when a check fails: `--fail-on` defaults to
  `fail` in both output modes. Pass `--fail-on never` to always receive the
  payload.
- The new `doctor` check `platform-services` names the selected platform
  provider and, on Linux, checks for the D-Bus session bus and
  xdg-desktop-portal. `gtk4-profile` no longer asks `Runic.Application.Desktop`
  projects to reference the GTK 4 provider packages.

## Build targets and Vite plugin

- Generator and frontend command failures are no longer wrapped in `MSB3073`.
  Canonical errors (generator, `tsc`) are logged once with their code and
  location; a failure without one gets a single `RUNICBRIDGE001` (generator) or
  the new `RUNICBRIDGE016` (frontend install or build).
- The frontend install also runs when `package.json` or the lock file changed
  since the last install (stamp in `obj/`), and a `package.json` without
  dependencies no longer fails because no `node_modules` was created.
- A test project (`IsTestProject`, set by TUnit and Microsoft.NET.Test.Sdk)
  that references a Runic application no longer runs Bridge generation or fails
  with `RUNICBRIDGE006` when it declares no Window or View and has no frontend.
  It uses the app's generated Bridges.
- `@runic-artifex/vite-plugin-runic`: `vite build` no longer warns that
  `webui.js` or the host client script "can't be bundled without
  type=module", and host scripts resolve from the web root in nested pages.

## Templates, Runic.Create and testing

- `dotnet new runic-app --tests` (and `dnx Runic.Create -- MyApp --tests`, or
  answering yes in the guided creator) adds `MyApp.Tests`, a TUnit test project
  that drives the Window's ViewModels and generated Bridges headlessly with
  `Runic.Application.Testing`. Run it with `dotnet test --project MyApp.Tests`.
  The test project builds the app without its frontend, and a `global.json`
  selects Microsoft.Testing.Platform for `dotnet test`.
- Generated apps register their ViewModels and Views in
  `WorkspaceServices.AddWorkspace()` (`WorkspaceServices.cs`), which
  `Program.cs` and the tests share. The window exposes `ViewModel` (and
  `Surface` on Desktop), and the Svelte frontend includes `svelte.config.js`.
- The template's Counter shows read-only state (`Count`, private setter) beside
  a two-way bound form field (`Step`, public setter) in every frontend and MVVM
  flavor.
- New `RunicWindowTestHost.Create<TViewModel>(IServiceProvider services, RunicWindowTestHostOptions? options = null)`
  builds a test host from the window's service scope: the root ViewModel, its
  generated Bridge, and the registered View locator, model context and logger
  factory, replacing four `GetRequiredService` calls. The
  `Runic.Application.Testing` README documents skipping the frontend build in
  test projects (`AdditionalProperties="RunicBridgeBuildFrontend=false"` on the
  app reference).
- In `Runic.Create`, `--output` / `-o` choose the destination directory, as with
  `dotnet new`; `--directory` keeps working as a hidden alias. The creator's
  output format is selected with `--format human|json`.

## Documentation and diagnostics

- Package READMEs on nuget.org and npm link to the documentation of the release
  you installed instead of the `main` branch.
- Every Bridge generator (`RUNICBRIDGE`), `dotnet runic`, asset packer and
  `Runic.Create` diagnostic links to its entry in the new
  [diagnostics catalog](https://github.com/Runic-Artifex/runic-sdk/blob/v0.7.0-preview.7/docs/diagnostics.md)
  at your release.
- The `dotnet runic`, `Runic.Application` and `Runic.Desktop` READMEs gain
  Troubleshooting sections for common setup problems.

## Upgrading

- Scripts that run `dotnet runic doctor --output json` and expect exit code 0
  with failed checks pass `--fail-on never`.
- Code that detected a user Cancel through an operation controller's `error`
  reads `cancelled` instead.
- Rename a command whose client member would be `new`, `constructor`, `then`,
  `__proto__`, `toJSON`, `toString` or `valueOf`, for example `NewCommand` to
  `CreateCommand`; the build now fails with `RUNICBRIDGE004`.
- Don't block a model-context turn on async work (`.Result`, `.Wait()`): like a
  UI thread, it now deadlocks because continuations queue as turns.
- Code that caught `ArgumentException` when `ConfirmCloseAsync` was set with an
  explicit browser catches `DesktopException` (`CapabilityDenied`).
- Use `--output` or `-o` for the `Runic.Create` destination and `--format` for
  its output format. Preview.6 creator documentation used `--directory`, which
  remains a hidden alias.
- A project that set only `RunicBridgeFrontendDir` finds its generated client
  under `<RunicBridgeFrontendDir>/src/generated`; set `RunicBridgeTypescriptDir`
  to keep the previous location.
- Code that reads `RunicModelContext.Closed` directly suppresses `RUNICNAV001`.
