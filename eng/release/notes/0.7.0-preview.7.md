# Runic SDK 0.7.0-preview.7

Install matching `0.7.0-preview.7` packages from NuGet and npm. Command Line
versions remain independent of this SDK.

This preview contains breaking changes; see [Upgrading](#upgrading).

## WPF Bridge generation

- Referencing `Runic.Application.Views.Wpf` alone now generates the Bridge,
  `AddRunicViews()` and the TypeScript client. Host adapters set
  `RunicApplicationHostAdapter` in their build props, so generation also turns on
  when an adapter is referenced transitively.
- WPF's temporary `*_wpftmp` markup-compile project no longer runs the generator
  or its bootstrap build, which removes the duplicate-member errors in
  single-project WPF applications with local XAML types. The generator skips
  types that depend on WPF assemblies instead of failing with `RUNICBRIDGE005`.
- `RunicApplicationFrontendGeneratedDirectory` (formerly `RunicBridgeTypescriptDir`)
  now defaults to `<RunicApplicationFrontendDirectory>/src/generated`. A project
  that set only the frontend directory previously wrote its client to
  `Frontend/src/generated` under the project folder.
- An application copies the built frontend of a referenced project that declares
  the Views to its own `www/` on build and publish. Custom copy targets, such as
  the ones the hybrid WPF example had, are no longer needed.
- A missing frontend folder or `package.json` is one `RUNICBRIDGE014` error
  instead of a raw `MSB6003`. A project that declares a Window or View while
  generation is off by default gets a `RUNICBRIDGE015` warning.
- WPF projects keep generation optional, so a WPF application whose Views live
  in a model project builds without its own Views.

## WPF navigation and hosting

- `Runic.Application.Views.Wpf` (experimental) adds the `RunicViewHost` control and
  the `RunicViewHostState` enum. Host a generated web View in XAML with
  `Model="{Binding}"`; the control manages open timing, serialized swaps,
  cancellation, disposal order and the native fallback. The README snippet is
  corrected.
- `Runic.Navigation.Wpf` (experimental) adds `NavigationHost.GuardWindowClose`,
  which runs the region's departure guards before its window closes and logs
  event 1088 when a guard fails. `NavigationDialogHost` supports
  `Button.IsDefault` and `Button.IsCancel`.
- `RunicModelContext.Closed` is now marked experimental (`RUNICNAV001`), like
  the `IRunicModelContextLifetime` interface it implements. The member remains
  binary compatible; code that reads it directly must suppress `RUNICNAV001`.
- `WpfBridgeView` publishes its close before releasing the session, so a
  `CloseAsync` or `DisposeAsync` re-entered on the same thread during release
  joins that close instead of releasing the session twice.
- `NavigationSelector` no longer throws `ObjectDisposedException` when a
  selector detaches or selects after a selection ended during dispatcher
  shutdown.
- The hybrid WPF editor example keeps a save that the store completed even when
  Cancel arrives afterward, and no longer reports a cancelled web-editor open
  as a host failure after a fast unload and reload.

## Navigation

- A request in a child region is now always `Rejected(Closed)` when a parent's
  navigation closes that region. Before, it could intermittently end
  `Superseded` if the parent committed just as the child request reached its
  guard or preparing step.
- `NavigationResult<T>.IsCommitted` and `ThrowIfFailed()` are added
  (experimental, `RUNICNAV001`).
- New `NavigationOutcome`, `NavigationOutcomeKind` and
  `NavigationResult<T>.Outcome` (experimental, `RUNICNAV001`): a summary of a
  navigation result (`Committed`, `Rejected`, `Superseded` or `Failed`, with the
  rejection) that can cross the Bridge.
- `CreateBackCommand(outputScheduler = null)` in `Runic.Navigation.ReactiveUI`
  returns `ReactiveCommand<RxVoid, NavigationOutcome>`
  (`ReactiveCommand<Unit, NavigationOutcome>` in `.Reactive`), so a ViewModel
  can expose it to a View. The scheduler is optional; without one, output and
  `IsExecuting` use ReactiveUI's main-thread scheduler. `CanExecute` turns false
  synchronously when a transition starts.
- New `RunicModelContext.Current` returns the model context whose turn is
  executing on the calling thread, or `null` outside a turn.
- Content that the navigator constructs can take its `NavigationEntryContext`
  as a constructor parameter (experimental, `RUNICNAV001`): `NavigationTarget.Create<T>()`,
  `PushAsync<T>()`, `ReplaceAsync<T>()`, `ResetAsync<T>()`,
  `PushForResult<T, TResult>()`, their typed-input forms and the initial target
  of `CreateRegion`. New `NavigationTarget.Create((services, entry) => ...)`
  overloads pass it to a factory. Resolving `NavigationEntryContext` from a
  container configured with `AddRunicNavigation()` throws an explanatory
  `InvalidOperationException`. A ViewModel no longer needs `InitializeAsync` only
  to keep its entry for `CompleteAsync`, `DismissAsync` or `BackAsync`; that
  pattern still works, and remains the way for `Own` and `Borrow` content.
- New `INavigationAware` (experimental, `RUNICNAV001`): `OnNavigatedTo(NavigationResume)`
  and `OnNavigatedFrom(NavigationExit)` are synchronous notifications in the
  commit turn. They are never raised for a rejected, superseded, cancelled or
  failed transition. `NavigationEntryContext.State` and `StateChanged` expose the
  entry's state. A throwing `StateChanged` handler or `INavigationAware` method
  is logged as event 1075 `NavigationEntryNotificationFailed`, and the
  navigation stands.
- `RunicNavigator.HookCancellationToken` (experimental, `RUNICNAV001`) is the
  token of the navigation hook running on the current flow. A browser
  interaction that a navigation hook requests through Runic.Application.Views is
  cancelled when that hook's transition is superseded, cancelled or closed, so
  the handler's `signal` aborts.
- `Runic.Navigation.ReactiveUI` (and `.Reactive`) adds
  `NavigationEntryContext` extensions `WhenNavigatedTo`, a per-arrival
  disposable scope that is disposed when the entry is left, and
  `WhenNavigatedFrom`, which emits `NavigationExit`. `CreateCompleteCommand`,
  `CreateDismissCommand` and `CreateCloseCommand` return
  `ReactiveCommand<…, NavigationOutcome>` that a View can bind. These three
  commands (and their typed forms) are disposed when their entry retires; a
  command created on an entry that already retired is disposed at once.
  `ReactiveLeaveConfirmation.WithInteraction` asks a leave confirmation through
  a ReactiveUI `Interaction`; an unanswered question fails the departure with
  `Failed(Guarding)` and event 1060 `NavigationGuardFailed`. All are
  experimental (`RUNICNAV001`).
- Command lifetime follows ReactiveUI's rule: dispose a command or subscription
  only when it observes an object that outlives its owner. Entry commands and
  `WhenNavigatedTo` end with the entry, and `CreateBackCommand` on the
  ViewModel's own region and handlers on its own `Interaction` need no disposal,
  so a navigation ViewModel needs no `MultipleDisposable` or `DisposeWith` for
  them.
- An `InitializeAsync` hook may set state directly on content that the navigator
  created for its entry: nothing presents that content before the commit, and the
  commit turn runs after the awaited hook. Use `InvokeAsync` for presented or
  shared state, in guards and in `ResumeAsync`.

## Experimental APIs

- `RUNICNAV001` and `RUNICWPF001` diagnostics link to
  [Experimental APIs](https://github.com/Runic-Artifex/runic-sdk/blob/v0.7.0-preview.7/docs/experimental.md)
  for the release you use. The page lists what each ID covers and how to
  suppress it, project-wide (`<NoWarn>`) or per site
  (`#pragma warning disable`), and the criteria for stabilizing navigation,
  which remains experimental.
- These diagnostics no longer appear in generated code. `Runic.Navigation.Wpf`
  and `Runic.Application.Views.Wpf` suppress their ID in the code that the WPF markup
  compiler generates for a named control such as
  `<rn:NavigationHost x:Name="Host" />`, so a per-file or per-site suppression
  in your own code is enough with `TreatWarningsAsErrors`.
  `Runic.Navigation.Wpf` therefore ships a small `buildTransitive` targets file.
- `Runic.Application.Views.ReactiveUI` and `.Reactive` no longer reference the
  experimental `Runic.Navigation.ReactiveUI` adapters, so an app without
  navigation has no experimental package. Reference `Runic.Navigation.ReactiveUI`
  (or `.Reactive`) yourself for region observables or `CreateBackCommand`.
  Generated Bridges suppress `RUNICNAV001` only when their ViewModel graph uses
  `Runic.Navigation` types.

## Model context and async commands

- Async command bodies started by the bridge resume on the window's model
  context after `await`, in both CommunityToolkit.Mvvm and ReactiveUI. Set
  ViewModel properties directly after `await`; `IRunicModelContext.InvokeAsync`
  is only needed for code that left the context (`ConfigureAwait(false)`,
  `Task.Run`, timers). `RunicModelContext` runs each turn under a
  `SynchronizationContext` that queues continuations as turns, in ready order.
  After the context closes, continuations run on the thread pool outside any
  turn. An exception thrown by an `async void` method started in a turn is
  reported through `UnhandledTurnException` instead of crashing the process.
- ViewModels no longer need `RunicModelContextRegistry.Shared.Bind`: the
  window binds its root and every child it presents, including one a ViewModel
  creates later, and a navigator binds the entries it owns. The ReactiveUI
  template and README no longer bind manually. An existing `Bind` to the
  window's context remains valid.
- A Bridge attached directly to a `WindowContentSession`, for example in a
  hand-built session without a root ViewModel, binds its ViewModel to the
  session's model context for the Bridge's lifetime. Previously the ViewModel
  stayed unbound, so its Bridge fell back to a lock that could deadlock with
  the window's model turns
  ([#132](https://github.com/Runic-Artifex/runic-sdk/issues/132)).
- A window root, presented content, directly bridged ViewModel or owned
  navigation entry that is already bound to a different model context fails
  with an `InvalidOperationException` naming the ViewModel type and the fix.

## ReactiveUI model context

- `AddRunicReactiveModelContext()`, `IRunicReactiveSchedulerProvider` and
  `RunicReactiveSchedulerProvider` moved from `Runic.Navigation.ReactiveUI` to
  `Runic.Application.Views.ReactiveUI` (namespace
  `Runic.Application.Views.ReactiveUI`), and likewise for `.Reactive`.
- `AddRunicReactiveModelContext()` replaces ReactiveUI's default main-thread
  scheduler (`RxSchedulers.MainThreadScheduler`) with one that delivers work
  scheduled in a model-context turn on that context. A bridged command delivers
  its results and `IsExecuting` on the model context of the Window that runs it,
  ordered with Bridge replies. Create commands without a scheduler; ViewModels
  no longer need `ISequencer`.
- Work scheduled outside a turn, for example from a timer or after
  `ConfigureAwait(false)`, runs on the replaced ReactiveUI scheduler and is
  logged once as `ReactiveSchedulerOutsideModelTurn` (Views event 1043,
  Warning). Pass an `ILoggerFactory` to the new
  `RunicReactiveSchedulerProvider.InstallMainThreadScheduler` to log it there;
  otherwise it goes to `Trace`.
- To opt out, set your own `RxSchedulers.MainThreadScheduler` (or use
  ReactiveUI's `WithMainThreadScheduler`) before `AddRunicReactiveModelContext()`,
  or replace it afterwards. A scheduler that the application or UI platform
  already set, such as WPF's dispatcher or a test scheduler, is kept. Commands
  read the scheduler when they are created, so register the model context
  before the ViewModels create their commands.
- The `Runic.Application.Views.ReactiveUI` README states that it targets the
  ReactiveUI 26 Primitives flavour and explains `RxVoid`, `ISequencer` and
  awaiting commands (`using ReactiveUI.Primitives.Signals;`).

## ReactiveUI command exceptions

- A generated Bridge now observes the `ThrownExceptions` of each bridged
  `ReactiveCommand`, so a ViewModel needs no subscription for every command. An
  unexpected exception that no Bridge call received is logged once at Error as
  `ReactiveCommandFailed` (event 1042), to category `Runic.Application.Views`
  through the Window's logger factory, with `Model.Command` as the source. A
  Bridge call's own failure stays with the Views runtime (event 1000
  `BridgeCommandFailed` or 1004 `BridgeOperationFailed`), as for every MVVM
  library, and is not logged twice. Declared failures and cancellations are not
  logged, and two Bridges that present one ViewModel log once.
- `ObserveBridgeExceptions` still works. While it observes a command, it is the
  opt-out: the Bridge does not log that command. A raw `ThrownExceptions`
  subscription does not suppress the Bridge's logging. Without a Bridge, for
  example a command that no Bridge presents, ReactiveUI's default handler
  applies; use `WithExceptionHandler`.
- New `ReactiveCommandExecution.ObserveFailures` in
  `Runic.Application.Views.ReactiveUI` (and `.Reactive`) and the additive init
  property `CommandDescriptor<T>.ObserveFailures` in `Runic.Application.Views`,
  which generated Bridges use.

## Leave guards in web Views

- A ReactiveUI interaction guard such as `ReactiveLeaveConfirmation.WithInteraction`
  now reaches the page's mounted web View handler when the shell's Back (or
  another command in the same window) leaves a dirty page, and for a guarded
  window close (`GuardClose`, `RequestCloseAsync`, Runic Desktop's close button).
  Before, only the page's own commands reached the browser; Back and close got the
  .NET fallback or failed with event 1060.
- Requests stay in the window and browser connection that started the departure.
  A command reaches another route's View only while a navigation hook that it
  started runs. A close has no invoking connection and asks only when exactly one
  presentation in the window has the handler mounted, never several. Navigation
  started by .NET code outside a command, and a command or close of another
  window, still need a .NET handler or fail closed.
- ReactiveUI's handler order is unchanged: the latest registered answers first.
  A web View's handler registers when its bridge attaches, after the ViewModel's
  constructor, so a constructor fallback answers only when no View is mounted or
  .NET code starts the departure. A WPF View's `WhenActivated` handler answers
  before both.

## Reload, reconnect and unmount in web Views

- Reloading a page (`location.reload()`) or navigating within it now works in
  WebView2 and Chromium-based browser presentations of Runic Views, including the
  WPF `RunicWebView` child. `DesktopSurface.SubscribeConnectionEvents`, which every
  Views host uses, put the page into WebUI's all-events mode, which cancelled page
  navigations: the reload was dropped and the surface raised neither
  `Disconnected` nor a second `Connected`. Linux/WebKitGTK was not affected.
- Several `SubscribeConnectionEvents` subscriptions on one surface now all receive
  every event, in subscription order; before, the latest one replaced the others,
  including the Views host's own `Disconnected` handler. `WebUiWindow.Bind("")`
  keeps WebUI's all-events semantics.
- `@runic-artifex/views`: after a CS-WebUI WebSocket reconnect, mounted Views are
  mounted again and their browser interaction handlers answer again. Before, .NET
  rejected the remount, because WebUI reuses the connection key: the Views stayed
  unmounted and deactivated, and interactions fell back to the .NET handler. The
  page now mounts each View again in a new browser session. Leases made by older
  copies of the package keep their previous behavior.
- `@runic-artifex/views/mock`: `disconnect()` ends the mounted presentations, and
  a later `Mount` in their browser session answers `disconnected`, as .NET does.
  Tests that relied on Views surviving a mock `disconnect()` remount them.
- Runic Desktop no longer reports an Error `capability-not-admitted` diagnostic
  when a page removed from a navigation region unmounts after .NET released its
  routes; every navigating app printed it to standard error. A call to a
  capability released a moment ago (the last 256) is late: nothing is invoked and
  nothing is reported. A name that was never admitted is still an Error, and the
  message now names the capability (`The presentation capability 'x' is not
  admitted for this session.`). Code, category and severity are unchanged.

## Bridge generation and generated clients

- A command whose generated client member is reserved in a TypeScript object
  type fails the build with `RUNICBRIDGE004` and a suggested name. `NewCommand`
  generated `new(): Promise<…>`, a construct signature, so the TypeScript did
  not compile; `constructor`, `then`, `__proto__`, `toJSON`, `toString` and
  `valueOf` are rejected as well. State properties with these names are
  unchanged.
- Presenting a ViewModel without a View in a content property, ViewModel
  collection or navigation region throws a `NotSupportedException` that names
  the region or slot and the ViewModel type and shows the View to declare,
  instead of "Main contains an unregistered ViewModel type."
- The new `RUNICBRIDGE013` build warning reports a public, concrete ViewModel
  in the application assembly that such a slot admits but that has no View.
  Broad slot types are skipped to avoid false positives: framework types, an
  application-wide base that the owner or a Window ViewModel shares, and a type
  that more than eight ViewModels without a View could fill. Add the View, or
  suppress the warning with `NoWarn` for a type that is never presented there.
  A build that reuses the cached generation repeats it.
- Read-only ViewModel state follows standard MVVM rules: as in WPF, Avalonia or
  MAUI, the C# setter's accessibility decides what any View, including the web
  frontend, may set. Only properties with a public setter get a generated
  `set<Property>` client member, as before, and that member now documents the
  setter it calls. Give status such as `IsDirty` or `Error` a private setter:
  `[ObservableProperty] public partial T X { get; private set; }` for
  CommunityToolkit.Mvvm, or a private setter (`RaiseAndSetIfChanged` or
  `[Reactive]`) for ReactiveUI. A field-based `[ObservableProperty] private T x;`
  generates a public setter, so the web frontend can set it.
- Generated `connect<Name>()` functions accept `{ timeout }`, in milliseconds
  (default 5000). `@runic-artifex/views` exports `BridgeConnectOptions`.
- `ViewRegistry<State["main"]>` accepts nullable region slots in React, Vue,
  Svelte and Angular.
- `RunicViewState.Read` explains how to read non-scalar properties.
- Generated TypeScript documents `long`, `ulong` and `BigInteger` as `bigint`.
  Summaries on partial `[ObservableProperty]` and `[Reactive]` properties appear
  in the generated client
  ([#169](https://github.com/Runic-Artifex/runic-sdk/issues/169)), and
  CommunityToolkit cancel commands are documented as "Cancels the running `x`
  call." instead of copying the Toolkit generator's C# comment.
- Generated-code plumbing in `Runic.Application.Views` and
  `Runic.Application.Views.ReactiveUI[.Reactive]` (`ViewModelBridge<T>`,
  `PropertyDescriptor<T>`, `CommandDescriptor<T>`, `BridgeJson`, `BridgeWire`,
  `ReactiveCommandExecution` and related descriptors) is hidden from
  IntelliSense with `[EditorBrowsable(Never)]`. The API itself is unchanged.
- `Runic.Application.Views` and its Bridge generator recognize CommunityToolkit.Mvvm
  and ReactiveUI through per-library convention modules; the shared contract
  and generator core work only with `ICommand`, `INotifyPropertyChanged`,
  `INotifyDataErrorInfo` and the Runic attributes. Generated bridges, TypeScript
  clients and contract fingerprints are unchanged. General-purpose packages
  (Views and Navigation cores, Platform, Desktop, Assets and tools) stay free
  of ReactiveUI, System.Reactive and CommunityToolkit.Mvvm dependencies, which
  CI now enforces.

## Cancelled web operations are not errors

- `createOperationController` and `createLatestOperationController` treat a
  `cancelled` terminal status as a normal end. The new `cancelled` state becomes
  true, `run()` resolves to `undefined`, and `error` stays undefined; previously
  pressing Cancel published `BridgeError("cancelled")` as `error`. `failed` and
  `timedOut` statuses are still `error`. Starting a run and `reset()` clear
  `cancelled`. A direct `operation.outcome()` call still rejects with
  `BridgeError("cancelled")`.
- Svelte `useOperation` exposes `cancelled`. `@runic-artifex/react` and
  `@runic-artifex/vue` add `useOperation(start, options?)`, and
  `@runic-artifex/angular` adds `injectOperation(start, options?)`, with the same
  operation state, including `cancelled`, and `run`, `cancel` and `reset`.

## Per-window platform services

- `services.AddRunicPlatformServices()` for Runic.Application.Views.Desktop and
  Runic.Application.Views.CsWebUi registers per-window `IWindowPlatformServices`,
  `IFileDialogs`, `ITextClipboard` and `IDesktopFileLauncher` that a ViewModel
  can take in its constructor. On Desktop they bind when the window opens and
  use the Windows, macOS, GTK 3 or GTK 4 (xdg-desktop-portal) provider for the
  running backend; a GTK 4 process never loads the GTK 3 provider. On CS-WebUI
  they report `OwnerUnavailable`.
- New `PlatformServices.ForWindow(DesktopNativeOwner)`,
  `PlatformServices.CurrentProvider` and
  `WindowPlatformServices.Unavailable(reason)`.
- `PickerResult<T>.Selected` deconstructs:
  `is PickerResult<IReadFileLease>.Selected(var lease)`.
- Runic.Application.Views.Desktop now depends on the Runic.Platform.Windows, MacOS,
  Linux, Linux.Gtk4 and Linux.Portal packages, so the `runic-app` template calls
  `AddRunicPlatformServices()` and no longer references
  `Runic.Platform.Linux.Gtk4` or `Runic.Platform.Linux.Portal` directly.
- `AddRunicPlatformServices()` also registers one `IDesktopSettings`
  singleton for the application, which needs no window. On Runic Desktop it is
  created by the new `PlatformServices.CreateSettings()` for the running
  backend; on CS-WebUI it reports `ProviderNotConfigured` until you register an
  `IDesktopSettings` from a platform provider before the call. Existing
  registrations are kept. New `DesktopSettings.Unavailable(reason)`.

## Directory access and native choosers

- The GTK3 file and directory chooser completes when its GTK loop stops while
  the chooser is open, so presentation shutdown no longer waits indefinitely.
  If the loop never runs again, the native dialog is left to the stopped loop.
- `PresentationFiles.OpenDirectoryAsync` always calls the backend's
  `OpenDirectoryAsync`. A custom `IPickerBackend` that implements directory
  selection must return `true` from `SupportsDirectorySelection`, which reports
  the `platform.directories.open` capability. An undeclared backend that returns a
  selection now throws `InvalidOperationException` instead of being reported
  unavailable without explanation.
- `IDirectoryLease.DisplayName` names a filesystem root by the root path, such
  as `/` or `C:\`, instead of returning an empty string.
- Presentation close releases directory leases. Preview.6 suggested retaining a
  lease in the presentation scope; when accepted application work, including
  recovery, uses the lease after the window closes, drain that work before
  stopping the `PresentationLifetime`, or dispose the lease at the end of the work.
- Linux saves chosen with the xdg-desktop-portal dialog (the GTK 4 default) or
  the GTK 3 dialog are atomic, including inside Flatpak through the document
  portal, and `platform.files.save` reports available on Linux. The commit uses
  `renameat2` and never falls back to copying: a cross-device or busy target is
  reported as not committed, and a new file whose name appeared since selection
  is a `Conflict`. A read-only or revoked document grant returns
  `Unavailable(AtomicReplaceUnavailable)` before anything changes. In every
  refusal the file is unchanged; offer Save As.
- Saving to a new file name on Linux and macOS failed with `IoError`; it now
  succeeds.
- New `NativeFileSelection.Location` and `NativeFileLocation` let a custom
  native picker provider say whether a selection is a host path or a document
  portal path.

## Accepted work and callback lifetime

- `AcceptedWorkScope` drain and disposal started from the scope's own accepted
  work, such as "Save and close" disposing its model, wait for all other
  accepted work but no longer for the calling task, which previously hung.
- Faults of accepted tasks are logged once instead of being silently observed:
  event 1013 at Error, or 1014 at Debug for a declared `RunicFailureException`.
  Pass a logger with `new AcceptedWorkScope(logger)`; without one, entries go
  to `Trace`. Drain still completes without throwing.
- The Runic.Desktop README and `RegisterCapability` documentation describe
  callback concurrency: async capability handlers hold a connection's turn only
  until their first incomplete await, can overlap other handlers and connection
  events, and can reply out of order. `Disconnected` follows every accepted
  call. Serialize handlers that need exclusive access, for example with a
  `SemaphoreSlim`.

## Desktop shutdown and windows

- One Window declaration and one open API for every host. Declare a Window as
  `public sealed partial class MainWindow : RunicWindow<MainViewModel>;`, with
  CommunityToolkit.Mvvm or ReactiveUI ViewModels. Open it with
  `await host.OpenWindowAsync<MainWindow>(options)` inside
  `RunicDesktopHost.Run(provider, async host => ...)` or
  `RunicCsWebUiHost.Run(provider, async host => ...)`, then
  `await window.WaitForCloseAsync()`. Both hosts implement `IRunicWindowHost`
  and take `RunicWindowOptions`; `RunicDesktopHost` adds `SurfaceOptions` and
  `WindowOptions`.
- `host.ValidateWindow<TWindow>(options)` returns a
  `RunicWindowValidationResult` on every host instead of throwing. Opening a
  misconfigured Window throws `RunicWindowConfigurationException` with its
  `Diagnostics`; on Desktop, the `DesktopConfigurationException` is the
  `InnerException`.
- Log event 1050 is now `WindowRegistrationMissing` on every host: a Window's
  generated Bridge is not registered when `ValidateWindow` or `OpenWindowAsync`
  runs. Desktop event 2001 is removed.
- Runic Desktop's window lifecycle is async-only: `DesktopWindow.WaitForCloseAsync`
  replaces `WaitForClose`, `FocusAsync`, `MinimizeAsync` and
  `ToggleMaximizedAsync` return `ValueTask`, `CloseAsync` takes a
  `CancellationToken`, and `MoveAsync(int, int)` and the `X`/`Y` window options
  are signed `int`: negative values are left of or above the primary screen's
  origin.
- `IBridgeWindow.CloseAsync(TimeSpan, CancellationToken)` and
  `WaitForCloseAsync(CancellationToken)` are available on every host's window.
- `DesktopEventLoop.Run(options, application)`, and `RunicDesktopHost.Run` on top
  of it, handle Ctrl+C, SIGTERM and
  SIGHUP (on Windows, closing the console window) like closing the last window
  ([#128](https://github.com/Runic-Artifex/runic-sdk/issues/128)). The first
  signal cancels the new `DesktopHost.ShutdownRequested` token and closes every
  open window without close confirmation; `WaitForCloseAsync` completes, the
  application releases its work and returns its exit code, and the host is
  disposed before the GTK, AppKit or plain loop ends. Previously the process
  ended without disposing the host or an installed-browser fallback profile.
- A second Ctrl+C, a second or more after the first signal, ends the process
  at once; copies of the signal forwarded by `dotnet run`, `dotnet watch` or
  `dotnet runic dev` do not.
- Set `DesktopHostOptions.HandleShutdownSignals = false` to keep the default
  signal handling, for example when the application registers its own handlers.
- Runic.Desktop reports `close-confirmation-unavailable`. When
  `ConfirmCloseAsync` is set with an explicit browser, opening fails with a
  `DesktopException` (`CapabilityDenied`) instead of an `ArgumentException`.
  With `EmbeddedThenBrowser`, a browser fallback opens without confirmation and
  reports a Warning.
- A `DesktopContent.Directory` entry is checked before a window waits for it.
  An entry with a `?query` or `#hash` is rejected when constructed with a
  `DesktopConfigurationException` (`content-entry-invalid`), and
  `CreateSurfaceAsync` with an entry that does not exist throws
  `DesktopConfigurationException` (`content-entry-not-found`), naming the entry
  and the known HTML pages. Both previously produced a window that timed out.
- New `IRunicWindowService` and `services.AddRunicWindowService()`: a ViewModel
  opens another Window from its constructor-injected service. The service is a
  singleton that works on Runic Desktop and CS-WebUI, and it releases each Window
  it opened when that Window closes; a release that throws is logged as event
  1051 `WindowReleaseFailed`. `examples/multi-window` shows opening Windows from
  a ViewModel, state shared across Windows and app-owned settings.
- A user close (title-bar button, Alt+F4, window manager) can ask the
  Window's navigation first. `RunicWindow<T>.GuardClose`, or an override of
  `protected virtual CanCloseAsync(CancellationToken)`, runs the departure guards
  of the Window's `NavigationRegion<T>` properties before the window closes; a
  veto or a failure keeps it open. Failures are logged as event 1052
  `WindowCloseGuardFailed`.
- `RunicWindow<T>.RequestCloseAsync(CancellationToken)` (also on `IRunicWindow`)
  closes a Window from code as its close button does and returns whether it
  closed. `CloseAsync`, disposal and host shutdown still close without asking.
- On Runic Desktop an embedded window honours `GuardClose` through
  `ConfirmCloseAsync`, ahead of a configured one, and `RequestCloseAsync` shares
  its native close decision. A browser presentation, or a custom host without
  `CloseConfirmation`, opens a `GuardClose` Window unguarded for the user's close
  and logs event 1053 `WindowCloseGuardUnavailable`. CS-WebUI can't keep a
  browser window open, so it always does the same; its `RequestCloseAsync`
  still asks `CanCloseAsync`. Host adapters get
  `RunicWindowOpening<T>.CloseGuard`, `ReportCloseGuardUnavailable` and
  `UseCloseRequest`.

## dotnet-runic

- `dotnet runic dev` prepares a development document for every HTML page in
  the Vite build input, not only `index.html`, so a second window with its own
  page loads in `dev` as it does after build and publish. You no longer need
  `RunicApplicationFrontendDevServerDocument` for that; when set, it still
  overrides the list. Angular projects keep `index.html`.
- A window page that is a build input but has no file stops `dev` before the
  build with `RAPPDEV1009: Window entry not found: '<page>'`, instead of a
  window that fails with `presentation-connection-timeout`.
- `dev` now reads the build inputs with Node.js (or Bun for a Bun frontend)
  before the build; a Vite configuration that cannot be resolved for
  `vite build` reports `RAPPDEV1010`.
- `dev` resolves `webui.js` and the host client scripts from the web root in
  nested pages such as `pages/settings.html`.
- `dev` stops the Window gracefully on Ctrl+C or SIGTERM and before a restart:
  the app gets SIGTERM (Ctrl+C on Windows) and up to 5 seconds to close its
  windows and finish its work before it is killed. `dev` sets
  `DOTNET_WATCH_PROCESS_CLEANUP_TIMEOUT_MS=5000` unless you set it, so
  `dotnet watch` gives the same grace when a C# edit restarts the app. `dev` no
  longer reports `Exited with error code 143` when `dotnet watch` restarts the
  application or `dev` stops it.
- `dev --no-restore` no longer requires `node_modules` for a frontend without
  dependencies.
- `doctor` and `size` both accept `--rid`, `--runtime` and `-r`, and both accept
  `--aot` and `--no-aot`. `doctor --rid <rid> --no-aot` checks a publish with
  `PublishAot=false`.
- `doctor --output json` exits 1 when a check fails: `--fail-on` defaults to
  `fail` in both output modes. Pass `--fail-on never` to always receive the
  payload.
- The new `doctor` check `platform-services` names the selected platform
  provider and, on Linux, checks for the D-Bus session bus and
  xdg-desktop-portal. `gtk4-profile` no longer asks `Runic.Application.Views.Desktop`
  projects to reference the GTK 4 provider packages.

## Build targets and Vite plugin

- Generator and frontend command failures are no longer wrapped in `MSB3073`.
  Canonical errors (generator, `tsc`) are logged once with their code and
  location; a failure without one gets a single `RUNICBRIDGE001` (generator) or
  the new `RUNICBRIDGE016` (frontend install or build).
- The frontend install also runs when `package.json` or the lock file changed
  since the last install (stamp in `obj/`), and a `package.json` without
  dependencies no longer fails because no `node_modules` was created.
- A test project (`IsTestProject`, set by TUnit and Microsoft.NET.Test.Sdk)
  that references a Runic application no longer runs Bridge generation or fails
  with `RUNICBRIDGE006` when it declares no Window or View and has no frontend.
  It uses the app's generated Bridges.
- `@runic-artifex/vite-plugin-runic`: `vite build` no longer warns that
  `webui.js` or the host client script "can't be bundled without
  type=module", and host scripts resolve from the web root in nested pages.

## Templates, Runic.Create and testing

- `dotnet new runic-app` and `dnx Runic.Create` now default to the Runic Desktop
  host (a native window) and ReactiveUI 26 ViewModels. CS-WebUI
  (`--host cswebui`, which opens a browser window, best effort) and
  CommunityToolkit.Mvvm (`--view-models toolkit`) remain supported; pass them
  explicitly to keep the previous defaults.
- The ReactiveUI option is described as "ReactiveUI 26 Primitives", and its
  ViewModels create commands without a scheduler.
- Generated apps declare their Window as a `RunicWindow<T>`, and `Program.cs`
  opens it with `OpenWindowAsync` inside `RunicDesktopHost.Run` or
  `RunicCsWebUiHost.Run`, so the same application code runs on both hosts.
- `dotnet new runic-app --tests` (and `dnx Runic.Create -- MyApp --tests`, or
  answering yes in the guided creator) adds `MyApp.Tests`, a TUnit test project
  that drives the Window's ViewModels and generated Bridges headlessly with
  `Runic.Application.Testing`. Run it with `dotnet test --project MyApp.Tests`.
  The test project builds the app without its frontend, and a `global.json`
  selects Microsoft.Testing.Platform for `dotnet test`.
- Generated apps register their ViewModels and Views in
  `WorkspaceServices.AddWorkspace()` (`WorkspaceServices.cs`), which
  `Program.cs` and the tests share. The Window exposes `ViewModel`, and the
  Svelte frontend includes `svelte.config.js`.
- The template's Counter shows read-only state (`Count`, private setter) beside
  a two-way bound form field (`Step`, public setter) in every frontend and MVVM
  flavor.
- The `runic-app` template builds as a Windows GUI application (`WinExe`) for
  `win-*` runtime identifiers, or without a runtime identifier on a Windows host,
  so no console window opens next to the app. Other builds are unchanged.
  Diagnostics written to standard error are not visible on Windows. The template
  README describes the publish output (the executable and `www`, without debug
  symbols) and links the "Ship a Desktop application" guide instead of asking
  you to distribute the whole folder.
- New `RunicWindowTestHost.Create<TViewModel>(IServiceProvider services, RunicWindowTestHostOptions? options = null)`
  builds a test host from the window's service scope: the root ViewModel, its
  generated Bridge, and the registered View locator, model context and logger
  factory, replacing four `GetRequiredService` calls. The
  `Runic.Application.Testing` README documents skipping the frontend build in
  test projects (`AdditionalProperties="RunicApplicationFrontendBuildEnabled=false"` on
  the app reference).
- In `Runic.Create`, `--output` / `-o` choose the destination directory, as with
  `dotnet new`; `--directory` keeps working as a hidden alias. The creator's
  output format is selected with `--format human|json`.

## Upgrading

This preview renames packages, merges the Window APIs of the two hosts and
renames build properties. The
[rename table](https://github.com/Runic-Artifex/runic-sdk/blob/v0.7.0-preview.7/packages/dotnet/Runic.Application.Views/README.md#moved-and-renamed-since-070-preview6)
lists every change.

- Replace the renamed packages in `PackageReference` and
  `Directory.Packages.props`. Namespaces are unchanged; the old package IDs get
  no further releases.

  | Old package | New package |
  | --- | --- |
  | `Runic.Application` | `Runic.Application.Views` |
  | `Runic.Application.CsWebUi` | `Runic.Application.Views.CsWebUi` |
  | `Runic.Application.Desktop` | `Runic.Application.Views.Desktop` |
  | `Runic.Application.Wpf` | `Runic.Application.Views.Wpf` |
  | `Runic.Application.ReactiveUI` | `Runic.Application.Views.ReactiveUI` |
  | `Runic.Application.ReactiveUI.Reactive` | `Runic.Application.Views.ReactiveUI.Reactive` |

- The Desktop and WPF assemblies are now `Runic.Application.Views.Desktop.dll`
  and `Runic.Application.Views.Wpf.dll`. Change XAML `xmlns` declarations to
  `assembly=Runic.Application.Views.Wpf`, and logging filters for the Desktop
  transport to the `Runic.Application.Views.Desktop` category.
- Rename `RunicBridge*` build properties, `RunicViewsWindowProject` and
  `RunicBridgeFrontendInput` items to their `RunicApplicationFrontend*` names,
  for example `RunicBridgeFrontendDir` to `RunicApplicationFrontendDirectory`
  and `RunicBridgeBuildFrontend` to `RunicApplicationFrontendBuildEnabled`. The
  old names still work in this preview and report warning `RUNICBRIDGE017` with
  the new name; they are removed in the next preview.
- In Angular, import `ViewOutlet` instead of `RunicViewOutlet`, as in React,
  Vue and Svelte. `RunicViewOutlet` remains a deprecated alias until the next
  preview; the `<runic-view-outlet>` element is unchanged.
- Derive every Window from `RunicWindow<T>` and open it with
  `host.OpenWindowAsync<TWindow>()`:

  | Before | Now |
  | --- | --- |
  | `CsWebUiWindow<T>`, `ReactiveRunicWindow<T>` | `RunicWindow<T>` (Views keep `ReactiveRunicView<T>`) |
  | `RunicWindow<T>(T dataContext)` constructor | `RunicWindow<T>()`; `OpenWindowAsync` assigns the ViewModel |
  | `provider.OpenWindow<TWindow, TViewModel>(...)`, `WebUiApplication.Wait()` | `RunicCsWebUiHost.Run(provider, async host => ...)` and `OpenWindowAsync` |
  | `DesktopEventLoop.Run(...)` around `provider.OpenDesktopWindowAsync(...)` | `RunicDesktopHost.Run(provider, options, async host => ...)` and `OpenWindowAsync` |
  | `ValidateWindow<TViewModel>()`, `ValidateDesktopWindow<TViewModel>(...)` | `host.ValidateWindow<TWindow>(options)`, which returns `RunicWindowValidationResult` |
  | `CsWebUiConfigurationException` | `RunicWindowConfigurationException` (`Diagnostics`) |
  | `DesktopWindow.WaitForClose()`, `window.Presentation.WaitForClose()` | `await window.WaitForCloseAsync()` |
  | Log events 1050 `CsWebUiWindowRegistrationMissing`, 2001 `DesktopWindowRegistrationMissing` | Event 1050 `WindowRegistrationMissing` |

- Await `DesktopWindow.FocusAsync`, `MinimizeAsync` and `ToggleMaximizedAsync`
  as `ValueTask`, and pass `int` to `MoveAsync` and the `X`/`Y` window options.
- Replace `using Runic.Navigation.ReactiveUI;` (or `.Reactive`) with
  `using Runic.Application.Views.ReactiveUI;` (or `.Reactive`) for
  `AddRunicReactiveModelContext()` and the scheduler provider. Add a
  `Runic.Navigation.ReactiveUI` reference if you use region observables or
  `CreateBackCommand`.
- Create ReactiveUI commands without a scheduler after
  `AddRunicReactiveModelContext()`. A ViewModel that injected `ISequencer` only
  to pass it to its commands no longer needs it.
- `CreateBackCommand` (experimental) now produces a `NavigationOutcome` instead
  of a `NavigationResult<T>`, and its scheduler parameter is optional.
- Scripts that run `dotnet runic doctor --output json` and expect exit code 0
  with failed checks pass `--fail-on never`.
- Code that detected a user Cancel through an operation controller's `error`
  reads `cancelled` instead.
- Rename a command whose client member would be `new`, `constructor`, `then`,
  `__proto__`, `toJSON`, `toString` or `valueOf`, for example `NewCommand` to
  `CreateCommand`; the build now fails with `RUNICBRIDGE004`.
- Don't block a model-context turn on async work (`.Result`, `.Wait()`): like a
  UI thread, it now deadlocks because continuations queue as turns.
- Code that caught `ArgumentException` when `ConfirmCloseAsync` was set with an
  explicit browser catches `DesktopException` (`CapabilityDenied`).
- Use `--output` or `-o` for the `Runic.Create` destination and `--format` for
  its output format. Preview.6 creator documentation used `--directory`, which
  remains a hidden alias.
- A project that set only `RunicApplicationFrontendDirectory` (formerly
  `RunicBridgeFrontendDir`) finds its generated client under
  `<RunicApplicationFrontendDirectory>/src/generated`; set
  `RunicApplicationFrontendGeneratedDirectory` to keep the previous location.
- Code that reads `RunicModelContext.Closed` directly suppresses `RUNICNAV001`.
- A ViewModel that captured its `NavigationEntryContext` in `InitializeAsync`
  only to complete or dismiss the entry can take the context in its constructor
  instead (experimental). Nothing has to change for it to keep working.
- A `GuardClose` Window that opens on a browser presentation or CS-WebUI is not
  guarded and logs event 1053; check the log if you rely on the guard there.
- Unexpected exceptions of bridged ReactiveUI commands are now logged as event
  1042 `ReactiveCommandFailed` (Error) without a subscription. An app that
  already logs them in a `ThrownExceptions` handler can drop that handler.
  `ObserveBridgeExceptions` on a command still replaces the Bridge's logging.
- `CreateCompleteCommand`, `CreateDismissCommand` and `CreateCloseCommand` are
  disposed when their entry retires. Remove `DisposeWith` calls for them; don't
  use such a command after its entry ended.
- A ReactiveUI interaction guard now asks the page's mounted web View on the
  shell's Back and on a guarded window close. If a constructor fallback kept
  edits on Back or close, the page asks instead while it is mounted.
- Code and tests that depended on a reload being dropped or on the latest
  `SubscribeConnectionEvents` replacing earlier ones see the corrected behavior.
  A test using the `@runic-artifex/views/mock` `disconnect()` expects mounted
  Views to end and to remount in a new session.
- Anything that filtered the `capability-not-admitted` diagnostic to hide the
  noise from removed pages can drop the filter; a late call is no longer reported.
