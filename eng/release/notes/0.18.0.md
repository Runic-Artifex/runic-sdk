# Runic SDK 0.18.0

Install matching `0.18.0` packages from NuGet and npm;
`Runic.Application.Views.CsWebUi` is `0.18.0-preview.1`.
Tested with Runic Translations 0.10.0 and Runic Command Line 0.12.0.

0.18.0 lets a hosted application become part of its host's own window. A host
can show a guest application's Window in a region of one of its pages instead of
in a window of its own (**region mode**, #866): an installer shows a separate
check tool as a step of its wizard, with its header and footer in place, one
taskbar entry and Tab moving in and out of the check. For applications of one
vendor, a region can show the guest's Views as a component in the host page's
own document (**trusted component mode**). An elevated host can now host an
elevated guest of the same user (#865), which such installers need. Runic's own
page text is available in German (#881), Desktop windows gain exact bounds and a
run-time minimum size (#864), a ViewModel's `PropertyChanged` no longer reads
every bridged getter (#887), and a collection replaced under another member's
notification keeps publishing its changes (#891).

Hosted applications, regions and components stay experimental
([`RUNICDESK103`](https://github.com/Runic-Artifex/runic-sdk/blob/v0.18.0/docs/experimental.md#RUNICDESK103),
and the npm packages' new `./experimental` entries). 0.18.0 moves the release
train to Runic Command Line 0.12.0 and Runic Translations 0.10.0, raises the
native server's C ABI to 5 and changes some behaviour and wording;
[Upgrading from 0.17](#upgrading-from-017) lists every such change, and the
[migration guide](https://github.com/Runic-Artifex/runic-sdk/blob/v0.18.0/docs/migration-1.0.md#from-017-to-018)
collects them. No public .NET API was removed or changed.

## Upgrading from 0.17

Update every Runic NuGet and npm package to 0.18.0 together and rebuild, so that
the generated clients are regenerated.

### Breaking changes

- **Runic Translations 0.10 and Runic Command Line 0.12.**
  `Runic.Application.Views.Translations` requires Runic Translations
  `[0.10.0, 0.11.0)`, so an application that uses it moves every Translations
  package to 0.10.0; NuGet reports a 0.9.x Translations package outside that
  range.
  `dotnet-runic`, `Runic.Create` and the `Runic.Assets` packer bundle Runic
  Command Line 0.12.0, and an application that uses Runic Command Line itself
  moves to 0.12.0 (#893).
- **The native presentation server's C ABI is 5.** `Runic.Desktop` 0.18.0 binds
  only ABI 5; a `Runic.Desktop.NativeServer` of another version fails at the
  first window with `native-server-unavailable`, naming both versions. Use the
  same version of both, as always. An application that links the server itself
  (`RunicDesktopNativeServerLinkage` `Application`, 0.17.1) depends on the
  `runic-server` crate at the `v0.18.0` tag.

### Behaviour and output changes

- **`describeBridgeError` shows Runic's sentence** for a `BridgeError`'s reason or
  kind and never its `message`, which is framework diagnostic text (#883). For
  example `rejected` with `invalid-input` reads "The input is not valid." and
  `failed` without a reason "The request failed."; `busy` reads like `capacity`.
  Application text still reaches the page through `FieldError` and other
  `Error`s, and `configureRunicText` replaces Runic's wording. An empty
  `integer` field's message is now "Enter a whole number."
- **GTK 4 windows** show `DesktopPlatformTexts.LoadingTitle` ("Loading…") until
  the page has a title, as WebView2 does, instead of "Runic Desktop" (#883).
- **A `PropertyChanged` that names a bridged member refreshes only that member**
  (#887). Each bridged getter is read about twice per publication unit instead of
  on every notification; a getter with side effects runs less often. Published
  frames are unchanged.
- **A collection or observed sub-object replaced under another member's
  notification** (or under a name the Bridge does not bridge) now publishes the
  later changes of the new instance; before, they were missed until its own
  member or every member was notified (#891). In a unit that follows a named
  notification, a list without keys is read once more (1 → 2) and an observed
  sub-object once more (2 → 3).
- **Hosts and guests list `region/1`** (and `region-component/1` where allowed)
  in their `hello`, and the Views protocol's `hosted-regions/1` is offered. A
  test that compared a host's or guest's `hello` exactly needs the new features.
- **Generated union encoders are typed** (#863): regenerate generated clients and
  mock doubles. Under `strict`, a union with list or dictionary members now
  compiles. Runtime behaviour does not change.
- **`dotnet runic doctor`** has a new `dotnet-runtime` check that requires the
  .NET 10 runtime, and `dotnet runic dev` stops with `RAPPDEV1013` before it
  starts an application whose runtime is missing (#874).

## Elevated hosts and guests (#865, experimental)

An elevated host may host an elevated guest of the same user, when both opt in:
the host sets `RunicGuestStartInfo.AllowElevatedGuest` and the guest
`RunicGuestOptions.AllowElevatedHost`. The guest accepts only its verified
parent, running elevated as the same user (Windows: an elevated token or High
integrity; Linux and macOS: uid 0); otherwise it refuses with `guest-elevated`,
`guest-elevated-host-not-elevated` or `guest-other-user`. An unelevated host
cannot allow it (`host-not-elevated`), and an elevated guest is started only from
a fully qualified path. Event 2025 records the accepted pair.
`RunicTestHostOptions.AllowElevatedGuest` plays an elevated host in tests.

**Elevated-peer admission**: a guest of the elevated pair admits connections to
every listener, its channel, page surfaces and region frame and component
surfaces, only from loopback peers that run elevated, checked before a
connection is read (Windows: the connection's owning process and its token;
Linux: the socket's owner, uid 0). A refused peer is closed without a response
(event 2029, `DesktopHostedPeerRefused`). macOS has no peer lookup: an elevated
guest refuses regions and components there. On Windows, CI showed that
WebView2 loads an elevated guest's page and region frames under this check.

See [Elevated hosts and guests](https://github.com/Runic-Artifex/runic-sdk/blob/v0.18.0/docs/security.md#elevated-hosts-and-guests).

## Region mode (#866, experimental)

A host's policy shows a guest's Window in a region of a host page with
`RunicHostedWindowDecision.Embed(region)` (`RunicHostedWindowRequest.CanEmbed`);
the page declares the region with `<runic-hosted-region name="…">`. The guest's
page loads in a sandboxed frame from the guest's own loopback origin, so the
engine lays it out and Tab moves in and out of it. Start with the
[hosted regions guide](https://github.com/Runic-Artifex/runic-sdk/blob/v0.18.0/docs/hosted-regions.md)
and the
[hosted region example](https://github.com/Runic-Artifex/runic-sdk/blob/v0.18.0/examples/hosted-region/README.md).

- **Protocol** (#870): `region/1` in the host protocol (`region-attach`,
  `region-detach`, `region-bounds`, `region-focus`, `region-page`, `set-title`,
  the region presentation of a window) and `hosted-regions/1` in the Views
  protocol, with conformance scenarios and threats T19–T23.
- **Guest** (#872): frame admission with a one-time frame launch code and a
  frame token in the address's fragment, one page at a time, no cookies,
  `frame-ancestors` naming only the host page's origin. Frames listen on the
  loopback family the host page does not use (`[::1]` for a page on
  `127.0.0.1`), so no host cookie reaches the guest; an embedded host may let the
  guest fall back to the same site (event 2027). `RunicTestHost` plays a region
  host (`EmbedWindow`, `AttachRegionAsync`, …).
- **Host** (#876): `Embed`, `RunicHostedRegion` with its states and events,
  `RunicHostedRegionOptions` (`Permissions`, heights, `ReattachOnReload`,
  `FocusOnAttach`), attach, detach and re-attach by name, `AsDepartureGuard()` for
  a wizard's Back and Next, presentation requests mapped for a region, dialogs and
  context menus of the host window, and the focus rule: a guest never takes the
  focus from the host page. A refused or failed attach is event 2026, a failure
  while handling a region event 2028.
- **Element and wrappers** (#873): `<runic-hosted-region>` in
  `@runic-artifex/views/experimental`, with content per state (`slot="waiting"`,
  `ended`, … and `fallback`), size, visibility and focus reports, and
  `RunicHostedRegion` components in the React, Vue, Svelte and Angular packages'
  new `./experimental` entries. These are the first `./experimental` npm entries
  since 0.10.0.
- **Browser hosts** (#877): a serve-only application shows guests in regions
  of its pages in the user's browser, with reduced features
  (`RunicHostedWindowRequest.CanOpenWindow` is `false`). Its frames are always
  cross-site, and an elevated guest refuses its pages.
- **Engines** (#878): drops onto a region's frame go to the guest
  (`files-dropped`) on WebView2, WKWebView and GTK 3; the frame's camera and
  microphone follow the region's permissions (WebKitGTK denies them); a shortcut
  the guest's page leaves unhandled runs the host window's menu item (WebView2);
  the end of a frame's content process detaches with `crashed`. Launch codes and
  frame tokens are redacted from logged page errors. `Runic.Desktop.Gtk4`'s
  window routes none of this.
- **Example and guide** (#895): the hosted region example (an installer and a
  check tool, with an elevated variant), the hosted regions guide and its
  troubleshooting. `<runic-hosted-region>` now styles its shadow root with a
  constructed stylesheet, so a host page's policy without `'unsafe-inline'`
  styles no longer shrinks the frame to an iframe's default size.

## Trusted component mode (#866, experimental)

A region can show a guest's Views as a component in the host page's own
document, with the page's theme and layout and without a frame boundary. Host
page and guest code then share one JavaScript realm, so both sides opt in:
`RunicGuestOptions.AllowComponentEmbedding` in the guest and
`RunicHostedWindowDecision.EmbedComponent` (`CanEmbedComponent`) in the host's
policy. See the
[hosted components example](https://github.com/Runic-Artifex/runic-sdk/blob/v0.18.0/examples/hosted-components/README.md)
and
[Components in a host page](https://github.com/Runic-Artifex/runic-sdk/blob/v0.18.0/docs/security.md#components-in-a-host-page).

- **Instance-scoped page runtime** (#871): the Views runtime's page-wide
  state belongs to a Runic instance (`createRunicInstance`, `instance.run`); the
  page instance keeps it where it was, so pages are unchanged.
- **Component build** (#875): `runic({ component: { entry } })` in
  `@runic-artifex/vite-plugin-runic` builds `_runic_component/`, an ES module that
  defines the guest's element with its CSS as constructable stylesheets, and
  `@runic-artifex/views/component` (`defineRunicComponent`, `RunicComponentMount`).
  Tags are `<name>-<build hash>` in every engine. Scoped custom element
  registries would let components keep plain tag names: WebView2 supports them
  (CI on win-x64 and win-arm64), but WebKitGTK 2.54 does not, so Runic does not
  use them yet.
- **Protocol and admission** (#879): `region-component/1`; a component token
  per attach, admitted only with the host page's origin as `Origin` and as the
  WebSocket subprotocol; the component build, blobs and uploads served with CORS
  to that origin only. Components of an embedded host are served from
  `127.0.0.1`, so the host page's policy needs `script-src … http://127.0.0.1:*`
  and `connect-src … ws://127.0.0.1:*`; a browser host's components come from
  `[::1]` (`127.0.0.1` when the page itself is on `[::1]`).
  `RunicTestHost.AttachComponentAsync` tests it. An elevated guest offers
  component mode under elevated-peer admission, except on macOS.

## Window building blocks (#864)

- `DesktopWindowState.Bounds`, `VisibleBounds` and `IsSnapped`,
  `DesktopWindow.SetBoundsAsync` (one native move and resize) and
  `SetMinimumSizeAsync`, `DesktopWindowBounds` and `DesktopWindowEdge`, with
  `DesktopWindowCapabilities.Bounds` and `MinimumSize` (#892). These APIs are
  stable. On Wayland `SetBoundsAsync` sets only the size and a position fails
  with `window-position-unavailable`; `IsSnapped` is best effort on macOS and
  where Windows lacks `IsWindowArranged`.
- Each window's surface has a second connection slot for a side panel (#885).
  It is groundwork for the side panel that 0.19 brings and has no public API.

## Runic's own text in German (#881)

The `runic-views` catalog covers the sentences of `describeBridgeError`, the key
names of `formatShortcut` and the GTK 4 loading title, in English and German
(#883). `configureRunicText` installs a page hook, and
`@runic-artifex/views-translations`' `configureRunicViewsText()` installs both
hooks. The German text of the 0.18 train was reviewed (#886).

## Smaller changes

- **.NET 11 SDK** (#874): `dotnet runic doctor` accepts the .NET 11 SDK (certified:
  11.0.100) for `net10.0` applications, and its new `dotnet-runtime` check
  requires the .NET 10 runtime they run on; `dotnet runic dev` reports a missing
  runtime before it starts the application (`RAPPDEV1013`), and on Linux and
  macOS stops when the SDK 11 `dotnet` command that started it ends.
- **Typed union encoders** (#863, #882).
- **Named `PropertyChanged` refresh** (#887, #890) and **replaced collections
  re-subscribed** (#891, #894), see [Upgrading from 0.17](#upgrading-from-017).
- **Command Line 0.12 and Translations 0.10** (#893): dotnet-runic, Runic.Create
  and the Runic.Assets packer bundle Command Line 0.12.0;
  `Runic.Application.Views.Translations` depends on Translations 0.10.0.
- **Train compatibility gate** (#884, #889): `train-compat.yml` checks Runic
  Command Line, Runic Translations and Runic SDK candidates together before
  publication, and Publish preview runs it before runic-sdk publishes.

## Known issues

- Assistive-technology behaviour of hosted regions (NVDA, Narrator, VoiceOver)
  was not checked manually for 0.18.0. Automated checks cover layout, focus and
  Tab order, not how a screen reader reads a guest's page inside a region.
- `Runic.Desktop.Gtk4`'s window routes nothing of a region's frame: drops onto it
  are discarded.
- On macOS an elevated guest cannot be shown in a region or as a component.
