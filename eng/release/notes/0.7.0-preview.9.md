# Runic SDK 0.7.0-preview.9

Install matching `0.7.0-preview.9` packages from NuGet and npm. Command Line
versions remain independent of this SDK.

## Content and navigation

- Retiring owned navigation content with nested Views no longer deadlocks when
  the browser unmounts its Views at the same time
  ([#245](https://github.com/Runic-Artifex/runic-sdk/issues/245)). A
  `WindowContentSession.Forget` outside model turns, as a navigator's
  retirement calls it, held a View attachment's lock while its bridges waited
  for a model turn, and the browser's unmount waited in a model turn for that
  lock. The application froze with an empty page area. Applications that call
  `Forget` inside a model turn to avoid the freeze can return to calling it off
  turn, as `INavigationPresentation.Forget` is documented.

## Views

- A command that replaces or leaves its own page in a navigation region, such
  as a page's Back, Close or Open details command, no longer rejects with
  `BridgeError { kind: "failed", message: "The Bridge returned no state." }`
  when .NET released the page's View before the reply
  ([#246](https://github.com/Runic-Artifex/runic-sdk/issues/246)). .NET now
  replies `ok` with `released: true` and no state, and the generated client
  resolves the call with the last state it accepted. A failed call keeps its
  error kind. A snapshot read of a released View replies `disconnected`.
- A late call of a route that Runic Desktop released shortly before, such as
  the snapshot read of a page that just left its region, is answered with the
  same `disconnected` envelope CS-WebUI sends for an unbound route, instead of
  an empty reply that the client reported as `failed` with "The Bridge returned
  an invalid response." The client reports that envelope as `disconnected` on
  every route, including `Can{Command}` and `Start{Command}`, and an operation
  start on a released View is `disconnected` as well. A capability that was
  never admitted still replies empty and is reported as an error. Applications
  that ignored `failed` diagnostics whose message starts with "The Bridge
  returned " for these cases can drop that filter.

## Logging

- An application that registers logging, for example
  `services.AddLogging(logging => logging.AddSerilog(...))`, now receives every
  Runic runtime message through it
  ([#249](https://github.com/Runic-Artifex/runic-sdk/issues/249)).
  `RunicDesktopHost.Run` passes the registered `ILoggerFactory` to the Desktop
  host when `DesktopHostOptions.LoggerFactory` is not set, so shutdown
  requests, failed close confirmations, configuration diagnostics, stalled
  browser launches and expired Bridge handshakes no longer go to
  `System.Diagnostics.Trace`. The WPF `RunicViewHost` and `WpfBridgeView`
  (events 1110-1114), Hot Reload (1100-1102), an undeletable browser profile
  (3008) and a failing `DiagnosticSink` (3009) log through it too. Without a
  registered factory, Runic still writes these messages to `Trace`.

## Tools

- `dotnet runic doctor` checks every Views host adapter the project references
  ([#241](https://github.com/Runic-Artifex/runic-sdk/issues/241)). Before, a
  project that referenced both `Runic.Application.Views.CsWebUi` and
  `Runic.Application.Views.Desktop` got only the CS-WebUI checks, and doctor
  could report every check as passing on a Linux machine without WebKitGTK. The
  new `views-hosts` check names each host doctor found and the checks that
  cover it. The new `desktop-runtime` check warns when this machine lacks
  Runic Desktop's embedded window runtime: `libgtk-3.so.0` and
  `libwebkit2gtk-4.1.so.0` on Linux, or the WebView2 Runtime on Windows. The
  GTK 4 profile keeps its `gtk4-profile` check. A project that references
  `Runic.Application.Views.Wpf` gets a `wpf-runtime` check. With both hosts,
  `platform-services` checks Runic Desktop's providers. With `--rid`, the
  target checks follow the primary host (CS-WebUI, then Runic Desktop, then
  WPF), doctor still probes the other hosts when the target has this machine's
  operating system, and `views-hosts` warns about a host that no check covers.
  A project that gets its adapter only through another package or project is
  reported as referencing a host indirectly.
- The new checks warn and never fail, so the default `--fail-on fail` keeps
  the exit code and the success of the JSON envelope of earlier releases. With `--fail-on warn`,
  doctor now fails, exiting 1 with a failed JSON envelope, on a machine without
  a referenced host's runtime, such as a headless CI image without WebKitGTK,
  and for a project without a Runic Views host. To keep the earlier result in
  such a job, run it with `--fail-on fail`, or install the runtime the warning
  names.
- The `runic.application.tool.doctor/1` JSON payload has a new `hosts` array
  that lists every referenced host (`cswebui`, `desktop` or `wpf`). The
  existing `host` property still names the host the `--rid` checks follow. It
  is now `wpf`, instead of `unknown`, for a project whose only host is WPF.
  A consumer that checks `host` against a fixed list must accept `wpf`, and a
  consumer that validates the payload with
  `additionalProperties: false` must allow `hosts`.

## Frontend build and hosts

- One frontend build runs on every host
  ([#237](https://github.com/Runic-Artifex/runic-sdk/issues/237)). The host
  packages copy their Views client into `www/` also as `runic-views.js`, so a
  page that loads `webui.js` and `runic-views.js` names no host, and the same
  `dist/` runs on Runic Desktop and CS-WebUI. The `runic-app` templates and the
  First Window examples now load `runic-views.js`, and the template's Vite
  configuration is `runic()` with `base: "./"` on every host:
  `runic({ desktop: true })` is not needed for Views pages. Pages that load
  `runic-cswebui.js` or `runic-desktop-views.js` keep working. A project that
  references both host packages sets the new `RunicApplicationHost` property
  (`desktop` or `cswebui`) to choose the client; without it the build copies
  no `runic-views.js` and reports warning `RUNICBRIDGE019` when a page loads
  it. Applications that keep loading a host's own client are not affected. The frontend build
  receives the host as `RUNIC_APPLICATION_HOST`.
- The frontend build is correct, not only incremental
  ([#236](https://github.com/Runic-Artifex/runic-sdk/issues/236)). A deleted
  `dist/`, or a file missing from it, builds the frontend again. So does a
  change of `RunicApplicationHost`, the build command, `NODE_ENV`, or an
  environment variable named by a new `RunicApplicationFrontendBuildEnvironment`
  item, such as a `VITE_*` variable set in the shell; only a hash of them is
  written to `obj/`. The state is shared by every configuration, because they
  share `dist/`. `RunicApplicationFrontendInput` items are documented as
  the way to add inputs outside the frontend directory, such as shared
  components imported through a Vite alias.
- The copy to `www/` mirrors `dist/`
  ([#236](https://github.com/Runic-Artifex/runic-sdk/issues/236)): files that
  an earlier copy wrote and that the frontend no longer has, such as assets
  with an old hash, are deleted from `www/` on build and publish. Only files the
  copy recorded, including `runic-views.js`, are deleted, and only when nobody
  wrote them since; host-specific client scripts, a `dotnet runic dev`
  document and files that the application puts in `www/` stay.

To adopt the host-neutral page, replace `runic-cswebui.js` or
`runic-desktop-views.js` in `index.html` with `runic-views.js`, and replace
`runic({ desktop: true })` with `runic()` and `base: "./"`. Remove a manual
`RunicApplicationFrontendInput` workaround only if it named files under the
frontend directory; inputs outside it are still needed. Assets left in `www/`
by an earlier SDK are not recorded, so delete `bin/<Configuration>/<TargetFramework>/www`
once after upgrading.
