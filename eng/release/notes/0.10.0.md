# Runic SDK 0.10.0

Install matching `0.10.0` packages from NuGet and npm;
`Runic.Application.Views.CsWebUi` is `0.10.0-preview.1`. Command Line versions
remain independent of this SDK.

0.10.0 contains every breaking and API-affecting change planned before 1.0. The
next release, 0.11.0, only adds APIs. After it come the release candidates
`1.0.0-rc.N`, which take only fixes, stabilization and documentation, and then
1.0.0. See
[Versioning and support from 1.0](https://github.com/Runic-Artifex/runic-sdk/blob/v0.10.0/eng/release/README.md#versioning-and-support-from-10).

This release removes the last experimental .NET APIs and every npm
`./experimental` entry. It moves the Views wire to protocol 3, gives the menu bar
and status icons one menu model, and replaces the Desktop availability probes
with one query. Embedded windows get safe defaults for links, new windows,
downloads and developer tools. Windows administration is supported. See
[Upgrading](#upgrading), [Behaviour changes](#behaviour-changes) and
[Security](#security).

The SDK tools run on Runic Command Line 0.8.0: they select output with
`--format`, share its exit codes and signal handling, and `Runic.Create` asks
its questions with Command Line prompts.

## Upgrading

Rebuild after updating: generated Bridge code changes namespace, and the
generated TypeScript clients and mocks speak Views protocol 3. Use
`Runic.Application.Views` and `@runic-artifex/views` of this release together;
a page and a host of different protocol versions no longer connect. Package
validation, the `PublicAPI` files and each pull request's description list the
changes in full; the tables below cover what application code usually touches.

### Build properties and build errors

- The ReactiveUI flavor is inferred from the Runic ReactiveUI adapter in the
  project's resolved references (package, transitive and project references).
  `RunicApplicationFrontendReactiveUiFlavor` is removed, and setting it or its
  former name `RunicBridgeReactiveUiFlavor` fails with `RUNICBRIDGE017`
  ([#483](https://github.com/Runic-Artifex/runic-sdk/pull/483)).
- Internal generator failures are reported as the new `RUNICBRIDGE024`, at the
  ViewModel's source line, and the other ViewModels are still generated.
  `RUNICBRIDGE001` now means only invalid configuration, unwritable output or a
  missing generator ([#483](https://github.com/Runic-Artifex/runic-sdk/pull/483)).
- A ReactiveUI command or interaction in a project that references neither
  Runic ReactiveUI adapter is the new `RUNICBRIDGE025`, at the member, instead of
  C# errors in generated code
  ([#483](https://github.com/Runic-Artifex/runic-sdk/pull/483)).
- `RUNICBRIDGE023` (mixed ReactiveUI flavors) now checks the resolved
  references, so mixes that arrive through packages or projects fail too; see
  [Behaviour changes](#behaviour-changes)
  ([#483](https://github.com/Runic-Artifex/runic-sdk/pull/483)).

- The implicit frontend install is always locked. A frontend whose
  `package.json` declares dependencies, built with the default install command
  and without the package manager's lock file (`package-lock.json` or
  `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `bun.lock` or `bun.lockb`), fails
  with the new `RUNICBRIDGE026` before anything is installed. Commit the lock
  file, or set `RunicApplicationFrontendAllowUnlockedInstall=true` to run
  `npm install`, `pnpm install` or `bun install` with `--ignore-scripts`. A
  project that sets `RunicApplicationFrontendInstallCommand`,
  `RunicApplicationFrontendNodeModulesDirectory` or
  `RunicApplicationFrontendInstallEnabled=false` is not checked. See
  [RUNICBRIDGE026](https://github.com/Runic-Artifex/runic-sdk/blob/v0.10.0/docs/diagnostics.md#runicbridge026)
  ([#497](https://github.com/Runic-Artifex/runic-sdk/pull/497)).

| Before | After |
| --- | --- |
| `<RunicApplicationFrontendReactiveUiFlavor>reactive</…>` (or `primitives`) | Remove it; reference `Runic.Application.Views.ReactiveUI.Reactive` for the System.Reactive flavor. Setting it fails with `RUNICBRIDGE017` |
| `<RunicBridgeReactiveUiFlavor>` | Remove it (`RUNICBRIDGE017` now says "removed", not "renamed") |
| `NoWarn` or a log filter on `RUNICBRIDGE001` for internal generator errors | `RUNICBRIDGE024` |
| A ReactiveUI command or interaction without a Runic ReactiveUI adapter: CS0234 in generated code | `RUNICBRIDGE025`; reference `Runic.Application.Views.ReactiveUI` or `.Reactive` |
| A flavor mix that arrives transitively, or `Runic.Application.Views.ReactiveUI` with `Runic.Navigation.ReactiveUI.Reactive`: built | `RUNICBRIDGE023`; use one flavor in every Runic ReactiveUI adapter the application gets |
| `Runic.Application.Views.ReactiveUI.Reactive`'s `buildTransitive` targets and props | Removed; the check is in `Runic.Application.Views`' build targets |
| `RUNICBRIDGE004` for a type named like the generated bridge (`CounterBridge` beside `CounterViewModel`) | No longer reported; both types can exist |
| No `package-lock.json`: the build ran `npm install --ignore-scripts` | `RUNICBRIDGE026`. Commit `package-lock.json` (run `npm install` once), or set `<RunicApplicationFrontendAllowUnlockedInstall>true</RunicApplicationFrontendAllowUnlockedInstall>` |
| pnpm/Bun without a lock file: the frozen install failed as `RUNICBRIDGE016` | `RUNICBRIDGE026` before the install runs; the opt-in runs `pnpm install` / `bun install` |
| `npm-shrinkwrap.json` only: `npm install` | `npm ci --ignore-scripts` |

### Platform and Runtime

- **One menu model.** Status icon menus and the Runic Desktop menu bar share
  `DesktopMenuEntry`, `DesktopMenu`, `DesktopMenuItem`, `DesktopMenuSeparator`,
  `DesktopMenuRole`, `DesktopShortcut` and `DesktopShortcutModifiers`, all in
  `Runic.Platform`. `DesktopMenuEntry` and `DesktopMenuRole` are open: keep a
  default arm ([#496](https://github.com/Runic-Artifex/runic-sdk/pull/496)).
- **`DesktopMenuItem` changes meaning.** It used to be the abstract base of
  status icon entries; it is now the sealed command item (the former
  `DesktopMenuCommand`), and the base is `DesktopMenuEntry`. A
  `case DesktopMenuItem` written against 0.9 still compiles but matches only
  command items. The constructor's arguments swap: convert with named arguments
  ([#496](https://github.com/Runic-Artifex/runic-sdk/pull/496)).

  ```csharp
  // 0.9
  new DesktopMenuCommand("open", "Open window")
  // 0.10: the title comes first
  new DesktopMenuItem(Title: "Open window", CommandId: "open")
  ```

- `IDesktopFileLauncher.LaunchUriAsync` opens Windows Settings pages
  (`ms-settings:<page>`) on Windows and returns `Unavailable(BackendUnavailable)`
  on Linux and macOS. The page rule is in [Security](#security)
  ([#482](https://github.com/Runic-Artifex/runic-sdk/pull/482)).
- `LaunchUriAsync` refuses a `mailto` URI that names an attachment, and
  `LaunchAsync(path, Open)` refuses more program types; see
  [Security](#security)
  ([#495](https://github.com/Runic-Artifex/runic-sdk/pull/495),
  [#499](https://github.com/Runic-Artifex/runic-sdk/pull/499)).

| Before | After |
| --- | --- |
| `Runic.Platform.DesktopMenuItem` (abstract base of status icon entries) | `DesktopMenuEntry`; `DesktopMenuItem` is now the command item, so a type pattern on the old base matches fewer entries |
| `new DesktopMenuCommand("open", "Open window")` | `new DesktopMenuItem(Title: "Open window", CommandId: "open")` (**arguments swap**) |
| `DesktopMenuCommand.Id`, `.Label` | `DesktopMenuItem.CommandId`, `.Title` |
| `new DesktopMenuSubmenu(label, items)`, `.Label` | `new DesktopMenu(label, items)`, `.Title` |
| `ImmutableArray<DesktopMenuItem>` (`DesktopStatusIconState.Menu`) | `ImmutableArray<DesktopMenuEntry>` |
| `activation.MenuItemId`, `new DesktopStatusIconActivation(kind, MenuItemId: …)` | `activation.CommandId`, `new DesktopStatusIconActivation(kind, CommandId: …)` |
| A `switch` over menu entries without a default arm | Add a default arm: the entry union is open |
| Status icon command ids starting with `runic.` | Rename them; the prefix is reserved for Runic's standard commands |
| `LaunchUriAsync(new Uri("ms-settings:…"))` threw `ArgumentException` | Opens Settings on Windows; `Unavailable(BackendUnavailable)` on Linux and macOS. Values outside the page rule, including `-action` pages, still throw |
| `snapshot.Statuses["platform.uris.launch"]` (and the other eight literals) | `snapshot.Statuses[PlatformCapabilityIds.UrisLaunch]`; the string values are unchanged |
| `LaunchUriAsync(new Uri("mailto:a@b?attach=…"))` was handed to the mail client | `ArgumentException` |
| `LaunchAsync(path, Open)` opened .vb, .ws, .xll, .jnlp, .msu, .rdp, .theme(pack), .iso, .img, .vhd(x), .dmg, .kext, .shortcut and similar files | `Failed(PermissionDenied)`; use `Reveal` or `ChooseApplication` if the user should open them |

### Navigation

All additive ([#485](https://github.com/Runic-Artifex/runic-sdk/pull/485)):

- `RunicNavigator.IsBusy` tells whether `WhenIdleAsync()` would wait. It is a
  snapshot without change notification; bind a progress indicator to a region's
  `IsBusy`.
- The non-generic `NavigationRegion` gains `BackToAsync(entry, …)` and
  `ClearHistoryAsync(…)`, returning `NavigationResult<object>`, for hosts typed
  `NavigationRegion` (`NavigationHost.Region`, `NavigationDialogHost.Region`).
- The WPF examples and the Runic.Navigation.Wpf README start the first page with
  `Main.Start(NavigationTarget.Create<T>())` before `Show()` instead of an
  unchecked `await Main.ResetAsync<T>()` in an `async void OnStartup`. Do the
  same: a construction failure then throws at startup.

### Views (.NET)

- Generated bridges are `internal sealed` classes in
  `Runic.Application.Views.Generated.Bridges` instead of the ViewModel's
  namespace; their names and constructors are unchanged, and the generated
  TypeScript is unchanged
  ([#483](https://github.com/Runic-Artifex/runic-sdk/pull/483)).
- Views protocol 3: `BridgeProtocol.Version` is 3, and .NET sends `released`
  where it sent `disconnected` for a released View
  ([#489](https://github.com/Runic-Artifex/runic-sdk/pull/489)).
- The ReactiveUI adapters keep the model turn and the failure bookkeeping for a
  plain `ReactiveCommand.Execute`; see [Behaviour changes](#behaviour-changes)
  ([#488](https://github.com/Runic-Artifex/runic-sdk/pull/488)).

| Before | After |
| --- | --- |
| Generated `<Name>Bridge` in the ViewModel's namespace, such as `FirstWindowDesktop.CounterBridge` | `Runic.Application.Views.Generated.Bridges.<Name>Bridge`. Code that constructs it (in the application, or a test project with `InternalsVisibleTo`) adds `using Runic.Application.Views.Generated.Bridges;` |
| `BridgeProtocol.Version` 2 (a `const`; recompile code that reads it) | 3 |
| Telemetry `runic.bridge.outcome` `disconnected` | `released` |
| `ObserveOn(ReactiveSchedulers.For(context))` added only because a plain `Execute` in a turn delivered on the task pool (event 1043) | Remove it; notifications arrive in later turns of the same model context. Don't block a turn on them |
| CPU-heavy `MainThreadScheduler` work after `ConfigureAwait(false)`, in `Task.Run` or from a timer created in a turn, relying on running on the task pool | It now runs on that turn's model context; move it off `MainThreadScheduler` (for example `ObserveOn(TaskPoolScheduler)`) |
| Event 1042 for a fire-and-forget failure during a Bridge call, logged at once | Logged when the outermost Bridge call in that flow ends |

### Views npm packages, wire and generated clients

- Every npm experimental API is exported from its package root, and the
  `./experimental` entries are removed. An `./experimental` import now fails at
  build time (TS2307, or `ERR_PACKAGE_PATH_NOT_EXPORTED` in Node); the names and
  signatures are unchanged. In a project, for example:
  `grep -rlE "@runic-artifex/[a-z-]+/experimental" src | xargs sed -i -E 's#(@runic-artifex/[a-z-]+)/experimental#\1#g'`
  (on macOS `sed -i ''`)
  ([#492](https://github.com/Runic-Artifex/runic-sdk/pull/492),
  [#493](https://github.com/Runic-Artifex/runic-sdk/pull/493)).
- Views protocol 3. The version check is strict: a page refuses a .NET host of
  another protocol version. The snapshot read that a connect starts with rejects
  with `BridgeError` kind `failed` and one `protocol` diagnostic, and so does the
  read after a reconnect. The package `version` stays informational, so a 0.10.1
  host works with a 0.10.0 page
  ([#489](https://github.com/Runic-Artifex/runic-sdk/pull/489)).
- `disconnected` is client-only and means "the Bridge is not connected to .NET";
  a released View is `released` on the wire. A protocol-3 client reads a wire
  `disconnected` as `failed`
  ([#489](https://github.com/Runic-Artifex/runic-sdk/pull/489)).
- Reply errors carry an open `reason`: `BridgeError.reason`
  (`BridgeErrorReason`), `"unavailable"` when a command's `CanExecute` is false
  and `"invalid-input"` when a value or argument does not decode or is rejected.
  views-effect exposes it as `ViewRejected.cause.reason`
  ([#489](https://github.com/Runic-Artifex/runic-sdk/pull/489)).

| Before | After |
| --- | --- |
| A mixed 0.9/0.10 .NET and npm pair connects and reports the `protocol` diagnostic | The connect rejects with `BridgeError` kind `failed` and one `protocol` diagnostic. Update both packages, rebuild and reload |
| Wire reply error kind, `Mount`/`Unmount` ack, operation admission and interaction reply `disconnected` for a released View | `released` |
| A custom `IBridgeTransport` that answers an unbound route with `{"ok":false,"state":null,"error":{"kind":"disconnected",…}}` | `{"ok":false,"state":null,"error":{"kind":"released","message":"This View was released."}}` |
| Telling "unavailable" from "invalid argument" by `BridgeError.message` | `BridgeError.reason` (`"unavailable"`, `"invalid-input"`; open) |
| `failNext(route, { kind: "disconnected" })` on the mock | `bridge.disconnect()` (`MockErrorFailure.kind` excludes `disconnected`) |
| Mock snapshot replies `protocol: 2`; hand-written test snapshot replies without `protocol` | `protocol: 3`; a successful snapshot reply without `protocol` is refused |
| `import { collectionViewport, createCollectionViewportController, createLatestOperationController } from "@runic-artifex/views/experimental"` (and their types) | `from "@runic-artifex/views"` |
| `import { followViewport, viewportChanges, type ViewportRange } from "@runic-artifex/views-effect/experimental"` | `from "@runic-artifex/views-effect"` |

A cached page or an external frontend built with 0.9 is not refused by a 0.10
host, because a 0.9 client only reports a protocol mismatch; some of its
`released` handling degrades to `failed`. Use one release on both sides
([#489](https://github.com/Runic-Artifex/runic-sdk/pull/489)).

### Framework adapters, SvelteKit and the Vite plugin

- `useLatestOperation()` (React, Vue, Svelte) and `injectLatestOperation()`
  (Angular) wrap one latest-operation controller for the owner's lifetime and
  expose every `LatestOperationState` field in the adapter's idiom. Owner
  disposal settles observation and never cancels accepted work
  ([#492](https://github.com/Runic-Artifex/runic-sdk/pull/492)).
- `useSuspenseView(source, { releaseTimeout })` sets how long an unclaimed
  connection or an unretried failure stays cached: a whole number of
  milliseconds from 1 to 2147483647, or `Infinity`; anything else throws a
  `RangeError`. The default stays 10 seconds
  ([#493](https://github.com/Runic-Artifex/runic-sdk/pull/493)).
- `@runic-artifex/vite-plugin-runic` and `@runic-artifex/sveltekit` require Vite
  `>=8.3.3 <9` (was `>=8.0.12 <9`), because of
  [GHSA-587h-7wmj-h5pm](https://github.com/advisories/GHSA-587h-7wmj-h5pm)
  ([#492](https://github.com/Runic-Artifex/runic-sdk/pull/492)).

| Before | After |
| --- | --- |
| `import { useSuspenseView, retrySuspenseView, useCollectionViewport } from "@runic-artifex/react/experimental"` | `from "@runic-artifex/react"` |
| `import { useCollectionViewport } from "@runic-artifex/vue/experimental"` (or `svelte`) | `from "@runic-artifex/vue"` (`@runic-artifex/svelte`) |
| `import { injectCollectionViewport } from "@runic-artifex/angular/experimental"` | `from "@runic-artifex/angular"` |

| Vite `>=8.0.12 <9` | Vite `>=8.3.3 <9`; update Vite to 8.3.3 or later |

### Runic Desktop and GTK 4

- **One availability query.** `DesktopPlatform.GetAvailability(options)` takes
  the `DesktopHostOptions` you start with and reports the configured window host,
  so with `WithGtk4()` or a WPF `RunicWebView` factory the embedded entry is that
  provider's answer. It needs no host or event loop. `availability.Embedded`,
  `availability.GetPresentation(browser)` and `availability.LinuxBackends`
  replace the separate probes. The embedded entry's `Capabilities` now include
  `Announcements`, and `State` and `FileDrop` where the built-in host supports
  them before loading its toolkit
  ([#487](https://github.com/Runic-Artifex/runic-sdk/pull/487)).
- **Custom window hosts are supported.** `IDesktopWindowHostFactory`,
  `IDesktopWindowHost` and its optional interfaces, `DesktopWindowHostOptions`,
  `DesktopHostOptions.WindowHostFactory`, `LinuxDesktopRuntime.ClaimBackend` and
  `IsLibraryAvailable` and `Gtk4WindowHostFactory` are no longer experimental.
  The Runic.Desktop README section
  [Custom window hosts](https://github.com/Runic-Artifex/runic-sdk/blob/v0.10.0/packages/dotnet/Runic.Desktop/README.md#custom-window-hosts)
  states what a host must do. Custom hosts receive the new web content policy in
  `DesktopWindowHostOptions.WebContent` and `AdditionalOrigins`
  ([#486](https://github.com/Runic-Artifex/runic-sdk/pull/486),
  [#499](https://github.com/Runic-Artifex/runic-sdk/pull/499)).
- **The low-level presentation transport is internal.**
  `DesktopSurface.RegisterCapability`, `RunJavaScriptAsync`,
  `NavigateAsync(string)`, `SendAsync` and the `Presentation*` types are gone
  from the public API; calls between the page and .NET go through Runic Windows
  and Views (`Runic.Application.Views.Desktop`).
  `DesktopSurface.ExecuteJavaScriptAsync` (now `ValueTask<string>`),
  `ConnectionCount` and `SubscribeConnectionEvents` are stable; a connection
  handler receives a `DesktopConnectionEvent` (`Kind`, `Surface`)
  ([#491](https://github.com/Runic-Artifex/runic-sdk/pull/491)).
- **Menu bar.** The menu bar uses the Runic.Platform menu model, and
  `IDesktopMenuCommandTarget` receives the `DesktopMenuItem`. Runic.Desktop now
  depends on Runic.Platform at exactly its own version
  ([#496](https://github.com/Runic-Artifex/runic-sdk/pull/496)).
- **Web content policy.** `DesktopWindowOptions.WebContent`
  (`DesktopWebContentPolicy`) controls links, new windows, downloads and
  developer tools; see [Behaviour changes](#behaviour-changes)
  ([#499](https://github.com/Runic-Artifex/runic-sdk/pull/499)).

| Before | After |
| --- | --- |
| `DesktopPlatform.IsEmbeddedWindowAvailable` | `DesktopPlatform.GetAvailability(options).Embedded.IsAvailable` |
| `DesktopPlatform.IsBrowserAvailable(browser, folder)` | `DesktopPlatform.GetAvailability(new() { BrowserFolder = folder }).GetPresentation(browser).IsAvailable` |
| `DesktopPlatform.GetAvailability(folder)`, `GetAvailability(folder, linux)` | `DesktopPlatform.GetAvailability(new DesktopHostOptions { BrowserFolder = folder, Linux = linux })` |
| `host.GetAvailability()` | `DesktopPlatform.GetAvailability(options)` with the host's options, or `host.Validate(windowOptions)` for a window request |
| `DesktopPlatform.GetLinuxEmbeddedBackends()` | `DesktopPlatform.GetAvailability().LinuxBackends` |

| Embedded `Capabilities == <six flags>` | Test flags with `HasFlag`: the set now includes `Announcements` and, per OS, `State`/`FileDrop` |
| `RUNICDESK100` suppressions around custom window host APIs | Remove them; no code change |
| `surface.RegisterCapability(name, handler)` and `PresentationResult` for page-to-.NET calls | Runic Windows and Views (`Runic.Application.Views.Desktop`): ViewModel commands and operations over the Bridge |
| `surface.RunJavaScriptAsync(script)` | `await surface.ExecuteJavaScriptAsync(script + "; return '';")` |

| `Runic.Desktop.DesktopMenuEntry`, `DesktopMenuRole`, `DesktopShortcut`, `DesktopShortcutModifiers` | The same names in `Runic.Platform`: add `using Runic.Platform;` |
| `IDesktopMenuCommandTarget.CanExecute(string commandId)` / `Execute(string commandId)` | `CanExecute(DesktopMenuItem item)` / `Execute(DesktopMenuItem item)`; read `item.CommandId` |

| Request path `<surface>/_runic_launch/…` served content | Reserved (403 unless it is the current launch code) |

### Windows administration

`Runic.Platform.Administration.Windows` is supported and no longer described as
experimental. Its local, LDAP/AD, DNS and Group Policy scenarios are accepted on
disposable fixtures under NativeAOT and JIT. It supports Windows x64 only, by
policy. Typed values replace the last raw and string values

### Command-line tools

- Without a Vite or Angular development server, `dotnet runic dev` shows
  frontend changes without a rebuild: the Runic Desktop window serves the
  frontend output directory (for example `Frontend/dist`, which the frontend's
  `dev` script or `RunicApplicationFrontendDevWatchTarget` rewrites) and reloads
  after each change. CS-WebUI windows keep showing the initial build. The query,
  hash and `pushState` route are not kept across a reload
  ([#498](https://github.com/Runic-Artifex/runic-sdk/pull/498)).
- `dotnet runic doctor --runtime <rid> --no-self-contained` checks a
  framework-dependent publish. Passing it together with `--self-contained` is a
  conflict error, and without `--runtime` it is the usage error `RAPPCLI1011`
  ([#480](https://github.com/Runic-Artifex/runic-sdk/pull/480)).

- The SDK tools use Runic Command Line 0.8.0 ([#501](https://github.com/Runic-Artifex/runic-sdk/pull/501)):
  - Every tool selects its output with `--format human|json`. `--output json`
    and `--output=json` remain hidden aliases for `dotnet runic` (including
    `support`), the asset packer and the Windows administration verifier until
    2.0; help and completions list only `--format`. The verifier used
    `--output` before. `Runic.Create` keeps `--output`/`-o` as its destination
    directory. Regenerate installed completion scripts.
  - Exit codes are 0 for success, 1 when the command failed or something it
    needs is unavailable, 2 for usage and validation errors, 3 for internal or
    host failures and 130 when cancelled. The verifier keeps its documented
    0/1/2.
  - Command Line handles Ctrl+C, SIGTERM and SIGQUIT: the first signal cancels
    with exit 130, a repeated signal exits at once with 130, 131 or 143, except
    while `dev` stops its process trees or the verifier cleans up. `dev` also
    stops on SIGHUP.
  - The asset packer honors `RUNIC_COMMANDLINE_NO_INPUT` and option
    environment fallbacks, and its JSON faults `RAS1001`–`RAS1004` carry
    `fault.helpUri`.
  - `Runic.Create` asks its questions with Command Line prompts on standard
    error, so redirecting standard output no longer turns them off. Pass
    `--yes`, set `RUNIC_COMMANDLINE_NO_INPUT=1` or redirect standard input to
    use the defaults; Escape or Ctrl+C at a question cancels with exit 130.

## Experimental APIs

No .NET API and no npm API is experimental any more.

- `RUNICDESK100` (custom window hosts) graduated and is retired. Remove its
  suppressions ([#486](https://github.com/Runic-Artifex/runic-sdk/pull/486)).
- `RUNICDESK101` (the low-level presentation transport) is retired: partly
  graduated (`DesktopSurface.ExecuteJavaScriptAsync`, `ConnectionCount`,
  `SubscribeConnectionEvents`), the rest internal. Remove its suppressions
  ([#491](https://github.com/Runic-Artifex/runic-sdk/pull/491)).
- `RUNICASSETS001` (the development-directory asset source) graduated and is
  retired; `IAssetWatch` is removed
  ([#498](https://github.com/Runic-Artifex/runic-sdk/pull/498)).
- The eleven npm `./experimental` exports of `@runic-artifex/views`,
  `views-effect`, `react`, `vue`, `svelte` and `angular` graduated to the
  package roots, and the `./experimental` entries are removed. Before 1.0 a
  future graduation removes the `./experimental` export in the same minor; from
  1.0 it stays as a deprecated alias until the next major
  ([#492](https://github.com/Runic-Artifex/runic-sdk/pull/492),
  [#493](https://github.com/Runic-Artifex/runic-sdk/pull/493)).
- `Runic.Platform.Administration.Windows`, which had no diagnostic ID, is no
  longer described as experimental
  ([#484](https://github.com/Runic-Artifex/runic-sdk/pull/484)).

[Experimental APIs](https://github.com/Runic-Artifex/runic-sdk/blob/v0.10.0/docs/experimental.md)
lists the graduated and retired IDs.

## Behaviour changes

- **Views protocol 3 is a strict match.** A page and a .NET host of different
  protocol versions no longer connect: the connect rejects with `BridgeError`
  kind `failed` and one `protocol` diagnostic. A released View is `released` on
  the wire, in `Mount`/`Unmount` acks, operation admissions, interaction replies,
  the unbound-route envelope of Runic Desktop and CS-WebUI, and telemetry;
  `disconnected` is client-only
  ([#489](https://github.com/Runic-Artifex/runic-sdk/pull/489)).
- **A plain `Execute` in a model turn keeps the turn.** A command that
  hand-written code starts with `command.Execute().Subscribe(…)` or
  `await command.Execute()` inside a model turn delivers its result,
  `IsExecuting`, `CanExecute` and `ThrownExceptions` on that model context, as a
  bridged execution does. Main-thread work from a turn's background flow (after
  `ConfigureAwait(false)`, in `Task.Run`, from a timer created in a turn) runs on
  that turn's model context instead of the task pool with event 1043. A turn that
  blocks on these notifications now deadlocks. Event 1042 is no longer logged
  for an exception that a plain `Execute` inside a Bridge call lets propagate or
  wraps; a fire-and-forget failure during a Bridge call is logged when the
  outermost call ends. Hand-written code that awaits a bridged command and
  handles the exception itself still logs 1042; use `ObserveBridgeExceptions`
  there ([#488](https://github.com/Runic-Artifex/runic-sdk/pull/488)).
- **Embedded windows keep their page on the application**
  (`DesktopWebContentPolicy`, on WebView2, WPF `RunicWebView`, WebKitGTK on
  GTK 3 and GTK 4, and WKWebView):
  - a clicked link to another site, `target="_blank"` included, opens in the
    default browser; navigations a script starts without a click are cancelled;
  - `window.open` never opens a second WebView window;
  - downloads are off unless `AllowDownloads = true`;
  - developer tools are on only when `DOTNET_ENVIRONMENT`, or else
    `ASPNETCORE_ENVIRONMENT`, is `Development` (as under `dotnet runic dev`),
    unless `DevTools` is set. Before, WebView2 always had them.

  `ExternalNavigation = AllowInWindow` restores the old link behaviour. On
  macOS, WKWebView reports a script's `a.click()` as a link activation, so a page
  script can still open an http/https/mailto URL in the browser. See
  [Links, new windows, downloads and developer tools](https://github.com/Runic-Artifex/runic-sdk/blob/v0.10.0/packages/dotnet/Runic.Desktop/README.md#links-new-windows-downloads-and-developer-tools)
  ([#499](https://github.com/Runic-Artifex/runic-sdk/pull/499)).
- **An installed browser opens a one-time launch code** instead of the surface
  address, and only the browser that used it can load the bootstrap scripts and
  open the Bridge; see [Security](#security)
  ([#494](https://github.com/Runic-Artifex/runic-sdk/pull/494)).
- **Menu bar and status icon rules.** Titles are literal text, not blank, at
  most 128 characters and without NUL. Command ids are 1–64 ASCII letters,
  digits, `.`, `_` or `-`, and ids starting with `runic.` (any letter case) are
  reserved. Building the host, `SetMenuBar` and `ShowAsync` throw an
  `ArgumentException` that names the offending id or title and the rule. The
  macOS menu bar now shows `IsEnabled = false` and `IsChecked` as declared
  ([#496](https://github.com/Runic-Artifex/runic-sdk/pull/496)).
- **Mixed ReactiveUI flavors fail to build.** `RUNICBRIDGE023` now runs on the
  resolved references, so it also sees package and transitive project
  references. It newly rejects `Runic.Application.Views.ReactiveUI` with
  `Runic.Navigation.ReactiveUI.Reactive`, and mixes that arrive transitively,
  which built before
  ([#483](https://github.com/Runic-Artifex/runic-sdk/pull/483)).
- **CS-WebUI calls run concurrently.** The Bridge admission gate is removed:
  concurrent calls no longer wait on each other (about 40 ms per queued call
  before) ([#479](https://github.com/Runic-Artifex/runic-sdk/pull/479)).

- **The implicit frontend install is always locked.** A frontend that declares
  dependencies without a lock file fails the build with `RUNICBRIDGE026` instead
  of running an unlocked `npm install`. `npm-shrinkwrap.json` counts as a lock
  file and installs with `npm ci`
  ([#497](https://github.com/Runic-Artifex/runic-sdk/pull/497)).

## Security

These come from the security review before 1.0. None needs action unless noted.

- **SEC-01: installed browsers are bound to the window that launched them.** On
  a shared Linux or macOS machine, another user could read the browser's command
  line, fetch the session credential from the bootstrap script and open the
  Bridge with a forged `Origin`. The command line now carries only a one-time
  launch code; the first request with it binds the surface to that browser
  through an `HttpOnly`, `SameSite=Strict` cookie, and every other client gets
  403 with `client-not-bound`. On Linux another user's request for the code is
  refused (`browser-launch-foreign-user`). On macOS, where the user cannot be
  checked, a process that uses the code first is detected: the window's sessions
  are closed and `browser-launch-conflict` is reported. This applies to the
  default `EmbeddedThenBrowser` fallback and to explicit browser presentation.
  A cross-site `AdditionalOrigins` entry no longer gets the bootstrap in browser
  mode; use a same-site origin
  ([#494](https://github.com/Runic-Artifex/runic-sdk/pull/494)).
- **SEC-02: Open refuses more program types.** On Windows and macOS,
  `LaunchAsync(path, Open)` also refuses script, add-in, installer,
  remote-desktop and theme files and disk images, and on Windows types the shell
  marks dangerous or whose open command runs the file itself. They return
  `Failed(PermissionDenied)`. The lists are best effort: reveal untrusted files
  (downloads, names a page supplies) or open them with `ChooseApplication`
  ([#495](https://github.com/Runic-Artifex/runic-sdk/pull/495)).
- **SEC-03: D-Bus nesting limit.** A peer could crash the process with deeply
  nested variants in one message. Values nested deeper than 64 levels are now
  rejected with `InvalidArgs`
  ([#495](https://github.com/Runic-Artifex/runic-sdk/pull/495)).
- **SEC-04: embedded windows have a web content policy.** A link could move the
  window to another site inside the application's chrome, popups ran without
  Runic's handlers, downloads went through without asking, and WebView2 had
  DevTools in Release builds, which allowed "paste this into the console"
  self-XSS with full Bridge access. See [Behaviour changes](#behaviour-changes)
  for the new defaults
  ([#499](https://github.com/Runic-Artifex/runic-sdk/pull/499)).
- **SEC-07: `mailto` attachments.** `LaunchUriAsync`, and the links embedded
  windows open, refuse a `mailto` URI with a header field whose name starts with
  `attach` (in any case or escaping), because some mail clients send the named
  file without asking. `LaunchUriAsync` throws `ArgumentException`
  ([#499](https://github.com/Runic-Artifex/runic-sdk/pull/499)).
- **SEC-08: Windows Settings URIs are restricted.** `ms-settings:` is allowed
  only as exactly `ms-settings:<page>`, the page 1 to 64 ASCII letters, digits
  or hyphens, with no path, query, fragment or percent-escapes; `-action` pages
  are refused. Anything else throws `ArgumentException` on every platform before
  any native call ([#482](https://github.com/Runic-Artifex/runic-sdk/pull/482)).
- **SEC-13: locked frontend installs.** Without a lock file, the implicit
  frontend install fell back to an unlocked `npm install --ignore-scripts`, so
  every build, CI included, resolved the declared version ranges afresh. A newly
  published malicious version would then run in the frontend build, for example
  as a Vite plugin; `--ignore-scripts` only stops install scripts. The build now
  fails with `RUNICBRIDGE026`. **Action:** commit your frontend's lock file
  (the templates already ship one), or opt in with
  `RunicApplicationFrontendAllowUnlockedInstall=true`
  ([#497](https://github.com/Runic-Artifex/runic-sdk/pull/497)).
- **Vite.** The Vite plugin and the SvelteKit adapter require Vite 8.3.3 or
  later because of
  [GHSA-587h-7wmj-h5pm](https://github.com/advisories/GHSA-587h-7wmj-h5pm)
  ([#492](https://github.com/Runic-Artifex/runic-sdk/pull/492)).
