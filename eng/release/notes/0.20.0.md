# Runic SDK 0.20.0

Install matching `0.20.0` packages from NuGet and npm;
`Runic.Application.Views.CsWebUi` is `0.20.0-preview.1`.

## `@runic-artifex/angular` in the Angular Package Format (#945)

`@runic-artifex/angular` is built with ng-packagr and published in the Angular
Package Format: one partially compiled FESM bundle per entry point under
`dist/fesm2022/`, with its typings under `dist/types/`, in place of the per-file
`ngc` output under `dist/esm/`. Imports don't change: `@runic-artifex/angular`,
`@runic-artifex/angular/forms` and `@runic-artifex/angular/experimental` export
the same API, and the Angular CLI builds and tests an application with them as
before. Bundlers that run the Angular linker only on APF files now link the
package too: a production `vite build` with `@analogjs/vite-plugin-angular`
failed in the browser with "JIT compiler unavailable" and now renders the page.

## Development source map and open in editor (#951)

Each build that generates Bridges now writes a development source map,
`obj/<Configuration>/<TargetFramework>/runic-bridge/sources.json`: every
ViewModel and every member its generated client and the Bridge frames name
(state, setters, commands, command state, interactions, View requests), with
the C# that runs for it (a command's `[RelayCommand]` method or the method its
command is created from) and its `{file, line, column}`, read from the
assembly's portable PDB. Without a PDB the members are listed without
locations and the build still succeeds.

Under `vite dev`, `@runic-artifex/vite-plugin-runic` serves the map at
`/__runic/sources` and adds `POST /__runic/open`, which opens a location in
your editor through Vite's own launcher (`LAUNCH_EDITOR`, VS Code, Rider). Unlike
Vite's `/__open-in-editor`, it opens only locations the map lists, and only for
a page of the development server's origin on the same machine. `dotnet runic
dev` tells the plugin where the map is; otherwise the plugin finds it under the
project's `obj`, and `runic({ sourceMap })` names it or (`false`) turns both
endpoints off. The map never enters generated TypeScript, `vite build` output,
publish output or a package.

## Bridge calls in the browser's developer tools (#953)

During development, each call a generated client makes can now be followed in
the browser. `@runic-artifex/views` reports every command, setter, checked
write, availability check, region request, operation start and query request
to a development **Bridge-call channel** (`runic.views.calls`), with a
client-local id, the route, contract and member, its start and end time, its
outcome (`ok`, `error` or `cancelled`) and the reply's revision. The
development client of `@runic-artifex/vite-plugin-runic` listens to it, so
under `vite dev` and `dotnet runic dev`:

- a Performance recording in Chrome, Edge or WebView2 has a **Runic** track
  group with a **Bridge calls** track, which the development client draws: one
  entry per call, such as `EditorViewModel.save #3`, coloured by outcome;
- a breakpoint after a reply, such as in a state subscriber, shows a
  `Runic command EditorViewModel.save` async stack segment that leads to the
  click handler that made the call (`console.createTask`).

Other engines get the channel's reports without the two Chromium extras.
Without a reader, as in every production build, a call costs one property read
and records nothing; the reporting code adds about 0.7 KB gzip to a client
bundle. The wire protocol is unchanged: the id stays in the page. See "Bridge
calls in the browser's developer tools" in the Views README for the event
fields.

## Runic Inspect: select an element and see how it is connected (#955)

Under `vite dev` and `dotnet runic dev`, press **Alt+Shift+X** in the page to
turn on **Runic Inspect**, a select mode of the
`@runic-artifex/vite-plugin-runic` development client. Hover outlines an
element; clicking it shows an overview, without running the page's own
handler for that click:

- its framework component and the components around it, with a link to the
  source: the element's JSX line in React 19 (from `_debugStack` through the
  module's source map), the element's line in Svelte 5, the component file in
  Vue 3 and the component class in Angular 17.1+;
- the commands it calls, with their C# handlers (such as the
  `[RelayCommand]` method) and file:line from the development source map
  (#951), and their availability (`canSave`);
- the ViewModel members it sets, and state members it shows, with their
  current values and C# members;
- its recent Bridge calls with duration, outcome and revision (#953);
- the texts its ViewModel sent as text references, with catalog, key and
  locale.

C# locations open in the editor through `/__runic/open`, frontend files
through Vite's `/__open-in-editor`. An element's commands are learned from
the calls it makes, so a button shows its command after it was used once in
the page. For agents and tests,
`globalThis[Symbol.for("runic.vite.inspect")].describe(element)` returns the
overview as data. Runic Inspect is plain DOM, so it works in every engine
`dotnet runic dev` runs (installed browser, WebView2, WKWebView, WebKitGTK).
It lives in the development client only: `vite build` output is
byte-identical with and without it, and `runic({ inspect: false })` turns it
off.

## Text helpers follow in-place message updates (runic-translations-sdk#176)

With the Translations Vite plugin 0.12.0 or later, `vite dev` updates an edited
message in place instead of reloading the page, and the page keeps its
component state, its language and its connection. The plugin signals the change
on a global text-change channel, `Symbol.for("runic.translations.text")`, and the
text helpers now render again on it as they do on a language switch:

- `configureTranslatedText` (`@runic-artifex/views`) follows the channel and
  notifies text subscribers, so `useText`, `injectText`, the `runicText` pipe,
  `texts` and `syncDocumentLocale` update.
- React: `useTextLocale()` renders again on a text change that keeps the locale,
  so components that call it, and their children except memoized ones, show the
  new text.
- Angular: `textLocaleSignal()` notifies on a text change that keeps the locale,
  so templates that call `m.*()` through the locale resolver, `OnPush` ones
  included, show the new text.
- Effect: `textLocales()` emits the same locale again on a text change.
- Vue and Svelte (`useTextLocale`) needed no change.

In place means a message's text, its plural and selector variants and the text
inside its markup, in any locale. An added, removed or renamed message, changed
inputs or markup, a new locale and a `runic.json` change still reload the page,
and so does a page that does not call `configureTranslatedText`. The Angular CLI's
dev server runs no Vite plugins and keeps reloading; in-place updates in Angular
need Angular built with Vite. In production nothing writes the channel: the
listener `configureTranslatedText` adds in the browser never runs, and the
helpers behave as before. With an earlier plugin, or with these helpers from
0.19 or earlier, the page reloads as before; only `@runic-artifex/views` 0.20
with the React or Angular helpers of 0.19 updates the catalog without rendering
again, so install matching versions.

## Fixes

- `DesktopWindow.OwnedWindows` no longer lists an owned window that has closed
  but whose `Closed` event has not run yet, for example right after its
  `WaitForCloseAsync` returned (#965).
