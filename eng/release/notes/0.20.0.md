# Runic SDK 0.20.0

Install matching `0.20.0` packages from NuGet and npm;
`Runic.Application.Views.CsWebUi` is `0.20.0-preview.1`.

## `@runic-artifex/angular` in the Angular Package Format (#945)

`@runic-artifex/angular` is built with ng-packagr and published in the Angular
Package Format: one partially compiled FESM bundle per entry point under
`dist/fesm2022/`, with its typings under `dist/types/`, in place of the per-file
`ngc` output under `dist/esm/`. Imports don't change: `@runic-artifex/angular`,
`@runic-artifex/angular/forms` and `@runic-artifex/angular/experimental` export
the same API, and the Angular CLI builds and tests an application with them as
before. Bundlers that run the Angular linker only on APF files now link the
package too: a production `vite build` with `@analogjs/vite-plugin-angular`
failed in the browser with "JIT compiler unavailable" and now renders the page.

## Bridge calls in the browser's developer tools (#953)

During development, each call a generated client makes can now be followed in
the browser. `@runic-artifex/views` reports every command, setter, checked
write, availability check, region request, operation start and query request
to a development **Bridge-call channel** (`runic.views.calls`), with a
client-local id, the route, contract and member, its start and end time, its
outcome (`ok`, `error` or `cancelled`) and the reply's revision. The
development client of `@runic-artifex/vite-plugin-runic` listens to it, so
under `vite dev` and `dotnet runic dev`:

- a Performance recording in Chrome, Edge or WebView2 has a **Runic** track
  group with a **Bridge calls** track, which the development client draws: one
  entry per call, such as `EditorViewModel.save #3`, coloured by outcome;
- a breakpoint after a reply, such as in a state subscriber, shows a
  `Runic command EditorViewModel.save` async stack segment that leads to the
  click handler that made the call (`console.createTask`).

Other engines get the channel's reports without the two Chromium extras.
Without a reader, as in every production build, a call costs one property read
and records nothing; the reporting code adds about 0.7 KB gzip to a client
bundle. The wire protocol is unchanged: the id stays in the page. See "Bridge
calls in the browser's developer tools" in the Views README for the event
fields.

## C# handler timing and one trace from the page to .NET (#958)

Under `dotnet runic dev`, a Bridge reply names the C# handler that ran and how
long it took, such as `EditorViewModel.Save` in 2.4 ms. The Vite development
client lists it on the call's **Bridge calls** entry and draws it on a new
**C# handlers** track below it. A .NET host sends the timing only when
`DOTNET_ENVIRONMENT` (or else `ASPNETCORE_ENVIRONMENT`) is `Development`, which
`dotnet runic dev` sets, and only to a page whose development tools ask for it.

Bridge calls can also be one trace with the C# they run. When the Vite
development server sees `OTEL_EXPORTER_OTLP_ENDPOINT`, the page gives each call
a W3C trace context, which the call's request carries to .NET. The
`runic.bridge.*` span of `Runic.Application.Views` becomes the child of the
page's span for the call, and the ViewModel's own spans, such as its HTTP and
database calls, follow it. The development server exports the page's spans as
OTLP/JSON, and the application exports its own spans with its usual
OpenTelemetry setup. The page loads no OpenTelemetry code, and `dotnet runic
dev` starts no container. The new
[tracing guide](https://github.com/Runic-Artifex/runic-sdk/blob/v0.20.0/docs/tracing.md)
sets it up with the standalone Aspire dashboard.

Both are Views protocol features (`trace-context/1` and `handler-timing/1`):
a page and a .NET host of 0.19 or earlier keep working with 0.20 in either
direction. Outside development nothing changes: no request carries the new
members, a host reads a trace context only while its `ActivitySource` has a
listener, and replies carry no timing.

## Fixes

- `DesktopWindow.OwnedWindows` no longer lists an owned window that has closed
  but whose `Closed` event has not run yet, for example right after its
  `WaitForCloseAsync` returned (#965).
