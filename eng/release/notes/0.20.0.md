# Runic SDK 0.20.0

Install matching `0.20.0` packages from NuGet and npm;
`Runic.Application.Views.CsWebUi` is `0.20.0-preview.1`.

## `@runic-artifex/angular` in the Angular Package Format (#945)

`@runic-artifex/angular` is built with ng-packagr and published in the Angular
Package Format: one partially compiled FESM bundle per entry point under
`dist/fesm2022/`, with its typings under `dist/types/`, in place of the per-file
`ngc` output under `dist/esm/`. Imports don't change: `@runic-artifex/angular`,
`@runic-artifex/angular/forms` and `@runic-artifex/angular/experimental` export
the same API, and the Angular CLI builds and tests an application with them as
before. Bundlers that run the Angular linker only on APF files now link the
package too: a production `vite build` with `@analogjs/vite-plugin-angular`
failed in the browser with "JIT compiler unavailable" and now renders the page.

## Development source map and open in editor (#951)

Each build that generates Bridges now writes a development source map,
`obj/<Configuration>/<TargetFramework>/runic-bridge/sources.json`: every
ViewModel and every member its generated client and the Bridge frames name
(state, setters, commands, command state, interactions, View requests), with
the C# that runs for it (a command's `[RelayCommand]` method or the method its
command is created from) and its `{file, line, column}`, read from the
assembly's portable PDB. Without a PDB the members are listed without
locations and the build still succeeds.

Under `vite dev`, `@runic-artifex/vite-plugin-runic` serves the map at
`/__runic/sources` and adds `POST /__runic/open`, which opens a location in
your editor through Vite's own launcher (`LAUNCH_EDITOR`, VS Code, Rider). Unlike
Vite's `/__open-in-editor`, it opens only locations the map lists, and only for
a page of the development server's origin on the same machine. `dotnet runic
dev` tells the plugin where the map is; otherwise the plugin finds it under the
project's `obj`, and `runic({ sourceMap })` names it or (`false`) turns both
endpoints off. The map never enters generated TypeScript, `vite build` output,
publish output or a package.

## Generated clients link to their C# sources (#952)

Each generated client is now two files: `<view>.ts` with the code, and
`<view>.contract.d.ts` with its types (state, checked fields, interactions,
View requests, operations, client and page reference interfaces) and a
declaration map, `<view>.contract.d.ts.map`, into the ViewModel's C#. Go to
Definition or Peek on `client.increment()`, `client.setStep(...)` or
`state.count` in VS Code, Visual Studio or another tsserver-based editor opens
the command's handler, the setter or the getter in the `.cs` file, with no
extension; Go to Type Definition on a `CounterClient` or `CounterState` opens
the ViewModel class. The locations are the development source map's (#951),
and the map's `sources` are relative to it, so committed clients don't depend
on the checkout. Without a PDB a client gets no map, and the build still
succeeds.

- **Imports keep working.** `<view>.ts` re-exports every contract type with
  `export type`, so `import { connectCounter, type CounterState } from "./generated/counter.js"`
  is unchanged. The built JavaScript is unchanged too: the contract holds only
  types.
- **Commit the new files.** A committed generated directory gains a
  `.contract.d.ts` and a `.contract.d.ts.map` per ViewModel, and the
  interfaces move out of `<view>.ts`; the example clients changed this way.
- **`tsc --declaration` into another directory:** `tsc` doesn't copy `.d.ts`
  inputs, so a library that emits declarations for its generated clients copies
  the `.contract.d.ts` files beside them.
- A generated client no longer imports types it doesn't use (a field-path
  client imported `FieldBaseline` and `FieldWriteOptions`), so it passes
  `noUnusedLocals`.
