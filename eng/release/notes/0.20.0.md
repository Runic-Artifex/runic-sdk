# Runic SDK 0.20.0

Install matching `0.20.0` packages from NuGet and npm;
`Runic.Application.Views.CsWebUi` is `0.20.0-preview.1`.

## `@runic-artifex/angular` in the Angular Package Format (#945)

`@runic-artifex/angular` is built with ng-packagr and published in the Angular
Package Format: one partially compiled FESM bundle per entry point under
`dist/fesm2022/`, with its typings under `dist/types/`, in place of the per-file
`ngc` output under `dist/esm/`. Imports don't change: `@runic-artifex/angular`,
`@runic-artifex/angular/forms` and `@runic-artifex/angular/experimental` export
the same API, and the Angular CLI builds and tests an application with them as
before. Bundlers that run the Angular linker only on APF files now link the
package too: a production `vite build` with `@analogjs/vite-plugin-angular`
failed in the browser with "JIT compiler unavailable" and now renders the page.

## `dotnet runic dev`: an IDE contract (#959)

`dotnet runic dev` prints `[dev] Window started: process <pid>` each time the
Window process starts or `dotnet watch` restarts it, with the application's own
process ID to attach a .NET debugger to, then `[dev] Ready`, and
`[dev] Window exited: process <pid>` when it exits. It writes
`obj/runic/dev-session.json` (`runic.application.tool.dev-session/1`): the
development server's URL and port, each page's URL, the Window's process ID,
the web root and the generated clients' directory, and WebView2's debugging
endpoint when `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` enables one. The file is
marked `"state": "stopped"` when `dev` ends. A failing `dev` prints its fault as
one line, `<project> : error RAPPDEV1007: <message>`, which VS Code's
`$msCompile` matches like the build's own errors. A background task can wait
for `Ready`; see
[IDE contract](https://github.com/Runic-Artifex/runic-sdk/blob/v0.20.0/tools/dotnet-runic/README.md#ide-contract).

## Debug the Window under your IDE while `dev` runs the frontend (#960)

`dotnet runic dev --no-window` runs only the frontend (the Vite or Angular
development server, or the frontend watcher), and your IDE's F5 builds and
starts the Window under its .NET debugger. While `dev` runs, any build of the
output it serves, such as the IDE's, skips the production frontend build and
keeps dev's development pages in `www/`, also after a clean; before, an IDE
build replaced them with `dist/`. Nothing restarts the Window behind the
debugger; use the IDE's Hot Reload. Publish is
unchanged, and `RunicApplicationFrontendDevSessionEnabled=false` turns the
build behaviour off. `--no-window` with an option that only describes how `dev`
starts the Window fails with `RAPPDEV1014`; a project without a development
server or watcher fails with `RAPPDEV1015`. The tool's README has the launch
profile and VS Code, Rider and Visual Studio setups; see
[Debug the Window in your IDE](https://github.com/Runic-Artifex/runic-sdk/blob/v0.20.0/tools/dotnet-runic/README.md#debug-the-window-in-your-ide).

## An IDE-ready `runic-app` template (#961)

Projects from `dotnet new runic-app` have `Properties/launchSettings.json`.
Its first profile starts the Window with `DOTNET_ENVIRONMENT=Development` in
Visual Studio, Rider and plain `dotnet run`, which uses the first profile, so
`dotnet run` now has the page's DevTools and detailed Bridge errors on. With
Runic Desktop, a second profile turns on WebView2 script debugging on Windows
(`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222`, and
`jsWebView2Debugging` for Visual Studio). `--editor vscode` (default `none`) adds
`.vscode/`: tasks for `dotnet runic dev` and `dev --no-window` that wait for
`[dev] Ready` and put `RAPPDEV` failures and build errors in the Problems panel,
debug configurations for the C# extension (F5 starts the Window under the
debugger while `dev --no-window` serves the frontend, or attaches to the Window
that `dev` started), a Windows compound that also attaches VS Code's JavaScript
debugger to WebView2, and the recommended extensions. `runic-create` asks for
the editor too. Both templates have an `ide.host.json` and an icon for Visual
Studio's New Project and Add New Item dialogs. See the generated README's "Debug it in
your IDE" section.

## The template's Vite pages compile their catalog with the Translations Vite plugin (#944)

`dotnet new runic-app --translations` with React, Vue, Svelte or SvelteKit no
longer has the .NET build write the page's ESM and mirror it into
`Frontend/.runic/translations`. The page compiles the catalog itself with
`runicTranslations()` from `@runic-artifex/vite-plugin-runic-translations`
0.11.0 in `Frontend/vite.config.ts` and imports it as
`virtual:runic-translations/app`. The plugin runs the
`dotnet-runic-translations` tool of `.config/dotnet-tools.json`, the release of
`Runic.Translations.Build`, so the page and C# (`AppText`, which the build still
generates) read the same catalog, and nothing else generates the page's copy.

- Under `dotnet runic dev`, an edited, added or removed message reaches the page
  without a build: the plugin compiles it again and the page reloads.
  runic-translations-sdk#176 will update the page in place instead.
- `dotnet build` and `dotnet publish` produce the same page. An edited message
  still rebuilds it, as the catalog is a frontend input.
- The types of the virtual modules are in `Frontend/.runic/translations/virtual.d.ts`,
  which Vite writes whenever it runs (the build, the development server, the
  frontend test) and `src/translations.ts` references, so `tsc`, `vue-tsc` and
  `svelte-check` see the exact messages after the first build, as before.
- The Angular template keeps the ESM from the .NET build: the Angular CLI runs
  no Vite plugins. An Angular template built with Vite (#946) is planned.

Applications created from an earlier template keep working. To move a Vite
page to the plugin: add `"@runic-artifex/vite-plugin-runic-translations": "0.11.0"`
to `devDependencies` and `runicTranslations()` to the Vite plugins; import
`virtual:runic-translations/app`, `/runtime` and `/transport` instead of
`../.runic/translations/messages.js`, `runtime.js` and `transport.js`; add
`/// <reference path="../.runic/translations/virtual.d.ts" />` to
`src/translations.ts`; and remove `RunicTranslationsEmitEsm` and
`RunicApplicationFrontendTranslations` from the project file.

The template's tests check each Vite frontend's development loop in Chromium:
an edited message shows on the page, and an added and a removed one reach the
development server's module, under `dotnet runic dev`.

## Fixes

- `DesktopWindow.OwnedWindows` no longer lists an owned window that has closed
  but whose `Closed` event has not run yet, for example right after its
  `WaitForCloseAsync` returned (#965).
