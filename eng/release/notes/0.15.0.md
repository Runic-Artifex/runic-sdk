## Views protocol (V5)

- **A late command no longer runs on the next page.** Mark a command
  `[RunicPresentationScoped]` and call `RunicPresentation.Renew(this)` where the
  page changes, as a wizard's Next and Back do. The page sends the command with
  the epoch of the state it showed, and the Bridge answers a call from an
  earlier page `superseded` without running it; the page's call resolves without
  an error, so command controllers show nothing (#755).
- **Wait until the page shows a state.**
  `await RunicPresentation.WaitForPresentedAsync(viewModel, timeout)` completes
  with `true` once a page rendered the ViewModel's current state, and
  `CloseAsync(timeout)` waits, within its timeout and at most 5 seconds, until
  the page acknowledged the close (`RunicWindowCloseResult.PagesAcknowledged`).
  A page that the application closed reports the connection state `"closed"`
  instead of `reconnecting` or `lost` (#727).

Both are new Views protocol features, `presentation-epoch/1` and `presented/1`,
negotiated in `hello`: a 0.14 page and a 0.15 host, or the reverse, connect and
behave as in 0.14. Design: `specs/application/README.md` ("Presentation epochs",
"Presented states and window close").

### Upgrading

Update every Runic NuGet and npm package to 0.15.0 together and rebuild, so that
the generated clients are regenerated. See the
[migration guide](https://github.com/Runic-Artifex/runic-sdk/blob/v0.15.0/docs/migration-1.0.md#from-014-to-015).

### Breaking changes

- **`BridgeConnectionState` has a fifth value, `"closed"`.** Code that switches
  over the connection state exhaustively, such as a `never` check in a
  connection banner, no longer compiles until it handles `"closed"`. The
  `runic-app` templates show "The application closed this window."

### Behaviour changes

- **Content presented again pushes its state.** When the open presentations of
  a content route resume on its new attachment (a slot showed other content and
  then this content again before the page saw it), the Bridge pushes the
  route's first state, so a kept client shows the current state and epoch
  without reading it again.
- **Renewals are full states.** `RunicPresentation.Renew` publishes the route's
  full `state` at a new revision, also when no member changed.
- **Closes push `closing`.** Every close the application starts (`CloseAsync`,
  `RequestCloseAsync` once it decided, `DisposeAsync`, host shutdown) tells pages
  that use `presented/1`; only `CloseAsync` with a timeout waits for their reply.
  A close that ends before every page replied is logged at `Debug`
  (`WindowCloseUnacknowledged`, 1026).

### Added

#### .NET (`Runic.Application.Views`)

- `RunicPresentationScopedAttribute`, on a command property or a CommunityToolkit
  `[RelayCommand]` method. The generated client lists the command in
  `scopedCommands`, and the View's contract fingerprint gets a `scoped:` line.
  On any other member it is warning `RUNICBRIDGE034`.
- `RunicPresentation.Renew(object viewModel)`: begins a new presentation epoch
  for every route that presents the ViewModel, in every window. An epoch also
  begins with each route's first state, so content presented again needs no
  call.
- `RunicPresentation.WaitForPresentedAsync(object viewModel, TimeSpan timeout,
  CancellationToken cancellationToken = default)`: `true` once a page reported
  that it painted the ViewModel's state including every change made before the
  call; `false` at the timeout, also when no page uses `presented/1`. Only waits
  ask the page to report.
- `RunicWindowCloseResult.PagesAcknowledged`: whether every page connected with
  `presented/1` replied to the close; `true` when there was none.

#### TypeScript (`@runic-artifex/views`)

- The client implements both features: scoped commands carry the epoch of the
  state the presentation's subscribers last received, a superseded call
  resolves with the current state (`commandOutcome`: `bridgeSuccess(state)`)
  and reports no diagnostic, a `present` request is answered after the state
  was delivered and one animation frame passed, and `closing` after the next
  frame.
- `ViewConnectOptions.scopedCommands` (generated).
- Mock Bridge (`@runic-artifex/views/mock`): `MockView.epoch`,
  `MockView.renew()`, `MockView.waitPresented(timeout?)` and
  `MockBridge.closeWindow(timeout?)`, for page tests of both features.
- The React, Vue, Svelte, SvelteKit and Angular bindings need no change: their
  command hooks see a superseded call as a resolved run, and their connection
  hooks report `"closed"`.

### Specifications

- Views protocol 4: features `presentation-epoch/1` (`epoch` in `open` and
  `snapshot` replies and `state` pushes, `epoch` on `command`, the `superseded`
  command reply) and `presented/1` (`present` and `closing` pushes, `presented`
  and `closing-reply` requests). The `runic.views.connection` shared global
  gains `closed` and `closedListeners`.
- Conformance: the `wizard` test View, the mutations `renew` and
  `waitPresented`, the step `closeWindow`, epoch mapping, and nine scenarios in
  `presentations`. The client's `hello` in scenarios that a client runner
  executes lists `features` as `$any`, since a client lists every feature it
  implements.

## Navigation (N1)

### Behaviour changes

- A retained result entry whose request already ended (its caller's token was
  cancelled, or it called `DismissAsync` while another entry covered it) no
  longer comes back when the entry above it goes back. That Back retires it
  too and resumes the entry below it; a return from a result entry may leave
  the region empty, a plain Back keeps the region's bottom entry. Before, the
  answered dialog was shown again and its `CompleteAsync` only went back.

### Added

- **`NavigationAdmission.Queue`** for `NavigationRegionOptions.Admission`,
  `NavigationSelectionOptions.Admission` and per request
  (`NavigationRequestOptions.Admission`). A request waits until the region's
  earlier requests have ended, in admission order, and supersedes none of
  them, so a second `PushForResult` into a dialog region stacks above the
  first instead of dropping it (`Supersede`) or being refused
  (`RejectWhileBusy`). `ExpectedCurrent` and a Back's history are checked when
  the request starts; its token cancels it while it waits
  (`Rejected(Cancelled)`, the `Completion` ends `Dismissed`); a request
  admitted with `Supersede`, such as a window close, still supersedes queued
  requests. Runic.Navigation README, "Queueing requests".
- Runic.Navigation.Wpf: `NavigationDialogHost` dismisses a closed dialog with
  the region's `Queue` policy in a queued region, so closing a dialog no longer
  supersedes a dialog pushed meanwhile.
- **`NavigationRegionOptions.AskOnParentRetain`**: a push that covers the
  entry owning the region asks the region's current entry, and the current
  entries of the regions below it, as `Retain`, before the covered entry's own
  guard. In a `NavigationSelection` only the selected region is asked, so a
  page whose tabs set it asks the shown tab's page when another page is pushed
  over it. Off by default; with `ResetToRoot` or `Clear` the removed entries
  are already asked.
- **`NavigationRegion.ConfirmDepartureAsync(kind, onConfirmed, options,
  cancellationToken)`** asks the guards a departure of the region's current
  entry as `kind` would ask, without navigating, as a transition of the region
  (`NavigationOperation.Confirm`): admitted with the region's admission policy,
  superseded by a commit in an asked region, cancelled by its token. When every
  guard agrees, its commit turn runs the guards' `OnCommitted` actions and then
  `onConfirmed`, so the agreed work happens in the same turn as the answer.
  Nothing else changes. Runic.Navigation README, "Asking without navigating".
- `NavigationOperation.Confirm`. The enum is open; guards that switch on
  `Operation` handle it in their default arm.

## Embedded frontends (H1, #726, #730)

### Added

- **CS-WebUI serves an embedded frontend** (#726).
  `RunicApplicationFrontendDelivery=Embedded` now works with
  `Runic.Application.Views.CsWebUi`: the build packs the frontend and
  `runic-cswebui.js`/`runic-views.js` into the assembly, and each window serves
  the archive through `WebUiWindow.SetFileHandler`, with no extraction to disk.
  `RunicCsWebUiHostOptions.Assets` serves another `IAssetSource`, as
  `RunicDesktopHostOptions.Assets` does. A path the source does not declare
  answers 404, never a file of WebUI's default root (the working directory).
  WebUI turns its authentication cookie off for the whole process when a file
  handler is installed; the host turns it back on, so a window stays bound to
  the first browser that loaded its `webui.js`.
- **`IAssetSource.Subdirectory(path, entryPoint = "index.html")`** presents one
  folder of a source, such as an archive with a main window's and a secondary
  window's frontend, as a frontend of its own (#730), for every host's
  `Assets` option. It fails with `DirectoryNotFoundException` for a folder
  without assets and `FileNotFoundException` for one without its entry point.

### Behaviour changes

- `RUNICBRIDGE030` no longer reports `Embedded` for the CS-WebUI host. A
  CS-WebUI project that set `RunicApplicationFrontendDelivery=Embedded` built
  as `Files` with the warning; it now embeds the frontend, and its build and
  publish output have no `www/`.
- `Runic.Application.Views.CsWebUi` depends on `Runic.Assets`.

## Startup (S1)

Measured on linux-x64 with NativeAOT unless stated; [the tables](../../../tests/benchmarks/native-server/results/linux-x64.md)
and [the asset archive benchmark](../../../tests/benchmarks/asset-archive/results/linux-x64.md) have the details.

### Changes

- **Embedded asset archives are read on demand.** `AssetArchive.ReadEmbedded`, which the Desktop, WPF and CS-WebUI
  hosts use for `RunicApplicationFrontendDelivery=Embedded`, reads the archive's manifest and ZIP directory in place
  and inflates each asset when it is first requested, instead of inflating and SHA-256-checking every asset at
  startup. For a 6 MiB frontend (1.9 MiB packed) the load takes 0.4 instead of 15.9 ms, the first page's assets
  5.5 ms, and the process's peak memory falls from 26 to 14 MiB. The digests are checked at build time instead: the
  archive is part of the assembly that holds the application's code. The packer reads back every archive it writes,
  and the build checks a `RunicAssetsEmbeddedArchive` before embedding it (`RAS2006`). An asset that inflates to
  another length or whose ZIP entry is damaged fails when it is opened. `AssetArchive.Read` and `ReadAsync`, for an
  archive file loaded at run time, still check every digest before they return; `ValidateAsync` checks them on
  demand.
- **No OpenSSL on Linux.** Window tokens, session credentials, client cookies and browser launch codes come from
  `getrandom(2)` instead of `RandomNumberGenerator`, which loaded OpenSSL (about 1.7 ms and 4.7 MiB) before the first
  window opened. Windows and macOS keep `RandomNumberGenerator`, which loads no extra library there.
- **No ICU in the host.** The surface's URL, the request path up to the first served page and the bootstrap script no
  longer touch culture data, which loaded ICU (about 1.9 ms and 4.8 MiB). An application that formats or compares
  text for a culture still loads ICU when it first does; templates keep full globalization, and
  [Packaging](../../../docs/packaging.md#startup-readytorun-and-invariant-globalization) names
  `InvariantGlobalization` as an option with its trade-offs.
- Together, for the Runic Desktop example on the native server (NativeAOT, serve-only, `LANG=C`): its URL is ready
  after 6.7 instead of 9.5 ms and its first page served after 10.1 instead of 12.6 ms, with 14.4 instead of
  24.2 MiB resident. A hello-world program takes 3 ms, so Runic's share of the URL halved from 6.6 to 3.6 ms.
- **The Views generator runs once per incremental build.** The bootstrap pass wrote its composition stub with a
  second generator process on every build; it now writes it only when the composition type, the generator or a
  referenced assembly changed (2 generator processes, 127–159 ms, to 1, 90–104 ms, in an incremental build of the
  Runic Desktop example).

### Added

- `Runic.Assets.Packer verify <archive>`, which the build runs on `RunicAssetsEmbeddedArchive`, with `RAS1006`,
  `RAS1007` and the build error `RAS2006`.
- `native-server.yml` measures a hello-world program beside each publish mode, the floor of the platform's process
  start, and checks that a NativeAOT Runic Desktop application loads neither ICU nor OpenSSL before its first page
  is served.

### Fixes

- **`PublishReadyToRun` works.** A publish with `-p:PublishReadyToRun=true` passed the property to the Views
  generator's own build and to the bootstrap pass, which clear the runtime identifier, and failed with
  `NETSDK1191`, as `PublishTrimmed` did before 0.14. ReadyToRun is now
  [recommended](../../../docs/packaging.md#startup-readytorun-and-invariant-globalization) for framework-dependent
  and self-contained publishes, though not a default: the example serves its first page framework-dependent after
  114 instead of 166 ms, and its publish grows from 15 to 25 MiB.

## Cleanups (C1)

### Breaking changes

- **`runicDevSession()` is removed** from `@runic-artifex/vite-plugin-runic`
  (deprecated in 0.14). A SvelteKit `vite.config.ts` that still imports it
  fails to load: use `runic({ html: false })`, which answers the
  `dotnet runic dev` session too, and load the development client from
  `src/hooks.client.ts`. `dotnet runic dev` no longer looks for its plugin
  (`runic:dev-session`) when it decides whether the server must confirm the
  session.

### Added

- **A state inspector in the development client.** With
  `@runic-artifex/views` 0.15, the client reports each open View's state as
  the page shows it, and the Vite DevTools dock shows it on a **Views** card:
  a card per View with its route, revision and presentation epoch, and the
  state as a tree. The state is bounded and redacted like timeline details
  (credential- and path-like members and values read `[redacted]`); it is also
  `views` in `/__runic/state`, for the Angular CLI. Development only: the
  build replaces the client with an empty module, and `@runic-artifex/views`
  reports nothing until the client asks (`runic.views.inspector` in
  `specs/application/README.md`, "Shared globals").
- **Superseded commands are visible in development.** A command the Bridge
  answered `superseded` resolves like one that ran (V5), so the page shows
  nothing; the client adds a timeline entry (`<member> superseded`,
  `detail.code: "superseded"`, with the route, the epoch it was issued for and
  the reply's revision), and the dock lists the latest on a **Superseded
  commands** card.
- `@runic-artifex/vue`: `useField`'s `commit()` resolves with the field's
  state, as in React, Svelte and Angular (it resolved with nothing), so Save
  can skip a failed write:
  `if ((await title.commit()).error === undefined) await editor.save()`.

### Documentation

- The Vue, Svelte and Angular READMEs say that `commit()` resolves with the
  field's state.
- The 0.14.0 notes say that Runic is tested against the ReactiveUI.Validation
  and DynamicData forks; no Runic package depends on them.
- `eng/release/README.md` step 6 lists the RS0026 suppressions that remain.
- The Runic.Desktop README says that `ConnectionTimeout` starts at an embedded
  WebView's first navigation: a slow first WebView2 start after a runtime
  update (tens of seconds) delays the window but does not use up the timeout.

### Fixed

- **A probe of a Desktop window's listener no longer counts as its page.** A
  development tool that requests each new loopback listener (t3code's preview
  discovery sends `GET /` with `User-Agent: node`) or a security scanner made a
  stalled browser look connected, so it was not relaunched, and moved the
  connection deadline. Only requests that carry the window's client cookie,
  which the page's first response sets, or the launched browser's launch code
  count, on Kestrel and on the native server; a WebSocket that offers the
  session credential counts too. Other requests get their usual answer. A probe
  also no longer ends an embedded WebView's progress extension (event 3021). A
  timeout before any request from the page names the first other request, which
  can also be the page's own first request when it loaded nothing after it.
- A show whose connection wait timed out, relaunched a stalled browser or was
  cancelled no longer leaves an unobserved task exception ("The window closed
  before bridge authentication completed") for `TaskScheduler.UnobservedTaskException`;
  neither does a browser-launch conflict while nothing waits for the connection.

## Windows administration (W1)

### Breaking changes

- `AdministrationErrorCategory.NotInstalled` (7) is reported for a component that
  is not installed or registered: class not registered (`0x80040154`, for example
  the Group Policy Management Console) and a missing WMI namespace or class
  (`0x8004100E`, `0x80041010`, for example the MicrosoftDNS provider on a computer
  without the DNS role). These were `Unavailable`, which now means only that an
  installed machine, endpoint or service cannot be reached (sdk#744).
- Native 1332 (no account mapping), 1376, 2220 (missing local group), 1387
  (missing member account) and 2221 are `NotFound`; 1388 (invalid member kind) is
  `InvalidData`. They were `NativeFailure` (sdk#738).
- Native 1460 (`ERROR_TIMEOUT`, for example a DNS server that does not answer) is
  `Unavailable`; it was `NativeFailure` (sdk#728).
- Native 1051 (`ERROR_DEPENDENT_SERVICES_RUNNING`), 1061 (a service cannot accept
  the control now) and 1062 (a service is not running) are `Conflict`, as 1056
  (already running) was; they were `NativeFailure` (sdk#739).

### Added

- `DomainMembership.DnsDomainName` and `ForestName`, read locally from
  `DsRoleGetPrimaryDomainInformation` without contacting a controller; null for a
  workgroup (sdk#744).
- `WindowsDomainClient.DiscoverControllerAsync(domainName, requirePrimary,
  requireWritable, DomainControllerNameFormat, cancellationToken)`:
  `DomainControllerNameFormat.Flat` returns the controller's and domain's NetBIOS
  names (`DS_RETURN_FLAT_NAME`), as `Win32_NTDomain.DomainControllerName` did
  (sdk#744).
- `WindowsFirewallClient.DeleteAllAsync(name)` deletes every rule of a native name,
  as `netsh advfirewall firewall delete rule name=…` does, and returns the number
  deleted; `DeleteAsync` still requires a unique identity (sdk#740).
- `FirewallClientOptions.WriteWhenLocalPolicyOverridden` and the
  `WindowsFirewallClient(FirewallClientOptions)` constructor: an explicit opt-in to
  write the local store while Group Policy overrides local rules or inbound traffic
  is blocked, which is refused by default. `GetLocalPolicyStateAsync()` reports the
  state as `FirewallLocalPolicyState` (sdk#740).
- `WindowsLocalGroupClient` (namespace `Accounts`): `AddMemberAsync`,
  `RemoveMemberAsync`, `EnumerateMembersAsync` and `GetGroupNameAsync` for local
  groups on the local or a remote computer (NetAPI). Groups and members are an
  `AccountReference.Name` or an `AccountReference.Sid`, so a well-known SID such
  as `S-1-5-32-544` addresses Administrators in every UI language. "Already a
  member" (1378) and "not a member" (1377) are returned as `false`; members carry
  SID, `DOMAIN\name` and `AccountKind` (sdk#738).
- `WindowsDnsResolverClient` (namespace `Dns`): resolver queries against one
  chosen DNS server by IP address (`DnsQueryEx` with a server list), bypassing the
  resolver cache, hosts file, LLMNR, NetBIOS and DNS suffixes. `QueryAsync(name,
  DnsRecordType)` and `ReverseLookupAsync(address)` return a `DnsResolution` with
  the `DnsResponseCode` (a name error is a result) and the answer records as
  `DnsAnswer` with typed `DnsRecordData` for A, AAAA, CNAME, PTR, MX, TXT, SRV and
  NS; `ReverseLookupName(address)` builds reverse names (sdk#728).
- `ProcessSnapshot.ImagePath`, the full executable path
  (`QueryFullProcessImageNameW`; null when access is denied), and
  `WindowsProcessClient.FindByImagePath(path)` to find the running instances of
  one program among programs that share a file name (sdk#729).
- `WindowsProcessClient.CloseOrKillAsync(processId, timeout)`: posts `WM_CLOSE` to
  the process's visible, unowned top-level windows (not console windows), waits, and terminates it otherwise, returning
  `ProcessCloseOutcome` (`NotRunning`, `Closed`, `Killed`);
  `TerminateAsync(processId, exitCode)` terminates at once (`taskkill /F`); and
  `StartAndWaitAsync(ProcessStartSpecification)` starts a program, optionally
  elevated through the shell's `runas` verb, and returns its exit code (sdk#729,
  sdk#739).
- `WindowsServiceClient.StopWithDependentsAsync(name, timeout)` stops the active
  dependents in dependency order, waits for them, requests the service's stop and
  returns the dependents it stopped (sdk#739).
- `ServiceSnapshot.ExecutablePath`: the executable of `BinaryCommandLine` as the
  Service Control Manager parses it, including the search through the prefixes of
  an unquoted path with spaces on the local computer (sdk#739).
- `WindowsSystemInformationClient.GetActiveConsoleUser()` returns the user signed
  in at the physical console (`WTSGetActiveConsoleSessionId`,
  `WTSQuerySessionInformationW`) as `ConsoleUser`, or null (sdk#739).

## Runic Desktop: an ordered list of fallback presentations (H1)

### Added

- **`DesktopWindowOptions.Fallbacks`** lists the presentations a window tries,
  in order, when the first one cannot open, for example
  `Browser = BrowserKind.Embedded, Fallbacks = [BrowserKind.ChromiumBased, BrowserKind.Firefox]`
  (#725). Before, `EmbeddedThenBrowser` tried the embedded WebView and one
  browser, and an application that needed a longer chain opened windows one
  after the other itself. `EmbeddedThenBrowser` stays the shorthand for the
  embedded WebView with one browser; a non-empty `Fallbacks` replaces that
  browser. A chain that repeats a presentation is `window-option-invalid`.
- **`DesktopPresentationException`** (a `DesktopException`) is thrown when no
  presentation of a chain opens. `Attempts` lists each presentation with the
  `DesktopException` it failed with, such as `browser-not-found`, so the
  application can show why each one failed; `Code`, `Category` and the inner
  exception are the last attempt's.
- `DesktopPresentationPreflight.Fallbacks` reports the availability of every
  fallback; `Fallback` remains the first one.
- Diagnostic `presentation-fallback` (Warning) when an installed browser of the
  chain fails and the next presentation is tried; the embedded WebView keeps
  `embedded-presentation-fallback`.

### Behaviour changes

- When the `EmbeddedThenBrowser` fallback browser fails too, `OpenWindowAsync`
  throws a `DesktopPresentationException` with the same `Code` and `Category`
  as before; its inner exception is now the browser's `DesktopException`, and
  the embedded WebView's failure is in `Attempts`.

## Desktop presentation servers (X2)

### Breaking changes

- `Runic.Desktop` no longer references the ASP.NET Core shared framework
  (`Microsoft.AspNetCore.App`). ASP.NET Core Kestrel, which served every Runic
  Desktop window, is the new package `Runic.Desktop.Kestrel`. A Runic Desktop
  application references it, or the native server `Runic.Desktop.NativeServer`,
  next to `Runic.Application.Views.Desktop`, `Runic.Application.Views.Wpf` or
  `Runic.Desktop`; an executable without either fails to build with
  `RUNICDESK004`. New applications use the native server (see below).
  Code that compiled against ASP.NET Core or `Microsoft.Extensions.Hosting`
  types through `Runic.Desktop` gets them from `Runic.Desktop.Kestrel`. See
  [Upgrading to 1.0](../../../docs/migration-1.0.md#desktop-presentation-server).
- `RunicDesktopMinimalHost` and `RUNICDESK001` belong to `Runic.Desktop.Kestrel`.

### Added

- `Runic.Desktop.Kestrel`: ASP.NET Core Kestrel as the presentation server, the
  same server and behaviour as 0.14. It has no public API; referencing it is the
  choice.
- `RunicDesktopServer` is a `Runic.Desktop` property: `Kestrel`, `Native` or
  `None` for an executable that opens no Runic Desktop window. With one server
  package it selects that server; with both, `Native` unless set. `RUNICDESK003`
  reports another value, `RUNICDESK004` a missing server package.
- A window that starts without any server fails with `DesktopException`
  `presentation-server-unavailable` instead of a type load error.

### Changes

- Runic Desktop's request handling no longer uses ASP.NET Core's `HttpContext`:
  both servers present requests through one internal exchange, and the native
  server no longer builds an ASP.NET Core `DefaultHttpContext` per request.
  Media types keep ASP.NET Core 10's table, and the client cookie, `Host` check,
  redirects and content security policy headers are unchanged.

### The native server for new applications

The native server becomes the default Desktop server at 1.0, with Kestrel as
the opt-in (D053.24). In 0.15:

- `Runic.Desktop.NativeServer` is no longer experimental, and it and its
  `Runic.Desktop.NativeServer.Static.<rid>` packages are published with the SDK.
  `RUNICDESK102` is retired: remove a `NoWarn` entry for it.
- `dotnet new runic-app` and `dnx Runic.Create` create Desktop applications on
  the native server; the new
  `--desktop-server kestrel` option creates them on `Runic.Desktop.Kestrel`.
  A template application then needs only the .NET runtime, and its NativeAOT
  executable is about a quarter smaller (linux-x64: 9.97 instead of 12.96 MiB).
- `RUNICDESK004` names the native server first.
- Nix: a template application's flake builds the native server from source and
  runs on the .NET runtime without ASP.NET Core, from its lock file alone.

### Native server: packages, Nix and measurements

- The NativeAOT static libraries moved into one package per runtime
  identifier, `Runic.Desktop.NativeServer.Static.<rid>` (≈6 MiB each), which
  NuGet restores through the main package's `runtime.json` only for a
  runtime-specific restore of that identifier. The main package keeps the
  shared libraries of all seven runtime identifiers, ≈4 MiB instead of ≈45 MiB.
  The static library no longer reaches the output of a self-contained JIT
  publish. `RUNICDESK005` reports a NativeAOT publish without it.
- `RunicDesktopNativeServerLibraryDirectory` replaces the package's libraries
  with a directory's.
- Nix: `buildRunicApplication` builds the native server's library from source
  (`nix/runic-server.nix`) for an application whose lock files list
  `Runic.Desktop.NativeServer`, or with `nativeServer = true`; `runicServer`
  replaces the library. Its default `dotnet-runtime` is then the .NET runtime
  without ASP.NET Core.
- The `native-server.yml` workflow runs the Desktop suite on the native server
  on Windows and macOS too, consumes the packed packages as an application
  would on each platform (JIT, self-contained and NativeAOT,
  `eng/native/verify-native-server-package.mjs`), checks the macOS library's
  signature, and measures size and startup on both servers
  (`tests/benchmarks/native-server/measure.mjs`).
