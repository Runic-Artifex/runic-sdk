## Windows administration (W1)

### Breaking changes

- `AdministrationErrorCategory.NotInstalled` (7) is reported for a component that
  is not installed or registered: class not registered (`0x80040154`, for example
  the Group Policy Management Console) and a missing WMI namespace or class
  (`0x8004100E`, `0x80041010`, for example the MicrosoftDNS provider on a computer
  without the DNS role). These were `Unavailable`, which now means only that an
  installed machine, endpoint or service cannot be reached (sdk#744).
- Native 1332 (no account mapping), 1376, 2220 (missing local group), 1387
  (missing member account) and 2221 are `NotFound`; 1388 (invalid member kind) is
  `InvalidData`. They were `NativeFailure` (sdk#738).
- Native 1460 (`ERROR_TIMEOUT`, for example a DNS server that does not answer) is
  `Unavailable`; it was `NativeFailure` (sdk#728).
- Native 1051 (`ERROR_DEPENDENT_SERVICES_RUNNING`), 1061 (a service cannot accept
  the control now) and 1062 (a service is not running) are `Conflict`, as 1056
  (already running) was; they were `NativeFailure` (sdk#739).

### Added

- `DomainMembership.DnsDomainName` and `ForestName`, read locally from
  `DsRoleGetPrimaryDomainInformation` without contacting a controller; null for a
  workgroup (sdk#744).
- `WindowsDomainClient.DiscoverControllerAsync(domainName, requirePrimary,
  requireWritable, DomainControllerNameFormat, cancellationToken)`:
  `DomainControllerNameFormat.Flat` returns the controller's and domain's NetBIOS
  names (`DS_RETURN_FLAT_NAME`), as `Win32_NTDomain.DomainControllerName` did
  (sdk#744).
- `WindowsFirewallClient.DeleteAllAsync(name)` deletes every rule of a native name,
  as `netsh advfirewall firewall delete rule name=…` does, and returns the number
  deleted; `DeleteAsync` still requires a unique identity (sdk#740).
- `FirewallClientOptions.WriteWhenLocalPolicyOverridden` and the
  `WindowsFirewallClient(FirewallClientOptions)` constructor: an explicit opt-in to
  write the local store while Group Policy overrides local rules or inbound traffic
  is blocked, which is refused by default. `GetLocalPolicyStateAsync()` reports the
  state as `FirewallLocalPolicyState` (sdk#740).
- `WindowsLocalGroupClient` (namespace `Accounts`): `AddMemberAsync`,
  `RemoveMemberAsync`, `EnumerateMembersAsync` and `GetGroupNameAsync` for local
  groups on the local or a remote computer (NetAPI). Groups and members are an
  `AccountReference.Name` or an `AccountReference.Sid`, so a well-known SID such
  as `S-1-5-32-544` addresses Administrators in every UI language. "Already a
  member" (1378) and "not a member" (1377) are returned as `false`; members carry
  SID, `DOMAIN\name` and `AccountKind` (sdk#738).
- `WindowsDnsResolverClient` (namespace `Dns`): resolver queries against one
  chosen DNS server by IP address (`DnsQueryEx` with a server list), bypassing the
  resolver cache, hosts file, LLMNR, NetBIOS and DNS suffixes. `QueryAsync(name,
  DnsRecordType)` and `ReverseLookupAsync(address)` return a `DnsResolution` with
  the `DnsResponseCode` (a name error is a result) and the answer records as
  `DnsAnswer` with typed `DnsRecordData` for A, AAAA, CNAME, PTR, MX, TXT, SRV and
  NS; `ReverseLookupName(address)` builds reverse names (sdk#728).
- `ProcessSnapshot.ImagePath`, the full executable path
  (`QueryFullProcessImageNameW`; null when access is denied), and
  `WindowsProcessClient.FindByImagePath(path)` to find the running instances of
  one program among programs that share a file name (sdk#729).
- `WindowsProcessClient.CloseOrKillAsync(processId, timeout)`: posts `WM_CLOSE` to
  the process's visible, unowned top-level windows (not console windows), waits, and terminates it otherwise, returning
  `ProcessCloseOutcome` (`NotRunning`, `Closed`, `Killed`);
  `TerminateAsync(processId, exitCode)` terminates at once (`taskkill /F`); and
  `StartAndWaitAsync(ProcessStartSpecification)` starts a program, optionally
  elevated through the shell's `runas` verb, and returns its exit code (sdk#729,
  sdk#739).
- `WindowsServiceClient.StopWithDependentsAsync(name, timeout)` stops the active
  dependents in dependency order, waits for them, requests the service's stop and
  returns the dependents it stopped (sdk#739).
- `ServiceSnapshot.ExecutablePath`: the executable of `BinaryCommandLine` as the
  Service Control Manager parses it, including the search through the prefixes of
  an unquoted path with spaces on the local computer (sdk#739).
- `WindowsSystemInformationClient.GetActiveConsoleUser()` returns the user signed
  in at the physical console (`WTSGetActiveConsoleSessionId`,
  `WTSQuerySessionInformationW`) as `ConsoleUser`, or null (sdk#739).

## Runic Desktop: an ordered list of fallback presentations (H1)

### Added

- **`DesktopWindowOptions.Fallbacks`** lists the presentations a window tries,
  in order, when the first one cannot open, for example
  `Browser = BrowserKind.Embedded, Fallbacks = [BrowserKind.ChromiumBased, BrowserKind.Firefox]`
  (#725). Before, `EmbeddedThenBrowser` tried the embedded WebView and one
  browser, and an application that needed a longer chain opened windows one
  after the other itself. `EmbeddedThenBrowser` stays the shorthand for the
  embedded WebView with one browser; a non-empty `Fallbacks` replaces that
  browser. A chain that repeats a presentation is `window-option-invalid`.
- **`DesktopPresentationException`** (a `DesktopException`) is thrown when no
  presentation of a chain opens. `Attempts` lists each presentation with the
  `DesktopException` it failed with, such as `browser-not-found`, so the
  application can show why each one failed; `Code`, `Category` and the inner
  exception are the last attempt's.
- `DesktopPresentationPreflight.Fallbacks` reports the availability of every
  fallback; `Fallback` remains the first one.
- Diagnostic `presentation-fallback` (Warning) when an installed browser of the
  chain fails and the next presentation is tried; the embedded WebView keeps
  `embedded-presentation-fallback`.

### Behaviour changes

- When the `EmbeddedThenBrowser` fallback browser fails too, `OpenWindowAsync`
  throws a `DesktopPresentationException` with the same `Code` and `Category`
  as before; its inner exception is now the browser's `DesktopException`, and
  the embedded WebView's failure is in `Attempts`.

## Desktop presentation servers (X2)

### Breaking changes

- `Runic.Desktop` no longer references the ASP.NET Core shared framework
  (`Microsoft.AspNetCore.App`). ASP.NET Core Kestrel, which served every Runic
  Desktop window, is the new package `Runic.Desktop.Kestrel`. A Runic Desktop
  application references it, or the experimental `Runic.Desktop.NativeServer`,
  next to `Runic.Application.Views.Desktop`, `Runic.Application.Views.Wpf` or
  `Runic.Desktop`; an executable without either fails to build with
  `RUNICDESK004`. `dotnet new runic-app` references `Runic.Desktop.Kestrel`.
  Code that compiled against ASP.NET Core or `Microsoft.Extensions.Hosting`
  types through `Runic.Desktop` gets them from `Runic.Desktop.Kestrel`. See
  [Upgrading to 1.0](../../../docs/migration-1.0.md#desktop-presentation-server).
- `RunicDesktopMinimalHost` and `RUNICDESK001` belong to `Runic.Desktop.Kestrel`.

### Added

- `Runic.Desktop.Kestrel`: ASP.NET Core Kestrel as the presentation server, the
  same server and behaviour as 0.14. It has no public API; referencing it is the
  choice.
- `RunicDesktopServer` is a `Runic.Desktop` property: `Kestrel`, `Native` or
  `None` for an executable that opens no Runic Desktop window. With one server
  package it selects that server; with both, `Native` unless set. `RUNICDESK003`
  reports another value, `RUNICDESK004` a missing server package.
- A window that starts without any server fails with `DesktopException`
  `presentation-server-unavailable` instead of a type load error.

### Changes

- Runic Desktop's request handling no longer uses ASP.NET Core's `HttpContext`:
  both servers present requests through one internal exchange, and the native
  server no longer builds an ASP.NET Core `DefaultHttpContext` per request.
  Media types keep ASP.NET Core 10's table, and the client cookie, `Host` check,
  redirects and content security policy headers are unchanged.

### Experimental native server: packages, Nix and measurements

`Runic.Desktop.NativeServer` stays experimental (`RUNICDESK102`) and outside the
release inventory.

- The NativeAOT static libraries moved into one package per runtime
  identifier, `Runic.Desktop.NativeServer.Static.<rid>` (≈6 MiB each), which
  NuGet restores through the main package's `runtime.json` only for a
  runtime-specific restore of that identifier. The main package keeps the
  shared libraries of all seven runtime identifiers, ≈4 MiB instead of ≈45 MiB.
  The static library no longer reaches the output of a self-contained JIT
  publish. `RUNICDESK005` reports a NativeAOT publish without it.
- `RunicDesktopNativeServerLibraryDirectory` replaces the package's libraries
  with a directory's.
- Nix: `buildRunicApplication` builds the native server's library from source
  (`nix/runic-server.nix`) for an application whose lock files list
  `Runic.Desktop.NativeServer`, or with `nativeServer = true`; `runicServer`
  replaces the library. Its default `dotnet-runtime` is then the .NET runtime
  without ASP.NET Core.
- The `native-server.yml` workflow runs the Desktop suite on the native server
  on Windows and macOS too, consumes the packed packages as an application
  would on each platform (JIT, self-contained and NativeAOT,
  `eng/native/verify-native-server-package.mjs`), checks the macOS library's
  signature, and measures size and startup on both servers
  (`tests/benchmarks/native-server/measure.mjs`).
