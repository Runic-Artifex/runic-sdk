# Runic SDK 0.14.0

Install matching `0.14.0` packages from NuGet and npm;
`Runic.Application.Views.CsWebUi` is `0.14.0-preview.1`.
Command Line versions remain independent of this SDK.

## Fixes

- A reply of a Views setter, checked write, command or operation start no longer
  resumes its caller inside a route's delivery. A caller that then waited
  synchronously for another reply, as a test that mixes `RequestAsync` with
  `Request` does, blocked that delivery: the route stopped publishing and every
  later reply waited 5 seconds. A reply that waits the full 5 seconds for its
  window's pushes is now logged once per window (`BridgeReplyWaitExceeded`,
  1024).

## Fork integration: validation and DynamicData (V1)

### Breaking changes

- `ViewModelBridge<T>`'s constructor takes a last optional parameter
  `BridgeValidationReader? validationReader`. Generated bridges are regenerated
  by the build; a hand-written bridge recompiles unchanged.
- An empty or blank validation message is reported as `Invalid value.`, in
  `validation` and in the `…Errors` arrays, instead of an empty string.

### Added

- **Rule changes reach the page.** The generated Bridge observes each
  ReactiveUI.Validation `ValidationContext` (`ValidationStatusChange`) of the
  ViewModel and of every object in its state graph. A rule that names no
  property, such as `this.ValidationRule(observable, message)`, now publishes
  `validation` when it changes; before, `ReactiveValidationObject` raised no
  event for it unless `HasErrors` changed.
- **`applied.validation`** of a checked write receipt carries the property's
  messages after the write, one per line, when the write left it invalid
  (`specs/application/README.md`, "Checked writes"); it was never set.
- **`IValidatableViewModel` without `INotifyDataErrorInfo`** (D053.3): a
  ViewModel or DTO that only implements ReactiveUI.Validation's
  `IValidatableViewModel` (either flavor) gets the `validation` member, as the
  Views README promised; it had none. Its `ValidationContext` property is left
  out of the contract. Such ViewModels' contract fingerprints change.
- Warning `RUNICBRIDGE031` for a type that implements an `IValidatableViewModel`
  of neither ReactiveUI.Validation flavor.
- `RunicValidationMessage.MemberPaths` may index lists and dictionaries:
  `Items[0].Name`, `Lookup[primary].Name`, `Groups[0][1]`.
- A nested DTO that derives from `ReactiveValidationObject` (either flavor)
  keeps `HasErrors` and `ValidationContext` out of its contract instead of
  failing with RUNICBRIDGE003.
- `BridgeValidation.Observe`, `BridgeValidation.WriteMessages` and
  `BridgeValidationReader` for generated code.

- **Collections and text of ViewModels with validation publish frames.** The
  generator no longer marks their `[RunicCollection]` descriptors
  `PublishesChanges: false` or their `[RunicAppendOnlyText]` members as plain
  members, a protocol 3 rule: a protocol 4 frame carries the indexed or text
  changes together with the `validation` they cause. Contract fingerprints do
  not change.
- Event 1025 `BridgeCollectionChangedOutsideModelTurn` (Warning, once per
  Bridge and field) when an observed collection changes outside the window's
  model turn, such as a DynamicData `Bind` without `ObserveOn` the window's
  scheduler.
- A System.Reactive DynamicData consumer check (`DynamicData.Reactive`,
  `Runic.Application.Views.ReactiveUI.Reactive`, `BatchBridgeSnapshots`), a
  frame-replay check (a viewport move, `SortAndBind` comparer changes, moves)
  and a NativeAOT publish with `RunicArtifex.ReactiveUI.Validation`.

### Fixes

- A disposed `ReactiveValidationObject`, whose `HasErrors` keeps its last
  value, reported `hasErrors: true` with no errors. An object read through its
  `ValidationContext` now takes `hasErrors` from its messages.
- A change notification after the window's model context closed threw
  `ObjectDisposedException` into the code that raised it, such as a DynamicData
  `Bind`, which ended the binding. It now counts as a change for a released
  Bridge.
- The scheduler diagnostic (event 1043) took application assemblies whose
  names start with a library's, such as `DynamicDataViewer` or
  `ReactiveUIDemo`, for that library and named no ViewModel. It now matches
  the exact name or a dotted child (`DynamicData.Reactive`).

### Specifications

- `specs/application/README.md` has a language-neutral
  [Validation](https://github.com/Runic-Artifex/runic-sdk/blob/v0.14.0/specs/application/README.md#validation)
  section: the wire shape of `validation` and `{name}Errors`, paths, order,
  limits and the rule that each message appears once (D033). Derived members
  such as `validation` are not covered by the client overlay. The conformance
  corpus has the `form` test View, the `rule` mutation and two scenarios: an
  edit followed by the frame with its validation, and a rule that names no
  member.

### Documentation

- The DynamicData example names the System.Reactive flavor's
  `DynamicData.Reactive.*` namespaces, and the ReactiveUI adapter's README has
  its own DynamicData section for both flavors.
- `eng/workspace.json` records the fork's `dynamicData.packageVersion` beside
  `forkRevision`; the engineering tests require the lock files to resolve it,
  and the DynamicData workflow requires the fork's `v{packageVersion}` tag to
  be the pinned revision. The workflow also runs for changes to the

## Producer performance (T1)

### Behaviour changes

- **Views: notification frames are at least 8 ms apart per route.** A route
  publishes the first change after a pause at once; further notifications
  within 8 ms coalesce into one frame that follows when the interval has
  passed, so the last change is always published. A model that raised 10,000
  notifications a second sent about 9,800 frames a second, and now sends 125.
  Replies are not delayed: a setter, command or checked write still publishes
  its change before it replies, together with any change that waited for the
  interval. A page that counts frames per notification can see fewer frames;
  the protocol always left a publication unit's size to the producer.
- **Views: a set encodes the state once.** The unit that a setter's own
  notification requested is skipped when the reply already published the
  change. Each unit compares a member with what the page has while it writes
  it, and keeps a new encoding only when it differs. A keystroke beside an
  unkeyed list of 10,000 rows took 6.4 ms and allocated 12.7 MB, and takes
  1.9 ms and 5 KB.
- **Views: changes of an observed collection no longer walk the data graph.**
  An added row only subscribes the row; a removed, replaced or reset row is
  released at the end of the publication unit. 500 single adds to an
  observable `[RunicCollection]` of 10,000 rows took 377 ms and allocated
  568 MB, and take 1.6 ms and 1.1 MB.
- **Views: pushes use pooled memory, and an open after attach reuses the first
  state.** States and frames are written into pooled buffers and members go
  straight into the message; the transport receives memory that is valid until
  `BroadcastAsync` completes, as `IBridgeTransport` documents. A custom
  transport that keeps the memory of a push after its task completed must copy
  it. An `open` of a route that has not changed since it attached copies the
  state captured at attach instead of encoding it again. Attaching and opening
  a route with 100,000 keyed rows took 95 ms and allocated 222 MB, and takes
  49 ms and 58 MB.
- **Views: a route's delivery no longer blocks a thread-pool thread for its
  model turn.** It awaits the model context's turn, so many routes of a busy
  model context no longer grow the thread pool: 64 routes on one context grew
  it from 4 to 49 threads, and now to 9.

### Added

- **`RUNICBRIDGE032`** (warning): a state property is an observable collection
  of DTO rows (`ObservableCollection<T>`, `ReadOnlyObservableCollection<T>`)
  that is not a `[RunicCollection]`, so every change encodes and sends the
  whole list. Declare the rows' key, or suppress the warning for a list that
  stays small.

## Text splices and requests with `hello` (P1)

- **Long text members cross as splices.** A keystroke in a 100,000-character
  `string` member sends about 130 bytes and receives about 160, instead of
  about 100 KB each way, and the host takes 35 µs and 200 KB instead of 60 µs
  and 300 KB. The page's client and the host negotiate the new
  `text-splice/1` feature in `hello`; nothing needs to be declared.
- **`open` goes out with `hello`.** A page sends its first requests without
  waiting for the `hello` reply, one round trip less per page load.

### Upgrading

Update every Runic NuGet and npm package to 0.14.0 together and rebuild so that
the generated clients, bridges and mocks are regenerated. Check these if they
apply to you; the [migration guide](https://github.com/Runic-Artifex/runic-sdk/blob/v0.14.0/docs/migration-1.0.md#from-013-to-014)
has before and after tables:

- An operation started under 0.13 and recovered after the upgrade is `unknown`:
  every contract fingerprint changes (prefix `runic-bridge-contract-v6`).
- Tests that send a request before `hello` to `InMemoryBridgeTransport` or the
  mock Bridge, and expect `no-hello`, now wait 5 seconds for a `hello` first.

#### Compatibility

- **Views protocol 4** stays protocol 4: features are additive. A 0.13 page and
  a 0.14 host, or the reverse, connect, list no common feature and use whole
  values; the `version` diagnostic reports the different releases as before.

### Breaking changes

#### Views: contract fingerprints

- Generated contract fingerprints start with `runic-bridge-contract-v6` and
  list each text member, because the members that accept splices are visible
  on the wire. Operations are identified by `{view}:{fingerprint}`, so an
  operation started by a 0.13 page is `unknown` to a 0.14 host.

### Behaviour changes

#### Views: `hello` and requests sent with it

- **Requests wait for `hello`.** A request that arrives on a connection before
  its `hello` succeeded is held, up to 5 seconds and 64 per connection, and
  admitted in arrival order once the `hello` succeeds; a `hello` that fails, a
  closed connection or the 5 seconds answer it `no-hello`. A `receive` is never
  held. CS-WebUI, which runs each call on its own thread, can deliver an `open`
  before the `hello` it followed; it now waits instead of failing.
- **`@runic-artifex/views` sends `open` with `hello`.** The runtime sends a
  connection's first requests right after its `hello`, without waiting for the
  reply, and sends a request answered `no-hello` again once the `hello`
  succeeded, so it also works against a 0.13 host.
- Log event 1019 `BridgeRequestBeforeHello` now reports a request answered
  `no-hello`, not every request before the `hello`.
- The mock Bridge (`@runic-artifex/views/mock`) holds requests before `hello`
  the same way, on its virtual clock with `scheduling: "manual"`.

#### Views: text members

- `string` state members are compared as strings at publication instead of by
  their encoding; what is published does not change without the feature.

### Added

#### Views protocol: features and `text-splice/1`

([#704](https://github.com/Runic-Artifex/runic-sdk/pull/704))

- **`hello` features.** The `hello` request and its successful reply carry
  `features: string[]`, the features each side implements, named
  `{name}/{version}`. A feature is in use on a connection when both lists
  contain it; unknown names are ignored.
- **`text-splice/1`.** Frames may change a text member (a `string` state member
  other than an append-only text field) with `splice` changes
  `{field, kind: "splice", length, index, delete, text, version?}`, and a `set`
  may carry `splice: {baseEdit | baseRevision, length, index, delete, text}`
  instead of `value`. A splice applies to the value the client named (its
  previous edit, or the route's state at a revision); the host rebuilds the
  value and runs the setter with it, so last-writer-wins and every setter rule
  stay as they were. A base the host no longer has is `rejected` with the new
  reason `splice-base` and admits nothing; the client then sends the value in
  full. Positions count UTF-16 code units and never split a surrogate pair. A
  splice that keeps fewer than 64 code units of the old value, `null`, and
  connections without the feature use whole values.
- A window with a page that does not list the feature publishes whole values to
  every page, also for a frame that was on its way when that page connected.

#### Views (.NET)

- `PropertyDescriptor<T>.TextMember` and `PropertyDescriptor<T>.TextSetter`,
  which generated bridges set for text members.
- `Runic.Application.Testing`: `RunicViewPublication.Splices` with
  `RunicTextSplice`; `RunicStateTracker` applies splice frames.
- `TextSpliceBenchmarks` in `tests/benchmarks/Runic.Application.Views.Benchmarks`.

#### Views npm packages

- `ViewConnectOptions.texts`, which generated clients pass, and
  `SharedRuntime.features`.
- `BridgeErrorReason` `"splice-base"`.
- The mock Bridge implements features, held requests and `text-splice/1`;
  `MockViewDefinition.texts` names a View's text members, and generated typed
  mocks fill it in.

### Specifications

- `specs/application/README.md`: "Features", the held requests of the
  handshake, "Text splices in `set`", the reason `splice-base`.
- `specs/application/state-changes.md`: "Text members", "Text splices",
  "Producing splices" and the client's checks.
- Conformance: the requirement `text-splice/1`, 21 scenarios (handshake, state
  changes, edits) and message vectors for `features`, `set` with a splice and
  `splice` changes.

## Testing: asynchronous drivers, typed inputs, window services (A1)

### Added

- **Asynchronous test drivers that never block.** `RunicViewDriver<T>` has
  `SnapshotAsync`, `SetAsync`, `SetJsonAsync`, `WriteAsync`, `MountAsync`,
  `UnmountAsync`, `ViewAsync`, `ViewsAsync` and `TrackAsync`; `RunicTestOperation`
  has `GetStatusAsync`, `CancelAsync` and `ReadStreamAsync`; `RunicStateTracker<T>`
  has `VerifyAsync`. `ExecuteAsync`, `CanExecuteAsync`, `StartAsync` and the
  transport's `RequestAsync` no longer block on the connection's `hello` or on the
  snapshot after a reply, and concurrent requests on one connection share its
  `hello`. The synchronous methods remain and document that they block the calling
  thread: in a suite that runs tests in parallel on the thread pool they can starve
  it, so such suites use the asynchronous ones.
- **Typed command inputs.** `ExecuteAsync(command, argument)`,
  `CanExecuteAsync(command, argument)` and `StartAsync(command, argument)` encode a
  .NET value as the generated client does: objects by wire name (camelCase,
  `[RunicAlias]`, `[JsonPropertyName]`, without ignored members), `[RunicUnion]` cases
  with `$case`, lists, string-keyed dictionaries and `[RunicCodec]` types. `Set` and
  `SetAsync` encode DTOs, lists and unions the same way instead of throwing
  `NotSupportedException`. Wire JSON that is not JSON throws an
  `ArgumentException` naming the typed overload.
- `RunicBridgeMessage.Kind` and `RunicBridgeMessage.Route`, read from the push, so a
  test selects one route's pushes from `TakeMessages()`.
- `RunicWindow<T>.Services` (and `IRunicWindow.Services`): the provider of the
  Window's dependency injection scope, which resolved its ViewModel.
- `RunicWindowTestHost.Create(services, viewModel, options)` creates a test host for a
  ViewModel the test built, without registering it; `RunicWindowTestHost<T>.Services`
  is the provider `Create` used. The Testing README documents the registrations
  `Create` needs.

### Behaviour changes

- **A console test runner gets no `RUNICBRIDGE006`.** A project that references
  `Runic.Application.Testing` directly is a test project, as one with
  `IsTestProject` is: when it declares no Window or View, Bridge generation stays
  off instead of failing with "no Runic Window/View classes found". The
  `RUNICBRIDGE006` message for an assembly without Windows now says how to turn
  generation off in a project that only uses another project's Bridges.

## Windows: activation on every host, a parameter for a new Window (A1)

### Added

- **`IRunicWindowHost.OpenWindowAsync<TWindow>(options, activation, cancellationToken)`.**
  Code that holds only the host-neutral `IRunicWindowHost` opens a Window for a
  launch with its `DesktopActivationContext`. `RunicDesktopHost` presents the new
  window with it, as its own method of the same signature did; other hosts open
  the Window and ignore the context (a default interface implementation, so
  custom hosts compile unchanged). `Runic.Application.Views` now depends on
  `Runic.Platform`, the contracts package that every host adapter already
  brings.
- **A parameter for a new Window.** `host.OpenWindowAsync<TWindow, TParameter>(parameter, options)`
  and `IRunicWindowService.OpenWindowAsync<TWindow, TParameter>(parameter, options)`
  hand a value to the new Window's scope, where its ViewModel takes
  `IRunicWindowParameter<TParameter>` in its constructor. Each Window gets its
  own, also when several open at once, which replaces hand-offs through a shared
  service and a semaphore. `AddRunicWindowService()` registers it; without it, the
  open fails with `window-parameter-not-registered`
  (`RunicWindowConfigurationException.WindowParameterNotRegisteredCode`). A test
  passes `new RunicWindowParameter<TParameter>(value)` to a ViewModel it builds.
  `IRunicWindowService`'s new method has a default implementation that throws
  `NotSupportedException`, so existing fakes compile.

## Runic Desktop: serve-only as an option, URIs without a window (A1)

### Added

- **`RunicDesktopHostOptions.ServeOnly`** serves the host's Windows to a browser,
  as `RUNIC_APPLICATION_SERVE_ONLY=1` does, without an environment variable that
  child processes inherit; `RunicDesktopHost.ServeOnly` reports the mode. With
  either switch, `RunicDesktopHost.Run` starts no window toolkit loop, so

- **URIs without a window**: open a served Window's page in the user's

  `DesktopPlatformServices.ForApplication().FileLauncher.LaunchUriAsync(url)`
  ([below](#platform-dialogs-launcher-and-message-boxes-without-a-window-a2)).

## Runic.Platform: an analyzer for swapped menu item arguments (A1)

### Added

- **`RUNICPLAT001`** (warning, new `RUNICPLAT` family): `new DesktopMenuItem(title, commandId)`
  whose title looks like a command id (`"file.new"`) and whose command id is not
  a valid one or reads like a title (`"New Window"`). The 0.11 rename from

## Linux: the directory picker knows a missing portal up front (A1)

### Fixes

- **`platform.directories.open` reports a missing FileChooser portal before the
  first pick.** The portal file dialogs of a Window read the FileChooser

## Client and host performance (T2)

### Breaking changes

- **Subscribers are notified once per animation frame.** The Views client
  applies each frame when it arrives and delivers the newest state to
  subscribers once per animation frame (a 16 ms timer while the page is
  hidden), instead of once per frame. A burst of 200 frames notifies once.
  Listeners no longer see every intermediate state, and `snapshot`, the state
  subscribers last received, can be up to one frame behind the frames the
  client applied. A setter's value still shows at once, and every call that
  resolves (setters, commands, checked writes, operations) first delivers the
  states that arrived before its reply. The mock Bridge delivers each push at
  once, and `flush()` delivers pending states, so tests keep reading a push's
  result right after it. See the migration guide, "Client notifications".
- **CS-WebUI shows no "Connection with the backend is lost" banner.**
  `runic-cswebui.js` now installs a WebUI event callback to observe the
  connection, and WebUI leaves out its own banner whenever a callback is set.
  A page that relied on that banner shows its own connection state instead,
  for example from `onConnectionChange` or the Views connection-state stream.

### Changed

- **Keyed collections keep a key index.** A frame checks only the keys of the
  rows it changes instead of every key of the collection: replacing one row of
  100,000 takes 0.62 ms instead of 9.1 ms in JavaScriptCore, and 0.23 ms instead
  of 7.9 ms in V8 (`tests/benchmarks/views-client`).
- **Large inserts no longer fail in V8.** An `add`, `replace` or `move` of more
  than 8,192 rows is applied in parts; 150,000 rows in one change threw a
  `RangeError` in V8 (WebView2, Chromium) and made the client recover with a
  snapshot. The mock Bridge's `collections.<field>.add` does the same.
- **Connecting follows the Bridge's connection report.** `waitForBridge`, and
  so every `connect…()` call, continues as soon as an installed Bridge reports
  its connection instead of checking every 50 ms.

### Desktop host

- **A page's first Views requests no longer wait for the Bridge's token
  reply.** Runic Desktop's `webui.js` reports the Views connection open once
  its WebSocket is open and the token check is sent, and
  `runic-desktop-views.js` sends each request right behind it on the same
  socket (`__runicDesktopViews.request`), saving one round trip per page load.
  The server reads a socket's packets in order, authenticates it before it
  reads the next one, and still drops every call of a socket that sent no
  token check or a wrong one, so nothing runs before authentication. The
  `Connected` event of a connection is now always dispatched before its first
  call. `webui.isConnected()` and `webui.call` still wait for the token reply.
- **Views requests and replies stay UTF-8 on Desktop.** A request reaches the
  window as a slice of the received WebSocket message instead of two copies,
  and a reply is copied once, into its packet, instead of being decoded to a
  string and encoded again. A message longer than the 16 KB receive buffer is
  received into its own array instead of growing a 256-byte one. Pushes of the
  Views and announcement functions are read in place by the page's bridge.
  A request round trip through a surface (`DesktopTransportBenchmarks`)
  allocates 2.7 KB instead of 4.6 KB at 256 bytes, 50 KB instead of 162 KB at
  16 KB and 157 KB instead of 483 KB at 60 KB, and takes 48 µs instead of
  62 µs at 16 KB and 91 µs instead of 212 µs at 60 KB.
- `/webui.js` and `/runic-desktop.js` are built once per window and
  presentation and served from their UTF-8 bytes instead of being rebuilt for
  every request. They stay `no-store`: in an installed browser they carry the
  session credential and token, and in a window they name this run's port.
- On Windows, the WebView2 window and WPF `RunicWebView` register their
  document-start scripts (credentials, file drops, menu keys) concurrently
  instead of one after another; they are still added in the same order, and
  the first navigation still waits for all of them.

### CS-WebUI

- **CS-WebUI pages learn of connection changes at once.** `runic-cswebui.js`
  observes WebUI's connection events instead of polling `isConnected()` every
  250 ms. A page's connection listeners, its `hello` after a WebSocket
  reconnect and the rejection of calls in flight when the connection is lost
  no longer wait up to 250 ms (median about 90–150 ms before, under 0.1 ms
  now, `tests/benchmarks/host-scripts/cswebui-bridge.mjs`). The script wraps
  `WebuiBridge.prototype.setEventCallback` before WebUI creates `window.webui`
  and installs its own callback when the Bridge starts watching; that callback
  calls the application's own `webui.setEventCallback` callback with every
  event, whether the application sets it before or after. As with any event
  callback, WebUI then leaves out its "Connection with the backend is lost"
  banner (see "Breaking changes"). A page that loads the script after `window.webui` exists, or a WebUI
  without the `WebuiBridge` class, keeps the 250 ms poll.
- **Mailbox messages are parsed once.** The script slices each message of a
  `receive` reply as .NET wrote it instead of parsing the reply and
  serializing every message again, so listeners get the message's text as the
  host sent it and the page parses it once. Delivering a receive reply takes
  about a third less time per message (operation 1.33 → 0.93 µs, interaction
  of 40 rows 12.6 → 8.3 µs). A reply in another layout is parsed as before.
- Copies of `runic-cswebui.js` kept outside `www/`, such as in a frontend's
  `public/` folder, should be updated to get these changes; an older copy keeps
  working.

## Checked-write splices (F1)

- **Checked writes of long text cross as splices.** Under `text-splice/1`, a
  `write` of a checked field that is a text member may carry
  `splice: {length, index, delete, text}` instead of `expectedValue` and
  `value`:
  `{"kind":"write","route":"editor","member":"body","requestId":"w-9","expectedVersion":7,"splice":{"length":100000,"index":5120,"delete":0,"text":"x"}}`.
  The splice applies to the field's value at `expectedVersion`; the write is
  exactly the full write whose `expectedValue` is that value and whose `value`
  is the value with the splice applied. Receipts are unchanged and carry the
  whole value.
- **Producer order.** The envelope (exactly one of `value` and `splice`, no
  `expectedValue` and no `baseEdit`/`baseRevision` with a splice), the feature
  and a checked text member (otherwise `invalid-request`), a retained
  `requestId`, the version (`conflict` with `incoming`), then the base: a
  value that is not a string or a splice that does not fit it is `rejected`
  with `splice-base`, and nothing is written or retained.
- **Retries repeat their form.** A retry with the same `requestId` gets the
  original receipt when it repeats `expectedVersion` and the splice; the same
  write in the other form is a `conflict`.
- **`@runic-artifex/views`.** `ViewConnection.write` sends a splice when the
  feature is in use, the member is a checked text member, both values are
  strings and the splice keeps at least 64 code units of `expectedValue`; on
  `splice-base` it sends the write in full with the same `requestId`. The mock
  Bridge implements the producer side.
- **Specifications.** `specs/application/README.md`: "Text splices in
  `write`" and the retry rule of checked writes. Conformance: six
  `write-splice-*` scenarios and request vectors for `write` with a splice.

## Frontend field API (F1)

- **Generated field descriptors.** Each generated client module exports
  `{View}Fields`, one descriptor per settable member (`EditorFields.title`):
  its kind (`text`, `number`, `bigint`, `boolean`, `choice`, `value`),
  nullability, setter, checked write and baseline, and, for a View with
  validation, its messages.
- **One field binding for every framework and member type.**
  `createFieldController` in `@runic-artifex/views`, React and Vue `useField`
  (`inputProps` to spread; `v-model`), Svelte `useField` with an attachment
  (`{@attach title.attach}`), Angular `injectField` and the `[runicField]`
  directive for Reactive Forms and Signal Forms
  (`@runic-artifex/angular/forms`).
- **Checked writes in fields.** A field reads every checked-write receipt:
  `rejected` and `conflict` keep the draft and say why, `committed-with-error`
  and `applied.validation` are reported. `checked: true` writes with the
  checked write, so a change by another writer while the user edits is a
  conflict (`retry()` or `reset()`), not lost.
- **Write after a pause and on blur.** `commit: "pause"` writes the draft after
  `delay` milliseconds (700 by default) without input and when the field loses
  focus; `commit()` resolves with the field's state once its writes settled,
  so Save can follow them and skip a failed write.
- **Checked writes of long text send splices** under `text-splice/1`.

### Behaviour changes

#### Views npm packages: text fields and checked writes

- `createTextFieldController`, `useTextField` and `injectTextField` read a
  checked-write receipt that their `write` resolves with. Before, every

## Trimmed self-contained publishing

### Fixes

- **A Runic Desktop application published self-contained with
  `PublishTrimmed=true` starts.** It failed when Kestrel bound its address,
  with `TypeLoadException: Method 'GetEnumerator' in type
  'System.Security.Cryptography.X509Certificates.X509Certificate2Collection' …
  does not have an implementation`, because ILLink 10.0 kept that type's
  interfaces without those of its base class (dotnet/runtime#135913). Runic
  Desktop now preserves the base class's interfaces. NativeAOT and untrimmed
  publishes were not affected.
- **The second call of a trimmed Runic Desktop page is answered.** ILLink 10.0
  drops a `lock`, `using` or `try`/`finally` inside a `finally` of some async
  methods (dotnet/runtime#136414). The Runic Desktop host's call dispatch then
  never released a lock after a page's first call, and every later call, such
  as a command, waited forever. The same ILLink bug skipped the end of the GTK 4
  application lifetime (`Gtk4Application.Run`) on Linux and the autorelease
  pool of a macOS thumbnail request (`IDesktopThumbnails.GetThumbnailAsync`).
  The cleanup now runs in separate methods, which ILLink keeps.
- An in-repository publish with `PublishTrimmed=true` builds the Bridge code
  generator untrimmed, as with `PublishAot`. It failed with `RUNICBRIDGE024`.

### Documentation

- The packaging guide lists the `dotnet publish` modes. WPF hosts
  (`Runic.Application.Views.Wpf`, `Runic.Navigation.Wpf`) can't be trimmed, and
  the .NET SDK reports `NETSDK1168` for them.

## Navigation hooks on the model turn (A2)

### Behaviour changes

- **Navigation: `RunicModelContext` schedules navigator hooks** (sdk#714). It
  implements `IRunicModelHookScheduler`, as WPF's `DispatcherModelContext`
  does, so a Desktop, served or CS-WebUI application without WPF runs target
  factories, departure guards, initialize, resume and arrival hooks, and the
  disposal of owned content, in the model context: each hook starts in a turn
  of its own, never inline in the caller or in a commit turn, and its awaits
  resume in later turns. A page sets its state in `InitializeAsync` or
  `OnArrivedAsync` directly, before and after `await`, as on a WPF dispatcher;
  before, those hooks ran on the thread pool and an arrival hook that wrote
  bridged state wrote it off-turn. No turn is held across a hook's awaits, so
  commits and bridge replies run between them. A hook that blocks its thread,
  such as `Wait()` or `Thread.Sleep`, now blocks the model context; await
  instead. Owned content is disposed in a turn of its own, and an instance that
  a factory returned for a target the navigator rejected is disposed
  asynchronously, after `WhenIdleAsync`. A wrapper that forwarded
  `IRunicModelContext` to `RunicModelContext` to schedule hooks itself can be
  removed.
- **Navigation: `NavigationEntryContext.DismissAsync` from a pending entry's
  own initialize hook cancels the hook's token before it returns**, as its
  documentation says, also when the hook runs on the model's thread (WPF
  included).

## Frontend connections and DX (F2)

### Breaking changes

- **Clients stay connected for a grace period after their component
  unmounts.** The view controller behind `useView`, `injectView` and
  Svelte's `useView` no longer disposes a client it connected at once: it
  keeps it for `keepAlive` milliseconds (2000 by default), keyed by the
  connector's `connect` function, and the next binding that follows the same
  connector takes it over with its state. StrictMode's second mount, Fast
  Refresh and HMR, `<Activity>`, toggled `{#if}`/`v-if` blocks and A→B→A
  navigation no longer show "Connecting…", remount `ViewOutlet` subtrees or
  reopen the route. A test that checks that a route closes when its component
  unmounts passes `keepAlive: 0` or waits for the period.

### Added

#### `@runic-artifex/views`

- `ViewControllerOptions.keepAlive` and `ViewController.release()`, which lets
  go of the client but keeps `current`, so a binding that mounts again shows
  its last state at once. While the same source connects again, `state` stays
  the last state with `pending: true`.
- `preloadView(source, { keepAlive? })`: connects ahead of the component, as
  in a router's `load` function, and hands the client to the first binding
  that follows `source`.
- `describeBridgeError(error)`: one English sentence for a status line or an
  alert, instead of `String(error)`. `isBridgeError(error, kind?)` narrows a

  controller)` and `commitFields(...fields)`: the DOM wiring of a field for

- `@runic-artifex/views/bindings`: `viewSourcePreview(source)`,
  `checkKeepAlive` and `defaultKeepAlive`, for framework bindings.

#### `@runic-artifex/react`

- `useView` lets go of its client with the controller's `release()` when its

  `UseViewOptions.keepAlive` sets the grace period.

- `useSuspenseView(source, { keepAlive })`: the shared client stays for

## Runic Desktop: slow WebView starts no longer time out

### Fixes

- An embedded window could fail to open with `presentation-connection-timeout`
  while Windows Update or other Windows servicing slowed the disk: a fresh
  WebView2 profile, which every window gets unless it sets `ProfilePath`,
  then took 5 to 25 seconds before its page reached Runic's server, past the
  15-second `ConnectionTimeout` (I-176). An embedded WebView that has
  requested nothing yet but is still loading the page now extends the
  timeout: it does not run out while the WebView's first navigation is in
  progress, nor within a whole timeout of the last startup step the WebView
  reported, up to four times `ConnectionTimeout` (60 seconds with the
  default). A WebView that hangs still fails, and the timeout then says how
  long it was still loading. The Windows WebView2 windows and `RunicWebView`
  report this progress; the GTK and macOS windows and browsers keep the plain
  timeout.
- Event 3021 `EmbeddedConnectionDeadlineExtended` (Warning, once per
  presentation) when a WebView's progress kept a window waiting past
  `ConnectionTimeout`, so slow starts show in the log also when they connect.
