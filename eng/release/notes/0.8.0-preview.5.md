# Runic SDK 0.8.0-preview.5

Install matching `0.8.0-preview.5` packages from NuGet and npm. Command Line
versions remain independent of this SDK.

## Behaviour changes

- Dropping a file onto an embedded window no longer navigates the window to the
  file. The drop is reported by `DesktopWindow.FilesDropped`
  ([#374](https://github.com/Runic-Artifex/runic-sdk/pull/374)).
- CS-WebUI registers more services as unavailable. The status icon, login
  startup and inhibition return `Unavailable(ProviderNotConfigured)`, like
  settings and notifications
  ([#365](https://github.com/Runic-Artifex/runic-sdk/pull/365)), and so do the
  secret store (`DesktopSecretStore.Unavailable(ProviderNotConfigured)`,
  [#366](https://github.com/Runic-Artifex/runic-sdk/pull/366)) and the trash
  (`DesktopTrash.Unavailable(ProviderNotConfigured)`,
  [#398](https://github.com/Runic-Artifex/runic-sdk/pull/398)).
- Login startup in an MSIX package reports `Unavailable(BackendUnavailable)`
  instead of success, because Windows redirects a package's writes to the Run
  key. Declare a `desktop:StartupTask` in the package manifest instead
  ([#383](https://github.com/Runic-Artifex/runic-sdk/pull/383)).
- A navigation request whose content implements `INavigationActivated` now
  completes after the content's activation hook has run, and commands that await
  such a request complete after it too
  ([#372](https://github.com/Runic-Artifex/runic-sdk/pull/372)).
- `NavigationRejection` ([#363](https://github.com/Runic-Artifex/runic-sdk/pull/363)) and `NavigationOwnership` ([#382](https://github.com/Runic-Artifex/runic-sdk/pull/382)) have new members, so a `switch` over either without a default arm gets a warning.
- On GTK 4 and macOS, a Window takes the page's `<title>`, as it does with GTK 3
  and on Windows; screen readers and window lists name the window by it
  ([#397](https://github.com/Runic-Artifex/runic-sdk/pull/397)).
- The standard macOS menus now include File ▸ Close (⌘W)
  ([#386](https://github.com/Runic-Artifex/runic-sdk/pull/386)).

## Navigation

- A navigation region can refuse requests while one runs, instead of letting the
  later request supersede the earlier one
  ([#363](https://github.com/Runic-Artifex/runic-sdk/pull/363)). Create it with
  `new NavigationRegionOptions { Admission = NavigationAdmission.RejectWhileBusy }`:
  while a request of the region has not completed, another request returns
  `Rejected(Busy)` (the new `NavigationRejection.Busy`). A Back that can join the
  pending Back still joins it. The region's new `IsBusy` is true from a request's
  admission until its task completes, which includes the retirement of the
  departed entries after the commit; `IsTransitioning` still turns false in the
  commit turn. `NavigationRegion<T>.WhenIdleAsync()` waits for one region's
  requests, and `NavigationRequestOptions.Admission` overrides the region's policy
  for one request. The WPF window close guard and dialog host, and the default
  `RunicWindow.CanCloseAsync`, use `Admission = Supersede`, so a user's close is
  never refused as busy. `NavigationHost.IsBusy` (WPF) and `WhenIsBusyChanged()`
  (ReactiveUI) expose the flag, and `BrowseBack` and `CreateBackCommand()` are
  disabled while a `RejectWhileBusy` region is busy.
- A departure guard can answer for a whole region instead of one page
  ([#367](https://github.com/Runic-Artifex/runic-sdk/pull/367)). Register an
  `INavigationRegionGuard` with `region.AddDepartureGuard(guard)`, or with
  `navigator.AddDepartureGuard(guard)` for every region. It is asked once per transition that departs from an
  entry of the region, after the entries' own guards, with a
  `NavigationRegionDeparture` (region, departing entries, `Kind`, `Operation`,
  `ModelContext`, `OnCommitted`). By default it is skipped when the entries are
  only retained and for `ClearHistory`; `NavigationRegionGuardOptions.AskOnRetain`
  and `AskOnClearHistory` opt in. A veto is `Rejected(Guard)` with no `By` entry.
  WPF's `GuardWindowClose` and a Runic View's `CanCloseAsync` ask these guards
  too; a navigator guard is asked once per region with entries.
- Content can load its data after its page is shown, and the navigation's caller
  can await it ([#372](https://github.com/Runic-Artifex/runic-sdk/pull/372)).
  `INavigationActivated.OnActivatedAsync` runs for each entry a commit made
  current, including every resume, after `OnNavigatedTo`, after the departed
  entries retired and, with WPF's `DispatcherModelContext` (or any model context
  implementing the new `IRunicModelPresentationYield`), after the new view was
  laid out and rendered. The request returns `Committed` after it, with the new
  `Activation` (`None`, `Completed`, `Failed` or `Cancelled`) and
  `ActivationError`; `ThrowIfFailed()` rethrows a failed hook's exception, and
  event 1076 logs it.  `INavigationActivated<TInput>`
  receives a `Create<T, TInput>(input)` target's input; the typed-input targets
  now accept content that implements `INavigationInitialize<TInput>`,
  `INavigationActivated<TInput>` or both. 
- Several entries can hold one instance
  ([#350](https://github.com/Runic-Artifex/runic-sdk/issues/350)).
  `NavigationTarget.Share(content)` (`NavigationOwnership.Shared`) holds a new
  instance, or the content of a live `Own`, `Create` or `Share` entry of the same
  navigator, together with the other entries that hold it; the navigator forgets
  and disposes it, and the entry scope of created content, when the last of them
  retires. `ReplaceAsync(NavigationTarget.Share(current))` hands the current
  page's content over to the next entry and disposes nothing. A departure whose
  content continues in another entry has the new
  `NavigationDeparture.ContentContinues`, and `LeaveConfirmation` doesn't ask for
  it. Shared content can't own regions, and a shared target can't be an initial
  target.

## Views

- `NavigationOutcome.Activation` reports how the activation hooks
  (`INavigationActivated`) of a committed navigation ended (`None`, `Completed`,
  `Failed` or `Cancelled`), and the generated client has a matching `activation`
  field. A web page can now show that the page it went back or navigated to failed
  to load its data. Like the `Failed` kind, it carries no exception; the hook's
  exception is still logged as event 1076. Regenerated clients have a new contract
  fingerprint ([#385](https://github.com/Runic-Artifex/runic-sdk/issues/385)).
- Generated TypeScript doc comments name the member, rather than the generic type,
  when a `<see cref>` points to a member of a generic type
  ([#385](https://github.com/Runic-Artifex/runic-sdk/issues/385)).
- A new [crash reporting guide](https://docs.runic-artifex.eu/guides/desktop/crash-reporting/) shows how to log an exception that ends the process, which Runic does not
  log, capture crash dumps for JIT and NativeAOT builds, keep NativeAOT symbols,
  and what to attach to a bug report, including `dotnet runic doctor --output json`
  ([#388](https://github.com/Runic-Artifex/runic-sdk/pull/388)).

## Windows and window state

- Windows can report their size and position. `DesktopWindow.State` reports an
  embedded window's bounds and its maximized and full-screen state, and the last
  state stays readable after the window closes. `DesktopWindow.StateChanged`
  reports each change. `PlatformServices.GetWindowState(window)` reports the same
  for a Runic Window and returns `OwnerUnavailable` on CS-WebUI
  ([#368](https://github.com/Runic-Artifex/runic-sdk/pull/368)).
- `DesktopWindowOptions.Placement` restores a saved `DesktopWindowState.Placement`.
  A placement saved on a monitor that is no longer connected opens on a monitor
  that exists now, shrunk to fit, and maximized if it was saved maximized. Runic
  Windows get this through `RunicDesktopHost.Placement`. Values use each
  platform's `MoveAsync`/`ResizeAsync` units, so a placement belongs to the machine
  that saved it. GTK 4 reports and restores the size and maximized state but no
  position.
- Custom window hosts take part through `IDesktopWindowStateHost`. A failing
  `StateChanged` handler is logged as event 3011, `WindowStateHandlerFailed`.

## File drop

- Dropped files reach the application with their real paths. On Runic Desktop's
  embedded window (Windows, macOS, Linux GTK 3 and GTK 4), `DesktopWindow.FilesDropped`
  reports each drop of files with absolute paths taken from the platform, never
  from the page. A Window's root ViewModel receives drops by implementing
  `IRunicFileDropTarget`; this also works in the WPF child web View.
  `data-runic-drop-target` on the element under the drop gives a routing label (`Target`).
  Custom window hosts take part through `IDesktopFileDropWindowHost`. New log
  events: 1054 `WindowFileDropFailed` and 3012 `FileDropHandlerFailed`
  ([#374](https://github.com/Runic-Artifex/runic-sdk/pull/374)).

## Opening files and URLs

- `IDesktopOpenRequests` delivers the files and URLs the user opens with the
  application to its running instance: registered URL schemes such as OAuth
  callbacks, and file types, at launch and later. Linux and Windows pass them as
  arguments, which `ApplicationInstance.CreateOpenRequests` takes from this launch
  and from forwarded launches. macOS delivers them as `odoc`/`GURL` Apple events,
  handled by `MacOSPlatformProvider.CreateOpenRequests`, which must be created on
  the main thread before the first window. `PlatformServices.CreateOpenRequests`
  selects the provider, and `DesktopOpenRequests.FromLaunch` is the argument parser
  ([#378](https://github.com/Runic-Artifex/runic-sdk/pull/378)).
- Treat opened URLs and files as untrusted input. The registration each platform
  needs (desktop entry `MimeType`/`x-scheme-handler`, `HKCU\Software\Classes`,
  `Info.plist` `CFBundleURLTypes`/`CFBundleDocumentTypes`) is documented in
  [`specs/platform/open-activation.md`](https://github.com/Runic-Artifex/runic-sdk/blob/main/specs/platform/open-activation.md).

## Menus and shortcuts

- macOS menu bar: applications add their own menus with
  `DesktopHostOptions.MenuBar`, bound to commands by id. The key window's root
  ViewModel runs them through `IRunicMenuCommandSource`, or the application through
  `RunicDesktopHost.MenuCommands`. Items follow the command's availability.
  `DesktopHost.SetMenuBar` rebuilds the menus, for example after a language change
  ([#386](https://github.com/Runic-Artifex/runic-sdk/pull/386)).
- Keyboard shortcuts: `DesktopShortcut` writes a shortcut once for every platform
  (`Primary` = ⌘ on macOS, Ctrl elsewhere). `matchesShortcut` and `formatShortcut` in
  `@runic-artifex/views` apply the same rule in the page
  ([#386](https://github.com/Runic-Artifex/runic-sdk/pull/386)).
- Windows and Linux show no native menu bar yet. Render menus in the page, bound to
  the same commands ([#386](https://github.com/Runic-Artifex/runic-sdk/pull/386)).

## Platform services

- `AddRunicPlatformServices()` registers every platform service. On Runic Desktop
  it also registers one `IDesktopInhibition` for the application
  (`PlatformServices.CreateInhibition(applicationId)`): a Windows power request, a
  macOS power assertion, or on Linux an xdg-desktop-portal Inhibit request that is
  not tied to a window (`PortalApplication.CreateUnparentedInhibition()`). On
  CS-WebUI it also registers the status icon, login startup and inhibition, which
  return `Unavailable(ProviderNotConfigured)` like settings and notifications.
  `DesktopInhibition.Unavailable(reason)` is new. The Runic.Platform guide documents
  what each service returns without a native owner
  ([#365](https://github.com/Runic-Artifex/runic-sdk/pull/365)).

## Credential storage

- `IDesktopSecretStore` gets, sets and deletes a secret by service and account in
  the user's credential store: the Secret Service on Linux (GNOME Keyring,
  KeePassXC, KWallet; encrypted session, libsecret-compatible items), Credential
  Manager on Windows and the login keychain on macOS. `AddRunicPlatformServices()`
  registers it; `PlatformServices.CreateSecretStore()` and the providers'
  `CreateSecretStore()` create it directly. Secrets are UTF-8 text of at most 2560
  bytes. A locked store that cannot ask the user reports the new
  `PlatformFailureCode.Locked`; a dismissed prompt `UserDismissed`; no store
  `Unavailable(BackendUnavailable)`. Inside Flatpak, allow
  `--talk-name=org.freedesktop.secrets`
  ([#366](https://github.com/Runic-Artifex/runic-sdk/pull/366)).

## File dialogs

- File dialogs take type filters and an initial folder: `OpenFileOptions` and
  `SaveFileOptions` have `Filters` (`new FileDialogFilter("Images", ["png", "jpg"])`,
  or `["*"]` for every file) and `InitialDirectory`, and `OpenDirectoryOptions` has
  `InitialDirectory`. `IFileDialogs.OpenFilesAsync` selects several files and
  returns an `IReadFileLeaseList`. Windows, macOS, the GTK 3 chooser and the
  xdg-desktop-portal (GTK 3 and GTK 4) support all three. Filters are hints that
  Runic does not enforce; macOS restricts its panel to the union of the filters and
  shows no filter pop-up. The new `platform.files.openMultiple` capability reports
  multiple selection. Provider authors get `NativeFileDialogRequest`, whose default
  implementations keep existing pickers working
  ([#370](https://github.com/Runic-Artifex/runic-sdk/pull/370)).

## Trash

- New `IDesktopTrash` (Runic.Platform) moves a file, directory or symbolic link to
  the user's trash. Linux follows the freedesktop.org Trash specification, including
  topdir trashes, and uses the Trash portal inside Flatpak and Snap. Windows uses
  the Recycle Bin and macOS the Trash. A location without a usable trash returns `Unavailable(BackendUnavailable)`. `AddRunicPlatformServices()` registers it; providers are
  `PortalPlatformProvider.CreateTrash()`, `WindowsPlatformProvider.CreateTrash()`,
  `MacOSPlatformProvider.CreateTrash()` and `PlatformServices.CreateTrash()`
  ([#398](https://github.com/Runic-Artifex/runic-sdk/pull/398)).
- New `PlatformFailureCode.NotFound` for a missing file or directory
  ([#398](https://github.com/Runic-Artifex/runic-sdk/pull/398)).

## D-Bus

- New package **Runic.Platform.Linux.DBus**: a D-Bus client and service API for
  Linux applications. Connect to the session or system bus
  (`DBusConnection.ConnectAsync`, or `services.AddRunicDBus()` for shared
  per-application connections). Call methods and read or write properties through
  `DBusProxy`, receive signals and property changes as ordered async streams, own
  and watch well-known names, and export your own objects with `DBusObject`.
  `DBusValue` covers every D-Bus type, including file descriptors. Errors arrive as
  `DBusException` with the D-Bus error name. NativeAOT-compatible; no Tmds.DBus type
  is public. Windows and macOS report `Unavailable(ProviderNotConfigured)`
  ([#380](https://github.com/Runic-Artifex/runic-sdk/pull/380)).
- Runic.Platform.Linux.DBus generates typed proxies and services from D-Bus
  introspection XML. List the XML as
  `<AdditionalFiles Include="…" RunicDBusMode="Proxy|Service|Proxy,Service" Namespace="…" />`
  to get a `DBusProxy` class per interface (`<Method>Async`, `Get/Set<Property>Async`,
  `Watch<Signal>Async`, typed `<Name>Properties`) and an abstract `DBusObject`
  service class per file (abstract method handlers, C# properties that emit
  PropertiesChanged, `Emit<Signal>`). It is NativeAOT-compatible. Problems in the
  XML are reported as `RUNICDBUS001`–`RUNICDBUS011`. The generator adapts parts of
  Tmds.DBus.Generator (MIT); the package includes the notice
  ([#390](https://github.com/Runic-Artifex/runic-sdk/pull/390)).

## Accessibility

- `DesktopWindow.AnnounceAsync` now reaches Narrator and other UI Automation clients
  on Windows. The WebView2 window raised its notification where UI Automation
  delivered it to no client
  ([#397](https://github.com/Runic-Artifex/runic-sdk/pull/397)).
- The Runic Desktop README's Accessibility section lists what Orca, Narrator/NVDA
  and VoiceOver get from each host, checked in CI on Linux, Windows and macOS (with
  VoiceOver), and the known gaps
  ([#397](https://github.com/Runic-Artifex/runic-sdk/pull/397)).

## Right-to-left

- The new [right-to-left guide](https://docs.runic-artifex.eu/guides/desktop/right-to-left/)
  says how a page sets `lang` and `dir` (with Runic Translations'
  `localeDirection`), where each WebView takes `navigator.language` from, which
  native pieces follow which direction per platform, and how an application sets
  GTK 4's direction when its language differs from the session's. CI checks an
  Arabic locale with GTK 4: the page and GTK's direction are right to left. Windows
  does not mirror the window frame or the status icon menu yet
  ([#389](https://github.com/Runic-Artifex/runic-sdk/issues/389)); see
  [#393](https://github.com/Runic-Artifex/runic-sdk/pull/393).

## Packaging

- **MSIX packages on Windows.** A process installed from an MSIX package shows
  notifications under its package's AppUserModelID (`PackageFamilyName!App`) and
  ignores the ID passed to `CreateNotifications` /
  `AddRunicPlatformServices(applicationId)`, as macOS uses the bundle identifier
  ([#383](https://github.com/Runic-Artifex/runic-sdk/pull/383)).
- **macOS bundles.** Without a `www` folder next to the executable, an application
  in an `.app` bundle loads its frontend from `Contents/Resources/www`, where Apple
  expects resources; `RunicWindowOptions.ContentRoot` still overrides it
  ([#383](https://github.com/Runic-Artifex/runic-sdk/pull/383)).
- **Packaging recipes.** `dotnet new runic-app --packaging` adds
  `packaging/package.mjs`, which packages the application from its project file's
  identity: an MSIX package on Windows, a hardened-runtime `.app` in a disk image on
  macOS (notarized with `--notary-profile`), and a Flatpak on the GNOME runtime with
  AppStream metadata on Linux. `RunicApplicationUrlSchemes` registers URL schemes in
  all three. Without signing credentials the packages are unsigned or ad-hoc signed
  for testing; the README lists the certificates and accounts each platform needs
  to ship. CI builds, installs and opens all three packages
  ([#394](https://github.com/Runic-Artifex/runic-sdk/pull/394)).

## Application template

- **Identity and icons.** `dotnet new runic-app` declares the application's identity
  once in the project file: `RunicApplicationId` (set with `--application-id`;
  default `com.example.<project name>`), `RunicApplicationName` and `Version`, read
  in code through `ApplicationIdentity`. The GTK 4 host uses the ID as its
  application ID, and `--nix` names the desktop entry and icon after it. A neutral placeholder icon is in `icons/` (SVG, PNG and ICO)
  ([#384](https://github.com/Runic-Artifex/runic-sdk/pull/384)).
- **Diagnostics on Windows.** Since Windows builds are GUI applications (`WinExe`),
  Desktop diagnostics also go to `diagnostics.log` in the user's local application
  data, in a folder named after the application ID; the log starts empty at each
  start ([#384](https://github.com/Runic-Artifex/runic-sdk/pull/384)).

## Nix packaging

- `buildRunicApplication`'s `dotnetTools` no longer reads the tool manifest from the
  store path of `src` at evaluation, which failed a read-only evaluation such as
  `nix flake check --no-build --all-systems` on an empty store
  ([#371](https://github.com/Runic-Artifex/runic-sdk/issues/371)). The manifest is
  read from `src` when it is a path, and from the unfiltered source when `src` is
  filtered by `lib.fileset.toSource`, `lib.cleanSource` or `lib.cleanSourceWith`;
  for any other `src`, `dotnetTools.manifest` may now be a path
  (`./App/.config/dotnet-tools.json`), which is read and restored from as it is.
- An npm frontend without `frontend.hash` no longer reads `package-lock.json` from
  the store path of `src` at evaluation, which failed a read-only evaluation such as
  `nix flake check --no-build --all-systems` on an empty store. As with
  `dotnetTools`, the lock file is read from `src` when it is a path, and from the
  unfiltered source when `src` is filtered by `lib.fileset.toSource`,
  `lib.cleanSource` or `lib.cleanSourceWith`; any other `src` needs `frontend.hash`
  ([#379](https://github.com/Runic-Artifex/runic-sdk/pull/379)).

## Supported platforms

- Runic Desktop is now CI-verified on `linux-arm64`, `win-arm64`, `linux-musl-x64`
  and `linux-musl-arm64`, and CS-WebUI on `linux-arm64`. The musl RIDs are tested in Alpine 3.22.
   `dotnet runic doctor --rid` reports these
  targets as supported
  ([#369](https://github.com/Runic-Artifex/runic-sdk/pull/369)).
