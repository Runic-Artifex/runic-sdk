## An interaction answered from the template (#1319)

`client.interactions.<name>.handle((input, { signal }) => answer)` suits a dialog service that returns a promise. A
component that renders its dialog in its own template had to write about 28 lines per interaction: a promise whose
resolver and input go into a signal, clearing it on the answer and on `signal`'s abort, ignoring a second answer, and
an `effect` that registers and removes the handler with the client. Without the abort handling the dialog stayed
open after .NET had stopped waiting. Angular's `injectInteraction`, and `useInteraction` in React, Vue and Svelte, now
do this:

```ts
readonly discard = injectInteraction(this.editor, "confirmDiscard");
// @if (discard.request(); as input) {
//   <app-confirm [text]="input.title" (yes)="discard.respond(true)" (no)="discard.respond(false)" />
// }
```

`request` is the input of the oldest open request, or `undefined`, and `respond(answer)` answers it. The handler is
registered while the client is connected and removed when the client changes or the component goes away. A request
also ends when .NET stops waiting for it: the command that asked was cancelled, the deadline passed, the window closed
or the client changed; an answer after that is ignored. Several open requests are answered in order, and `pending`
counts them, for an interaction whose input is empty. The name, input and answer are typed from the generated
client's interaction (`Interaction<TInput, TOutput>` or `ViewQuestion<TInput, TOutput>`), and the generated mock's
`interactions.<name>.request(input)` drives it in tests. The framework-neutral `createInteractionController` in
`@runic-artifex/views` holds the logic. See
[Interactions as state](../../../packages/web/views/README.md#interactions-as-state).
