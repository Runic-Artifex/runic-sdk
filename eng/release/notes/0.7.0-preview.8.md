# Runic SDK 0.7.0-preview.8

Install matching `0.7.0-preview.8` packages from NuGet and npm. Command Line
versions remain independent of this SDK.

## WPF Bridge generation

- The frontend's `node_modules` and `dist` folders are no longer default
  project items, so a project that keeps its frontend in its own folder does not
  list them in IDEs or walk them during evaluation.

## Navigation

- `NavigationRegion<TContent>.Start(target)` gives a region created empty its
  root page, synchronously and on the path of `CreateRegion`'s initial target:
  `OnNavigatedTo(Reset)` and the region's notifications run before it returns.
  A shell whose root page navigates its own region calls
  `Main.Start(NavigationTarget.Borrow<IPage>(list))` in its constructor instead
  of a discarded `_ = Main.ResetAsync(...)`, so the page is current when
  `OpenWindowAsync` returns, and a failure to create it throws and fails the
  open instead of being logged with an empty Window. `Start` is allowed once,
  before any navigation request, and throws `InvalidOperationException`
  otherwise. The Runic.Navigation README's "The root page" section shows the
  pattern, and the initial-target cycle error now suggests it.

## WPF navigation and hosting

- `Runic.Application.Views.Wpf` declares the XAML namespace
  `https://runic-artifex.eu/xaml/views` (prefix `rv`), so XAML no longer names
  the assembly in `clr-namespace:…;assembly=…`.
- Leaving borrowed content, as a `NavigationSelector` tab switch does, asks the
  current page of each region the content owns, and of the regions below it,
  as a `Retain` departure. A page whose guard keeps it keeps the tab selected,
  and the regions keep their entries when the switch commits. Before, only the
  tab's own guard was asked. `LeaveConfirmation` asks on a tab switch only with
  `askOnRetain`. A region the tab only refers to, owned by the application, is
  still not asked; create a tab's page regions with the tab's model as owner.
  The Runic.Navigation README lists which departures ask a child region.

## Per-window platform services

- Runic.Application.Views.Desktop has a new `net10.0-windows` assembly with the
  same API that depends only on Runic.Platform.Windows, so a Windows-only
  application, including every WPF application, no longer ships the Linux and
  macOS providers or `Tmds.DBus.Protocol`.
- `AddRunicPlatformServices()` on Runic Desktop also registers one
  `IDesktopNotifications` for the application, so a ViewModel takes it in its
  constructor without an `OperatingSystem` branch.
  `AddRunicPlatformServices(applicationId)` passes the Windows AppUserModelID or
  the Linux desktop-entry ID; without one, Linux uses the identity the portal
  infers and Windows reports `Unavailable(ProviderNotConfigured)`.
  `PlatformServices.CreateNotifications(applicationId)` creates the same service
  for custom composition. CS-WebUI's registration and the new
  `DesktopNotifications.Unavailable(reason)` report the reason for every request.
  Portal diagnostics of these notifications are logged as event 2003.
- The Linux portal's `portal-identity-registration-failed` remediation names
  the desktop entry to install and, for development, the null application ID
  that the portal factories and `AddRunicPlatformServices()` accept.

## Windows from ViewModels

- `IRunicWindowContext.RequestCloseAsync()` lets a ViewModel close its own
  Window as its close button does, asking `CanCloseAsync` and the navigation
  guards of a `GuardClose` Window, and returns whether it closed.
  `AddRunicWindowService()` registers it per Window scope and `OpenWindowAsync`
  binds it before the ViewModel is resolved, on Runic Desktop and CS-WebUI, so
  a Quit command needs no holder of the Window.

## Build targets and Vite plugin

- A failed `svelte-check` in the frontend build logs each error and warning as
  `file(line,column): error : text`, from its default output and from
  `--output machine`, so IDE error lists link the source line instead of
  showing only `RUNICBRIDGE016`. `tsc` and `vue-tsc` errors already kept their
  codes and locations.
- `@runic-artifex/vite-plugin-runic` pre-bundles its dev client while
  serving. With a cold `node_modules/.vite` cache, Vite found the injected
  client only on the first page load and reloaded the page, which closed the
  host's connection and failed a test's first script.

## Templates, Runic.Create and testing

- The React, Svelte and Vue starters list `index.html` in
  `build.rolldownOptions.input`, with a comment naming the step to add a
  second Window's page.
- `RunicDesktopHost` honours `RUNIC_APPLICATION_SERVE_ONLY=1` like the
  CS-WebUI host: it opens no window, writes `RUNIC_APPLICATION_URL=<url>`, and
  serves until a line is read from standard input or the process ends. A
  headless browser test drives it through `DesktopBridgeWindow<T>.Surface`
  (`ExecuteJavaScriptAsync`). The `first-window-desktop` example drops its own
  `--serve-only` switch.
- In a CS-WebUI window, a reload, a same-origin link or a fragment before the
  page's first Bridge call is no longer dropped. WebUI cancels these
  navigations and reports them; the host now carries out a same-origin one,
  and a cross-origin one stays cancelled. Applications that keep their own
  copy of `runic-cswebui.js` should update it.

## ReactiveUI model-context scheduler

- `IReactiveUIBuilder.WithRunicModelContext()` (both ReactiveUI adapters) sets
  the model-context main-thread scheduler on ReactiveUI's builder, as
  `WithAvalonia()`, `WithMaui()` and `WithWpf()` set theirs. An application
  that calls `RxAppBuilder.CreateReactiveUIBuilder()…BuildApp()` adds it there;
  without it, `WithPlatformServices()` (and platform calls that include it)
  replaces the scheduler with ReactiveUI's default outside a test runner.
  `AddRunicReactiveModelContext()` alone remains enough for other applications.
- Runic Desktop, CS-WebUI and `RunicWindowTestHost.Create` pass the
  application's `ILoggerFactory` to the installed scheduler before a window
  resolves its ViewModel, so `ReactiveSchedulerOutsideModelTurn` (event 1043)
  reaches the application's logs as a Warning without code.
- Event 1043 is logged once per ViewModel type that schedules work outside a
  model turn, as found on the call stack, instead of once per process. Its new
  `Source` property names the ViewModel, or "an unidentified source".
- When such a window opens and ReactiveUI's main-thread scheduler is not
  Runic's, Runic logs `ReactiveSchedulerKept` (1090, Information) for a
  scheduler set before `AddRunicReactiveModelContext()`, or
  `ReactiveSchedulerReplaced` (1091, Warning) for one set afterwards, once per
  scheduler type. A UI dispatcher's scheduler, such as WPF's, is not reported.
- The `AddRunicReactiveModelContext()` summary states the opt-out: to opt out,
  set `RxSchedulers.MainThreadScheduler`, or call `WithMainThreadScheduler` on
  ReactiveUI's builder, before `AddRunicReactiveModelContext()`, or replace it
  afterwards.
- `Runic.Application.Views` has `IRunicWindowOpeningObserver`, which the
  Desktop, CS-WebUI and test hosts call before a window resolves its ViewModel.
  MVVM adapters register it; applications do not.

## Documentation and diagnostics

- The `@runic-artifex/react` README shows how a page answers a ViewModel
  interaction with `client.interactions.<name>.handle(...)` in an effect.
- The `Runic.Application.Testing` README has an Interactions section: tests
  answer interactions with .NET handlers, and the generated frontend mock tests
  the browser's handler.
- The `Runic.Application.Views` README and the `Runic.Navigation.ReactiveUI`
  walkthrough show ReactiveUI commands that open a Window and close a guarded
  one with `RequestCloseAsync`. The ReactiveUI READMEs note that a departure
  during a page's first render is answered by the ViewModel's .NET fallback.
- The `Runic.Application.Views` README shows how to give a Window its own page:
  the Vite 8 build inputs, `RunicWindowOptions.StartPage`, pages in folders,
  and the `content-entry-not-found` and `RAPPDEV1009` failures for a page the
  build does not emit.

## Release tooling

- Before the first package is pushed, and in the dry run, the release checks
  that the nuget.org trusted-publishing policy can push every unpublished NuGet
  package ID, so a new ID it does not cover stops the release before anything
  is published instead of failing part-way.
