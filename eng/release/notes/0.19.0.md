# Runic SDK 0.19.0

Install matching `0.19.0` packages from NuGet and npm;
`Runic.Application.Views.CsWebUi` is `0.19.0-preview.1`.
Tested with Runic Translations 0.11.0 and Runic Command Line 0.13.0.

0.19.0 is about windows and what a ViewModel costs. A window can show a second
page beside its own in a **side panel** (#864) and grow by its width, so the
page keeps its size and its place on the screen. A Window can stay open after
its close was decided until its accepted work has **drained** (#900), and each
operation declares whether a close cancels it or waits for it, also when the
application shuts down. ViewModels and code that holds a `DesktopWindow` can
**maximize, restore and place** an open window (#897), a window the application
opened itself gets the **per-window services** of a Runic Window (#896), and a
Windows title bar without a forced colour scheme follows the system's dark mode
(#888). A host can give a guest's window in a region an
[appearance of its own](#an-appearance-override-per-hosted-region-917-experimental)
(#917).

The Bridge runtime is no longer generic over the ViewModel (#901): a NativeAOT
executable grows by about 24 KiB per bridged ViewModel instead of about 118 KiB.
Three costs that grew with a ViewModel's state are gone (#909, #910, #911), and a
new scaling suite keeps them from coming back. Because of #901, **assemblies with
Bridges that 0.18 generated must be rebuilt**; a stale one now names itself in
`RUNICBRIDGE038` (#916).

The side panel (`RUNICDESK104`), the close drain (`RUNICDESK105`) and the region
appearance (`RUNICDESK103`, with the rest of hosted applications) are
experimental. 0.19.0 moves the release train to Runic Command Line 0.13.0 and
Runic Translations 0.11.0. [Upgrading from 0.18](#upgrading-from-018) lists what
to change, and the
[migration guide](https://github.com/Runic-Artifex/runic-sdk/blob/v0.19.0/docs/migration-1.0.md#from-018-to-019)
collects it.

## Highlights

- [Side panel](#side-panel-864-experimental): a second page beside the window's
  page on Windows, macOS and Linux, with a refusal and a reason where the window
  cannot grow.
- [Close drain](#close-drain-900-experimental): durable work is never cancelled
  halfway by a window close, a quit, Ctrl+C or SIGTERM.
- [Maximize, restore and placement](#maximize-restore-and-placement-of-an-open-window-897)
  of an open window, for `DesktopWindow`, ViewModels, WPF and hosted windows
  (stable).
- [Smaller NativeAOT executables](#smaller-nativeaot-executables-per-viewmodel-901):
  about 79 % less executable per bridged ViewModel.
- [Bridge costs](#bridge-costs-that-grew-with-the-viewmodel-909-910-911): row
  edits, collection bursts and scalar changes no longer cost time in proportion
  to the rows, collections or members.
- [An appearance override per hosted region](#an-appearance-override-per-hosted-region-917-experimental).

## Upgrading from 0.18

Update every Runic NuGet and npm package to 0.19.0 together and rebuild, so that
the generated clients and Bridges are regenerated.

### Breaking changes

- **Rebuild every assembly that contains generated Bridges** (#901), including a
  separate `RunicApplicationFrontendModelAssembly` and ViewModel libraries that
  other applications reference. The Bridge runtime and its descriptors in
  `Runic.Application.Views.Generated` lost their ViewModel type parameter, so a
  Bridge that the 0.18 generator wrote fails to load on 0.19. The host reports
  it at the first Window or View as `RUNICBRIDGE038`, which names the assembly
  to rebuild (#916). The wire protocol and the generated TypeScript client
  are unchanged. Hand-written Bridges, such as test doubles, follow the new shape:
  [migration guide](https://github.com/Runic-Artifex/runic-sdk/blob/v0.19.0/docs/migration-1.0.md#rebuild-every-assembly-with-generated-bridges).
  These types are the generated-code support API; no application API was
  removed.

- **Runic Command Line 0.13 and Runic Translations 0.11** (#937).
  `dotnet-runic`, `Runic.Create` and the `Runic.Assets` packer bundle Runic
  Command Line 0.13.0, and `Runic.Application.Views.Translations` requires Runic
  Translations `[0.11.0, 0.12.0)`, so an application that uses it moves every
  Translations package to 0.11.0; NuGet reports a 0.10.x Translations package
  outside that range. The template pins Translations 0.11.0. An application that
  uses Runic Command Line itself moves to 0.13.0; see the
  [Command Line 0.13.0 notes](https://github.com/Runic-Artifex/runic-cli-sdk/blob/v0.13.0/eng/release/notes/0.13.0.md).

### Behaviour and output changes

- **The tools' help and usage errors** follow Command Line 0.13:
  - Help lists arguments by their placeholder (`<source-directory>` instead of
    `source-directory`), and its `[requires: …]` and `[conflicts: …]` notes name
    options by their spelling (`--factor`) instead of their ID.
  - A missing argument reads "The <source-directory> argument is missing."
  - Flags no longer show `[default: False]`.
  - In `--format json`, a usage diagnostic that names one argument or option
    (`RCLI1005` and the value errors) gains a `binding` member with its ID, and
    `RCLI1005`'s `arguments` now hold the placeholder (`["<source-directory>"]`).
    A script that read the ID from `arguments` reads `binding` instead.

- **A Windows title bar without a forced colour scheme follows the system's dark
  mode** (#888). A WebView2 window whose `ColorScheme` is `NoPreference` (the
  default, also after `SetColorSchemeAsync(NoPreference)`) was light. It now
  takes the system's app mode, and a WPF window takes it after
  `IRunicWindowPresentation.SetColorSchemeAsync(NoPreference)`. On a dark Windows,
  such a window now has a dark title bar. An application that needs a light title
  bar there sets `Light`, which also pins the page's `prefers-color-scheme`.

- **The new generator warning `RUNICBRIDGE039`** reports a
  `[RunicOperationClose]` declaration that reaches no operation. Only code that
  uses the experimental close drain can meet it.

- **`RunicTestWindowPresentation.AllFeatures`** (a `const`) now includes
  `SidePanel`, `Maximize` and `Placement`. A test that compared `Features` with
  a list of its own adds them.

([experimental APIs](https://github.com/Runic-Artifex/runic-sdk/blob/v0.19.0/docs/experimental.md#suppressing-a-diagnostic)),
for example `<NoWarn>$(NoWarn);RUNICDESK104</NoWarn>`, and may change in 0.20:

| ID | Feature | Opt in |
| --- | --- | --- |
| [`RUNICDESK104`](https://github.com/Runic-Artifex/runic-sdk/blob/v0.19.0/docs/experimental.md#RUNICDESK104) | [Side panel](#side-panel-864-experimental) | Suppress the ID where the application calls `OpenSidePanelAsync` |
| [`RUNICDESK105`](https://github.com/Runic-Artifex/runic-sdk/blob/v0.19.0/docs/experimental.md#RUNICDESK105) | [Close drain](#close-drain-900-experimental) | Suppress the ID in the project that sets `CloseDrain` or declares `[RunicOperationClose]`; on npm, import `onBridgeDraining` from `@runic-artifex/views/experimental`. `AcceptedWorkScope.WaitForAcceptedAsync` is stable |
| [`RUNICDESK103`](https://github.com/Runic-Artifex/runic-sdk/blob/v0.19.0/docs/experimental.md#RUNICDESK103) | [Appearance per hosted region](#an-appearance-override-per-hosted-region-917-experimental), part of hosted applications | Already suppressed by a host that uses regions |

The window building blocks of 0.18 and the maximize, restore and placement API
are stable.

## Smaller NativeAOT executables per ViewModel (#901)

The Bridge runtime (`ViewModelBridge` and its property, command, collection,
state and interaction descriptors) now holds the ViewModel as `object` instead of
being generic over it. NativeAOT shares method bodies across instantiations, but
it still needed type descriptors, generic dictionaries and hash-table entries for
every closed generic type the runtime used, about 110–120 KiB of executable per
bridged ViewModel on linux-x64. Generated Bridges now cast the ViewModel in
static lambdas and pass `typeof` of it to the runtime, so every Bridge shares one
copy of the runtime. On the scaling suite's fixture the executable grows by
about 24 KiB per ViewModel instead of about 118 KiB, and with nine
ViewModels the executable is 0.9 MiB smaller. Managed (JIT)
applications are unaffected apart from a cast per member read.

## A stale generated Bridge reports which library to rebuild (#916)

An assembly whose Bridges another Runic release generated used to fail at its
first Window with a `TypeLoadException` or `MissingMethodException` that named
a Runic type but not the library. It now fails with `RUNICBRIDGE038`, a
`RunicBridgeContractException` whose message and `AssemblyName` name the
assembly and say "Rebuild this library against Runic 0.19.0", with the original
exception as its `InnerException`.

From 0.19 the generated `AddRunicBridges()` passes the generated-code contract
version its generator wrote to the runtime, which checks it before it registers
a Bridge, so a future break of the generated-code support API reports the
library at registration, before any Bridge type loads. The check is one integer
comparison and reads no metadata, also under NativeAOT. Bridges from 0.18 and
earlier make no such call, so the hosts (Runic Desktop, CS-WebUI, WPF's
`RunicViewHost` and `RunicWindowTestHost`) report their load failure when the
first Window or View attaches the Bridge.
[Diagnostics](https://github.com/Runic-Artifex/runic-sdk/blob/v0.19.0/docs/diagnostics.md#runicbridge038).

## Bridge costs that grew with the ViewModel (#909, #910, #911)

Three Bridge costs grew with a ViewModel's state although only one value
changed. Published frames are unchanged, and applications see no behaviour
change.

- **Row edits after a notification** (#909). A named `PropertyChanged` cleared
  every keyed collection's row index, so the next row edit rebuilt it: O(rows)
  per edit. A notification now drops only the indexes of the collections its
  member holds, and a replaced collection's index is dropped as soon as the
  Bridge finds the replacement, so it no longer keeps the old rows alive.
- **Collection bursts** (#910). Each `CollectionChanged` of a keyed collection
  read the getter of every keyed collection to find the one that changed, and
  counted the whole pending list against the frame's 4,096-change limit:
  O(n²) for a burst of n changes. The Bridge now finds the collection by its
  instance and keeps a count per collection.
- **A unit after one scalar change** (#911) encoded every member to find the
  changed ones. The Bridge now keeps the value of each scalar member it last
  published and encodes a scalar only when it differs; objects, lists,
  availability and validation are still encoded every unit, so members that
  never announce a change stay correct.

The new scaling suite (`tests/dotnet/Runic.Application.Scaling.Tests`,
`bun run scaling`) counts such work at two sizes over generated Bridges for
CommunityToolkit.Mvvm and ReactiveUI ViewModels, and fails CI when a count grows
faster than its budget in `tests/scaling/budgets.json`. A NativeAOT size budget
per bridged ViewModel (#914) does the same for #901.

## Side panel (#864, experimental)

A window can show a second page beside its own, in a strip on one edge by which
the window grows, so the page keeps its size and its place on the screen: its
viewport, media queries and `position: fixed` elements do not change. A ViewModel
opens it with `IRunicWindowPresentation.OpenSidePanelAsync`, and code that holds
the window with `DesktopWindow.OpenSidePanelAsync`. The panel's page is a route of
the application's own frontend and a second connection of the window, bound to the
same ViewModel tree. Where the window cannot grow (maximized, full-screen, snapped,
no room in the work area, the left edge on Wayland, or no native window at all),
the request is refused with a reason and the application keeps its overlay.
Experimental for this minor under
[`RUNICDESK104`](https://github.com/Runic-Artifex/runic-sdk/blob/v0.19.0/docs/experimental.md#RUNICDESK104); the window building
blocks of 0.18 stay stable.

- Windows (WebView2), macOS (WKWebView) and Linux (WebKitGTK, GTK 3 and GTK 4,
  also `Runic.Desktop.Gtk4`'s window). Installed browsers, serve-only
  applications, WPF, CS-WebUI, custom window hosts and hosted windows refuse it
  with `Unsupported`.
- `RunicTestWindowPresentation` grows and refuses as a desktop window does, so a
  test checks a ViewModel's fallback.
- The [side panel guide](https://github.com/Runic-Artifex/runic-sdk/blob/v0.19.0/docs/side-panel.md) covers the panel's page
  (no address sync, `window.close()`, drops refused), the fallback, accessibility
  and each platform's limits. The
  [side panel example](https://github.com/Runic-Artifex/runic-sdk/blob/v0.19.0/examples/side-panel/README.md) is an 860 × 640
  window with a debug panel and the overlay fallback.
- The screen reader checks read a window with a side panel: the panel's
  landmark, the reading order on both edges, and what NVDA, Orca and VoiceOver
  say as the focus moves into the panel and back.
- On macOS, VoiceOver reads the control that Tab focuses in the panel or back in
  the page, not the view's web content group (#929, listed under
  [Fixes](#fixes)).

Known issues: see [Known issues](#known-issues) and
[Known limits](https://github.com/Runic-Artifex/runic-sdk/blob/v0.19.0/docs/side-panel.md#known-limits).

## An appearance override per hosted region (#917, experimental)

A host can give a guest's window in a region its own appearance, such as an
installer whose wizard step shows the design the user picked, under the new
`runic-host/1` feature `region-appearance/1`. It is experimental with the rest of
hosted applications
([`RUNICDESK103`](https://github.com/Runic-Artifex/runic-sdk/blob/v0.19.0/docs/experimental.md#RUNICDESK103)).

- `RunicHostedRegionOptions.Appearance` sets the override from the window's
  open, and `RunicHostedRegion.SetAppearanceAsync` changes or removes it later,
  also while the window is detached; `MoveToAsync` and re-attaching keep it.
  `RunicHostedAppearance` has nullable members, each replacing the host's
  desktop value; `DesktopColorScheme.NoPreference` reads as `null`, so a design
  menu's "System" choice maps to it directly, and `TextScale` is from 0.5 to 4.
- The guest merges the override with the host's desktop appearance for that
  window's pages only, a component's included, before their first content.
  Windows it owns, the guest's other windows and the host's own pages keep the
  desktop's. The Views `appearance` push lists the members the host decided in
  its new `override` member, so a page's combined appearance takes them over
  the engine's media queries.
- The host page sets the override's colour scheme as the CSS `color-scheme` of
  the region's frame or component (the new `colorScheme` member of
  `hosted-region-content` and `hosted-region-update`). Whether the frame's
  `prefers-color-scheme` follows it depends on the engine and is best effort:
  style a region's page from its appearance, not from media queries.
- A 0.18 guest still shows in the region, with the desktop's appearance:
  `RunicHostedWindowRequest.CanOverrideAppearance` and
  `RunicHostedRegion.CanSetAppearance` are `false`, `SetAppearanceAsync` returns
  `false`, and the host logs `DesktopHostedRegionAppearanceUnavailable`
  (event 2030) once for the window.
- `RunicTestHost` plays the host: `RunicTestHostOptions.RegionAppearance` and
  `SetRegionAppearanceAsync(window, appearance)`.
- Runic's guest, host and browser host list `region-appearance/1` in their
  `hello`. The host conformance corpus has its scenarios RA1–RA12.
  [Appearance in a region](https://github.com/Runic-Artifex/runic-sdk/blob/v0.19.0/specs/desktop/host-protocol.md#appearance-in-a-region-region-appearance1).

## Maximize, restore and placement of an open window (#897)

- `DesktopWindow.MaximizeAsync` and `RestoreAsync` ask for a state and do
  nothing when the window is in it already, unlike `ToggleMaximizedAsync`.
  `RestoreAsync` leaves full screen, un-maximizes and un-minimizes the window;
  a window minimized while it was maximized comes back at its normal bounds.
  A hidden window stays hidden and shows in the state asked for.
- `DesktopWindow.SetPlacementAsync(DesktopWindowPlacement)` gives an open
  window a placement as `DesktopWindowOptions.Placement` gives a window that
  opens: the bounds it restores to, in the units `State.Placement` reports, and
  whether it is maximized or full-screen. It also sets the restored bounds of a
  maximized, minimized, full-screen or hidden window, which `SetBoundsAsync`
  refuses. The placement is fitted to the monitors that exist now, as at open.
  With a side panel open it is the page's placement.
- `DesktopWindowCapabilities.WindowPlacement` on WebView2, WKWebView (not for a
  sheet), GTK 3 and `Runic.Desktop.Gtk4`. Custom window hosts implement
  `IDesktopWindowShowStateHost`. The API is stable.
- Windows activates a window that it maximizes or brings back from minimized,
  as when the user does; `RestoreAsync` of a visible maximized window does not
  activate it. On Wayland a placement with a position fails as a whole with
  `window-position-unavailable`, and a minimized GTK window comes back only
  with `FocusAsync`.
- ViewModels do the same through `IRunicWindowPresentation`: `MaximizeAsync`,
  `RestoreAsync` and `SetPlacementAsync(RunicWindowPlacement)`, with the
  window's `Placement`, which `PropertyChanged` reports in a turn of the
  Window's model context. `Features` lists them as `Maximize` and `Placement`.
  They are default interface members, so a custom presentation compiles
  unchanged and reports `BackendUnavailable`. The API is stable.
- `RunicWindowPlacement` uses the host's placement units: on Runic Desktop
  those of `DesktopWindowState.Placement`, converted with `ToRunicPlacement()`
  and `ToDesktopPlacement()` (Runic.Application.Views.Desktop), and in WPF
  device-independent pixels. WPF's `ForWindowPresentation` implements all
  three. An installed browser, CS-WebUI and a host application's region report
  `BackendUnavailable`, and a serve-only Window reports `OwnerUnavailable`.
- Hosted windows (`runic-host/1`) gain the `maximize`, `restore` and
  `set-placement` requests, behind the window features `maximize` and
  `placement`. The host's policy can refuse them (`PermissionDenied`) or clamp
  a placement (`RunicHostedPresentationKind.Maximize`, `Restore`,
  `SetPlacement` and `RunicHostedPresentationRequest.Placement`), and they count
  among the requests that can activate a window. The `placement` push and the
  `window-open` reply carry the restored bounds, which the guest's `Placement`
  reports. An older host lists neither feature, and its guest reports
  `BackendUnavailable`.
- `RunicTestWindowPresentation` records the three requests, keeps a placement
  and simulates a user's move with `SetPlacement`; `RunicTestHost` lists the
  new features and pushes a placement with `RunicTestHostedWindow.SetPlacementAsync`.


## Per-window services for a window the application opened itself (#896)

An application that opens its `DesktopWindow` itself, with
`DesktopSurface.OpenWindowAsync`, rather than through `RunicDesktopHost`, now
gives that window a DI scope's per-window services with
`DesktopPlatformServices.AttachWindowServices(window, scope.ServiceProvider, content)`.
Its ViewModels then present, minimize and hide the window and set its colour
scheme through `IRunicWindowPresentation`, with the results of a
`RunicDesktopHost` Window. Its locale (`IRunicWindowLocale`) follows the content
session, with the native layout direction. Its page connections
(`IRunicConnections`), dialogs and clipboard are attached too, and the page
receives the desktop's appearance (`appearance/1`) when only this computer can
reach it. `IRunicWindowContext.RequestCloseAsync` asks the window's
`ConfirmCloseAsync`; `IRunicWindowContext.Window` stays `null`. ViewModels the
scope resolved before the attach follow the window from then on. For ViewModels
without a scope, `DesktopPlatformServices.ForWindowPresentation(window)` is the
window's presentation, as `WpfPlatformServices.ForWindowPresentation` is for a
WPF window. The Views README now has a table of the per-window services each way
of opening a window provides.

## Windows title bar and the system's dark mode (#888)

Under `DesktopColorScheme.NoPreference`, a Windows window's title bar now follows
the system's app mode (Settings > Personalization > Colors, `AppsUseLightTheme`).
It also switches when the user changes the mode while the window is open
(`WM_SETTINGCHANGE` "ImmersiveColorSet"). The page's `prefers-color-scheme`
keeps following the system through the WebView2 profile, as before, so an
application's "System" theme option shows a dark title bar over a dark page
without pinning the page's scheme. A contrast theme keeps its own title bar
colours. `Light` and `Dark` behave as before. This applies to the WebView2
window host and to a WPF window's `IRunicWindowPresentation`. A WPF window whose
scheme was never set keeps WPF's default title bar.

## Close drain (#900, experimental)

A Window can stay open after its close was decided until its accepted work has
drained, and each operation can declare what a close does to it, so durable
work is never cancelled halfway. The close-drain API is experimental for one
minor ([`RUNICDESK105`](https://github.com/Runic-Artifex/runic-sdk/blob/v0.19.0/docs/experimental.md#RUNICDESK105)).

- `AcceptedWorkScope.WaitForAcceptedAsync` (stable) waits until the work the
  scope accepted before the call has finished and keeps admission open, so a
  close guard can wait for work and still keep its Window open.
- `[RunicOperationClose(Cancel)]` marks a read-only operation, asked to cancel
  as soon as a close is decided; `[RunicOperationClose(Durable)]` an operation
  that no window close, disposal or host shutdown asks to cancel. The Window's
  scope stays until durable work ended
  (`RunicWindowCloseResult.RemainingDurableWork`). The generator forwards the
  declaration like `RunicOperationRetirement`, warns with the new
  `RUNICBRIDGE039` where it reaches no operation, and the TypeScript client and
  contract hash do not change. Unmarked operations behave as before.
- `IRunicWindowContext.DrainOnClose(scope)` makes the Window's close wait for an
  application's `AcceptedWorkScope`, without cancelling its work.
- `RunicWindowOptions.CloseDrain` (`None`, `For(timeout)`, `UntilDrained`)
  keeps the window visible after every guard agreed. The page receives
  `closing` with `draining: true`, stays connected and keeps receiving the
  window's state, and a second user close is ignored. `@runic-artifex/views`
  reports it through `onBridgeDraining` (`./experimental`).
  `RunicWindowTestHost` drains as well (`RunicWindowTestHostOptions.CloseDrain`,
  `RunicTestWindow.IsDraining`).
- Runic Desktop keeps the window open: `RunicDesktopHostOptions.CloseDrain` sets
  the default for every Window. The embedded window of every host (WebView2,
  WKWebView, WebKitGTK with GTK 3 and `Runic.Desktop.Gtk4`) stays visible and
  responsive after the user's close, `RequestCloseAsync` or a quit was
  approved, and closes by itself once the work has drained. A second close by
  the user is ignored, and `RequestCloseAsync` returns `true` at the decision.
  A hosted application's Window drains before it reports `window-closed`, and
  the host keeps its window, or its region, until then; the protocol is
  unchanged. An installed browser, serve-only mode and CS-WebUI cannot keep a
  window open: they log `WindowCloseDrainUnavailable` (event 1055), and the
  Window's scope still waits for durable work.
- `DesktopWindowOptions.CloseDrainAsync` is the primitive underneath, for
  windows an application opens itself (`DesktopPlatformServices.AttachWindowServices`):
  `CloseDrainAsync = (_, ct) => new(work.WaitForAcceptedAsync(ct))`. Its
  `DesktopCloseDrainContext.Reason` says whether the user, a request, a quit or
  a shutdown started it. Where the window cannot refuse a close, it runs after
  the window is gone, with the warning `close-drain-unavailable`.
- A shutdown drains too: Ctrl+C, SIGTERM, SIGHUP, a closed Windows console and
  a quit cancel the new `DesktopHost.ShutdownStarting` first, close the windows
  without a drain, and keep the draining windows visible for up to
  `DesktopHostOptions.ShutdownDrainTimeout` (30 seconds by default).
  `ShutdownRequested` is cancelled after the drains, and together with
  `ShutdownStarting` when no window drains, as before. Runic cancels no durable
  work at the limit; only the operating system or a second Ctrl+C ends the
  process earlier. Keep systemd's `TimeoutStopSec`, `docker stop -t` and a
  hosting application's `StopTimeout` above the drain.

## Appearance per hosted region (#917, experimental)

- `@runic-artifex/views`: the `appearance` push's new `override` member lists
  the members the host decided for the window. `appearance()` and
  `onAppearance` report the host's value for those members over the engine's
  media queries, from the first push on, so a guest's page in a region with
  an override gets it in its first render. `<runic-hosted-region>` sets the
  CSS `color-scheme` of its frame, or of a component's element, from the
  region's `colorScheme`. The mock bridge's `setAppearance(value, { override })`
  plays such a push in page tests.

## Fixes

- `Runic.Desktop.Gtk4` on X11 no longer leaves a window at its old position,
  offset by the window manager's decorations, when `SetBoundsAsync`, a placement
  or a side panel on the left edge moves and resizes it (#926).
- On macOS, VoiceOver reads the control that Tab focuses in a side panel or back
  in the page, not the view's web content group (#929).

## CI and tests

- The scaling suite and the NativeAOT size budget per ViewModel; see
  [Bridge costs](#bridge-costs-that-grew-with-the-viewmodel-909-910-911).
- A Views test that waited a fixed time for a garbage collection now collects
  until its condition holds or 5 seconds pass, and names the controllers that
  are still reachable when it fails (#930).

## Known issues

- The side panel's left edge is refused on Wayland (`PositionUnavailable`),
  transparent GTK 3 windows refuse the panel, and drops on the panel are
  refused. Frame capture and Tab between the views are unverified on Windows on
  Arm. See
  [Known limits](https://github.com/Runic-Artifex/runic-sdk/blob/v0.19.0/docs/side-panel.md#known-limits).
- An installed browser, serve-only mode and CS-WebUI cannot keep a window open
  during a close drain: they log `WindowCloseDrainUnavailable` (event 1055), and
  the Window's scope still waits for durable work.
- Assistive-technology behaviour of hosted regions (NVDA, Narrator, VoiceOver)
  was not checked manually for 0.19.0 either. Automated checks cover layout,
  focus and Tab order, not how a screen reader reads a guest's page inside a
  region.
- With an appearance override, a guest page's `prefers-color-scheme` in a region
  is best effort: WebView2 and WebKitGTK 2.54 follow the frame's
  `color-scheme`, WKWebView and older WebKitGTK do not. Style the page from its
  appearance (`appearance()`), which every engine receives before the first
  content. See
  [Engine support](https://github.com/Runic-Artifex/runic-sdk/blob/v0.19.0/docs/hosted-regions.md#engine-support-for-prefers-color-scheme-in-a-region).
