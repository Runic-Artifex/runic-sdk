Install matching `0.19.0` packages from NuGet and npm.

## Upgrading from 0.18

Update every Runic NuGet and npm package to 0.19.0 together and rebuild, so that
the generated clients are regenerated.

- **Rebuild every assembly that contains generated Bridges** (#901), including a
  separate `RunicApplicationFrontendModelAssembly` and ViewModel libraries that
  other applications reference. The Bridge runtime and its descriptors in
  `Runic.Application.Views.Generated` lost their ViewModel type parameter, so a
  Bridge that the 0.18 generator wrote fails to load on 0.19. The host reports
  it at the first Window or View as `RUNICBRIDGE038`, which names the assembly
  to rebuild (#916). The wire protocol and the generated TypeScript client
  are unchanged. Hand-written Bridges, such as test doubles, follow the new shape:
  [migration guide](https://github.com/Runic-Artifex/runic-sdk/blob/v0.19.0/docs/migration-1.0.md#from-018-to-019).

- **A Windows title bar without a forced colour scheme follows the system's dark
  mode** (#888). A WebView2 window whose `ColorScheme` is `NoPreference` (the
  default, also after `SetColorSchemeAsync(NoPreference)`) was light. It now
  takes the system's app mode, and a WPF window takes it after
  `IRunicWindowPresentation.SetColorSchemeAsync(NoPreference)`. On a dark Windows,
  such a window now has a dark title bar. An application that needs a light title
  bar there sets `Light`, which also pins the page's `prefers-color-scheme`.

## Smaller NativeAOT executables per ViewModel (#901)

The Bridge runtime (`ViewModelBridge` and its property, command, collection,
state and interaction descriptors) now holds the ViewModel as `object` instead of
being generic over it. NativeAOT shares method bodies across instantiations, but
it still needed type descriptors, generic dictionaries and hash-table entries for
every closed generic type the runtime used, about 110–120 KiB of executable per
bridged ViewModel on linux-x64. Generated Bridges now cast the ViewModel in
static lambdas and pass `typeof` of it to the runtime, so every Bridge shares one
copy of the runtime. On the scaling suite's fixture the executable grows by
about 24 KiB per ViewModel instead of about 118 KiB, and with nine
ViewModels the executable is 0.9 MiB smaller. Managed (JIT)
applications are unaffected apart from a cast per member read.

## A stale generated Bridge reports which library to rebuild (#916)

An assembly whose Bridges another Runic release generated used to fail at its
first Window with a `TypeLoadException` or `MissingMethodException` that named
a Runic type but not the library. It now fails with `RUNICBRIDGE038`, a
`RunicBridgeContractException` whose message and `AssemblyName` name the
assembly and say "Rebuild this library against Runic 0.19.0", with the original
exception as its `InnerException`.

From 0.19 the generated `AddRunicBridges()` passes the generated-code contract
version its generator wrote to the runtime, which checks it before it registers
a Bridge, so a future break of the generated-code support API reports the
library at registration, before any Bridge type loads. The check is one integer
comparison and reads no metadata, also under NativeAOT. Bridges from 0.18 and
earlier make no such call, so the hosts (Runic Desktop, CS-WebUI, WPF's
`RunicViewHost` and `RunicWindowTestHost`) report their load failure when the
first Window or View attaches the Bridge.
[Diagnostics](https://github.com/Runic-Artifex/runic-sdk/blob/v0.19.0/docs/diagnostics.md#runicbridge038).

## Windows title bar and the system's dark mode (#888)

Under `DesktopColorScheme.NoPreference`, a Windows window's title bar now follows
the system's app mode (Settings > Personalization > Colors, `AppsUseLightTheme`).
It also switches when the user changes the mode while the window is open
(`WM_SETTINGCHANGE` "ImmersiveColorSet"). The page's `prefers-color-scheme`
keeps following the system through the WebView2 profile, as before, so an
application's "System" theme option shows a dark title bar over a dark page
without pinning the page's scheme. A contrast theme keeps its own title bar
colours. `Light` and `Dark` behave as before. This applies to the WebView2
window host and to a WPF window's `IRunicWindowPresentation`. A WPF window whose
scheme was never set keeps WPF's default title bar.

## Per-window services for a window the application opened itself (#896)

An application that opens its `DesktopWindow` itself, with
`DesktopSurface.OpenWindowAsync`, rather than through `RunicDesktopHost`, now
gives that window a DI scope's per-window services with
`DesktopPlatformServices.AttachWindowServices(window, scope.ServiceProvider, content)`.
Its ViewModels then present, minimize and hide the window and set its colour
scheme through `IRunicWindowPresentation`, with the results of a
`RunicDesktopHost` Window. Its locale (`IRunicWindowLocale`) follows the content
session, with the native layout direction. Its page connections
(`IRunicConnections`), dialogs and clipboard are attached too, and the page
receives the desktop's appearance (`appearance/1`) when only this computer can
reach it. `IRunicWindowContext.RequestCloseAsync` asks the window's
`ConfirmCloseAsync`; `IRunicWindowContext.Window` stays `null`. ViewModels the
scope resolved before the attach follow the window from then on. For ViewModels
without a scope, `DesktopPlatformServices.ForWindowPresentation(window)` is the
window's presentation, as `WpfPlatformServices.ForWindowPresentation` is for a
WPF window. The Views README now has a table of the per-window services each way
of opening a window provides.

## Close drain, part 1: accepted-work waits and operation close policies (#900, experimental)

A Window can stay open after its close was decided until its accepted work has
drained, and each operation can declare what a close does to it, so durable
work is never cancelled halfway. The close-drain API is experimental for one
minor ([`RUNICDESK105`](https://github.com/Runic-Artifex/runic-sdk/blob/v0.19.0/docs/experimental.md#RUNICDESK105)).

- `AcceptedWorkScope.WaitForAcceptedAsync` (stable) waits until the work the
  scope accepted before the call has finished and keeps admission open, so a
  close guard can wait for work and still keep its Window open.
- `[RunicOperationClose(Cancel)]` marks a read-only operation, asked to cancel
  as soon as a close is decided; `[RunicOperationClose(Durable)]` an operation
  that no window close, disposal or host shutdown asks to cancel. The Window's
  scope stays until durable work ended
  (`RunicWindowCloseResult.RemainingDurableWork`). The generator forwards the
  declaration like `RunicOperationRetirement`, warns with the new
  `RUNICBRIDGE039` where it reaches no operation, and the TypeScript client and
  contract hash do not change. Unmarked operations behave as before.
- `IRunicWindowContext.DrainOnClose(scope)` makes the Window's close wait for an
  application's `AcceptedWorkScope`, without cancelling its work.
- `RunicWindowOptions.CloseDrain` (`None`, `For(timeout)`, `UntilDrained`)
  keeps the window visible after every guard agreed. The page receives
  `closing` with `draining: true`, stays connected and keeps receiving the
  window's state, and a second user close is ignored. `@runic-artifex/views`
  reports it through `onBridgeDraining` (`./experimental`). In this release
  part the visible drain runs in `RunicWindowTestHost`
  (`RunicWindowTestHostOptions.CloseDrain`, `RunicTestWindow.IsDraining`);
  Runic Desktop's windows and its shutdown follow.
