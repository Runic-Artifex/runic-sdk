# Runic SDK 0.8.0-preview.4

Install matching `0.8.0-preview.4` packages from NuGet and npm. Command Line
versions remain independent of this SDK.

## Runic Command Line 0.7.0-preview.2

`dotnet-runic`, the project creator (`Runic.Create`), the asset packer and the
Windows administration verifier use Runic Command Line 0.7.0-preview.2 (see its
[release notes](https://github.com/Runic-Artifex/runic-cli-sdk/blob/main/eng/release/notes/0.7.0-preview.2.md)).
Their commands, options and JSON payloads are unchanged.

A Runic.CommandLine command can start the Desktop host, such as a `ui` command
that opens an application's Window
([#301](https://github.com/Runic-Artifex/runic-sdk/issues/301)). The host must
start on the process main thread before any `await`, and a command runs
asynchronously, so an application had to recognize such a command line itself
before `CommandApp.RunAsync`. The command now hands `DesktopEventLoop.Run` or
`RunicDesktopHost.Run` back to `Main` with
`CommandExecutionContext.ContinueOnCallingThread`, and `Main` returns
`CommandApp.Run(args)`, which runs it on the main thread once the command
succeeded. The Runic.Application.Views.Desktop README's
[From a command line](https://github.com/Runic-Artifex/runic-sdk/blob/main/packages/dotnet/Runic.Application.Views.Desktop/README.md#from-a-command-line)
section shows such a command.

## Privileged actions

`PrivilegedActionDeclaration` compiles its `ArgumentPattern` on the first
`AcceptsArguments` (or `CreateArgumentVector`) instead of when it is created.
The `NonBacktracking` regex cost tens of milliseconds under the JIT (45 ms in
one application) in every process that read the generated `PrivilegedActions`
class, such as a status icon at startup. Matching is unchanged. `RunicPrivilegedAction` items are still checked
at build time (`RUNICPA008`); a declaration written by hand with an invalid
pattern now throws `ArgumentException` or `NotSupportedException` from that
first check rather than from the `ArgumentPattern` initializer.

`RunicApplicationInstallPrefix` defaults to `/usr` in builds that do not set
it, so `Program="$(RunicApplicationInstallPrefix)/bin/my-app"` names
`/usr/bin/my-app` there rather than `/bin/my-app`
([#295](https://github.com/Runic-Artifex/runic-sdk/issues/295)). The Nix
builder still sets it to the package's `$out`; set it for another prefix, such
as `-p:RunicApplicationInstallPrefix=/opt/my-app`.

Several operations of one program can share one action, and so the one
authorization that `auth_admin_keep` retains for it, as commands
([#294](https://github.com/Runic-Artifex/runic-sdk/issues/294)).
`RunicPrivilegedCommand` items name a command of an action and the patterns of
the arguments after it, by position, with optional trailing arguments:

```xml
<RunicPrivilegedCommand Include="activate-output" Action="org.example.app.system"
                        Arguments="switch|boot;/nix/store/[a-z0-9]{32}-nixos-system-[A-Za-z0-9._+-]+" />
<RunicPrivilegedCommand Include="gc" Action="org.example.app.system" Arguments="[1-9][0-9]{0,2}" MinimumArguments="0" />
```

The generated declaration carries them as the new
`PrivilegedActionDeclaration.Commands` (`PrivilegedActionCommand` values), so
the application's request and `PolkitHelper.Match`, `ElevatedHelper.Match` and
the macOS daemon check each position; before, the positional rules lived only
in the privileged program. The policy keeps one entry per action. Invalid
commands are the new build error `RUNICPA015`. Declarations without commands
are unchanged.

## Single instance

Found while building nix-manager's daemon on Runic. Both changes are additive,
and the instance protocol is unchanged, so instances and launching processes of
earlier previews still work together.

- `ApplicationInstanceOptions.ForwardOnly` forwards a launch to the running
  instance without ever becoming it
  ([#308](https://github.com/Runic-Artifex/runic-sdk/issues/308)). Without a
  running instance, `ClaimAsync` reports the new
  `ApplicationInstanceClaim.NotRunning`. Before, a command line that should only
  talk to a running daemon had to claim the instance and release it at once,
  and a daemon starting in that moment found the command line listening and
  retried until it let go.
- `IApplicationLaunchReply.CancelRequested` and `IApplicationLaunchReply.Disconnected`
  tell a launching process's cancel request (`IForwardedLaunchReply.CancelAsync`,
  such as on Ctrl+C) from one that went away or a running instance that ends
  ([#309](https://github.com/Runic-Artifex/runic-sdk/issues/309)). `Cancelled`
  is unchanged and is cancelled for both, after the specific token. An operation
  given `CancelRequested` outlives a dropped SSH session and still stops on
  Ctrl+C. The interface's default implementations return `Cancelled`, so other
  implementations keep compiling.

## File watching

`RunicWatchTarget.Files(path, pattern)` watches each matching entry of a
directory as `RunicWatchTarget.File` watches one file: an entry added, removed,
renamed, written, or replaced by renaming a temporary file over it
([#302](https://github.com/Runic-Artifex/runic-sdk/issues/302)). A
`Directory` target reports only changes to the set of names, so a record that
another process rewrites atomically needed a watch of its own. `Directory` is
unchanged.

## Serve-only mode on Runic Desktop

- A line on standard input ends the Windows serving at that moment. A Window
  the application opens after it serves until the next line; before, the first
  line was read once per process, so such a Window closed at once.
- `PlatformServices.PresentAsync(IRunicWindow, context, cancellationToken)`
  brings a Window forward on any host. In serve-only mode, where
  `DesktopBridgeWindow<TViewModel>.NativeOwner` throws because there is no
  presentation, and for a Window on another host, it reports
  `OwnerUnavailable`. The change is additive.
- The redirect from a directory to its index page, such as from the URL that
  serve-only mode prints to `index.html`, keeps the query string
  ([#313](https://github.com/Runic-Artifex/runic-sdk/issues/313)). A served page
  that reads its route from `location.search` opened on the index without it.
  The browser keeps the fragment, which the server never receives.
- A Window can serve application files that are not part of its frontend
  build, such as icons from a cache, in a native window and in serve-only mode
  alike ([#313](https://github.com/Runic-Artifex/runic-sdk/issues/313)).
  `RunicDesktopHost.Resources` chooses a `ContentHandler` for each Window as it
  opens, and becomes the new `DesktopSurfaceOptions.Resources` of its surface,
  which is asked for what the content has no file for, before 404. Before, a
  page could only load such files as data URLs through its ViewModel.
- A served Window can end with its last browser tab
  ([#317](https://github.com/Runic-Artifex/runic-sdk/issues/317)).
  `RunicDesktopHost.GetSurface(window)` returns a Window's surface without
  naming its ViewModel type, and the new `DesktopSurface.ConnectionCount`
  counts its connected pages; a connection event's handler already sees the
  count with that event. Counting the events yourself could go wrong, since a
  connection that loses its admission right after its token check is reported
  disconnected without having been reported connected. The changes are
  additive.

## Runic Desktop on Linux

Found while porting nix-manager to Runic
([#313](https://github.com/Runic-Artifex/runic-sdk/issues/313),
[#318](https://github.com/Runic-Artifex/runic-sdk/issues/318)). The changes are
additive: `RunicDesktopHost.OpenWindowAsync<TWindow>(options, activation, cancellationToken)`
and `DesktopWindowHostOptions.ReportDiagnostic` are new. The activation follows
the options, so existing calls with one argument still open as before.

- A Window opened for a launch or a click can get focus.
  `RunicDesktopHost.OpenWindowAsync<TWindow>(options, activation, cancellationToken)`
  opens the Window as `host.OpenWindowAsync<TWindow>(options)` does, then
  presents it with the desktop's activation token or startup ID, such as
  `ApplicationLaunch.PlatformContext` of a launch the running instance
  received. Before, KWin and other Wayland compositors opened such a Window
  behind the active one, because nothing passed it the token. A hidden window, a
  served one and an installed browser are not presented. An open Window is
  brought forward with `PlatformServices.PresentAsync(window, context)` as
  before. The status-icon example opens its Window this way.
- A crashed WebKitGTK web process no longer leaves a blank or frozen window that
  logs nothing. The embedded window, with GTK 3 or GTK 4, reloads its page and
  reports `web-process-terminated` to `DesktopHostOptions.DiagnosticSink` and the
  logger as the new event 3010, `EmbeddedWindowDiagnostic`, a warning. After
  three reloads within a minute it stops reloading, and the diagnostic is an
  error. A process the application ended itself is reported without a reload. A
  custom `IDesktopWindowHost` reports its own events through the new
  `DesktopWindowHostOptions.ReportDiagnostic`.
- The Runic.Desktop README's
  [Accessibility](https://github.com/Runic-Artifex/runic-sdk/blob/main/packages/dotnet/Runic.Desktop/README.md#accessibility)
  section describes two WebKitGTK 2.54.1 limitations.
  Live regions and changed accessible names or descriptions are silent under
  Orca, because WebKitGTK sends no AT-SPI event for them; report changes through
  native semantics instead, such as a spin button whose value Orca reads. A
  list item whose only content is a button whose last node has no box, such as
  whitespace or the comments Svelte inserts, aborts the web process when Orca
  reads it, with GTK 3 and GTK 4; give such list items `display: contents` and
  their position with `aria-setsize` and `aria-posinset`.

## Screen-reader announcements

Runic Desktop windows can ask the screen reader to speak a status message, such
as "Saved", without moving focus
([#318](https://github.com/Runic-Artifex/runic-sdk/issues/318)). WebKitGTK
reports no ARIA live region to Orca, so before this a page on Linux had no way
to announce a result. The changes are additive.

- `DesktopWindow.AnnounceAsync(message, priority)` takes a
  `DesktopAnnouncementPriority`, `Polite` (the default) or `Assertive`, and
  needs the new `DesktopWindowCapabilities.Announcements`. GTK 3 emits ATK's
  `notification` signal, which AT-SPI sends as `Object:Announcement`. GTK 4.14
  and later calls `gtk_accessible_announce`. WebView2 raises a UI Automation
  notification, and WKWebView posts
  `NSAccessibilityAnnouncementRequestedNotification`. An installed browser
  cannot announce.
- `PlatformServices.AnnounceAsync(window, message, priority)` announces for a
  Runic Window, and `DesktopWindowPlatformServices.AnnounceAsync(message, priority)`
  for a ViewModel. Both return a `PlatformResult`, which reports a Window
  without an embedded window as `OwnerUnavailable`.
- A custom `IDesktopWindowHost` that reports `Announcements` implements the new
  `AnnounceAsync` default interface method.

## WPF

`WpfPlatformServices.PresentAsync(window)` brings a WPF window forward for a
launch that another copy of the application forwarded
([#267](https://github.com/Runic-Artifex/runic-sdk/issues/267)). It shows a
hidden window, restores a minimized one and takes the foreground the forwarding
launch allows, or flashes the taskbar button and reports `PermissionDenied`, as
`PlatformServices.PresentAsync` does for Runic Desktop windows. Before, a WPF
application called `Window.Activate()`, which does neither. It is additive and,
like the rest of the package, experimental (`RUNICWPF001`).

## Navigation

- A region's `CurrentEntry` and `History` return the same `NavigationEntry<T>`
  instance for an entry on every thread
  ([#288](https://github.com/Runic-Artifex/runic-sdk/issues/288)). The typed
  entry is created on its first read. Before, threads that read it for the first
  time together could each get their own instance and keep it, so a
  `ReferenceEquals` comparison with a later read could fail. Comparing entries by
  `Id` was not affected.
- With `GuardWindowClose` in Runic.Navigation.Wpf, closing the window right
  after a guard kept the draft, once the region stopped transitioning but before
  the close check had finished, was silently dropped. Such a close now asks the
  guards again ([#358](https://github.com/Runic-Artifex/runic-sdk/issues/358)).

## Views

- A `RunicPathWatcher` without a `failed` callback no longer writes a warning
  to `Trace` for a directory that does not exist yet, such as a state
  directory an application creates on its first start
  ([#312](https://github.com/Runic-Artifex/runic-sdk/issues/312)). It polls
  for it as before and logs the new event 1016, `PathWatchPolling`, at Debug
  level. Lost events, watch limits and failed watches are still warnings
  (event 1015).
- The Views README describes how to open Windows from a second service
  provider in the same process, with a host for that provider on the running
  Desktop host
  ([#312](https://github.com/Runic-Artifex/runic-sdk/issues/312)).

## Live logs

A read-only `string` marked `[RunicAppendOnlyText]` (new in
Runic.Application.Views) crosses as the text it appends
([#300](https://github.com/Runic-Artifex/runic-sdk/issues/300)). Before, a
live log in ViewModel state was resent whole on every change, up to 128 KB per
line of output in nix-manager. The Bridge compares the new value with the one
the page has and publishes a frame with the number of UTF-16 code units
dropped from its start and the text appended, so a log that keeps its last
128 KB sends only its new lines. Appends in one batch are one change; `null`,
a change together with other state and a ViewModel with validation get full
states, and a page that misses a frame reads a snapshot. The page still sees
an ordinary `string`. The frame is a new `text` change of the collection delta
frames, applied by `@runic-artifex/views` through the new `defineText` of its
`generated` entry; the generated .NET Bridge uses the new
`PropertyDescriptor<T>.AppendOnlyTextField`. Generated clients and the .NET
application are rebuilt together.

## Application template

The Svelte, React and Vue frontends' `build` script runs `vite build` before
`svelte-check`, `tsc --noEmit` or `vue-tsc --noEmit`. Type-checking first failed
on a clean checkout once a Vite plugin that generates declarations was added,
such as Runic Translations, whose `virtual:runic-translations/...` declarations
Vite writes
([runic-translations-sdk#84](https://github.com/Runic-Artifex/runic-translations-sdk/issues/84)).
`typecheck` is unchanged.

## Nix packaging

- `buildRunicApplication` with `nativeAot = true` sets `PublishAot` for
  `projectFile` alone, as if its project file set it, instead of passing
  `-p:PublishAot=true` to every project. `testProjectFile` is restored with its
  usual lock file and runs under the JIT, without a NativeAOT lock file or
  `TreatAsLocalProperty="PublishAot"`.
- The Nix guide's note on NativeAOT lock files is corrected: whether the
  runtime's section lists `runtime.<rid>.Microsoft.DotNet.ILCompiler` depends
  on whether restore took the compiler package from nuget.org or from the .NET
  SDK in nixpkgs; both build.
- `buildRunicApplication` runs Microsoft.Testing.Platform tests, such as
  TUnit's, with `doCheck = true` and the new
  `testRunner = "Microsoft.Testing.Platform"`: it runs each test application
  of `testProjectFile` that it built, with `dotnetTestFlags` as its options.
  nixpkgs' `dotnet test` passes VSTest options, which they reject
  ([#296](https://github.com/Runic-Artifex/runic-sdk/issues/296)). The default,
  `"VSTest"`, is unchanged.
- `dotnet new runic-app --nix --tests` locks the test project for `linux-x64`,
  and the flake runs its tests in both packages and in `nix flake check`.
  Restore it with `dotnet restore RunicWindowApp.Tests` before the first build.
- The Nix guide describes passing `nodejs` and `dotnet-sdk` to `mkDevShell` to
  match an existing shell or the build.
- `buildRunicApplication` restores local .NET tools offline with the new
  `dotnetTools = { manifest; hashes; }`: each tool of the `dotnet-tools.json`
  is downloaded by the hash of its package, and the build runs
  `dotnet tool restore` before the projects' restore. A build step such as the
  Translations Vite plugin, which runs `dotnet tool run runic-translations`,
  then works in the sandbox without a copy of the tool
  ([#303](https://github.com/Runic-Artifex/runic-sdk/issues/303)). A manifest
  at the root of the source, which nixpkgs restores by itself and which failed
  there with lock files ("File exists"), works with it too.
- A `postConfigureNuGet` passed to `buildRunicApplication` without
  `nugetLockFiles` runs again; it was dropped.
- A Bun frontend whose `bun.lock` or `package.json` changed while
  `frontend.hash` did not fails with `frontend.hash is out of date`. Nix names
  the fixed-output install by its name and hash, so the build reused the
  install of the previous lock file without a word
  ([#311](https://github.com/Runic-Artifex/runic-sdk/issues/311)). The install
  now keeps the files it was installed from, so **every Bun frontend hash
  changes once**: set it to `lib.fakeHash` and copy the hash Nix reports.
- `frontend.hash` takes one hash per system, `{ x86_64-linux = ...;
  aarch64-linux = ...; }`, and the Bun install is told the system's OS and CPU,
  so `nix build .#default.frontendNodeModules.fetchedFor.aarch64-linux`
  computes the `aarch64-linux` hash on any system
  ([#314](https://github.com/Runic-Artifex/runic-sdk/issues/314)).
- `nugetLockFiles` takes lock files per runtime identifier,
  `{ linux-x64 = [ ... ]; linux-arm64 = [ ... ]; }`, and a locked restore
  rejects a lock file with another runtime's section at evaluation instead of
  failing the restore with `NU1004`. The Nix guide describes one lock file per
  runtime ([#314](https://github.com/Runic-Artifex/runic-sdk/issues/314)).
- `buildRunicApplication` takes `withSpeechSynthesis` (default `true`)
  ([#313](https://github.com/Runic-Artifex/runic-sdk/issues/313)). With
  `false` the wrapper loads a WebKitGTK built without the Web Speech API's
  speech synthesis and without flite, for GTK 3 and GTK 4. That is 72.6 MiB less
  closure for WebKitGTK 4.1, for an application whose page never speaks; screen
  readers are not affected. nixpkgs' binary cache has no such build, so
  WebKitGTK then compiles from source, which takes hours: build it on your own
  cache.
- `buildRunicApplication` installs the shell completions a command-line
  program prints, with the new `completions = { program; command; shells; }`:
  after the build it runs the installed program once per shell, by default
  `<program> completion bash|zsh|fish` (Runic.CommandLine's command; use
  `command = [ "--completions" ]` for `CommandCatalogBuilder.CompletionOption`),
  and installs the scripts for bash, zsh and fish
  ([#321](https://github.com/Runic-Artifex/runic-sdk/issues/321)). A cross
  build installs none.

## Bridge generation

- With `[assembly: RunicBridgeJsonIgnore]`, a DTO member marked
  `[JsonExtensionData]` stays on .NET, as an unconditional `[JsonIgnore]`
  does ([#299](https://github.com/Runic-Artifex/runic-sdk/issues/299)). Before,
  such a member, which keeps the JSON members the type does not declare, failed
  generation with `RUNICBRIDGE003` or needed `[RunicIgnore]`. Without the
  opt-in it remains part of the Bridge contract.
- A `JsonElement` or `JsonNode` crosses the Bridge as any JSON value, `unknown`
  in TypeScript ([#304](https://github.com/Runic-Artifex/runic-sdk/issues/304)),
  as state, a DTO member, a command argument or result, or an interaction
  value. Before, it failed generation with `RUNICBRIDGE003`, and an application
  wrote its own `[RunicBridgeCodec]`, which still takes precedence. A
  `JsonElement` holds JSON `null`; a non-nullable `JsonNode` cannot, so it is
  `NonNullable<unknown>` and rejects `null`. The client checks the value in
  both directions and rejects what `JSON.stringify` would change or drop, such
  as `NaN`, a `bigint` or `undefined` in an array, through the new
  `json` decoder of `@runic-artifex/views/generated/wire`. `JsonObject`,
  `JsonArray`, `JsonValue` and `JsonDocument` still fail generation, now with a
  message that names `JsonNode`.
- A `bool` property that `[RelayCommand(CanExecute = nameof(CanCreate))]`
  names, and whose wire name is the command's `canCreate` availability, is that
  availability ([#305](https://github.com/Runic-Artifex/runic-sdk/issues/305)).
  Before, the two collided with `RUNICBRIDGE004`, and the property needed
  `[RunicIgnore]`. The state carries `canCreate` once, from the command's
  `CanExecute`; the generated client is unchanged.
- A CommunityToolkit `[RelayCommand]` method that returns `Task<T>` delivers
  its `T` to the page
  ([#312](https://github.com/Runic-Artifex/runic-sdk/issues/312)): its
  `startX` operation is a `BridgeOperation<T>` whose `outcome()` carries the
  value, as for a ReactiveUI command. Before, the operation was a
  `BridgeOperation<void>` and the result was dropped. The awaited `x()` call
  still resolves to the state, and a method that returns `Task` still has no
  result. The contract fingerprint now includes the result type, so such a
  ViewModel's generated client and .NET application are rebuilt together.
- A DTO that only the page sends, as a command input or an interaction result,
  declares the members .NET fills in as optional in TypeScript
  ([#312](https://github.com/Runic-Artifex/runic-sdk/issues/312)): a nullable
  member, which is `null` when missing, a constructor parameter with a default,
  which takes it, and a nullable member with a setter, which keeps its
  initializer. A page can call `start({ action: "switch" })` instead of passing
  every member. A type that also reaches the page keeps every member required
  in TypeScript, and .NET fills in what is missing either way.
- A `JsonElement` DTO member tells an absent value from `null`
  ([#312](https://github.com/Runic-Artifex/runic-sdk/issues/312)): a default
  `JsonElement` is left out of the object, the member is optional
  (`previous?: unknown`), and a missing member reads as a default
  `JsonElement`.
- A DTO that only reaches the page, as state, a command result, a declared
  failure or an interaction input, needs no constructor that maps to its
  members ([#312](https://github.com/Runic-Artifex/runic-sdk/issues/312)).
  Before, `RUNICBRIDGE003` required one for every DTO.
