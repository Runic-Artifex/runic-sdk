# Runic SDK 0.24.0

Install matching `0.24.0` packages from NuGet and npm;
`Runic.Application.Views.CsWebUi` is `0.24.0-preview.1` and
`Runic.Spelling` is `0.24.0-preview.1`.
Tested with Runic Translations 0.16.0 and Runic Command Line 0.15.0.

0.24.0 makes an application with more than one project work from a fresh
clone, lets a CI build the web on Linux and publish on Windows or macOS without
Node.js, makes `dotnet runic dev` and the IDEs start an application the same
way, and states the Views, host, server and assets contracts so that a Rust or
C++ implementation can be written and checked from the specification alone.

A library of ViewModels now generates their TypeScript clients once, into its
own frontend package, and the applications that present them import them from
there (#1318). The build installs a Bun, npm or pnpm workspace once at its
root, builds the library and workspace packages that the page imports, and
checks their exports; `dotnet runic dev` watches those packages and rebuilds
them, and `dotnet runic doctor` checks the workspace, the package managers and
how the page's imports resolve. `dev`, `doctor`, `package` and `size` start
from a solution root, and `dotnet new runic-app --library <Name>` creates an
application and a client library in one solution.

For split CI, a build writes a web bundle (`rax.web-bundle/1`) with every
project's page, generated clients and View fingerprints; a build on another
machine publishes from it with neither Node.js nor Bun, and fails when its own
Views no longer match the bundle's. `dotnet runic bundle` writes and checks a
bundle, `dotnet runic package --frontend-bundle` publishes from one, and
[`examples/split-ci`](https://github.com/Runic-Artifex/runic-sdk/tree/v0.24.0/examples/split-ci)
shows the workflow for GitHub, Gitea and Forgejo Actions.

`dotnet runic dev` now runs the Window with the project's first launch profile,
as `dotnet run` and the IDEs do, passes both the project's `StartArguments` and
the profile's arguments as Visual Studio and Runic DevKit do, and `doctor`'s
`launch-arguments` check shows what each one passes. For application code, a
field can write only when it loses focus (#1316), a View makes command handles
on demand (#1317), an interaction can be answered from the component's own
template (#1319), a ViewModel can publish only the members marked
`[RunicInclude]` (#1320), and a hosted region tells a slow guest from a failed
one (#1377, #1380, experimental).

The Views TypeScript clients are now written from the contract IR by
`@runic-artifex/views/codegen`, which the build runs with Node.js or Bun, and
each View has a contract fingerprint of its own, so every generated contract
string changes once. The Views conformance corpus, the Runic host protocol
scenarios, a new Desktop server corpus and the Assets archive vectors run
through one language-neutral driver, against the .NET implementation, the
native Desktop server and the TypeScript client. The native Desktop server is
now `rax_server` (C ABI 6), and it, the Kestrel server and the Assets readers
follow the RFCs and the archive specification where they did not.

0.24.0 fixes the Views runtime's ordering and capacity edge cases, a client
that did not type-check for a field named like a descriptor member, CS-WebUI's
Development browser left running after a hard kill, Linux browser profiles and
directory watches, `dev`'s stops and restarts, a failure that stopped `dev`
missing from VS Code's Problems, and an AppImage package that needed the
network. See [Fixes](#fixes).

The 0.24 release train is Runic Command Line 0.15.0, Runic Translations 0.16.0
and runic-sdk 0.24.0; Runic's editor extensions 0.24.0 follow this release.
[Upgrading from 0.23](#upgrading-from-023) lists what an application changes,
and the
[migration guide](https://github.com/Runic-Artifex/runic-sdk/blob/v0.24.0/docs/migration-1.0.md#from-023-to-024)
collects it.

## Upgrading from 0.23

Update every Runic NuGet and npm package to 0.24.0 together, rebuild, and commit
the regenerated clients: every View's contract string changes once, since each
View now has a fingerprint of its own. Views protocol 4 is unchanged, so a 0.23
page and a 0.24 host still connect, but an operation that a 0.23 page started
answers `unknown` after the upgrade. A project that generates Views clients
needs Node.js or Bun when it builds, also without a frontend, and the toolchain
floor is .NET SDK 10.0.404 and Node 24.22.3.

Most applications change nothing else. Code that reads or spreads a generated
field descriptor's members reads them under `fieldMembers`, an application that
names the native Desktop server's files or links it into its own Rust library
moves to `rax_server`, and an application that uses Runic Translations moves to
0.16.0. `dotnet runic dev` now applies the first launch profile; for a profile
that sets more than `DOTNET_ENVIRONMENT`, `--no-launch-profile` keeps 0.23's
behaviour.

- **Runic Translations 0.16 and Runic Command Line 0.15.**
  `Runic.Application.Views.Translations` requires Runic Translations
  `[0.16.0, 0.17.0)`, so an application that uses it moves every Translations
  package, NuGet and npm, to 0.16.0. The template pins Translations 0.16.0 three
  ways: the `dotnet-runic-translations` tool, `Runic.Translations` and
  `.Build`, and `@runic-artifex/vite-plugin-runic-translations`; `dotnet runic
  doctor` checks for Translations 0.16.0 and Command Line 0.15.0. Runic's own
  catalog and the ESM output of 0.16 are those of 0.15, so pages and generated
  modules are unaffected.
  `dotnet-runic`, `Runic.Create` and the `Runic.Assets` packer bundle Runic
  Command Line 0.15.0. An application that uses Command Line itself moves to
  0.15.0 with Translations 0.16, whose `Runic.Translations.CommandLine` requires
  `[0.15.0, 0.16.0)`. Command Line 0.15 adds catalog validation codes
  (`RCLI0028` to `RCLI0030`, a stricter `RCLI0019`), leaves `--version` out of a
  command's and a group's help (root help keeps it), ends a root command's usage
  error with root help's usage line, and no longer suggests a root command's
  name for a mistyped command. Update tests that compare such help or standard
  error text. The tools' own help and errors change the same way; none of them
  needed another change. See the
  [Translations 0.16.0 notes](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.16.0/eng/release/notes/0.16.0.md#upgrading-from-015)
  and the
  [Command Line 0.15.0 release](https://github.com/Runic-Artifex/runic-cli-sdk/releases/tag/v0.15.0).

### Breaking changes

- **Runic Assets archive readers no longer read Deflate64 (compression method 9).** `AssetArchive.Read`, `ReadAsync`,
  `ReadEmbedded` and `Inspect` read only methods 0 (stored) and 8 (deflate), as the
  [archive specification](../../../specs/assets/archive-v1.md#zip-container) states, and reject an archive with an
  entry of any other method with `InvalidDataException`. `ReadEmbedded` now finds such an entry when it reads the
  archive, not when its asset is first opened (#1373). `AssetArchive.Write*` and the packer never write Deflate64, so only an archive that another
  ZIP tool wrote with it is affected: write it again with the packer.

- **A generated Views field descriptor keeps its own members under `fieldMembers` (#1395).** `{View}Fields.title.name`,
  `.kind`, `.read`, `.write`, `.checked`, `.baseline`, `.errors`, `.validating`, `.constraints`, `.choices` and the
  other `BridgeField` members are now `{View}Fields.title[fieldMembers].name` and so on, and
  `fieldDefinition(field)` returns them for a generated descriptor or a hand-written definition. `BridgeField` is
  `{ readonly [fieldMembers]: BridgeFieldMembers }`; `BridgeFieldMembers` is the former interface. Passing a descriptor
  to `useField`, `injectField`, `bindField` or `createFieldController` is unchanged, as are `Fields.address.street`
  and `Fields.lines.at(key).quantity`. Only code that reads or spreads a descriptor's members changes, and a client
  generated before 0.24 needs the build to write it again:

  ```ts
  // Before
  const { maxLength } = EditorFields.title.constraints ?? {};
  const held = { ...EditorFields.title, write: queuedWrite };
  // After
  import { fieldDefinition, fieldMembers } from "@runic-artifex/views";
  const { maxLength } = fieldDefinition(EditorFields.title).constraints ?? {};
  const held = { ...EditorFields.title[fieldMembers], write: queuedWrite };
  ```

  A hand-written object typed as `BridgeField` (`{ name, kind, read, write }`) is a `FieldDefinition` or
  `BridgeFieldMembers` now; the bindings take it as before.

- **The native Desktop server's library is `rax_server`, C ABI 6.** `Runic.Desktop.NativeServer` ships
  `librax_server.so`, `librax_server.dylib` and `rax_server.dll` (static: `librax_server.a`, `rax_server.lib`) instead
  of `librunic_server.*` and `runic_server.*`; its C functions are `rax_server_*`, its header is `rax_server.h`, and
  the Rust package in `native/runic-server` is `runic-artifex-server`. An application that uses the packages at the
  same version needs no change. A directory named by `RunicDesktopNativeServerLibraryDirectory` must hold the new
  file names. An application that links the server into its own Rust library (`RunicDesktopNativeServerLinkage`
  `Application`) depends on `runic-artifex-server` at tag `v0.24.0` and names it with `use rax_server as _;`
  ([NativeAOT and an application's own Rust library](../../../packages/dotnet/Runic.Desktop.NativeServer/README.md#nativeaot-and-an-applications-own-rust-library)).
  A library of ABI 5 or earlier is not found under the new name and fails at the first window with
  `native-server-unavailable`.

- **Every Views contract string changes once: each View has a fingerprint of its own.** A View's contract fingerprint is
  now `runic.views.fingerprint/1`, the SHA-256 of the canonical form of the View's own contract IR
  ([contract IR, Fingerprint](../../../specs/application/contract-ir.md#fingerprint)). Until 0.23 it was one hash over
  every View of the assembly (`runic-bridge-contract-v6`), so a change to one View changed every View's contract. The
  operation contract `{ViewModel}:{fingerprint}` and the interaction and view request contracts
  `{fingerprint}:interaction:{Name}` and `{fingerprint}:request:{Name}` derive from it. So every `bridgeContract`,
  mock `contract`, `runicClientContracts` entry and interaction contract in committed generated clients changes once:
  rebuild and commit the generated clients, and publish a client library's package with them. An operation that a
  0.23 page started and recovers after the upgrade answers `unknown`, as it did after the 0.13 and 0.14 fingerprint
  changes. A Rust or C++ producer can compute the same fingerprint from its own descriptions. Hot Reload still
  recomputes a reflection hash of the assembly's Views, which the generated Bridge now carries as `ContractShape`, so
  an edit that changes a contract still asks for a restart (event 1100).

- **Building a project that generates Views clients needs Node.js or Bun.** The TypeScript clients are now written by the
  Views TypeScript emitter, `@runic-artifex/views/codegen`, which the build runs with Node.js or Bun
  (`RunicViewsGenerateClients`) after the .NET generator has written the C# Bridges and the contract IR
  (`obj/<configuration>/<framework>/runic-bridge/contract.ir.json`); the .NET generator writes no TypeScript any more. A
  project with `RunicApplicationFrontendGenerationEnabled=true` (the default with a host adapter) therefore needs `node`
  or `bun` on `PATH`, or `RunicApplicationFrontendCodegenRuntime` set to one, also when it builds no frontend; there is
  no .NET fallback. Without either, the build fails with
  [`RUNICBRIDGE084`](../../../docs/diagnostics.md#runicbridge084). The emitter is the one of the frontend's
  `@runic-artifex/views` when it is installed (resolved from `RunicApplicationFrontendDirectory`), which must then be
  0.24 or later, and the build installs the frontend's dependencies before it generates the clients (previously before
  the frontend build). Otherwise the build uses the copy of the emitter that `Runic.Application.Views` bundles, which
  matches the generator's version: when the project has no frontend (no `package.json` in
  `RunicApplicationFrontendDirectory`), such as a library or a test project, when the frontend's `package.json` declares
  no `@runic-artifex/views`, and when the build does not build the frontend (`RunicApplicationFrontendBuildEnabled=false`,
  as the `runic-app` template's test project sets). A frontend that declares `@runic-artifex/views` but does not have it
  installed after the install step (the install is disabled or failed) is RUNICBRIDGE084. The generated files are
  unchanged. A project with generation off, or without Views, needs neither.

### Behaviour and output changes

- `[RunicInclude]` together with `[RunicIgnore]` on a ViewModel property is error `RUNICBRIDGE077`, and
  `[RunicInclude]` on a ViewModel field, a static, non-public or inherited property, or an indexer is warning
  `RUNICBRIDGE078`. Until 0.24 the generator did not read `[RunicInclude]`, so both built without a word; neither
  changes a contract. See [Which members are published](../../../packages/dotnet/Runic.Application.Views/README.md#which-members-are-published) (#1320).

- **Runic Assets archive readers follow the archive specification's new reader rules.** `AssetArchive.Read`,
  `ReadAsync`, `ReadEmbedded` and `Inspect`, and so the packer's `verify`, now reject an archive in which an entry's
  bytes do not match its ZIP CRC-32, an entry is marked encrypted, the manifest is not UTF-8 or has two members of the
  same name in one object, or a `cacheMode` is not one of the names `NoStore`, `Revalidate` and `Immutable` (a number
  such as `"2"` or a padded name was accepted). `ReadEmbedded` checks each asset's CRC-32 when it is first opened, so a
  damaged embedded entry fails to open instead of being served. An archive whose manifest has no assets, no entry point
  or two now fails with `InvalidDataException`, as documented, instead of `ArgumentException`. Archives that
  `AssetArchive.Write*` and the packer write are unaffected. See the
  [reader rules](../../../specs/assets/archive-v1.md#reader-rules) and the
  [archive vectors](../../../specs/assets/vectors/README.md).

- **The Views version diagnostic follows the producer's Runic release, and Views accepts the names of the 0.25
  rename.** `@runic-artifex/views` now reports its `version` diagnostic when a `hello` reply's `release` differs from
  its own release, whatever the producer is called; without `release` it compares the version of
  `Runic.Application.Views` or, from now on, `RunicArtifex.Application.Views`. The message names the producer instead
  of a .NET host. A `hello` reply whose `release` is not a string is an invalid response. For the rename window, from
  0.24 through 1.0.x, the .NET producer also reserves routes that start with `rax.`, and Runic Desktop and CS-WebUI
  serve the in-page menu bar as `rax.menu-bar` as well as `runic.menu-bar`, pushing under the name the page watched.
  0.24 still sends today's names. See the [rename window](../../../specs/application/README.md#rename-window).

- **`dotnet runic dev` runs the Window with the first launch profile.** Like `dotnet run`, `dev` now uses the first
  `Project` profile of `Properties/launchSettings.json` when no `--launch-profile` is given, so the profile's
  `commandLineArgs` and `environmentVariables` apply. Before, it used none. The template's first profile only sets
  `DOTNET_ENVIRONMENT=Development`, which `dev` sets anyway. For a profile that sets more, `--no-launch-profile` restores
  the 0.23 behaviour. A `-e` value of a name the profile also sets still wins: `dev` passes it to `dotnet run -e`.

- `dotnet runic dev` passes `RunicApplicationFrontendDevSessionProject` instead of `RunicApplicationFrontendBuildEnabled=false`,
  `RunicApplicationFrontendCopyEnabled=false` and `RunicApplicationFrontendInstallEnabled=false`, and the build installs
  the frontend packages. With `--no-restore` it passes `RunicApplicationFrontendInstallMode=Never`; with `--no-build`
  nothing installs them, and missing packages stop `dev` with `RAPPDEV1008`. On a fresh clone `dev` reads the Vite
  build inputs after the build that installs Vite. With Views targets older than the tool, `dev` warns with
  `RAPPDEV1019` and keeps the old behaviour.

- The frontend install's record moved from the stamp `obj/runic-bridge-frontend-install.stamp`, which still exists, to
  the hash `node_modules/.runic-install` in the folder the install runs in: the install runs again when the install
  command, the lock file or a `package.json` changed, or when `node_modules` is gone, not when a file's time changed.
  With `RunicApplicationFrontendInstallEnabled=false` the build looks for no JavaScript workspace and selects the package
  manager from the frontend's folder, as before. See
  [JavaScript workspaces](../../../packages/dotnet/Runic.Application.Views/README.md#javascript-workspaces).

- A client library whose frontend package has a `build` script now builds it (`RunicApplicationFrontendBuildEnabled`
  defaults to `auto` instead of `false` in a client library), and installs the frontend's packages for that build. Set
  `RunicApplicationFrontendBuildEnabled=false` in the library to keep building the package yourself. A package without
  a `build` script stays unbuilt, as before.

- **The renamed build names have their own list, the old-name guards (D079.11).** The `RunicBridge*`,
  `RunicViewsWindowProject`, `RunicApplicationId` and `RunicApplicationName` names that fail with `RUNICBRIDGE017` are
  now listed in `buildTransitive/Runic.Sdk.RenamedNames.targets`, which `Runic.Application.Views` and `Runic.Desktop`
  ship and import once. Each old name is still reported once, with the same message. The list gains two kinds that 0.24
  leaves empty: an old package ID in the package graph (`RUNICBRIDGE085`) and an old environment variable that is set
  (`RUNICBRIDGE086`). The rename release fills them, so a project that mixes packages of the old and the new names
  fails to build with an error that names the new ID and `rax migrate`
  ([RUNICBRIDGE085](../../../docs/diagnostics.md#runicbridge085)).

- **Toolchain floor: .NET SDK 10.0.404 (runtime 10.0.15) and Node 24.22.3.** The packages are built with the
  November 10, 2026 .NET security release, and the compatibility set that `dotnet runic doctor` checks follows the
  repository's toolchain pins: `dotnet-sdk` now fails below SDK 10.0.404 (10.0.403 before) and certifies 10.0.404 or
  11.0.100, and `javascript-runtime` wants Node 24.22.3 or a later Node 24 (24.22.1 before), or Node 26 as before.
  `RUNICBRIDGE033` warns on a build with an SDK older than 10.0.404. Install .NET SDK 10.0.404 or a newer 10.0
  release and Node 24.22.3 or later, then rebuild self-contained and NativeAOT packages, which embed the runtime.
  Bun 1.4.4 and the npm and pnpm baselines are unchanged.

- The documentation of generated clients names no .NET type or language, so that it fits a producer in any language:
  a setter `set{Name}` says ``Calls the producer's setter of `title`.`` instead of
  ``Calls the public C# setter of `EditorViewModel.Title`.``, a checked field's `write{Name}` names the member's wire name
  (``Writes `title` …``) instead of the .NET type and member, and a shared client's documentation lists the implementing
  Views by their public names (`ImportResult`) instead of their .NET type names, and calls its setters the producer's.
  The code is unchanged.

- **Generated TypeScript writes its string literals with `JSON.stringify`.** The Views TypeScript emitter used to escape
  strings as the .NET generator did, writing `+`, `&`, `'`, `<`, `>`, a backtick and every non-ASCII character as
  `\uXXXX`, so that its output equalled the .NET generator's during the switch-over (R3). It now writes them as
  `JSON.stringify` does: only `"`, `\` and control characters are escaped, so a wire name such as `höhe` appears as
  `"höhe"` instead of `"höhe"`. The values are the same, so nothing changes at run time; a committed generated
  client whose strings hold such characters changes once when it is regenerated.

## A field that writes when it loses focus (#1316)

WPF binds `TextBox.Text` with `UpdateSourceTrigger=LostFocus`, so a ViewModel's setter runs once, when the user leaves
the field, and ported setters often validate, normalize or start work such as a lookup. A field controller could
write each input or after a pause, but not only on blur: `delay` must be finite, so the workaround was the longest
delay a timer takes. `commit: "change"` keeps the draft, with no timer, until the field is committed:

```ts
readonly hostName = injectField(this.settings, SettingsFields.hostName, { commit: "change" });
// <input [runicField]="hostName">: the setter runs when the input loses focus.
```

The draft is written by `commit()`, which `[runicField]`, `bindField`, React's `inputProps`, Svelte's `attach` and a
Vue or Svelte `@blur`/`onblur` handler call on blur; by a form's `submit()` and `commit()`; by `commitAllFields()`; and
by the runtime's flush before a window close or a departure (`field-flush/1`). Otherwise the mode is `"pause"`: the
field shows the draft, handles IME composition, sets `editing` and writes a pending draft when it is disposed. A
choice is still written at once, as WPF's default `PropertyChanged` trigger does for those controls: the bindings
commit after the `change` of a checkbox or `<select>` they wire, `[runicField]` also of a radio, and Vue's `v-model` and
Svelte's `bind:value` a value set on a boolean field or a field with `choices`. `FieldController.field.commitMode`
reports the mode. It is in `@runic-artifex/views` and every binding that takes field options: Angular `injectField`
and `[runicField]`, React, Vue and Svelte `useField`. See
[Fields](../../../packages/web/views/README.md#fields).

## Command handles that a View makes on demand (#1317)

A component that called a View's commands from its template declared one `injectCommand` or `useCommand` per command,
usually a one-line pass-through such as `injectCommand(() => this.orders.client()?.refresh())`, only so that `run()`
never rejects. Angular's `injectCommands(view)`, and `useCommands(view)` in React, Vue and Svelte, now make these
handles:

```ts
readonly orders = injectView(this.page);
readonly commands = injectCommands(this.orders);
// <button (click)="commands.refresh.run()">Refresh</button>  <button (click)="commands.archive.run(row.id)">Archive</button>
```

`commands.<name>` has the same `run`, `pending`, `error`, `failure` and `reset` as `injectCommand` and `useCommand`,
and each handle has its own `pending` and `error`. A handle is made when the component first reads its name and kept
for the component's lifetime; React's is the same object across renders until its own state changes. `run()` calls the
client connected when it starts, resolves to `undefined` before the client connected, and never rejects. The names and
arguments are typed from the generated client: each `<Name>Client` now lists its published commands as
`<Name>CommandName`, a type-only list that adds no code to the page, so setters, `canX(input)`, `startX`, `recoverX`,
`upload` and `dispose` are not offered, and in explicit publication (#1320) neither is a command that is not
published. The framework-neutral `createCommandHandles` in `@runic-artifex/views` holds the logic. See
[Command handles](../../../packages/web/views/README.md#command-handles).

## Share ViewModels and their clients through a library (#1318)

A library of ViewModels that several applications present, such as an about dialog or a support menu, had its
TypeScript clients generated into each application, so a frontend package of shared components for them had no
generated types to import: it hand-mirrored them, or left the wiring to each application. Now the library that declares
the Views of its ViewModels generates their clients once, into the package, and applications import them from there.

```xml
<!-- The library -->
<RunicApplicationFrontendClientLibrary>true</RunicApplicationFrontendClientLibrary>
<RunicApplicationFrontendDirectory>$(MSBuildProjectDirectory)/../shared-ui</RunicApplicationFrontendDirectory>

<!-- Each application, beside its ProjectReference to the library -->
<RunicApplicationFrontendClientModule Include="SharedUi" Specifier="@acme/shared-ui/generated" />
```

- **The library** (`RunicApplicationFrontendClientLibrary=true`) writes its clients, contracts, mocks and named types
  with two barrels for the package to export: `runic-clients.ts`, with `runicClientContracts`, and `runic-mocks.ts`. It
  builds and copies no frontend by default, and an application that references it no longer copies its frontend to the
  application's web root. A library without a View is `RUNICBRIDGE006`.
- **The application** (`RunicApplicationFrontendClientModule`) still generates the C# Bridges of the library's
  ViewModels, which its content slots construct, and `AddRunicViews()` registers the library's Views. It writes no
  client, contract or mock for them, deletes the copies an earlier build generated, and its own modules import their
  page functions and page references from the specifier. It must not declare Views of those ViewModels itself.
- **A stale package fails the frontend's type check.** The application's `runic-client-modules.ts` compares the
  contract of each client in the package the frontend resolves with the library build the application compiles
  against, so a package generated from another build is `TS2344`, naming both contracts.
- **Diagnostics:** `RUNICBRIDGE079` (the mapped assembly is not referenced or not a client library), `080` (Views of one
  ViewModel in two assemblies), `081` (a library ViewModel presents content of another owner, or a shared client has
  implementers with different owners), `082` (a malformed item) and the warning `083` (a mapped library without
  Views).
- **Not supported:** a library ViewModel that presents the application's or another library's ViewModels, and shared
  clients with implementers in both.

A correction to the issue: the contract fingerprint that a generated client embeds is not checked when a page
connects in a production build. The development build of `@runic-artifex/views` checks it since this release (#1324,
under [Fixes](#fixes)), and the type check above is the guard for a release build.

The guide is
[Share ViewModels and their clients through a library](../../../packages/dotnet/Runic.Application.Views/README.md#share-viewmodels-and-their-clients-through-a-library),
with the package's `exports`, the copy step for a compiled package and Vite's `resolve.dedupe`, and
[`examples/shared-library-clients`](../../../examples/shared-library-clients/README.md)
is a library, a package and an application that maps it.

## An interaction answered from the template (#1319)

`client.interactions.<name>.handle((input, { signal }) => answer)` suits a dialog service that returns a promise. A
component that renders its dialog in its own template had to write about 28 lines per interaction: a promise whose
resolver and input go into a signal, clearing it on the answer and on `signal`'s abort, ignoring a second answer, and
an `effect` that registers and removes the handler with the client. Without the abort handling the dialog stayed
open after .NET had stopped waiting. Angular's `injectInteraction`, and `useInteraction` in React, Vue and Svelte, now
do this:

```ts
readonly discard = injectInteraction(this.editor, "confirmDiscard");
// @if (discard.request(); as request) {
//   <app-confirm [text]="request.input.title" (yes)="request.respond(true)" (no)="request.respond(false)" />
// }
```

`request` is the oldest open request, `{ input, respond(answer) }`, or `undefined`. Its `respond` answers that request
only and is ignored once the request has ended, so a double click or an answer after .NET stopped waiting never
reaches another request. The handler is registered while the client is connected and removed when the client changes
or the component goes away. A request ends when .NET stops waiting for it: the command that asked was cancelled, the
deadline passed, the window closed or the client changed. Several open requests are answered in order, and an
interaction whose input is empty (`Unit`) still has a request object while one is open. The name, input and answer
are typed from the generated client's interaction (`Interaction<TInput, TOutput>` or `ViewQuestion<TInput, TOutput>`),
and the generated mock's `interactions.<name>.request(input)` drives it in tests. The framework-neutral
`createInteractionController` in `@runic-artifex/views` holds the logic. See
[Interactions as state](../../../packages/web/views/README.md#interactions-as-state).

## Explicit publication for ViewModels (#1320)

A ViewModel's Bridge publishes every public instance property that its class declares, so a ViewModel ported from WPF
needed `[RunicIgnore]` on each member its page does not read, and a member added later was published unless someone
remembered the attribute. `[RunicPublication(RunicPublicationMode.Explicit)]`, on the assembly that declares the
ViewModels or on a ViewModel class, turns that around: only the properties marked `[RunicInclude]` are published,
commands included, and a member stays on .NET until it is marked.

```csharp
[assembly: RunicPublication(RunicPublicationMode.Explicit)]

public sealed partial class ImportResultViewModel : ReactiveObject
{
    [RunicInclude] public ResultPage Page => BuildPage();
    public IReadOnlyList<ImportRow> Imported { get; }   // not published
}
```

- The properties that implement a member of a `[RunicSharedClient]` interface the ViewModel implements count as
  included, so its shared client keeps working.
- A declaration on the class, or the nearest one on a base class, wins over the assembly's;
  `[RunicPublication(RunicPublicationMode.Implicit)]` returns one ViewModel to the default.
- The generator, the analyzer and the Hot Reload contract fingerprint select the same members, so a member the
  contract omits is never inspected or sent in a snapshot, and needs no `[RunicIgnore]` for a WPF type.
- `[RunicInclude]` with `[RunicIgnore]` is the new error `RUNICBRIDGE077`, and `[RunicInclude]` on a member the Bridge
  cannot publish, such as a field or a property that a base class declares, the new warning `RUNICBRIDGE078`.

The default stays `Implicit`, and a ViewModel without the attribute generates exactly what it did before. See
[Which members are published](../../../packages/dotnet/Runic.Application.Views/README.md#which-members-are-published).

## Loading and failure of a hosted region (#1377)

A host application can now tell a guest that is slow to start from a region that fails again and again, and show its
own text for each (experimental, `RUNICDESK103`). The host page shows a region as `attached` only once the guest's page
connected; until then the application decides how long it waits. By default it keeps waiting, as before.

```csharp
#pragma warning disable RUNICDESK103
region.FrameLoaded += async (_, e) =>
{
    if (e.Region.FrameLoads >= 2 && e.Region.State == RunicHostedRegionState.Loading)
        await e.Region.FailAsync("unreachable");
};
```

```html
<runic-hosted-region name="check">
  <p slot="loading">Starting the system check…</p>
  <p slot="stalled">The system check is taking longer than usual…</p>
  <p slot="failed">The system check could not start. <button type="button" id="check-retry">Try again</button></p>
</runic-hosted-region>
```

```js
document.getElementById("check-retry").addEventListener("click", event => event.target.closest("runic-hosted-region").retry());
```

- **Host.** `RunicHostedRegion.FrameLoads` and `FrameLoaded` count the frame's loads that the host page reported since
  the region started loading, while the guest's page had not connected; `LoadingTime` is how long it has been loading.
  `FailAsync(reason)` gives the region up: the new state `RunicHostedRegionState.Failed`, with `FailureReason`.
  `RetryAsync` loads the frame again with a new frame launch address from the guest, under the same checks as any
  attach.
- **Page.** `<runic-hosted-region>` has the state `failed`, which shows `slot="failed"` content (else `slot="fallback"`),
  and `stalled` while its frame loaded without the guest's page connecting for a second, which shows `slot="stalled"`
  content in place of `slot="loading"`. `runicregionstatechange` carries `stalled` and the host's `reason`, and the
  element has `stalled`, `failureReason` and `retry()`.
- **Retry from the page.** `retry()` asks the host; it never names an address. Runic's host loads the region again only
  when it failed, at most 3 times a minute, and logs event 2031 for a request over that limit.
- **Protocol.** The Views feature `hosted-region-loading/1`, with `hosted-regions/1`
  ([loading and failure](../../../specs/application/README.md#loading-and-failure)): `hosted-region-update` gains
  `connected`, `hosted-region-empty` the reason `failed` with `failure`, and the page sends `hosted-region-loaded` and
  `hosted-region-retry`. Without the feature on either side, a region attaches on its frame's load, and a failure
  reaches the page as `detached`.

See [hosted regions](../../../docs/hosted-regions.md).

## Stalled and failed hosted regions in React, Vue, Svelte and Angular (#1380)

`RunicHostedRegion` in the `./experimental` entries of `@runic-artifex/react`, `vue`, `svelte` and `angular` now shows
what a [loading or failed region](#loading-and-failure-of-a-hosted-region-1377) needs: content for a stalled region,
content for a failed one with the host's reason, and a way to ask the host to try again.

```tsx
<RunicHostedRegion name="check" fallback={<p>Starting the system check…</p>}
  stalled={<p>The system check is taking longer than usual…</p>}
  failed={({ failureReason, retry }) => <p>The check could not start ({failureReason}). <button onClick={retry}>Try again</button></p>} />
```

| | Stalled content | Failed content | Stalled, reason, retry |
| --- | --- | --- | --- |
| React | `stalled` | `failed`, content or a function of `{stalled, failureReason, retry}` | the arguments of `failed` and of a `fallback` function (`(state, status)`) |
| Vue | `#stalled` slot | `#failed="{ failureReason, retry }"` slot | the `fallback` and `failed` slot props; a template ref's `state`, `stalled`, `failureReason` and `retry()` |
| Svelte | `stalled` snippet | `failed(status)` snippet | the snippets' `status` (`fallback(state, status)`); `bind:this` and `retry()` |
| Angular | a projected `slot="stalled"` element | a projected `slot="failed"` element | `stalled()`, `failureReason()` and `retry()` on the `runicHostedRegion` template ref |

As with the element, a stalled region without stalled content shows the fallback for `loading`, and a failed one
without failed content the fallback for `failed`. `retry()` asks only for a failed region and never names an address.
The state change callback or output (`onStateChange`, `@state-change`, `onstatechange`, `(stateChange)`) also carries
`stalled` and the reason, and also comes when only those changed.

See [hosted regions](../../../docs/hosted-regions.md).

## Assets archive conformance for any language

The Runic Assets archive vectors now run through the language-neutral conformance driver:

## `dotnet runic dev` and `doctor` start from a solution root

In a folder with a solution (`.sln` or `.slnx`) instead of one `.csproj`, such as the root of an application with a

(`RunicApplicationFrontendWindowProject=true`); `--project` may also name a solution or its folder. Before, they

## `dotnet runic dev` watches the library packages that the page imports

While `dev` runs, it watches every compiled frontend package that the page depends on: a client library's package, or a
workspace package that no .NET project owns. It reads them from `RunicViewsGetFrontendDependencies` after the build.

- **Watch.** A package with a `watch` script runs it. Otherwise `dev` reruns the package's build, debounced, when one of
  its files changes. `node_modules`, `bin`, `obj`, hidden folders and the package's output folders don't count. Vite
  reloads the page from the new output.
- **Failures keep the page working.** A rebuild that fails, or that doesn't write the package's exports, is reported as
  a `RAPPDEV1018` line in MSBuild's form, and `dev` puts the output folders of the last good build back. A watch script
  writes its own output, so `dev` reports its located errors (`src/x.ts(3,1): error TS1005: …`) the same way; with
  `tsc -w`, `noEmitOnError` keeps its last good output.
- **Fails at the start.** A package build that fails in `dev`'s initial build stops `dev` with `RAPPDEV1018` and the
  build's own error instead of `RAPPDEV1006`. A compiled package whose exports are missing after the build stops it
  too, naming the missing file and why, for example a package build that is off.
- **Fails fast.** When Vite answers the application entry with HTTP 500 twice, such as for an import it cannot resolve,
  `dev` stops at once with Vite's own error, and names the package and its state when the import is a dependency
  package. Before, it waited 30 s for a `RAPPDEV1007` timeout that pointed at `doctor`. A development server that exits
  reports the first error line of its output.
- **Repeated lines.** An identical line of the development server or of a package watcher, printed less than 10 s
  before, is held back and counted (`[vite] (repeated 1,106 more times) …`). One unresolved import used to print 1,107
  times.
- **Session file.** `dev-session.json` lists the packages as `dependencies`, each with its owner, kind, specifier, build
  and watch commands, exports, `state` (`built`, `building`, `failed`, `missing-output`, `source` or `not-built`),
  `watch` (`script`, `rebuild`, `vite` or `none`) and last failure. The schema stays
  `runic.application.tool.dev-session/1`, since the change only adds a property.

See [dotnet-runic](../../../tools/dotnet-runic/README.md#library-packages-under-dev).

## `dotnet runic doctor` checks how the page's library imports resolve

`doctor` gains two checks, each with a fix:

- **`client-modules`**: each specifier that the page imports from a library or workspace package resolves from the
  frontend as Vite resolves it: every `RunicApplicationFrontendClientModule` specifier to a file that the package's

- **`views-dedupe`**: when a linked package that the page depends on imports `@runic-artifex/views`, the Vite

## `dotnet runic doctor` checks the JavaScript workspace and the library packages that the page imports

`doctor` gains four checks, each with a fix:

- **`frontend-workspace`**: the JavaScript workspace root that installs the frontend, found as the build finds it, and
  that the root's `workspaces` (or `pnpm-workspace.yaml`) list the frontend (the build's `RUNICBRIDGE087`). A frontend
  with its own lock file below a workspace warns, since it installs on its own.
- **`package-manager-agreement`**: the root's `packageManager` and lock files, `RunicApplicationFrontendPackageManager`,

- **`frontend-dependencies`**: every client library's package and workspace package that the page depends on is built,

  without a build.
- **`windows-targeting`**: on Linux and macOS, a project of a Windows target framework, such as a WPF project on

## Frontends in JavaScript workspaces

A frontend that is a member of a Bun, npm or pnpm workspace, such as an application's frontend beside the frontend
package of a client library, now builds from a fresh clone with plain `dotnet build`. The build finds the workspace root
(the nearest folder above the frontend whose `package.json` has `workspaces`, or that has `pnpm-workspace.yaml`) and:

- installs once at the root, with the root's lock file (`--frozen-lockfile` or `npm ci`, with `--ignore-scripts`), for
  every member. Builds of the workspace's projects that run at the same time wait for one install, and a build with
  nothing changed runs none;
- takes the package manager from the root's `packageManager` or lock file;
- checks that the workspace lists the frontend (`RUNICBRIDGE087`), and warns about a member that declares another
  package manager (`RUNICBRIDGE089`).

`RunicApplicationFrontendWorkspaceRoot` names the root, or `none` installs a frontend on its own. A frontend with a lock
file of its own, as the `runic-app` template creates, is its own root and builds as before. The build resolves the
workspace with `runic-frontend-graph.mjs`, which writes `obj/runic/frontend-graph.json` (`rax.frontend-graph/1`); the
same script is the `@runic-artifex/views/frontend-graph` export. See
[JavaScript workspaces](../../../packages/dotnet/Runic.Application.Views/README.md#javascript-workspaces).

### Faster rebuilds

A rebuild with nothing changed runs no package manager at all, also not its `--version`. The install runs when its
hash changed: the install command, the lock file, every `package.json` of the workspace and the package manager's
executable. It also runs when `node_modules` is gone or the manager's own record of a complete install is missing (npm's
`.package-lock.json`, pnpm's `.modules.yaml`). A touched but unchanged lock file no longer installs, and an npm workspace
no longer installs on every build. The new `RunicApplicationFrontendInstallMode` property chooses `Auto` (the default),
`Always` (install on every build) or `Never` (the same as `RunicApplicationFrontendInstallEnabled=false`, which keeps
working). The frontend build reruns after an install that installed something else. See
[Fast iteration](../../../packages/dotnet/Runic.Application.Views/README.md#fast-iteration).

## Runic host protocol conformance through the driver

The conformance driver runs the [Runic host protocol scenarios](../../../specs/desktop/host-conformance/README.md) as
the corpus `host/1`: for the guest role it plays the host over a real loopback WebSocket, and for the host role the
guest, through a relay guest and a channel listener of its own. It drives the implementation under test through a small
adapter, so a guest or host in any language is checked by the same steps. `bun run conformance dotnet-desktop` runs
Runic's .NET guest and host, which pass all 180 scenarios. The scenarios now name the seams a runner needs, how an
outcome is derived from an implementation's features, and the page-transport profile that the region scenarios' frame
and component requests use after their upgrade.

The driver also runs the Desktop presentation contract's scenarios and codec vectors
([`specs/desktop/conformance`](../../../specs/desktop/conformance/README.md)) as `desktop.presentation/1`:
`bun run conformance dotnet-desktop-presentation` runs each abstract operation against a real Runic.Desktop host on
loopback. Six of the ten cases pass; four are known failures, where the scenarios name error codes, a message or an
order that Runic.Desktop does not produce.

## Library packages build with the application

A client library's frontend package is built by the library's build when its `package.json` has a `build` script, so
an application that imports a compiled package (`exports` into `dist/`) builds from a fresh clone with plain
`dotnet build`. `RunicApplicationFrontendBuildEnabled` is now `auto` in a client library; `false` still turns the
package build off. After the build, the generated `.contract.d.ts` files and their maps are copied to the folder of the
package's `./generated` export, which the guide described as a manual step, and every file that the package exports must
exist (`RUNICBRIDGE088`, naming the library).

- **Workspace packages that no .NET project owns**, such as a component or tokens package, are built too, with the
  workspace's package manager, dependencies first, by the project whose frontend depends on them.
- **Incremental.** A package builds only when one of its files, its command or the install changed, or an export is
  missing; a rebuild with nothing changed starts no JavaScript process. The folders of the packages become frontend
  inputs of the application, also for Visual Studio's fast up-to-date check, so the application's own
  `RunicApplicationFrontendInput` items for them are no longer needed.
- **As data.** `RunicViewsGetFrontendDependencies` returns an application's frontend packages, with their owner, kind,
  build and watch commands and mapped specifier, without building; `obj/runic/frontend-graph.json`
  (`rax.frontend-graph/1`) lists the JavaScript side.

See [Library packages](../../../packages/dotnet/Runic.Application.Views/README.md#library-packages).

## Publish from a web bundle, without Node.js, checked against the build's Views

`-p:RunicApplicationFrontendPrebuiltDirectory=<dir>` makes a build take each project's page from a web bundle that
another job wrote (D082), for example a Windows release job from the bundle of a Linux job. The build runs no frontend
install, no package or frontend build and no TypeScript client emission, so the runner needs neither Node.js nor Bun,
also with this release's emitter, which otherwise runs on Node.js or Bun in every build that generates Bridges. A WPF
application's model project takes its own entry, and `RunicApplicationFrontendDelivery=Embedded` packs the bundle's
page into the assembly. The property is also read from the environment, so `dotnet runic package` can use it.

Before it uses a page, the build compares the bundle's View fingerprints with the contract IR that its generator has
just written. A View that changed, or that only one side has, is `RUNICBRIDGE094`, which names the View and both
fingerprints; a page built for another host is `RUNICBRIDGE095`. Both are errors; `RunicApplicationFrontendPrebuiltCheck=warning`
publishes anyway with a warning. A missing entry or a page other than the bundle recorded, as after a truncated
download, is `RUNICBRIDGE093`, and an optimized build that takes a development page warns with `RUNICBRIDGE096`. See
[Building the frontend in another job](../../../packages/dotnet/Runic.Application.Views/README.md#building-the-frontend-in-another-job).

## Desktop server conformance for any language

The [Desktop server corpus](../../../specs/desktop/server/README.md) states what the HTTP and WebSocket server under a

- **One JavaScript workspace:** the root `package.json` lists both frontends and the package manager, and the template

- Every frontend works with it: React, Vue, Svelte, SvelteKit, and Angular with the Angular CLI or Vite. It does not

## `dotnet runic bundle`, and `package --frontend-bundle` without Node.js

For a CI whose Linux jobs build and test everything web and whose Windows or macOS job only publishes (split CI, D082):

- **`dotnet runic bundle`** builds the project or solution with `RunicApplicationFrontendBundleDirectory`, checks the
  web bundle (`rax.web-bundle/1`) it wrote, and prints each project's kind, Views and the files, size and SHA-256 of its
  page; `--format json` gives `runic.application.tool.bundle/1`. Its output directory must be new, empty or an earlier
  bundle (`RAPPBUNDLE1001`–`1004`).
- **`dotnet runic package <target> --frontend-bundle <dir>`** publishes with the bundle's pages through
  `RunicApplicationFrontendPrebuiltDirectory`, so the runner needs neither Node.js nor Bun. `package` checks the bundle
  first, and the build compares each View's fingerprint with its own (`RUNICBRIDGE094`).
- **`package` passes MSBuild properties through**: `--property NAME=VALUE` or `-p:NAME=VALUE`, as `dotnet publish`
  takes them, reach the identity's evaluation and the publish of every target but `flathub`. `-p` with a separate value
  stays `--project`. Properties that `package` sets itself are refused (`RAPPPKG1008`).
- **`dotnet runic doctor --bundle <dir>`** checks a downloaded bundle offline, as its `web-bundle` check: the manifest,
  the hash of each page and an entry for the project.

See [Write a web bundle](../../../tools/dotnet-runic/README.md#write-a-web-bundle).

## `dotnet runic translations` runs the Translations tool

`dotnet runic translations …` runs the installed Runic Translations tool, `runic-translations …`, with the arguments
unchanged and returns its exit code, so one command reaches both tools. The core finds the tool through
`RAX_TRANSLATIONS_TOOL` (a path), the nearest .NET tool manifest (`dotnet tool run`), `node_modules/.bin` or `PATH`, in
that order. Without it, the command fails with `RAPPCLI1013` and prints the install command for the tested release, for
example `dotnet tool install dotnet-runic-translations --version 0.16.0 --local`; it never installs anything itself.
`doctor` gains the `extensions` check: it asks the installed tool for its version (`--extension-info`, or `--version`
for older releases) and fails for another protocol or an older release line than the compatibility set's, warning for
an older release of the line or a later line. The tool IDs and commands are unchanged. `dotnet runic support` finds the Translations tool the
same way. See [Tool extensions](../../../tools/dotnet-runic/README.md#tool-extensions).

## A Views conformance corpus for any language

The Views protocol 4 conformance corpus now states everything a producer or client in another language needs, so a
Rust or C++ implementation can be written from the specification alone. See the
[conformance corpus](../../../specs/application/conformance/README.md).

- **The `hello` reply names the Runic release.** A producer adds the optional member `release`, the version of the
  Runic release it ships with, to every `hello` reply; the .NET producer sends its package version. A client of
  another release can then report its version diagnostic for any Runic producer, not only one named
  `Runic.Application.Views`. Clients that do not read the member ignore it, as protocol 4 requires. See
  [Handshake](../../../specs/application/README.md#handshake).
- **Revisions are specified as .NET publishes them.** When one change shows on several routes, each route's frame
  takes its own revision; a publication withheld for invalid keys takes a revision too; and a checked field's
  `version` counts the field's changes, not revisions. Each rule has a scenario. See
  [Publication units](../../../specs/application/state-changes.md#publication-units).
- **The corpus describes its own setup.** Message vectors commit the `hello` a producer runner sends first and name the
  roles that run them; the README gives the valid-request criterion, the provided ids with their types, the closed
  list of requirement names (now with `blobs/1`, `client-errors/1`, `field-flush/1` and `validation-pending/1`), and the
  test Views in full, including the 256 MiB upload limit of the `files` View.
- **What a second producer found is specified as .NET behaves.** Rust and C++ producers written from the
  specification alone found the gaps that the corpus now closes, each with a case where it shows on the wire:
  reply and delivery order per route, the order of a `start`'s and an upload's checks, value directions and the
  field paths of rows that hold blobs, path-write receipts, operation and interaction identities, public names and
  optional members, a close without a timeout, the page-wait limit, and which terminal operation expires first.
  The .NET producer passes every new case unchanged. See [State changes](../../../specs/application/state-changes.md)
  and [contract IR](../../../specs/application/contract-ir.md).
- **The TypeScript client runs the client cases.** `bun run conformance ts-client` runs every client case of the
  corpus and its value vectors against the production build of `@runic-artifex/views`, with the driver playing the
  producer; a client in another language adds an adapter of its own.

## Web bundles: build the frontend in one CI job, publish in another

`-p:RunicApplicationFrontendBundleDirectory=<dir>` makes a build write a web bundle (D082): after its build, every
project that declares Views writes its built page (`projects/<assembly>/www/`), its generated clients
(`projects/<assembly>/clients/`) and its entry of `web-bundle.json`, format `rax.web-bundle/1`. The entry records the
project's View fingerprints from the contract IR, its host, `NODE_ENV`, lock file hash and `@runic-artifex/views`
version, and the manifest the .NET SDK, Node.js and commit. The projects of a solution build, such as a WPF
application's model project and the application, or a client library and its application, write their entries side by
side. A project whose frontend build is off cannot write its page (`RUNICBRIDGE092`). The format is in
[specs/application/web-bundle.md](../../../specs/application/web-bundle.md); see
[Building the frontend in another job](../../../packages/dotnet/Runic.Application.Views/README.md#building-the-frontend-in-another-job).

## Fixes

- **A CS-WebUI window's Development browser ends with the application, also when the application is killed.** With a
  DevTools Protocol endpoint (`RUNIC_WEBUI_REMOTE_DEBUGGING_PORT`, as `dotnet runic dev --debug-endpoint` and Runic
  DevKit's "Debug the Window" ask), the Chrome or Edge window that CS-WebUI started kept running after a debugger's Stop,
  Task Manager or `kill -9` ended the application. It still held the endpoint's port, so DevKit refused the next "Debug the
  Window" until the window was closed (#1263). That browser, which runs with the run's own profile, now ends with the
  application: on Windows it is in a kill-on-close job object that only the application holds, and on Linux and macOS a
  small watcher ends the processes that use that profile once the application is gone, then deletes the profile. On
  Windows the next run deletes a profile left behind. Browsers the application did not start, including the user's own,
  and windows without an endpoint are not affected.
- **A query collection's waiting load or key search no longer fails when the query changes.** With a row source whose
  cancellation ends its call at once (many database drivers' does), a `RunicQueryCollection.LoadAsync` or
  `IndexOfAsync` that waited across `SetQuery` or `Refresh` could end cancelled instead of reading the new query: it
  retried inside the query change and took the replaced query's cancellation (#1270).
- **A generated browser profile no longer stays behind on Linux after Google Chrome is killed.** Runic deletes the
  profile it created for a browser window once the browser ends. It took the close of the browser's output pipes as the
  sign that every browser process had ended, but Google Chrome's Linux launcher puts that output behind two `cat`
  processes. When the browser's processes were killed, as by a crash, the OOM killer or a process-tree kill, the `cat`s
  could end first, and Chrome's network service wrote its cache into the profile after Runic had deleted it (#1273).
  On Linux, Runic now also waits until no process names the profile on its command line before deleting it.
- **A build that writes a generated client without its declaration map or comments says why.** The generator finds
  member locations, and the summaries of `[Reactive]` and `[ObservableProperty]` partial properties, through the PDB of
  the assembly that declares a ViewModel. When that assembly has none, as with `<DebugType>none</DebugType>` in Release,
  the clients of its ViewModels lost their `.contract.d.ts.map`, their `sourceMappingURL` comment and those summaries, so
  committed clients changed between Debug and Release builds without a hint (#1298). The new warning `RUNICBRIDGE076`
  names the client and the assembly without a PDB when a build writes a client with fewer mapped members or
  documentation lines than the file it replaces; the fix is a portable or embedded PDB
  (`<DebugType>portable</DebugType>`) in every configuration of every assembly whose ViewModels the application
  presents. The Views README's new
  [Commit generated clients](https://github.com/Runic-Artifex/runic-sdk/blob/main/packages/dotnet/Runic.Application.Views/README.md#commit-generated-clients)
  section says so.
- **`dotnet runic doctor` checks the Vite entry module below Vite's root.** The `vite-entry` check resolved
  `RunicApplicationFrontendViteDevServerEntry` against the frontend package directory, while Vite and `dotnet runic dev`
  resolve it against Vite's `root`, so a frontend whose `vite.config.*` sets `root` (as in an Angular workspace) failed
  the check, and its advice broke `dev` (#1300). The new `RunicApplicationFrontendViteRoot` property names that root
  for doctor (default: the frontend directory); `dev` warns when the resolved Vite root differs from it. `dev`'s
  readiness probe now also requires the entry to be served as JavaScript: Vite's `index.html` fallback for a path that
  is not below its root fails with `RAPPDEV1007`, naming the entry and Vite's root, instead of reaching the window as
  its entry module.
- **A page generated from another build of its ViewModel no longer connects silently in development.** A generated
  client embeds its View's contract, `"{ViewModel}:{fingerprint}"`, but nothing compared it with the application's
  Bridge when a page connected, so a page from a stale `generated/` folder or a frontend package built from an earlier
  library decoded the state with the wrong members and codecs, without a diagnostic (#1324). With the new Views
  protocol feature `view-contract/1`, `Runic.Application.Views` names the route's contract in each `open` reply, and
  the development build of `@runic-artifex/views` compares it with the page's: on a mismatch the View fails to connect
  with a `BridgeError` saying the page and the application were generated from different builds, and one `contract`
  diagnostic (`onBridgeDiagnostic`, the Runic DevTools dock) names the View and both fingerprints. The production
  build does not list the feature and connects as before, and a .NET host before 0.24 names no contract, so its pages
  are not checked.
- **A radio group can be bound to one field with `bindField`, React's `useField` and Svelte's `attach`.** These
  bindings treated a radio like a text input: they set every radio's `value` to the field's text, so the radios lost
  their options, and wrote the `value` of a radio that had not been checked (#1327). A radio now keeps its `value`, is
  checked while that is the field's text, and writes only when it becomes checked; with `commit: "change"` the choice
  is written at once, as for a checkbox or `<select>`. `bindField` takes the radios of a group together
  (`bindField(document.querySelectorAll("input[name=size]"), editor, EditorFields.size)`), Svelte's `{@attach
  size.attach}` goes on each radio, and React's new `radioProps(option)` is spread on each radio
  (`<input {...size.radioProps("Large")} />`). Angular's `[runicField]` and Vue's `v-model` already handled radios.
- **`dotnet runic package flathub --build` tries the runtime install once more when a download from Flathub fails.**
  Installing the GNOME runtime, SDK and extensions failed when Flathub's CDN broke a download, for example "While
  fetching https://dl.flathub.org/repo/deltas/…: [92] Stream error in the HTTP/2 framing layer", and a run a few minutes
  later passed (#1334). A failure on such a download (flatpak-builder's "While pulling", "While fetching", or a curl or
  HTTP error) now runs the install once more after 30 seconds. A manifest or build error, and a second download
  failure, still end the build.
- **The native Desktop server answers a request with two `Host` lines with 400.** `Runic.Desktop.NativeServer` checked
  only the first `Host` header field line against the loopback rule and served the request; RFC 9112 §3.2 requires
  400 (Bad Request) for a request with more than one, and the server now answers so before the `Host` check, as
  Kestrel does (#1341). Browsers send one `Host` line, so pages are not affected. The
  [presentation host contract](../../../specs/desktop/presentation-host.md) now states the rule for every server.
- **A View whose ViewModel name starts with a non-ASCII letter gets a client that type-checks.** For a ViewModel such as
  `ÜbersichtViewModel`, the generated `übersicht.ts` left `ÜbersichtState`, `ÜbersichtClient` and the View's other
  types out of its imports and re-exports, because the name scans read a name only from an ASCII letter on (#1355). The
  TypeScript emitter's scans now read a name from any letter on. Names that only contain non-ASCII letters, such as
  `GrößenViewModel`, were not affected.
- **On Linux, a write inside a watched directory no longer restarts its watch.** `RunicPathWatcher` identifies a
  watched directory by device, inode and birth time, so it notices a directory deleted and created again. On Linux,
  .NET's `Directory.GetCreationTimeUtc` returns the change time, so every entry created, renamed or deleted in the
  directory looked like a replacement: the watcher restarted its watch and read its targets again without an event
  (#1360). The watcher now reads the birth time with `statx`. On a file system that records no birth time, it keeps
  the change time and the restarts.
- **A command or operation that is not available answers `unavailable`, also when the window is at capacity.** A
  `command` of an asynchronous command and a `start` checked the window's capacity before the command's key and
  availability, so a window running 64 awaited commands, or retaining 64 operations, answered `capacity` for a command
  that could not run anyway (#1370). Both now check the capacity last, after availability, which tells the page the
  reason that retrying does not change. A command whose key an asynchronous resolver resolves still answers `capacity`
  before its key, since the resolution is itself awaited work of the window.
- **An asynchronous command invoked with `command` replies after the frame of its end.** A command whose task completed
  inside another publication unit, as when a change in the model completes the task it awaits, published the frame of
  its end and then replied at once, without waiting for that frame. The page could then see the reply before the
  frame, with a revision it had not yet received (#1370). The reply now waits for the frame, as every other reply of a
  request that changes state does.
- **Runic Assets archive readers check the last of the archive specification's reader rules.** `AssetArchive.Read`,
  `ReadAsync`, `ReadEmbedded` and `Inspect`, and so the packer's `verify`, now reject an asset whose deflate data
  inflates past its `length`, which was served as its first `length` bytes; an entry whose local header has another
  name or compression method than its central directory record; and entries whose bytes overlap each other or the
  central directory (#1373). A lone surrogate escape in a member that the reader ignores is now invalid too: in its
  value it was accepted, and in its name the read failed with `InvalidOperationException` instead of the documented
  `InvalidDataException`. An asset over 2³¹−1 bytes, which `AssetArchiveReadOptions` cannot allow, now fails with a
  limit message instead of "unexpected length"; the options document that fixed bound. Archives that
  `AssetArchive.Write*` and the packer write are unaffected. See the
  [reader rules](../../../specs/assets/archive-v1.md#reader-rules).
- **A hosted region whose frame failed to load shows the page's own content, not the engine's error page.**
  `<runic-hosted-region>` left `loading` on its frame's `load` event, which Chromium and WebView2 also fire for a
  navigation that failed, such as while the guest still starts, and then show a grey error page: the element went
  `attached`, its fallback content went away, and the user saw that error page while `RunicHostedRegion.State` stayed
  `Loading` (#1377). The element now stays `loading`, with its fallback content over the hidden frame, until the host
  says that the guest's page connected (`hosted-region-loading/1`), and only then shows the frame. A host page or host
  of an earlier release keeps the earlier behaviour.
- **Opening a window that waits for its connection returns with the page connected.** With
  `DesktopHostOptions.WaitForConnection`, `OpenWindowAsync` could return before the page's `Connected` event, so
  `DesktopSurface.ConnectionCount` was still 0 right after it. The page's token reply ended the wait, and the event
  followed a moment later on another thread. On a busy machine this often happened, and the Translations editor's GTK 4
  canary reported a reconnect that never took place (#1383). The open now returns only after the page's `Connected`
  event has been raised: `ConnectionCount` counts the page, and every `SubscribeConnectionEvents` handler has seen the
  event. This holds for a browser window and for embedded WebView2, WKWebView and WebKitGTK windows. A connection
  handler must not wait for the open that is waiting for it.
- **`runic-app --library` no longer drops `--translations` and `--nix` silently.** A solution with a library does not
  support them yet, and `dotnet new runic-app --library <Name>` created it without them and said nothing (#1386).
  `dotnet new` still creates the solution without them, and now prints a warning that names each option it left out;
  `dnx Runic.Create` refuses the combination with `RCREATE006`. Visual Studio and Rider no longer grey the two options
  out beside a library project, because the template engine drops a greyed-out option without a trace; their
  descriptions say that they do not apply to it. See
  [A solution with a library](../../../tools/Runic.Application.Templates/README.md#a-solution-with-a-library).
- **A burst of Views frames right after a route attaches no longer recovers too early.** While the route's delivery
  waited for the model to run a publication unit, such as the unit that captures the route's first state, the frames
  that the model's turn published meanwhile all queued, the first one included. The first frame then counted toward
  the bound of 64 frames, so the 65th frame of a burst replaced the frames with a recovery state although the
  transport was free (#1387). The first frame is now the one being delivered as soon as it is queued, as it is when the
  delivery is idle, and the route keeps 64 frames behind it before it recovers.
- **A blob in an editable row is no longer a field path.** The generated client of a `[RunicRowEditor]` collection
  whose rows hold a `RunicBlob` declared the blob member as a field path (`field-paths/1`), so the page could send writes
  that the window always refused with `invalid-input`: the page never sends a blob (#1391). A member that holds a blob is
  now never a field path, and a write of it is `invalid-request`, as for any other member that is not a field path. The
  other members of the row, and of an object in it, stay field paths, and their copy keeps the blob. A row or object
  of a sealed class that the generator copies through its wire form (no copy constructor or `Clone()`) cannot keep a
  blob in such a copy, so when it holds one it now has no field paths. This changes the contract fingerprint of a View
  whose editable rows hold a blob; Views without such rows keep theirs.
- **A window bounds the number of its unclaimed uploads, not only their bytes.** Uploads that no command claimed were
  limited by `MaximumPendingUploadBytes` alone, so empty uploads were held until they expired after 10 minutes, each with
  its file (#1392). A window now holds at most 256 unclaimed uploads at once by default, counting those it is still
  receiving, and refuses another with HTTP 507 (`capacity`), as it refuses one beyond the byte limit; a claimed upload
  frees its place. The new `MaximumPendingUploads` option sets the number on `RunicWindowOptions` and
  `WindowContentSessionOptions`, with host defaults on `RunicDesktopHostOptions`, `RunicCsWebUiHostOptions` and
  `RunicWindowTestHostOptions`.
- **A Views field below a checked member, or a row cell, may be named like a field descriptor member.** A generated
  client whose checked object member or editable row has a field named `name`, `read`, `write`, `checked`,
  `baseline`, `errors`, `validating` or `container` (such as a checked `Billing` address with a `Name`) failed
  `tsc --strict`, because the field's descriptor shared one object with the descriptor's own members (#1395, since
  0.16). A descriptor now keeps its own members under the `fieldMembers` symbol of `@runic-artifex/views`, so
  `InvoiceFields.billing.name` is the field of `billing`'s `name`, and no field name is reserved. `useField`,
  `injectField`, `bindField` and `createFieldController` take the descriptors as before; code that reads a
  descriptor's members itself changes ([breaking changes](#breaking-changes)).
- **A terminal Ctrl+C stops `dotnet runic dev` quietly.** Ctrl+C reaches the whole process group, so the development
  server could exit before `dev` handled its own signal, and `dev` then reported `RAPPDEV1007: The vite development
  server exited unexpectedly with code 130` and exited with 1 (#1396). When the development server, the frontend
  watcher or the native host exits with a stop signal's code (130 for SIGINT, 143 for SIGTERM, 129 and 131, or Windows'
  Ctrl+C status), `dev` now waits up to 2 seconds for its own stop and ends with 130 as cancelled. Any other exit
  reports `RAPPDEV1007` at once, as before.
- **A `dotnet runic dev` started right after one that was killed installs the frontend packages again.** A killed
  `dev` (a tree kill on Windows, a crash) leaves `obj/runic/dev-frontend`, and a build within 30 s of its last renewal
  took the session for a running one. It skipped the frontend build and, for a frontend with only a watcher
  (`npm run dev` without Vite), the install, which the build has owned since 0.24. On a fresh clone the watcher then
  started without its packages. `dev` now checks the session file when it starts and, before its first build, removes
  the marker and development pages of a `dev` that no longer runs. It prints `[dev] Removed …` when it does. A build
  that `dev` didn't start, such as an IDE's while `dev` runs, keeps the running session's frontend as before (#1405).
- **The native Desktop server ignores `Range` on methods other than `GET`.** A file body answered a `Range` header on
  any method, so `HEAD` and `POST` got 206 and a part of the file. RFC 9110 §14.2 defines range handling for `GET`
  only, and `Runic.Desktop.NativeServer` now sends the whole file with 200 for other methods (no content for `HEAD`,
  which keeps the whole file's `Content-Length`) (#1413). Browsers send `Range` with `GET` only, so pages and media
  elements are not affected.
- **The native Desktop server answers a WebSocket upgrade with another version with 426 and
  `Sec-WebSocket-Version: 13`.** An upgrade whose `Sec-WebSocket-Version` was not 13 reached the host as an ordinary
  request, and no response named the version the server understands. As RFC 6455 §4.2.2 and §4.4 ask,
  `Runic.Desktop.NativeServer` now answers it itself, before the host sees it, with 426 (Upgrade Required),
  `Sec-WebSocket-Version: 13` and `Upgrade: websocket` (#1414). Browsers send version 13, so pages are not affected.
- **The native Desktop server answers an HTTP/1.1 request without `Host` with 400.** `Runic.Desktop.NativeServer`
  answered it with 421 (Misdirected Request), as it does a foreign `Host`; RFC 9112 §3.2 requires 400 (Bad Request),
  which the server now sends before the `Host` check (#1415). The request is refused before the host sees it either
  way. An HTTP/1.0 request without `Host` still gets 421.
- **A Runic Desktop window on Kestrel answers a WebSocket upgrade with another version with 426 and
  `Sec-WebSocket-Version: 13`.** An upgrade on a window's `_webui_ws_connect` path whose `Sec-WebSocket-Version` was not
  13 got 426 (Upgrade Required) without naming the version the host understands or the protocol it requires. As
  RFC 6455 §4.2.2 and §4.4 and RFC 9110 §15.5.22 ask, `Runic.Desktop.Kestrel` now adds `Sec-WebSocket-Version: 13`,
  `Upgrade: websocket` and `Connection: upgrade` to that 426, and every other 426 on the path carries
  `Upgrade: websocket` (#1418). Browsers send version 13, so pages are not affected.
- **`dotnet runic doctor --bundle` passes on a publish runner without Node.js or Bun.** A build that takes its pages from
  a web bundle runs no install, frontend build or client emission, but doctor still ran its JavaScript checks, so
  `javascript-runtime` and `package-manager` failed on a target-OS runner that publishes from a bundle (#1421). With
  `--bundle`, or when the project builds with `RunicApplicationFrontendPrebuiltDirectory`, doctor now reports
  `javascript-runtime`, `package-manager`, `lock-file`, `frontend-workspace`, `package-manager-agreement`,
  `frontend-dependencies`, `client-modules` and `views-dedupe` as not needed (`SKIP`, status `skip` in JSON, with the
  reason) and checks the bundle as `web-bundle`; the exit code follows the remaining checks. The JSON summary counts
  them as `skipped`. Without a bundle nothing changes.
- **A solution with a Runic application and its library builds each project once.** The Views targets' bootstrap pass
  passed `PublishAot=false` and the other publish properties it clears on to the projects it references, so MSBuild built
  a referenced library a second time with them, into the same `bin/` and `obj/`. The test project of
  `dotnet new runic-app --library --tests` also built the application a second time, with
  `RunicApplicationFrontendBuildEnabled=false`. With `-m`, these builds ran at the same time and could fail a solution
  build with an `IOException` on a file in `bin/` or `obj/runic-bridge/bootstrap/` (#1424). The bootstrap pass now builds
  its references with the properties of the real build, and the template's test project references the application without
  extra properties. Remove `AdditionalProperties="RunicApplicationFrontendBuildEnabled=false"` from a test project that is
  in one solution with the application it references.
- **`dotnet runic package appimage` no longer needs the network to validate the metainfo.** appimagetool's built-in
  AppStream check fetched the metainfo's URLs, so an offline machine, or a URL that answered with an error such as a 504,
  failed the package. The command now validates the metainfo itself with `appstreamcli validate --no-net`, as
  `package flatpak` does, and runs appimagetool with `--no-appstream`. A rejected metainfo is `RAPPPKG1006`; without
  `appstreamcli` the metainfo is not validated and the command warns with `RAPPPKG2003`. Fixes #1444.
- **A CS-WebUI page opened at `/?…` keeps its query (preview).** `Runic.Application.Views.CsWebUi` now needs CsWebUi
  2.5.0-beta.4.11, which bundles WebUI nightly `8a55352c2`. WebUI answered `/` and folder URLs with a redirect to
  their index file that dropped the query string, so a page opened at `http://localhost:<port>/?mode=x` arrived at
  `/index.html` without `mode` ([cs-webui#33](https://github.com/Runic-Artifex/cs-webui/issues/33)). The redirect now
  keeps it ([webui-dev/webui#729](https://github.com/webui-dev/webui/pull/729)); requesting `/index.html?…` directly
  is no longer needed. CS-WebUI's API is unchanged.
- **Arguments for Debug builds are documented.** An argument that only Debug builds get, such as `/mock`, belongs in
  MSBuild's `StartArguments` in a Debug-conditioned `PropertyGroup`: `dotnet run`, `dotnet runic dev`, Visual Studio
  and Runic DevKit read it, and Release builds don't get it. A launch profile's `commandLineArgs` can't be limited to
  Debug. [Arguments for Debug builds](../../../docs/debugging.md#arguments-for-debug-builds) shows which surface reads
  which, and what happens when the project and the profile both set arguments. The `dotnet-runic` README also says how
  to run `dotnet runic` at a solution root: the tool manifest belongs there.
- **A failure that stops `dotnet runic dev` reaches VS Code's Problems panel through the session file.** VS Code removes
  a background task's problems when its process ends, so a `dev` that stopped at its start (a failed first build, or
  `RAPPDEV1018` after a frontend package's build error) left Problems empty when the template's `runic: dev` task ran it,
  from F5 or from Terminal > Run Task, and Runic DevKit's dependency tree still said "built". `dev` now writes the failure
  into its session file before it exits: a `failure` member with `dev`'s code and message, the project and the frontend
  package that failed, and the diagnostics of the step that failed (file, line, column, severity, code and message; at
  most 100). Runic DevKit 0.24 reads it and keeps the errors in Problems and the package "failed" in its tree, however the
  task was started. `failure` is null while `dev` runs and after a stop without a failure; readers that do not know it
  ignore it (`runic.application.tool.dev-session/1` only adds properties). The template's `.vscode/tasks.json`, its
  README, `docs/debugging.md` and the `dotnet runic dev` README now say what Problems shows with and without DevKit.
- **`dotnet runic dev` builds the library packages that the page imports.** `dev` turned the frontend build off with a
  global property, which reached every project it built, so a client library's compiled frontend package was never
  built under `dev`: on a fresh clone Vite logged `Failed to resolve import "@acme/shared-ui"` over a thousand times and
  `dev` stopped after 30 s with `RAPPDEV1007`. `dev` now names the project it serves in
  `RunicApplicationFrontendDevSessionProject`, and only that project skips its production frontend build; libraries
  build their packages, so `dev` reaches Ready from a fresh clone.
- **`dotnet runic dev` no longer reinstalls the frontend packages on every start.** It ran the package manager's install
  itself before each build (`npm ci` deletes and reinstalls `node_modules`, and the clients were then regenerated).
  The build's incremental install now runs instead, so a start with nothing changed runs no install: in the
  shared-library example's npm workspace a warm start takes 3.5 s instead of 4.3 s and starts 3 JavaScript processes
  (the Vite configuration probe, `npm run dev` and Vite) instead of 8.
- **`dotnet runic dev` starts in a Bun or pnpm workspace.** Its own install took the package manager from the
  frontend's folder, so a member without `packageManager` was installed with npm and failed (`RAPPDEV1006`). The build
  installs the workspace at its root with the workspace's manager.
- **A new `runic-app --editor vscode` project's `dev` tasks no longer list a failure twice in Problems.** `dev` also
  prints a failure as a sentence, such as "…, so dev did not start: /path/to/index.ts(12,14): error TS2322: …", and the
  tasks' pattern, VS Code's `$msCompile` after `dev`'s label, filed a copy of the error under that sentence. The pattern's
  file now holds no `": "` and the subcategory before `error` no colon, as in Runic DevKit's matcher. The pattern in the
  `dotnet runic dev` README has the same change. An existing project's `.vscode/tasks.json` can take the three tasks'
  `regexp` from a new project.
- **`dotnet runic dev` runs the development server with the workspace's package manager.** In a Bun or pnpm workspace
  whose frontend declares no `packageManager`, `dev` ran `npm run dev`, because it read only the frontend's folder. It
  now finds the workspace root as the build does, with the same order: `RunicApplicationFrontendPackageManager`, the
  root's `packageManager`, the root's lock file, then the frontend's own.
- **`dotnet runic dev` reads the targets' dev session protocol after restoring a fresh clone.** It checked for the
  restore's assets file after the restore had written it, so an unrestored project that takes the Views targets from
  its packages fell back to the pre-0.24 behaviour (`RAPPDEV1019`).
- **`dotnet runic doctor` checks the workspace's package manager and lock file.** In a Bun or pnpm workspace whose
  frontend declares no `packageManager` and has no lock file of its own, `javascript-runtime` and `package-manager`
  checked Node and npm, and `lock-file` failed for a missing `package-lock.json` in the frontend's folder. They now use the
  manager that the build uses, from `RunicApplicationFrontendPackageManager`, the workspace root's `packageManager` or
  lock file, then the frontend's own, and `lock-file` looks for the lock at the workspace root. An unsupported
  `packageManager` now fails the check instead of stopping doctor.
- **Windows desktop windows compare the per-webview token of file-drop and menu-key messages in constant time**, as the
  other credential checks of `Runic.Desktop` already do.
- **Drag regions in a frameless window are documented.** A page marks the parts of a `DesktopWindowOptions.Frameless`
  window that move it with `--webui-app-region: drag`, and takes controls out with `no-drag`; the nearest declaration
  decides. [Drag regions in a frameless window](../../../packages/dotnet/Runic.Desktop/README.md#drag-regions-in-a-frameless-window)
  describes the gesture, the window hosts it covers, and how it relates to macOS `app-region`.
- **A workspace member's build no longer asks for a lock file it cannot have.** A frontend in a Bun, npm or pnpm
  workspace failed with `RUNICBRIDGE026` ("has no bun.lock … Create the lock file with 'bun install'"), because the build
  looked for the lock file only in the frontend's folder; the advice could not be followed, as the install in a member
  writes the root's lock. The build now uses the root's lock file, and `RUNICBRIDGE026` names the root when it is
  missing.
- **The Views guide no longer tells a workspace to turn the install off.** Its advice to set
  `RunicApplicationFrontendInstallEnabled=false` in a workspace made a fresh clone fail with `RUNICBRIDGE084`, because
  nothing installed the workspace. The build now installs it at the root.
- **A member without a lock file of its own installs with its workspace's package manager.** A member that declared no
  `packageManager` was installed with npm, which fails in a Bun or pnpm workspace on `workspace:*`
  (`npm error Unsupported URL Type "workspace:"`).
- **An npm workspace builds once and stays installed.** npm installs every member's packages into the root's
  `node_modules`, so the member's build failed with `RUNICBRIDGE016` ("did not create …/node_modules") and installed
  again on every build. The build checks the root's `node_modules`.
- **A missing package manager is named before the install.** Without Bun (or Node.js) on `PATH`, the install failed
  with `RUNICBRIDGE016` and exit code 127. The build now runs the manager's `--version` before the install and reports
  `RUNICBRIDGE090` with the manager and where it was declared; a frontend build that exits with 127 because the manager
  is missing is reported the same way.
- **An application whose library package is compiled builds from a fresh clone.** Nothing built a client library's
  frontend package, so the application's bundler failed with `Failed to resolve import "@acme/shared-ui"`, reported as a
  generic `RUNICBRIDGE016`. The library now builds its package, and a package that a frontend depends on and that has
  not been built is `RUNICBRIDGE088`, which names the package and the project that builds it. A frontend build that
  still fails on such an import names the package in `RUNICBRIDGE016`.
- **A compiled library package keeps its client types.** `tsc` does not copy the generated `.contract.d.ts` files, so a
  consumer's type check failed with `TS7006` or saw `any`. The build copies them beside the compiled clients.
- **`dotnet runic package` and `size` start from a solution root.** In a folder with a solution (`.sln` or `.slnx`)
  instead of one `.csproj`, they stopped with `RAPPDEV1002: No .csproj was found in the directory. Use --project.`
  They now select the project as `dev` and `doctor` do: the solution's one Window project, or a list of the Window
  projects with the `--project` to choose one. `--project` may name a solution or its folder, and `-p <path>` is still
  the project beside `-p:NAME=VALUE`.

## CI and tests

- **The Markdown link check covers anchors.** `tests/engineering/markdown-links.test.mjs` also fails on a fragment link,
  in the same document or to another tracked Markdown file, that names no heading (GitHub's slug, repeats numbered) and
  no HTML `id` or `name` of its target, compared in lowercase as GitHub does. A code span now ends at a backtick run of
  its own length within its paragraph or table row, so an unmatched backtick no longer hides links further on (#1265).
- **A fresh-clone test of a library and an application in a JavaScript workspace.** The repository's
  `Directory.Build.props` turns the frontend install off for every in-repository project, so no check installed a
  workspace or built a compiled library package, and the workspace failures that 0.24 fixes went unnoticed.
  `examples/shared-library-clients/fresh-clone-smoke.mjs`, in the Views journeys job, copies the shared-library example
  out of the repository as a Bun, npm and pnpm workspace with a compiled package, then checks three things from a fresh
  clone: `dotnet runic dev` reaches Ready, `dotnet build` passes, and a second build installs and builds no frontend.
- **Tests lease the loopback ports they hand to a child.** A port taken by binding port 0 and closing the listener could
  go to any other bind or connection before the child bound it (#1257). `tests/support/TestPorts.cs` and
  `tests/support/ports.mjs` lease a random port outside the ephemeral range that no socket uses, held until the child
  starts; the tests' private free-port helpers, the inspector, WebView2 and web-content smokes and js-debug's DAP
  scenarios use them.
- **Tests stop a process tree before deleting the directories it used.** `tests/support/TestProcesses.cs` ends a test's
  process with its descendants, waits for all of them on Linux, and deletes a directory on Windows with a bounded,
  scaled retry while a stopped process's handles close (#1268). The tool tests' workspace, the running-instance tests
  and the CS-WebUI browser guard checks use it.
- **The split CI example runs on every package pull request.** The package consumers job runs `examples/split-ci`
  against the packed packages (`examples/split-ci/package-smoke.mjs`): the tests and the web bundle, then a `win-x64`
  publish from the bundle with neither Node.js nor Bun on `PATH`, and a ViewModel change that `RUNICBRIDGE094` must
  stop. The engineering job lints the example's two workflow files, and `tests/engineering/split-ci-example.test.mjs`
  checks that they differ only in the artifact actions and the default runner labels.

## Known issues

- **No visible close drain on an installed browser or in WPF.** A Window in an installed browser closes at once,
  with `WindowCloseDrainUnavailable` (event 1055); its scope still waits for durable work. A WPF window is the
  application's own, so `RunicViewHost` drains nothing visibly: wait for the work in the window's `Closing`
  handler, as
  [Closing after the Window's work has drained](../../../packages/dotnet/Runic.Application.Views/README.md#closing-after-the-windows-work-has-drained)
  shows. Both stay this way in 1.0.
- **CS-WebUI (preview) under `dotnet runic dev --browser`: an application's own absolute navigation leaves the
  session address (#1225).** The page's WebUI connection goes to the Window's own port, so `dev` cannot move a
  navigation sent over it. The host sends none, and Views routes in the URL's fragment, but
  `WebUiWindow.Navigate` with an absolute URL of the Window, or a second `Show`, takes the tab to the Window's own
  address, outside `dev`'s admission. Pass `Navigate` a relative path. See
  [What a window opens](../../../packages/dotnet/Runic.Application.Views.CsWebUi/README.md#what-a-window-opens).
- **`Runic.Desktop.Gtk4` is not CI-verified on musl.** CI runs Runic Desktop on Alpine with GTK 3 and
  WebKitGTK 4.1; the GTK 4 window host is not run there
  ([Supported platforms](../../../eng/release/README.md#supported-platforms)).
- **Screen readers in hosted regions are checked by hand.** Automation checks that a guest's controls in a region's
  frame are in the accessibility tree; whether NVDA, Narrator and VoiceOver speak them in document order is a manual
  check ([Hosted regions: Still checked by hand](../../../docs/hosted-regions.md#still-checked-by-hand)).
- **With the .NET 11 SDK, a SIGTERM does not stop `dotnet runic dev` on Linux.** The SDK's native `dotnet` entry
  point exits on SIGTERM without forwarding it to the local tool
  ([dotnet/sdk#57091](https://github.com/dotnet/sdk/issues/57091)), so `dev` keeps running without its parent, with
  its Window and development server. A process manager or IDE that stops it with SIGTERM leaves it behind. Stop it
  with Ctrl+C, send the signal to `dev` itself (the session file's `processId`), or set `DOTNET_CLI_ENABLEAOT=0`,
  which makes SDK 11 forward the signal as SDK 10 does. Runic DevKit stops `dev` through its standard input
  (`RUNIC_DEV_STOP_ON_INPUT`), which SDK 11 does not affect.
- **Side panel on Wayland and on transparent GTK 3 windows.** On Wayland the left edge is refused with
  `PositionUnavailable`, and the right edge is not checked in CI, which has no headless compositor. A transparent
  GTK 3 window refuses the panel with `Unsupported`. See
  [Side panel: Known limits](../../../docs/side-panel.md#known-limits).
- **WebKit's own `inspector://` port is open to other local users.** Under `dotnet runic dev` on Linux, WebKitGTK's
  remote inspector server, which the debugging adapter and GNOME Web connect to, cannot be filtered: another local
  user can connect to it, also while a debugger is attached, and a client that replaces another one can crash the
  Window on WebKitGTK 2.54. On a shared machine, run `dotnet runic dev --no-debug-endpoint`. See
  [The browser's developer tools per engine](../../../docs/debugging.md#the-browsers-developer-tools-per-engine).
- **On Windows on Arm (win-arm64), drag-and-drop and the side panel are not CI-verified.** The hosted runner
  delivers no `SendInput` to WebView2, so drops onto and drags out of WebView2 are not checked there
  ([#391](https://github.com/Runic-Artifex/runic-sdk/issues/391)), and its desktop shows GDI nothing, so neither is
  the side panel's frame capture or Tab between the views
  ([Side panel: Known limits](../../../docs/side-panel.md#known-limits)). The rest of win-arm64 runs in CI.
