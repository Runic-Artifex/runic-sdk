# ADR 0017: v0.2 product identity and package topology

- Status: Accepted
- Date: 2026-08-13
- Supersedes: ADR 0001's Runic Toolkit product identity; ADR 0016's
  repository-placement decision only

## Context

The current Runic Toolkit preview publishes implementation seams as separate
products. A new application must select lifecycle, hosting, web UI, bridge,
generator, build, and desktop packages independently even though those pieces
are one application experience. The package graph and repository layout no
longer express the product's ownership boundaries.

This decision freezes the v0.2 public identities and migration destinations.
It deliberately does not rename packages, namespaces, projects, source paths,
templates, lockfiles, or package metadata. Those changes follow in separately
verified implementation waves.

## Decision

### Product names

The display name is **Runic Application**. The default .NET and NuGet identity
is `Runic.Application`; the repository is `runic-application`. The unified
developer-command distribution is `dotnet-runic`, invoked as `dotnet runic`.
The template package is `Runic.Application.Templates`.

The v0.2 application package topology is:

| Public package | Purpose |
|---|---|
| `Runic.Application` | Default application lifecycle, composition, and desktop abstractions. |
| `Runic.Application.Bridge` | Application Bridge runtime and its bundled analyzer/source generator. |
| `Runic.Application.CsWebUi` | Complete CS-WEBUI application integration. |
| `Runic.Application.Hosting` | Generic Host integration, retained because its `Microsoft.Extensions.Hosting` dependency warrants isolation. |
| `Runic.Application.Testing` | Later-wave headless and deterministic test host; it is new, not a rename of a current package. |
| `Runic.Application.Templates` | `dotnet new` application templates. |
| `dotnet-runic` | Unified developer command distribution. |

`@runic-artifex/application-bridge` remains its existing public npm identity.
It is the Effect-based TypeScript bridge runtime. Its repository metadata moves
with the repository consolidation, but its npm ID does not change.

Generators ship as analyzer assets of the package whose APIs they generate;
they are not independently installed public products. Internal assemblies may
remain split where useful, but do not create additional public package choices.

### Repository topology

`runic-toolkit` is renamed to `runic-application`. First-party Svelte and Vite
integration sources are imported there so cross-language bridge changes remain
atomic, while their distinct npm package authorities remain intact. This
supersedes ADR 0016 only where it assigned those sources to separate
repositories; its protocol-runtime and integration-boundary decisions remain in
force.

`runic-toolkit-examples` becomes `runic-examples` and remains a separate,
package-only compatibility laboratory. Command Line, Assets, Translations,
Translations Editor, CS-WEBUI, docs, brand, and release automation remain
independent authorities. Flow is excluded from the v0.2 public release train
pending its later evidence gate.

### Sole authorities

Each authoritative artifact has one owner. Consumers may compose or read it,
but must not clone its model.

| Artifact | Sole authority | Consumers |
|---|---|---|
| Command catalog and command I/O schema | Runic Command Line generator | CLI runtime, help, completions, tests, automation adapters |
| Application composition manifest | Runic Application generator | Development host, runtimes, test host, publisher |
| Bridge contract, schema, and fingerprint | Runic Application Bridge generator | .NET dispatcher, TypeScript client, Vite diagnostics, tests |
| Asset archive and manifest | Runic Assets | Application host, CS-WEBUI boundary, publisher |
| Translation catalog | Runic Translations | Generated C#/ESM clients, Svelte integration, Editor |
| Release-train manifest, version, and compatibility data | Release Automation | Documentation, examples, CI, dependency-update tooling |
| Desktop and lifecycle contracts | Runic Application | CS-WEBUI integration, hosting, test host |
| CS-WEBUI native boundary | CS-WebUI | `Runic.Application.CsWebUi`, application host |
| Svelte projection | `@runic-artifex/svelte` | Svelte applications and templates |
| Vite development diagnostics | `@runic-artifex/vite-plugin-runic` | Vite projects and `dotnet runic dev` |

The machine-readable release-train manifest at the Release Automation boundary
is the authority for all published product identities and compatibility data.
No repository-local package list may become a competing release authority.

### Migration and compatibility policy

Every retired, renamed, merged, or internalized preview NuGet identity receives
one final deprecation release with its exact table destination and migration
link. Old packages stop evolving after that release. There are no permanent
forwarding packages, code-facing compatibility facades, namespace aliases, or
second package identities.

Serialized formats and wire contracts are governed separately from package
identity: they retain explicit versioning, compatibility reporting, and
migration support where required. The unchanged npm bridge package preserves
its package ID and import path. Final NuGet and npm name ownership must be
rechecked and claimed immediately before publication; a registry absence does
not reserve a name.

## Consequences

- Applications obtain a task-oriented package surface rather than the current
  implementation-seam graph.
- Lifecycle and desktop code share the `application` ownership boundary;
  Application Bridge remains a separately owned authority until its source
  migration is complete.
- Runic Assets becomes the only frontend asset archive and manifest model.
- This ADR makes a public compatibility commitment without changing the current
  published package metadata in this decision-record wave.
